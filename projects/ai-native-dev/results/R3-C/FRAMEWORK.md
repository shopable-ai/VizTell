## 1. 区分知识对象（不必按固定顺序）
| 对象 | 问题 | 输出语义 |
|---|---|---|
| 原始想法/来源 | 用户说了什么、发生了什么 | 原话/观察及来源，不能自行改写成批准需求 |
| 目标 | 为什么做、需要达到什么结果 | 成功条件、范围、非目标 |
| 问题 | 当前与期望的差距是什么 | 现状、症状、影响，原因可能未知 |
| 主体及场景 | 谁、何时、何条件、做什么 | 触发、条件、路径、结果 |
| 业务规则 | 怎样判断允许、拒绝或状态变化 | 规则、约束、例外 |
| 能力 | 为达目标需要具备什么能力 | 不依赖具体界面的能力及边界 |
| 功能 | 产品以什么行为提供能力 | 用户/系统可见的行为，可能多对多满足需求 |
| 需求 | 哪些性质、行为或限制必须满足 | 功能要求、质量要求、约束；另区分项目和过程要求 |
| 验收 | 怎样证明满足需求及目标 | 事前判据、环境、预期、必要证据 |
IREB CPRE glossary 将需求的语义和功能、质量、约束等类别区分，并将项目/过程要求与系统要求区分；借用该区分，不要求采用其全部术语。

## 3. 需求的分类轴（不混成单树）
- 来源：明确表达、已有业务规则、从目标推导、利益相关者约束、领域知识、故障或风险、历史决策。
- 类型：行为、质量、约束；项目及过程要求另标。
- 范围：目标/系统/业务域/功能/接口；层次关系是分解或分配，不强制所有层都有文件。
- 状态：原始陈述、候选、待证、冲突、已决策、变更/废弃。事实、假设、偏好、硬约束及设计选择分开。
- 优先和义务：必要、可选、延期、非目标；来源与理由，不以用户没提到就判不必要。

## 4. 不同入口的推理路径
| 入口 | 优先恢复 | 应推导内容 |
|---|---|---|
| 全新想法 | 原始目的、相关主体、现状替代 | 目标、场景、能力、必要行为、质量/约束及验收 |
| 新功能/变更 | 有效旧需求、已有能力和受影响边界 | 新旧差异、兼容、受影响行为和回归 |
| 缺陷反馈 | 预期行为、实际现象、当前版本 | 已有需求是否遗漏或实现偏差、根因未知项、修复验收 |
| 质量改进 | 可测当前表现、约束和风险 | 质量场景、目标阈值、取舍及不回退要求 |
| 探索研究 | 待解决未知及决策需求 | 可否证假设、证据要求，不提前生成产品功能 |

## 5. 收敛与边界
候选需求须回答：为什么与目标相关、何时适用、满足什么可观察结果、是否有替代、如何验证、是否涉及用户必须决策的价值/权限/不可逆取舍。G中的“必要”仅在证明/明确假设成立时使用。最小充分是对当前已知场景和风险的条件判断，不宣称完备。停止不是数量：没有高影响冲突或未知能被轻易消除，重要未决项显式隔离，要求与判据能够衔接。局部工作不要求重新构造所有树。

## 6. F2：需求发现机制的输入输出与必要性判据

| 方法 | 输入 | 输出 | 选择条件 |
|---|---|---|---|
| 意图澄清 | 原话、来源、上下文 | 目标/问题/非目标、疑义 | 意图有多个重要解释 |
| 场景展开 | 目标、主体、条件 | 正常、替代、异常、恢复路径 | 行为、时序或主体未知 |
| 目标反推 | 目标、约束、领域知识 | 候选必要条件与替代集合 | 缺少达到目标的前提 |
| 差量推导 | 有效基线、新目标 | 变更及影响、保留项 | 存量目标或条件变化 |
| 约束发现 | 角色、环境、质量与风险 | 不可越界条件与待确认阈值 | 存在权限、成本或失效后果 |
| 冲突消解 | 相互冲突的候选、权责 | 取舍/升级/分区决策 | 不能同时满足或存在重大价值差异 |
| 验收逆向 | 目标与候选需求 | 可观察条件、判据与证据缺口 | 不能判断是否满足 |
| 收敛裁剪 | 候选集、价值、必要性与证据 | 已确认/待证/延期/排除 | 增量已无实质收益 |

这是从原四组机制展开的新操作表，**不是已找回历史九机制**。IREB CPRE Requirements Elicitation 公开说明明确强调来源、适情境的方法选择、冲突解决、需求确认（https://cpre.ireb.org/en/concept/requirements-elicitation，本轮查阅），支持调查与协商不可由模型纯推理代替；上表为自主归纳，不是 IREB 官方八步骤。

**必要性反例：** A⇒G、B⇒G 只说明两者各自可能是充分方案，不推出 G⇒A。若要求 A，则需独立约束或证明其他方案均不可行；否则只保留 A/B 候选。需求可能是选择空间的约束，而不是先生成具体功能后才存在。用户没有说出的需求分为：目标逻辑所需、环境/领域规范所需、风险所需、偏好或候选增强；最后一类不能自动升级为必要。
**停止规则：** 目标和适用范围有可追溯解释；候选要求有必要性依据、冲突处理与可判断判据；高影响未知已标记，无法合法推断的决策留给有权主体。

本节为F2通用结构推导和概念反例，未进行具体应用；重要分类和完整专业知识仍须独立核验。

## 7. 原八节点及事实—规格链的精确归属

原reference/04八节点仍完整保留：原始想法→目标与问题→角色与场景→业务链路→能力与功能→需求推理→需求审计与收敛→需求与验收结果。它是面向需求发现的阅读链，而不是要求需求必须在功能之后才出现。已经明确的需求/约束可反向限制能力与功能。

原事实到规格链的修正：来源→候选事实/未知→证据支持的事实；另一条为用户/权责主体→原始需求→候选需求→适用决策/确认。两者汇合到场景、业务、能力/功能候选、需求与判据。需求自审和适用的批准形成基线，然后才进入研究/设计、Spec、Task、Workflow、Skill/Tool等下游。原“已批准事实/业务需求”拆为证据认知状态与授权决策状态：批准本身不能证明事实为真。人工批准是原链的候选决策门，按风险和权责判断，非强制每条需求停下审批。

KAOS目标细化/障碍和责任指派（UCL项目页与作者机构摘要）支持目标、约束、假设、主体分开；IREB支持来源与冲突消解。此处是对原始链的语义修正而非新实现协议。


## R1 深化：需求必要性、候选空间和验收语义

本节强化原四组方法，而非补造缺失的历史九机制。依据R2 04及本专题前文；公开SEBoK System Requirements Definition 将利益相关者需要转换为可测的系统义务、追溯来源、理由、验证成功条件；这是专业参照，不将其视为唯一需求流程。

### 1. 从「想到功能」改为「判明义务」

定义 D 为已限定且一致的领域/环境假设，G 为目标，H 为硬约束，R 为候选要求，S 为可选择的设计空间。只有在 D∧H∧G 有可行解释且 D∧H∧G∧¬R 在该空间不可满足时，才可在该边界内称R是实现G的必要条件。若 G 本身不可达，则形式蕴含可能空真，不能得出任何有用的必要需求。R∧D∧H 足以支持G与 G 蕴含R也是不同判断；可用反例搜索识别欠充分与过强需求。形式化只适用于能表达的命题，现实模糊目标要以限定性论证和未知项替代伪证明。

抽象反例：D允许路径 A 或 B，目标 G=(A∨B)，且 A、B 可独立达到G。A足以实现G，但不必要。必要义务是维持 G 的可达性，或在新增合法约束排除B后再将A确定为必要。若存在外部强制规定 A，即使目标可由B达到，A仍可能是独立的规范义务；不能只按目标逻辑删除它。

### 2. 四组方法的独立推导职责

| 组 | 输入与实际思考操作 | 可接受产出 | 拒绝 |
|---|---|---|---|
| 理解与展开 | 原话/现象/已知事实→分别解释目标、问题、受影响主体、当前范围，比较多个解释的差异 | 带来源的目标、场景、未知和非目标 | 把推测当用户批准 |
| 反推与发现 | 从G问成功前置、阻碍与外部约束；枚举替代满足方式；由角色、数据、质量、生命周期条件推导义务 | 必要条件、候选要求、适用假设、可替代关系 | 一条充分路径当成全部必要条件 |
| 质疑与补漏 | 构造违反义务/目标的反例，考察初始、转换、临界、异常和恢复；发现冲突及无法控制的前提 | 条件性遗漏、冲突、风险或待证 | 把一切异常都升级为功能 |
| 裁剪与收敛 | 区分硬义务、软偏好、备选设计和假设；检查组合可实现性、成本和证据；明确未决/延期 | 可说明理由的基线及验收义务 | 只按功能数量或个人偏好裁剪 |

从目标细化到主体分配还需区分「环境应满足的假设」与「被研制系统可控制的义务」。若主体不能控制P，不得写成其无条件保证P；可以要求在P不成立时检测、反馈、阻止或退化至有定义的状态，具体选择受目标和风险约束。父目标细化需检查一致性、足够性、可实现性和责任归属；逻辑一致≠资源可实现。

### 3. 需求与验收的可推导边界

最低语义：主体/对象、触发或适用范围、前置、应当/禁止行为或质量约束、可观察结果、来源与理由、优先及决策状态。验收义务单列「对象及版本范围、观测条件、输入/事件、可判别结果、允许偏差与证据限制」。安全性质可写成任何允许路径都不进入坏状态；活性性质关注给定公平性/环境假设下目标最终可达，不等于固定时间界；需要时间上限时另写量化阈值。质量值未知则标待定，不能杜撰阈值。有限正例不能证明全称安全义务；若反例存在，至少当前命题被否定。需求自身正确/一致/适合利益相关者，与未来实现满足规格是不同主张。

何时问用户：仅当不同合理解释将显著改变目标、权责、不可逆选择或高代价义务，且无法靠可靠资料、保守裁剪或可逆假设解决时，记录需要决策；其他未知保留条件化结论。收敛是当前界内高影响未知有明确归属，不是声称发现所有隐藏需求。

## R1.1 裁决：从逻辑必要性到可实现的最小充分需求

**核心修正：** R1中 D∧H∧G 可满足且 D∧H∧G 蕴含R，只能在已定义解释域中证明逻辑必要性；不可据此认定存在可实现系统。需求推理必须区分领域事实/假设D、硬义务H、目标G、系统可控设计与环境行为。

### 1. 三层判断

- 逻辑层：在有非空解释的 D∧H∧G 中检查是否存在 ¬R 的反例。没有反例只能在指定形式域及完整证明条件下称逻辑必要。
- 实现层：定义可采用的设计/策略s、允许环境e及其可能行为集合 B(s,e)。成功策略必须对每个允许e具有非空、合法的行为，并使所有需保证的行为满足H与G（若目标是概率或期望性质，应明确另一个量化语义）。存在这样的策略才称目标可实现；若尚未证明则标未知。实现层必要条件是每个成功且可实现的策略都满足R；空解集不授予必要性结论。
- 规范层：来自法律、明确授权、业务规则、组织承诺的义务可独立成立，不须由G演绎；某方案引出的接口要求属于**方案条件义务**，不是所有方案都需要的普遍需求。偏好、探索候选与事实假设也不自动升级为义务。

抽象反例：环境e∈{0,1}，系统输出a必须等于e，却不能观测e。对每个e均存在a=e的满足赋值；但单一不可观测策略不能保证成功。∀e∃a 与 ∃策略∀e 不是一回事。不能把逻辑相容当作技术可实现，不能通过将全部环境行为排除来获得空真的保证。

### 2. 最小充分性不是最短需求表

给定目标解释、领域假设、硬约束、验收语义，R集合充分须至少能在允许模型中推出目标义务，且存在可实现的联合满足方式；逐条合理不保证组合充分。对每项候选义务尝试删除：若剩余义务允许违反目标的行为，给出反例或独立硬义务理由；若无影响且不是独立规范义务，则可裁剪。有限集合中不可再删除得到的是**包含意义下极小集合**，非全局最少条数、非唯一、更非经济最优。例：G=(A∧B)∨C，在各变量独立允许时，{A,B}与{C}均可为极小充分方案；不能将三个均宣布普遍必要，不能忽略A/B方案的代价或C的可行条件。需求应表达结果和约束，保留替代空间；方案选定后再派生条件需求。

### 3. 模糊目标与冲突的处理

| 情形 | 应做的推理 | 可输出结论 |
|---|---|---|
| 意图有多义 | 区分用户原话、各解释、受益者、非目标，找改变义务的判别问题 | 条件化需求或需要授权裁决，不自行批准 |
| 软目标不可精确二值化 | 定义关注性质、测量尺度、可接受范围和比较方向；阈值未授权则未知 | 多个非劣候选、已知取舍 |
| 硬义务逻辑冲突 | 找不相容条件及最小冲突子集候选，核查适用范围和权责 | 不可同时满足/待证；不可用分数掩盖 |
| 资源或策略冲突 | 分别检查可实现性、机会成本、时间条件 | 可行边界与有权决定的取舍 |

### 4. 验收义务的两次转换

需求性质→可判别的验收条件（适用域、量词、环境、阈值、预期）→验证方法与实际证据→裁决。验收判据自身是否准确表达目标是一项独立主张；证据是否满足判据是另一项。有限例证不能证明无界全称性质；活性“最终发生”不等于限时发生，且依赖环境公平/可达假设。目标解释改变时回查判据与证据，不自动复用旧验收。

理论参照：van Lamsweerde 的目标导向需求工程公开研究入口 https://webperso.info.ucl.ac.be/~avl/gore.php 及 SEBoK 系统需求定义（上轮）；Alpern & Schneider 1985, Defining Liveness（公开摘要，DOI 10.1016/0020-0190(85)90056-0）。本节形式判据、两个反例和裁剪规则为本轮推导；不宣称实现可判定、能自动穷尽需求或已完成实际对照。
