# 03 · Superpowers 与 BMAD 核心能力对比及复用结论

> 状态：源码层比较已完成；实操证据尚未取得。复用建议是候选结论，不是最终验收结论。

## 1. 本质区别

一句话：

- **Superpowers：重点回答 AI 应该怎样把研发工作做对。**
- **BMAD：重点回答研发目标由什么专业视角、通过什么工作流和产物来推进。**

Superpowers 更像研发过程纪律与执行质量控制；BMAD 更像角色体系、阶段工作流和项目产物管理。两者不是同一类框架的简单竞品。

## 2. 核心机制对比

| 维度 | Superpowers v7.0.2 | BMAD v6.12.4 |
|---|---|---|
| 核心对象 | 研发过程与执行纪律 | 专业角色、工作流与产物 |
| 入口 | using-superpowers 等 Skill | Agent Skill、PRD / SPEC / Build Skill |
| 需求探索 | Brainstorming | Analyst、PM、bmad-prd、bmad-spec |
| 设计门槛 | 设计批准后才计划实施 | SPEC 检查、开放问题解决、用户批准 |
| 任务计划 | Writing Plans | bmad-build Step 02、Epics / Stories |
| 实施 | TDD、Inline 或 Subagent | Oneshot 或 Dispatch |
| 审核 | 任务审核 + 整分支审核 | 配置的多层审核和问题分类 |
| 恢复 | Git + SDD progress ledger | SPEC 状态 + Memlog + 工作流产物 |
| 多 Agent | 依赖宿主 multi-agent | Party Mode / Dispatch，依赖宿主 |
| 程序化支持 | Brief、账本、审核包脚本 | 安装器、配置解析、Workflow Renderer、Memlog |
| 主要限制 | 很多门槛依赖模型遵循 | 角色扮演不等于独立 Agent，路由仍依赖模型判断 |

## 3. 真正值得复用的能力

### 3.1 从原始想法到可执行契约

可组合：

- Superpowers Brainstorming：先弄清用户要解决什么，再讨论设计。
- BMAD 五字段 SPEC：Why、Capabilities、Constraints、Non-goals、Success signal。
- Superpowers Writing Plans：将已批准设计拆成文件、接口、测试和验证命令明确的任务。

组合价值：既避免过早实现，也避免需求文档只有概念没有可执行任务。

### 3.2 决策必须持久化

值得复用 BMAD Memlog 的追加式记忆思路：

- 决策有时间顺序和原因。
- 后续变化追加记录，不静默覆盖历史。
- 需求文档从可信记录推导。
- 新会话通过文件恢复，而不是依赖聊天记忆。

实际应用还需补充备份、恢复、冲突处理和审计策略；单个日志文件不等于完整知识管理系统。

### 3.3 TDD 必须保留失败证据

复用 Superpowers RED → GREEN：

- 实现前测试必须失败。
- 失败原因必须是目标功能缺失。
- 实现后同一测试通过。
- 最后运行完整测试集。
- 保存命令、原始输出、退出码和测试摘要。

这比只统计覆盖率更能证明测试有能力发现目标错误。

### 3.4 只在独立性有价值时使用 Subagent

复用原则：

- 明确主代理和执行代理的边界。
- 给 Subagent 独立上下文和明确任务。
- 用真实工具调用识别 Agent，而不是根据发言角色识别。
- 宿主不支持时明确降级，不伪造并行执行。

不要把所有小任务都强制变成多 Agent。共享状态和强顺序依赖任务盲目并行会增加协调成本。

### 3.5 用不同权威来源恢复不同事实

建议分别保存：

- 需求与决策：规范化需求文件 + 追加式决策记录。
- 任务进度：独立任务账本。
- 代码事实：Git 提交和 Diff。
- 验收事实：测试命令、原始输出和退出码。
- Agent 事实：调度调用、输入范围、结果文件和完成回执。

不同事实有不同权威来源，一个摘要文件不能代替所有证据。

## 4. 不应直接照搬

1. 不要把“Skill 写了必须执行”当作程序已经强制执行。
2. 不要把 BMAD Agent 角色定义当成独立 Agent。
3. 不要把 Party Mode 默认 session 误认为真实多人协作。
4. 不要在宿主不支持时假设可以派发 Subagent。
5. 不要让简单任务承担过重的 PRD、架构、Epic 和多层审核。
6. 不要仅凭 SPEC、Plan 或完成报告宣称软件已验收。
7. 不要为了开启多 Agent 擅自修改用户全局 Codex 配置。

## 5. 推荐组合方向（候选，待真实实验验证）

~~~text
原始想法 / 需求变更 / 缺陷反馈
             ↓
       需求意图理解与探索
             ↓
          专业视角补缺
             ↓
    SPEC / 设计文档 / 决策记录
             ↓
        用户确认关键意图
             ↓
          可执行计划
             ↓
        任务规模与依赖判断
           ↙           ↘
        Inline        Subagent
           ↘           ↙
         TDD + 自动化测试
                 ↓
          独立审核与修复
                 ↓
          完成前新鲜验证
                 ↓
     需求、代码、测试与证据归档
                 ↓
           可恢复的持续迭代
~~~

按任务复杂度选择能力：

- 小任务：轻量需求确认 + 简洁 SPEC + TDD + 验证。
- 中型功能：设计批准 + 计划 + TDD + 审核。
- 多任务、长周期或高风险工作：增加独立实施 Agent、任务级审核、持久化账本和恢复流程。
- 高不确定性产品探索：先用 PM / Analyst 补足需求，再决定是否进入实现。

这不是机械叠加两套框架的所有步骤。
