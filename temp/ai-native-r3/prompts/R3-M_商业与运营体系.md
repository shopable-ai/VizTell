## 原始总目标（不得漂移）

建立真正可用的 AI 原生软件研发方法：用户只需提出不完整的原始想法、功能变更或缺陷反馈，AI 能理解目标、发现必要需求和遗漏、研究并选择合理方案、设计产品与技术实现、组织研发、测试、修复、真实验收与持续演化。成果应能被人理解、被AI正确使用，并在实际研发中产生价值。

R2 的资料只是已筛选的高质量线索，不是权威结论、已批准规范或已经实现的系统。保持原始目标与来源，不要求维持已有分类、数量、名称和关系。可以推翻、补充、合并或淘汰，但要说明理由。当前是独立专题研究与方法发现，不是全量重新整理，也不是立即开发完整软件。

## 五、15条链路的独立深化任务（整理建议）

保留每条链路的原始定义，在下一轮分别回答它实际需要的输入、推导节点、输出、错误与回退、适用模型、角色、Skill、证据。不先扩写所有链路。

| 链路 | 最值得优先验证的具体问题 |
| --- | --- |
| 目标推理链 | 用户的表达与真正要解决的问题不一致时，怎样发现？ |
| 需求推理链 | 目标、场景、能力、功能之间怎样推导，怎样避免遗漏必要需求？ |
| 业务建模链 | 正常、异常和恢复场景的角色、对象、行为与规则怎样表达？ |
| 产品设计链 | 每个功能能否支持一个实际用户旅程，界面是否减少操作成本？ |
| 研究链 | 一个未知项何时需要搜索、源码、实验，什么证据足够？ |
| 方案决策链 | 多个方案如何比较，什么条件下否决或重新选择？ |
| 技术设计链 | 模块边界、数据、接口如何保持与需求一致？ |
| 任务拆分链 | 任务粒度怎样按复杂度控制，如何处理依赖与输入输出？ |
| 研发执行链 | 实现、构建、运行、自检如何产生真实证据？ |
| 测试验收链 | 测试是否真正覆盖必要行为及失败条件？ |
| 发布交付链 | 已构建产物是否就是目标环境实际安装和运行的版本？ |
| 运营价值链 | 用户反馈和真实效果怎样反馈到需求和功能？ |
| 问题解决链 | 怎样区别已证实根因与假设，并形成回归？ |
| 知识沉淀链 | 怎样提炼有适用边界且能在未来任务复用的经验？ |
| 生命周期链 | 状态、维护、迁移与退役怎样回到真实业务目标？ |

专项链路不等于15套必须全走的工作流。只有结合具体任务和验证结果，才决定采用哪些链路及哪些节点。
