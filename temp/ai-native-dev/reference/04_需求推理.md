## 八节点专项链路（L235–279）

| 节点 | 核心问题 |
| --- | --- |
| 原始想法 | 用户最初想做什么？ |
| 目标与问题 | 为什么需要这个软件？解决什么问题？ |
| 角色与场景 | 谁会使用？在什么情况下使用？ |
| 业务链路 | 用户怎样从问题走向期望结果？ |
| 能力与功能 | 为了实现结果，系统必须具备什么？ |
| 需求推理 | 有哪些必要需求、隐藏需求、规则和异常？ |
| 需求审计与收敛 | 是否遗漏、重复、冲突或过度设计？ |
| 需求与验收结果 | 最终要开发什么？怎样证明问题得到解决？ |

## 四组需求推理机制（L462–484）

| 机制 | 职责 |
| --- | --- |
| 理解与展开 | 理解原始目标、角色、问题、场景和业务链路 |
| 反推与发现 | 从预期结果反推必要条件，发现隐含需求 |
| 质疑与补漏 | 发现异常、依赖、冲突、风险及遗漏 |
| 裁剪与收敛 | 删除重复和不必要的需求，确定最小范围 |

原文提到九种候选机制，但没有逐项提供完整清单。四组机制与后文13种通用推理模式不宜混为一谈；其真实效果、独立价值和最小充分性均待实证。

## 从事实到研发规格的参考链（L316–338）

原始资料 Source → 候选事实／未知项 → 已批准事实／业务需求 → 场景／业务链路 → 能力 Capability → 功能 Function → 功能需求草稿 → AI 自检 → 人工批准／需求基线 → 研究／架构决策／工程设计 → Spec → Task → Workflow → Skill／Tool。

这是原文的候选链。整理建议：保留人工批准作为原链路的候选决策门，实际是否需要逐项批准由风险和任务类型决定，不在本轮确立新的强制审批规则。

## 四组机制与八节点链路的关系（整理建议）

| 机制 | 主要作用对象 | 候选产出 |
| --- | --- | --- |
| 理解与展开 | 原始想法、目标与问题、角色与场景、业务链路 | 初始目标与场景 |
| 反推与发现 | 能力与功能、必要条件、隐含需求 | 候选需求与规则 |
| 质疑与补漏 | 场景、业务、功能、异常与冲突 | 需要新增或修正的内容 |
| 裁剪与收敛 | 候选需求、依赖、价值及范围 | 需求基线与验收条件 |

四组机制是专项工作方法；八节点是推导链；13种推理模式是通用思考工具。它们有交叉但不相互替代。

## 后续实际验证任务（整理建议）

选一个真实但不完整的需求：固定相同原始描述和已有项目资料，对照普通直接推理与四组机制辅助推理。逐项比对有效新增需求、无效新增、重复、遗漏、冲突、可验收性及执行成本。由独立审核者依据原始目标判断，不能以生成字数或自评高分替代有效性。原文提到的九种候选机制完整清单尚缺，需要从相应历史材料恢复，而不是猜测补齐。
