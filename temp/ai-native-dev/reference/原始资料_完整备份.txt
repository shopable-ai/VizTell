### **2. 工程模型体系**

今天另一个非常重要的对话是「工程模型体系探索」，其中提出了一个关键观点：

**一个软件项目不能只有需求树和任务树，还需要多种工程模型来描述不同的问题。**

| 工程模型 | 解决什么问题 |
| --- | --- |
| Goal Tree 目标树 | 为什么开发？ |
| Problem Model 问题模型 | 用户遇到了什么问题？ |
| Stakeholder Model 利益相关者模型 | 涉及哪些人员，他们需要什么？ |
| Requirement Tree 需求树 | 用户需要什么结果？ |
| Scenario Model 场景模型 | 在什么情况下使用？ |
| User Journey 用户旅程 | 用户怎样完成任务？ |
| Business Flow 业务链路 | 业务怎样运行？ |
| Capability Tree 能力树 | 系统必须具备什么能力？ |
| Feature Tree 功能树 | 产品需要提供哪些功能？ |
| UI Tree 界面树 | 需要哪些界面和交互？ |
| Architecture Graph 架构图 | 系统内部如何组织？ |
| Data Model 数据模型 | 数据怎样定义、保存和流转？ |
| Task DAG 任务依赖图 | 开发任务怎样拆解和执行？ |
| Test Matrix 测试矩阵 | 怎样验证全部必要功能？ |
| Evidence Graph 证据关系图 | 怎样证明真正完成？ |

这是更容易理解的核心模型集合，不是完整模型目录，也不是要求每个项目生成15份文件。

后续研究已经扩展为35个候选模型家族、14个主领域，但我认为应该先保留上面这种直观阅读视图。

2. 需求推理体系（Reasoning）
之前已经研究了九种候选推理机制，其核心价值是让AI不只是被动执行用户明确说出的需求。
1
理解与展开
理解原始目标、角色、问题、场景和业务链路


2
反推与发现
从预期结果反推必要条件，发现隐含需求


3
质疑与补漏
发现异常、依赖、冲突、风险及遗漏


4
裁剪与收敛
删除重复和不必要的需求，确定最小范围


这四组机制具有较好的阅读价值，但其真实推理效果、独立价值和最小充分性仍然没有完成实证。
3. 研发工作流（Workflow）
工作流应该组织工程模型、推理、角色和Skill，而不是与它们重复建设。
研发环节	主要输入	主要输出
目标理解	用户原始想法	目标、问题、范围
需求推理	目标、领域知识	需求、场景、约束
产品设计	需求与场景	功能、规则、交互设计
技术设计	产品设计	架构、数据、接口、技术方案
工程实施	已批准设计	任务、代码、构建产物
测试验收	需求、判据、实现	测试结果、验收证据
持续迭代	用户反馈、运行结果	缺陷、变更、知识沉淀

每一个环节都可以关联适当的专家角色、推理方式、Skill 和验证机制。

这三个表比之前大量的抽象概念、关系登记和候选协议，更适合作为总体框架的核心阅读内容。

## **三、角色宇宙应该包含什么？**

建议建立两个相互关联但独立维护的角色库。

### **3.1 利益相关者宇宙：发现不同人的需求与利益**

| 角色类别 | 候选角色 | 主要发现的问题 |
| --- | --- | --- |
| 使用方 | 直接用户、间接用户、管理员、受益者 | 使用价值、操作困难、特殊场景 |
| 商业方 | 客户、付费者、投资人、产品所有者 | 收益、成本、商业可持续性 |
| 建设方 | 产品、设计、研发、测试、外包团队 | 实现成本、质量、交付风险 |
| 运营方 | 客服、运营、运维、维护人员 | 日常管理、故障、恢复成本 |
| 生态方 | 平台、渠道、供应商、合作伙伴、资源提供者 | 外部依赖、合作条件、资源限制 |
| 约束方 | 审核机构、监管机构、合规部门 | 权限、安全、政策与法律边界 |
| 受影响方 | 非用户、数据主体、竞争者、利益受损方 | 负面影响、利益冲突、外部风险 |

**助力方、阻力方、中立方不应该成为固定身份分类。** 它们是某个利益相关者在特定目标、特定时期下的态度。同一个平台方可能同时提供资源，又限制某些功能。

这七类是初始检查框架，并不声称覆盖所有行业。

### **3.2 专业能力宇宙：发现不同领域的问题**

| 专业领域 | 候选专家 | 核心判断 |
| --- | --- | --- |
| 用户研究 | 用户研究专家、领域专家 | 用户真正需要什么？ |
| 产品与业务 | 产品经理、业务分析师 | 应该开发哪些功能？ |
| 交互与体验 | UI、UX、无障碍专家 | 产品是否容易理解和使用？ |
| 技术与架构 | 架构师、技术选型专家 | 方案是否合理且可实现？ |
| 工程实现 | 前端、后端、浏览器扩展、数据专家 | 怎样可靠实现？ |
| 质量验证 | QA、测试架构师 | 如何发现错误并证明正确？ |
| 安全与合规 | 安全、隐私、平台审核专家 | 有哪些不可接受的风险？ |
| 商业与运营 | 商业、增长、运维专家 | 是否可持续运营？ |
| 决策质量 | 反方、事实核查、独立审计专家 | 是否存在错误假设、遗漏或过度设计？ |

专业能力是可以组合、扩展和复用的，不必为每一种能力创建一个永久运行的 Agent。

例如，修改浏览器扩展侧边栏的按钮间距，通常没有必要调用商业专家、后端专家或监管专家。


01

避免需求遗漏

02

独立判断
避免思维污染与盲目认同

03

对抗与质疑
主动发现错误、反例和盲区

04

权衡与决策
处理利益冲突及方案冲突

05

这些模式是 AI 可以按需调用的思考工具，而不是每次研发都必须执行的13个步骤。
推理模式	核心问题	输入	输出与停止条件
正向推理	这样执行会发生什么？	条件、行为	结果与状态路径明确
逆向推理	要实现结果，必须具备什么？	目标或失败结果	必要条件及候选原因明确
因果推理	为什么会发生？	现象、变量	有证据支持的原因或待验证假设
对抗推理	怎样可能使方案失败？	方案、规则	高影响反例及防御措施
反事实推理	如果改变某个条件会怎样？	原条件、替代条件	可比较、可验证的预测
类比推理	其他成熟系统怎样解决？	相似案例	可复用机制及适用边界
组合推理	多个条件同时发生会怎样？	状态、变量	达到预设组合覆盖要求
约束推理	哪些方案实际上不可行？	规则、资源、限制	可行方案与冲突处理
场景推理	用户实际怎样使用？	角色、环境、行为	正常、异常及恢复场景
边界推理	到达极限或越界会怎样？	数量、时间、权限等	临界条件与越界处理
价值推理	这个功能真的有必要吗？	目标、收益、成本	保留、延期或删除的理由
证据推理	凭什么认为结论正确？	主张、测试、事实	证据适用范围及剩余未知
时间演化推理	系统长期运行后会怎样？	当前系统、变化条件	维护、升级、迁移与退役策略

## **三、成熟方法研究：真正值得吸收的能力**

本轮网络研究发现，尤其值得研究的是 KAOS、STPA、FMEA、FTA、形态分析和组合测试。它们比单纯要求 AI「深入思考」「多专家讨论」提供了更具体的查漏机制。

| 成熟方法 | 最有价值的思想 | 应用于 AI 研发 |
| --- | --- | --- |
| [KAOS 目标导向需求工程](https://webperso.info.ucl.ac.be/~avl/gore.php?utm_source=chatgpt.com) | 从目标分解必要条件，并寻找阻碍目标实现的因素 | 发现隐藏需求与异常场景 |
| [系统思维与系统动力学](https://mitmgmtfaculty.mit.edu/jsterman/business-dynamics/?utm_source=chatgpt.com) | 关注系统关系、反馈、延迟 | 发现模块之间的隐藏影响 |
| [NASA 系统工程](https://www.nasa.gov/reference/4-0-system-design-processes/?utm_source=chatgpt.com) | 需求、设计、使用环境和目标互相验证 | 防止局部完成而整体失败 |
| [形态分析 GMA](https://swemorph.com/ma.html?utm_source=chatgpt.com) | 枚举关键变量及其可能取值，筛除不相容组合 | 发现未考虑的场景组合 |
| [TRIZ](https://aitriz.org/pages/triz?utm_source=chatgpt.com) | 从矛盾出发寻找更好的解决方案 | 避免接受错误的技术取舍 |
| [Design Thinking / 双钻模型](https://www.designcouncil.org.uk/resources/the-double-diamond/?utm_source=chatgpt.com) | 问题发现、发散探索、聚焦验证 | 防止过早确定错误需求 |
| [因果与反事实推理](https://pmc.ncbi.nlm.nih.gov/articles/PMC2836213/?utm_source=chatgpt.com) | 区分相关性、干预结果与反事实 | 防止把猜测当根因 |
| [Premortem 事前验尸](https://hbr.org/2007/09/performing-a-project-premortem?utm_source=chatgpt.com) | 假设项目失败，再寻找原因 | 提前发现隐藏风险 |
| [FMEA 失效模式与影响分析](https://swehb.nasa.gov/pages/viewpage.action?pageId=103776712&utm_source=chatgpt.com) | 从局部故障推导整体影响 | 发现异常传播路径 |
| [FTA 故障树分析](https://swehb.nasa.gov/pages/viewpage.action?pageId=72025075&utm_source=chatgpt.com) | 从不希望发生的结果反推可能原因 | 找到缺失的保护条件 |
| [STPA 系统理论过程分析](https://stamp-institute.org/stpa-primer/?utm_source=chatgpt.com) | 检查动作缺失、错误动作、错误时序 | 发现自动化系统交互风险 |
| [QAW / ATAM](https://www.sei.cmu.edu/library/sei-architecture-analysis-techniques-and-when-to-use-them/?utm_source=chatgpt.com) | 用场景检查质量需求与架构取舍 | 发现性能、安全、兼容性冲突 |
| [Scenario-Based RE](https://ieeexplore.ieee.org/abstract/document/738340?utm_source=chatgpt.com) | 从正常场景派生异常路径 | 扩充业务场景与测试案例 |
| [NIST 组合测试](https://csrc.nist.gov/pubs/sp/800/142/final?utm_source=chatgpt.com) | 有选择地覆盖多变量交互 | 控制场景组合爆炸 |
| [Google SRE](https://sre.google/workbook/canarying-releases/?utm_source=chatgpt.com) | 真实环境观测与渐进式发布 | 发现交付之后的风险 |

这些方法的共同价值不是保证找出所有问题，而是提供**结构化的遗漏发现机制，以及能够被检查的分析产物**。

例如，NASA 软件工程手册明确区分了 FMEA 的自底向上分析与 FTA 的自顶向下分析；KAOS 的障碍分析则直接研究如何从目标无法实现的情况反推需求。三者非常适合作为本轮双向推理的理论基础。![](https://www.google.com/s2/favicons?domain=https://swehb.nasa.gov&sz=32)Global Site+2

## **四、工程模型职责表**

之前研究工程模型时，最大的理解障碍是：虽然知道存在很多模型，但不知道什么时候真正需要使用它们。

**工程模型本质上是帮助 AI 理解软件不同方面的知识结构。**

下面是优先阅读的常用模型。

| 工程模型 | 解决什么问题 | 使用环节 | 下游用途 | 必要性 |
| --- | --- | --- | --- | --- |
| 目标树 | 为什么开发？ | 目标理解 | 需求与验收 | 核心 |
| 问题模型 | 用户遇到什么问题？ | 目标理解、缺陷修复 | 需求、根因定位 | 核心 |
| 利益相关者模型 | 为谁开发？谁受影响？ | 需求分析 | 场景与责任 | 核心 |
| 需求树 | 必须满足什么要求？ | 需求设计 | 功能与规格 | 核心 |
| 场景树 | 用户在什么情况下使用？ | 需求设计 | 行为与测试 | 核心 |
| 用户旅程 | 用户怎样完成完整任务？ | 产品设计 | 交互设计 | 按需 |
| 业务链路 | 业务怎样正常运行？ | 业务设计 | 能力与规则 | 核心 |
| 能力树 | 系统必须具备什么能力？ | 业务设计 | 功能设计 | 核心 |
| 功能树 | 产品需要提供哪些功能？ | 产品设计 | 功能需求卡 | 核心 |
| 状态与行为模型 | 不同状态下怎样运行？ | 业务、技术设计 | 逻辑与测试 | 复杂行为必需 |
| UI树 | 需要哪些界面与组件？ | 交互设计 | 前端实现 | 按需 |
| 架构图 | 系统内部怎样组织？ | 技术设计 | 模块与接口 | 按需 |
| 数据模型 | 数据怎样定义、保存与流转？ | 技术设计 | 存储与接口 | 按需 |
| 任务依赖图 | 怎样拆分与组织开发？ | 工程执行 | 开发任务 | 核心语义 |
| 测试矩阵 | 哪些情况需要验证？ | 工程设计、测试 | 测试执行 | 核心 |
| 证据关系图 | 怎样证明已经完成？ | 真实验收 | 验收裁决 | 核心 |

完整保存的职责表覆盖已有 **35个候选工程模型家族**，包括权限、风险、变更、部署、治理、运行观测等支撑模型。


### **工程模型之间最重要的推导关系**

**目标树**

为什么做

**场景与业务链路**

用户怎样完成任务

**能力树**

完成任务必须具备什么能力

**功能树**

产品需要提供什么功能

**功能需求与行为规格**

功能在什么条件下怎样工作

**解决方案与工程设计**

架构、UI、数据、接口

**验证设计**

测试矩阵、验收判据

**Spec 与 Task**

基于已批准需求和设计拆分研发任务

**代码实现与实际测试**

**证据 → 验收裁决 → 真实交付**

这并非不可逆的单向流程。发现问题时，应返回最早受影响的工程环节，而不是整个项目重新执行。

## **五、Skill 专业能力表**

Skill 不等于角色，也不等于工作流。

例如，架构师是一种角色，技术选型是一种专业能力，而 GitHub、浏览器、编译器是执行工具。

| Skill 能力 | 解决什么问题 | 触发条件与输入 | 工具及输出 | 失败处理与退出条件 |
| --- | --- | --- | --- | --- |
| P1 意图与现状分析 | 防止目标、上下文漂移 | 新任务、存量项目 | Git、检索；范围与现状 | 事实冲突保留未知 |
| P2 需求推理 | 发现隐含需求 | 模糊想法、需求草案 | 正向、逆向、异常推理；候选需求 | 必要需求收敛，未决项明确 |
| P3 专业研究 | 解决未知问题 | 缺少事实或可行性依据 | 官方资料、源码、实验 | 无证据不下定论 |
| P4 业务行为建模 | 理清复杂业务逻辑 | 目标、场景、规则 | 业务链、状态、功能需求 | 行为和异常可验证 |
| P5 方案与局部设计 | 选择或细化实现方案 | 需求、约束、候选方案 | 原型、源码、技术实验 | 不可行则返回方案研究 |
| P6 测试设计 | 提前发现验证遗漏 | 行为规格、风险 | 边界分析、组合测试；矩阵 | 覆盖范围和判据明确 |
| P7 规格与任务拆分 | 将设计变为可执行任务 | 批准需求、设计 | Spec、Task、依赖图 | 无孤儿任务和错误依赖 |
| P8 实现与构建 | 实现确定的功能 | Spec、Task、代码 | 编辑器、编译器、TDD | 完成局部实现与检查 |
| P9 缺陷定位与修复 | 找到真实错误原因 | 复现、日志、代码 | 因果分析、失败回归、补丁 | 修复并重跑相关回归 |
| P10 实际验证 | 证明软件实际正确 | 候选版本、测试判据 | 浏览器、测试工具、运行日志 | 取得证据或记录阻断 |

## **五、Skill 专业能力表**

Skill 不等于角色，也不等于工作流。

例如，架构师是一种角色，技术选型是一种专业能力，而 GitHub、浏览器、编译器是执行工具。

| Skill 能力 | 解决什么问题 | 触发条件与输入 | 工具及输出 | 失败处理与退出条件 |
| --- | --- | --- | --- | --- |
| P1 意图与现状分析 | 防止目标、上下文漂移 | 新任务、存量项目 | Git、检索；范围与现状 | 事实冲突保留未知 |
| P2 需求推理 | 发现隐含需求 | 模糊想法、需求草案 | 正向、逆向、异常推理；候选需求 | 必要需求收敛，未决项明确 |
| P3 专业研究 | 解决未知问题 | 缺少事实或可行性依据 | 官方资料、源码、实验 | 无证据不下定论 |
| P4 业务行为建模 | 理清复杂业务逻辑 | 目标、场景、规则 | 业务链、状态、功能需求 | 行为和异常可验证 |
| P5 方案与局部设计 | 选择或细化实现方案 | 需求、约束、候选方案 | 原型、源码、技术实验 | 不可行则返回方案研究 |
| P6 测试设计 | 提前发现验证遗漏 | 行为规格、风险 | 边界分析、组合测试；矩阵 | 覆盖范围和判据明确 |
| P7 规格与任务拆分 | 将设计变为可执行任务 | 批准需求、设计 | Spec、Task、依赖图 | 无孤儿任务和错误依赖 |
| P8 实现与构建 | 实现确定的功能 | Spec、Task、代码 | 编辑器、编译器、TDD | 完成局部实现与检查 |
| P9 缺陷定位与修复 | 找到真实错误原因 | 复现、日志、代码 | 因果分析、失败回归、补丁 | 修复并重跑相关回归 |
| P10 实际验证 | 证明软件实际正确 | 候选版本、测试判据 | 浏览器、测试工具、运行日志 | 取得证据或记录阻断 |
| P11 证据核查 | 防止虚假完成 | 运行结果、证据 | 版本核对、结果读回 | 证据不足不得放行 |
| P12 多角色评审与盲区检查 | 发现遗漏、错误与过度设计 | 当前阶段成果、风险 | 多视角、反例、审计 | 关键分歧得到处置 |
| P13 复盘与知识沉淀 | 减少未来重复错误 | 实际经验、失败记录 | Git、知识库、回归测试 | 经验具有来源及适用边界 |

**重要发现：这些能力目前还不能全部称为已经实现的 Skill。**

在 AI-Project-OS 当前仓库中，我核实到了 Skill 契约、模板及合成测试示例，但没有找到上述专业研发能力对应的完整正式 Skill 包。

因此，这13项是基于已有职责建立的候选能力使用索引，并非13个已经开发完成、能够直接安装运行的 Skill。




例如，开发一个全新产品、修改一个复杂功能、修复一个按钮缺陷，不应该执行同样复杂的工作流。

## **四、工程模型职责表**

之前研究工程模型时，最大的理解障碍是：虽然知道存在很多模型，但不知道什么时候真正需要使用它们。

**工程模型本质上是帮助 AI 理解软件不同方面的知识结构。**

下面是优先阅读的常用模型。

| 工程模型 | 解决什么问题 | 使用环节 | 下游用途 | 必要性 |
| --- | --- | --- | --- | --- |
| 目标树 | 为什么开发？ | 目标理解 | 需求与验收 | 核心 |
| 问题模型 | 用户遇到什么问题？ | 目标理解、缺陷修复 | 需求、根因定位 | 核心 |
| 利益相关者模型 | 为谁开发？谁受影响？ | 需求分析 | 场景与责任 | 核心 |
| 需求树 | 必须满足什么要求？ | 需求设计 | 功能与规格 | 核心 |
| 场景树 | 用户在什么情况下使用？ | 需求设计 | 行为与测试 | 核心 |
| 用户旅程 | 用户怎样完成完整任务？ | 产品设计 | 交互设计 | 按需 |
| 业务链路 | 业务怎样正常运行？ | 业务设计 | 能力与规则 | 核心 |
| 能力树 | 系统必须具备什么能力？ | 业务设计 | 功能设计 | 核心 |
| 功能树 | 产品需要提供哪些功能？ | 产品设计 | 功能需求卡 | 核心 |

这里的必要性是指相关工程知识不能遗漏，不代表必须为每一种模型创建独立的 Markdown 文件。

### **工程模型之间最重要的推导关系**

**目标树**

为什么做

**场景与业务链路**

用户怎样完成任务

**能力树**

完成任务必须具备什么能力

**功能树**

产品需要提供什么功能

**功能需求与行为规格**

功能在什么条件下怎样工作

**解决方案与工程设计**

架构、UI、数据、接口

**验证设计**

测试矩阵、验收判据

**Spec 与 Task**

基于已批准需求和设计拆分研发任务

**代码实现与实际测试**

**证据 → 验收裁决 → 真实交付**

这并非不可逆的单向流程。发现问题时，应返回最早受影响的工程环节，而不是整个项目重新执行。
