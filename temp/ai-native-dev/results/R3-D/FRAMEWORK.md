# 工程模型体系 · 总体框架 F1

**独立问题：** 工程需要表达哪些不同的知识和关系，哪些模型有独立用途？不构建元模型软件或要求每个模型对应文件。

## 1. 模型、对象、视图、表示
对象是目标、需求、业务实体、组件等；模型抽象表达对象及关系；视图从模型中选择关心的内容；树/图/表/自然语言是表示形式。同一业务知识可以有多个视图，不应建立多份互相冲突的真相。ISO/IEC/IEEE 42010:2022 的公开摘要区分架构与架构描述，并不规定实现工具或媒介，支持这类语义分离。下列为新候选模型族，非声称已恢复历史35族或14领域。

## 2. 模型族地图（原17入口不丢失）
| 一级用途 | 二级模型族及最小内容 | 解决的问题 |
|---|---|---|
| 目标、价值与现状 | 目标模型（目标、子目标、满足条件）；问题模型（现状、差距、影响、假设）；利益相关者模型（主体、利益、权限、责任）；价值/指标模型（成果、受益、测量） | 为什么、为谁、怎样算价值 |
| 需求与业务 | 需求模型（需求、来源、类型、条件、判据）；场景模型（主体、触发、环境、路径）；业务过程模型（角色、对象、流转、规则）；业务规则模型（条件、决策、约束）；状态行为模型（状态、事件、转移、不变量） | 必须发生什么和不得发生什么 |
| 产品能力与交互 | 能力模型（结果能力、依赖）；功能模型（可提供行为、覆盖需求）；用户旅程（用户目标、阶段、触点、痛点）；UI/信息架构模型（页面、组件、导航、交互状态） | 用户如何获得能力及完成任务 |
| 系统与技术 | 系统上下文（系统、外部实体、边界）；架构模型（结构、模块、责任、依赖）；数据模型（实体、关系、约束、所有权）；接口契约模型（消息/输入输出、错误、身份、版本）；运行/部署模型（节点、环境、拓扑、配置、资源） | 如何实现、集成、运行 |
| 约束、质量与安全 | 质量属性模型（场景、刺激、响应、度量）；权限/信任模型（主体、资源、授权、信任边界）；风险/危险模型（损失、条件、缓解）；决策/取舍模型（选项、判据、假设、决定） | 哪些方案可接受，怎样控制失败 |
| 计划与交付 | 项目/产品结构模型（范围、部件、交付物）；任务依赖模型（任务、前置、产出、负责人）；配置/版本模型（工件、候选、基线、版本关系）；变更影响模型（改动、影响对象、失效证据） | 怎样拆分、协同并维护可追溯版本 |
| 验证与演化 | 测试模型（对象、用例、环境、预期、覆盖）；证据模型（主张、证据、适用版本、裁决）；观测/运营模型（事件、指标、反馈）；演化/维护模型（迁移、退役、兼容、恢复） | 怎样证明、运行、演进 |
上表保留原17个阅读条目，并补上下文、接口、质量、权限、风险、决策、部署、配置、变更与运营等常被漏掉的模型用途。数量不作为目标；业务规则可表达为决策表或约束，状态可用状态机或文字，任务可以一条清单；不要求所有模型都存在。

## 3. 高价值辨析
- 目标是期望结果，需求是必须满足的性质，能力是达成结果的能力，功能是产品对外提供的行为，模块是实现结构。不是同一颗树；一个功能可满足多个需求，一个能力可由多个功能/外部服务提供。
- 场景描述条件下的一条或一组行为；业务过程描述多主体运行与交接；用户旅程从体验视角组织触点；状态模型描述事件与状态转换，规则限制允许的行为。它们可来自同一业务事实。
- 测试模型定义要怎样检验，证据模型记录实际获得什么以及支持何种主张，任务图表示执行依赖。完成任务不等于满足需求。
- 架构视图显示关键结构关系，不必等于目录结构。逻辑设计与物理/部署设计可独立变化。

## 4. 关系与最小模型集
| 关系 | 例（抽象） |
|---|---|
| 分解/细化 | 子目标细化父目标；子需求细化高层需求 |
| 派生/约束 | 场景、规则及约束导出候选需求 |
| 满足/分配/实现 | 功能满足需求；能力分配给组件；组件实现契约 |
| 依赖/交互 | 组件依赖服务；事件改变状态 |
| 验证/支持/反驳 | 测试检验需求，证据支持或反驳裁决 |
| 影响/版本 | 变更影响关系和证据，版本绑定实际产物 |
选择模型的触发条件是需要回答的问题：目标模糊用目标/问题；业务复杂用场景/规则/状态；跨系统用上下文/契约；风险高用安全/质量；变化大用影响/版本；验收必须有判据和证据语义，但未必画图。不要生成模型只是为了齐全。

## 6. F2：模型选择与必要的表示语义

| 待回答问题 | 优先模型 | 最小语义 | 不应添加的理由 |
|---|---|---|---|
| 为什么做 | 目标/价值/问题 | 主张、层级、条件、结果 | 目标单一且清楚，不强制生成复杂树 |
| 谁需要什么 | 角色、需求、场景 | 主体、约束、需求、情境 | 不把每项角色名称单独建图 |
| 怎样发生 | 业务链、过程/事件 | 起点、条件、行为、结果 | 无顺序依赖时无需完整流程图 |
| 状态能否改变 | 状态模型 | 状态、触发、守卫、迁移 | 不用状态图替代所有业务规则 |
| 能力如何承担 | 能力、功能与架构 | 职责、分配、依赖、接口 | 功能与组件并非一一对应 |
| 信息如何有效 | 数据、契约 | 概念、关系、身份、约束 | 不因表示逻辑数据而提前确定存储技术 |
| 怎样组织交付 | 任务与依赖 | 工作单元、前置、输出、责任 | 不从技术树机械生成任务树 |
| 如何判断 | 质量、验证与证据 | 主张、判据、范围、证据、裁决 | 验证计划不是验证结果 |

保留原17模型入口，表中为选择索引而非缩减模型总数。模型应满足最小充分表达：能回答当前问题、与共享概念一致、能够表达反例及重要约束。形式随复杂度选择文字、表、树、图、状态或形式化表达；不是所有概念都要单独落盘。ISO 42010公开摘要支持区别架构和表达；模型族的划分及选择表为本轮推断。

**抽象反例：** 功能 F1、F2 共用技术组件 C；若强制功能树与组件树同层同数，会制造重复组件或遗漏共用关系。采用多对多分配/实现关系。一个模型内部语义自洽但遗漏外部约束，也不能称充分；用 A 的相关因素和 H 的高影响审查补充，不增建重复图。模型停止扩展于能解答当前问题且未遗漏关键关联、未知和冲突。

本节为F2通用结构推导和概念反例，未进行具体应用；重要分类和完整专业知识仍须独立核验。

## 7. 原17阅读条目的精确映射（reference/05）

目标树→目标模型；问题模型→问题模型；利益相关者模型→利益相关者模型；需求树→需求模型；场景树→场景模型；用户旅程→用户旅程；业务链路→业务过程模型；能力树→能力模型；功能树→功能模型；业务规则→业务规则模型；状态与行为模型→状态行为模型；UI树→UI/信息架构；架构图→架构模型；数据模型→数据模型；任务依赖图→任务依赖模型；测试矩阵→测试模型；证据关系图→证据模型。以上17项逐项保留，树、图、矩阵是可选表示方式，不自动等于模型语义。新增模型只在解决独立知识问题时保留；历史35/14没有恢复。
