# R3-J Skill、Tool、Agent：框架 F1

## 独占问题
将 AI 的能力如何识别、封装、组合与使用？先定义语义及分类，不提前开发 Skill 市场、运行时或插件。

| 对象 | 定义与边界 | 不等同于 |
|---|---|---|
| Method 方法 | 一类问题可重复使用的思考或操作原则 | 执行实例 |
| Capability 能力 | 在给定前提下达到一类结果的能力描述 | 必须已有工具 |
| Skill | 局部、可复用、可描述输入输出且可评价的能力包 | 专家角色、整条研发工作流 |
| Tool | 具有明确调用接口和权限边界的操作能力 | 负责目标判断的主体 |
| Agent | 根据目标、状态与授权组织行动的执行主体 | 角色名称或模型名称 |
| Workflow | 多活动之间的控制与衔接 | 单一 Skill |
| Model | 提供推断、生成等能力的模型资源 | 天然具备授权、记忆、工具或专业资格 |

## Skill 候选分类
| 领域 | 二级能力族 |
|---|---|
| 认知 | 意图理解、上下文恢复、事实提取、未知识别、术语辨析 |
| 研究 | 检索、资料筛选、证据比较、来源核验、知识抽取 |
| 推理与决策 | 需求推导、约束分析、备选构造、权衡、反证 |
| 知识表达与设计 | 业务建模、交互设计、架构/数据/接口设计 |
| 工程执行 | 代码理解、变更计划、实现、构建、迁移 |
| 质量与验证 | 审查、测试设计、运行验证、缺陷定位、验收证据 |
| 知识与协作 | 记录归纳、知识更新、交接、冲突识别 |

它们是功能族候选，不是现有 Skill 库或必须一项一包。某能力是否成为 Skill 由稳定性、重复需求、边界、可评价性决定。专业领域的不同方法可共用一个执行接口，也可保持独立；不能因为名称相近即合并。

## 能力描述的最低必要结构
消费者；职责；适用及不适用条件；输入、输出及版本；模型判断与确定性代码的边界；可用工具和权限；失败及未知处理；证据/评价；兼容性与维护者。先用人可阅读的方法说明，稳定后再考虑 manifest。Tool 另需参数、返回、外部副作用与失败语义。Agent 另需目标、授权、上下文、可用能力和停止条件。角色 F 是职责与责任，不能默认映射成单个 Agent。

## F2：从能力索引到可复用单元的判断

候选方法是否值得封装，看重复性、结果稳定性、局部责任可识别、输入/输出可理解、权限可限定、可独立评价、维护成本。不存在稳定共性时保留专业方法，不造 Skill；一次性调用已有 Tool 足够时不必封装。多个步骤需要跨阶段状态控制时归 I 的 Workflow；不因为具备多个 Tool 就称具备专业能力。

| 需要 | 应选择 | 拒绝 |
|---|---|---|
| 专业判断未知 | 方法/专业视角 + 模型 | 用调用成功代表判断正确 |
| 确定性转换 | Tool 或确定性能力 | 强制用模型重复完成可确定操作 |
| 重复局部专业工作 | Skill 候选 | 以名称、提示词或文件数当成熟能力 |
| 跨活动依赖与恢复 | Workflow | 把整条研发路线封进局部Skill |
| 自主协调执行 | Agent（具备真实运行条件） | 把角色模拟当实际Agent |

接口中的未知/失败应当可区别：缺必要输入、无法判断、工具失败、权限拒绝、结果不满足判据。消费者根据差异决定补信息、换方法、恢复或停止，而不是统一重试。原13能力中P8/P9/P10需未来实际执行证据；P11/P12有评价职责但不能自动自证独立。本阶段无包、代码、自动化调用或运行验收。


## R1 深化：能力封装的最小契约、组合与失效

原P1–P13保留为需求索引，不是13个现成Skill。方法的有效性、能力描述、实现形式、实际运行证据是不同成熟状态。

### 1. 局部能力的独立性

候选Skill若要成立，应可解释：消费者及问题、输入与适用前提、方法与关键判断、预期输出及错误、允许使用的资源与权限、完成证据、适用版本及维护责任。方法可以有多个实现，也可以由人、模型、确定性工具共同承担；模型具备语言推理能力不表示它拥有相应信息或授权。若共性仅是名称、实际前提和产物无法稳定描述，不封装；如果能力只是一次确定性操作，优先Tool；若包含跨责任、跨阶段协调与恢复，交I编排。

| 原能力族 | 重点边界与拆分选择 |
|---|---|
| P1/P2/P3 | 恢复事实、推导义务、解决未知的证据标准不同，不能混成一次无来源的「需求生成」 |
| P4/P5/P6 | 表达行为、比较设计、预设判据各自产物不同；可共享专业知识，但验证设计不能只由方案生成逻辑自证 |
| P7/P8/P9 | 计划与实现分开；诊断、修正、回归各有退出条件，可组合但不可跳过根因不确定性 |
| P10/P11/P12 | 产生证据、核查证据、质疑主张的责任和独立性分开；同一主体可自审，但不能冒称独立 |
| P13 | 仅提取有范围的学习结论与失效条件，消费K的知识治理，不重复构建知识平台 |

### 2. 组合与失败语义

若A的输出满足B的输入契约、语义版本相容、必要前提成立且权限允许，才可以组合；格式相同不证明含义相同。B的权限必须由真实授权单独限定，而非从A输出文本或A拥有的权限推得；组合执行的每一步都不得越权。外部文档和工具返回是数据/证据候选，不能自行授予新权限或更改目标。

区分「输入不足」「不适用」「分析不确定」「调用失败」「权限拒绝」「未知结果」「产物不满足判据」。消费者按语义选择补输入、换方法、核对状态、等待有权裁决或停止；不能统一重试。抽象反例：A输出文本结论及来源，B需要已验证事实，二者即使JSON字段相同也不能直接组合；需增加证据裁决，不应为满足接口将未知转换为真。工具回执是运行记录，不自动证明真实业务目标。

本轮仅理论研究（依据reference/10、I/L/K及F的独立性）。未编写包、脚本、manifest、运行时或测试；何种能力值得正式封装依后续应用证据，而非框架阶段硬门。
