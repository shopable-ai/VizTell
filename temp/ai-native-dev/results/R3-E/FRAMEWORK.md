# 项目多维拆分 · 总体框架 F1

**独立问题：** 怎样把复杂的软件研发对象及工作拆成可理解、可交付、可验证、可复用的单元？不把不同结构混成一个项目目录。

## 1. 多轴拆分地图
| 拆分轴 | 候选层级 | 产生什么 |
|---|---|---|
| 目标轴 | 总目标→子目标→成功条件 | 目标和价值边界 |
| 业务轴 | 业务领域→业务能力→过程/场景/规则 | 业务职责与对象 |
| 产品轴 | 产品→子产品/能力→功能→交互/行为 | 产品范围与用户结果 |
| 技术轴 | 系统→子系统→服务/模块→组件→实现单元 | 技术职责、接口和依赖 |
| 交付轴 | 项目/变更→交付增量→工作包→任务→检查 | 可验收成果与执行依赖 |
| 垂直方法轴 | 专业问题→方法→步骤→输入输出→检查与回退 | 可重复执行的专业工作方法 |
| 横向复用轴 | 共性问题→可复用方法/知识/组件→适配条件→复用实例 | 跨任务、跨项目资产 |
前五类回答不同“拆什么”；后两类回答“如何深化专业工作及复用”。水平、垂直、横向是便于阅读的方向，不是强制物理层级。
 
## 2. 交叉关系（核心）
目标/子目标由多个需求支撑；业务能力可跨产品功能；功能可能跨技术模块；一项交付增量可包括多个模块的差量。任务依赖图描述前置、结果及共享资源，不等于产品树或代码树。
- 优先以用户可见结果/风险降低作为交付切片，再根据内部依赖拆技术任务；不能把所有前端/后端任务完成等同一个业务闭环。
- 拆分边界以语义责任、接口、状态和验证独立性确定。组合变更必须有集成/跨边界验证责任。
- 有循环依赖时识别实际耦合，允许把不可独立验收的任务组成一个工作包、显式迭代，不伪造 DAG 无循环。
- 最小任务需要有目标或需求链接、范围/非范围、输入/前置、产出、验收与失败处理；其表达可以很短。

## 3. 粒度与动态裁剪
| 类型 | 优先粒度 | 禁止的机械做法 |
|---|---|---|
| 新系统 | 目标/领域→可运行业务切片→必要实现 | 先造全量目录及所有基础设施 |
| 跨模块变更 | 受影响行为→接口/状态/数据/兼容→差量任务 | 只拆代码文件不检查集成 |
| 局部缺陷 | 现象/期望→定位→必要修改→定向回归 | 重建整个系统模型 |
| 专业研究 | 待解问题→知识分支→证据与结论 | 把搜索次数当完成 |
| Skill复用 | 共性方法→稳定输入输出→适配和验证 | 每个任务复制一个Skill |
拆分继续的理由是任务不可理解/不可安全执行、依赖不明、验收不可定义或风险跨边界。到足够小且可验证时停止。拆分过度会导致协调、集成、上下文成本高于价值。 

## 4. 框架审查问题
是否有无来源任务、目标未分配、重复任务、输入没人产出、产物无人消费、无验收或跨模块无人负责？是否假设技术树等于业务树？是否混用专业方法步骤与项目任务层级？这些是结构检查，不是完整应用验证。

## 5. F2：何时拆分、何时合并

| 拆分驱动 | 适合的轴 | 合并/停止条件 |
|---|---|---|
| 目标不清或过大 | 目标与价值 | 子目标可说明组合如何支持父目标 |
| 业务职责复杂 | 业务对象/行为/能力 | 高耦合业务不因数量机械拆成独立域 |
| 用户体验不同 | 产品/交互 | 共用能力保留复用关系 |
| 技术职责与依赖复杂 | 技术模块/接口 | 边界内高内聚，外部依赖可识别 |
| 交付不可安排/验收 | 任务/交付 | 产物、责任、条件和验收可独立判断 |
| 多次出现相同能力 | 垂直专业方法/横向复用 | 可分离稳定共性与变体，不提前抽象 |

**递归拆分规则：** 选轴→确定父目标/范围→子单元覆盖与组合关系→标记跨边界依赖→审查接口和验收→只有子单元仍不可理解或不可判断才继续拆。对于并行任务，区分知识依赖、资源冲突、写入冲突和实际执行顺序。依赖环可能意味着需共同迭代，不能武断删除一条边使图变成 DAG。

**反例：** A 和 B 均独立正确，但接口契约冲突，组合结果失败；因此局部验收不是组合验收。若拆分增加交接成本且不能降低认知、风险、执行或评价负担，合并更好。分解后的对象仍需可追溯到父目标，避免孤儿、重复与无人负责的接口。

## R1 深化：分解、接口组合与工作单元边界

原四方向与本专题七轴不变。重点是决定何时拆、按什么轴拆、怎样证明组合没有丢掉父目标，而不是再造统一任务树。

### 1. 三种不应混淆的切分

目标/业务分解依意义和充分性组织；技术分解依变化隔离、职责内聚、信息隐藏和接口稳定性；交付分解依可评价结果、工作量、风险、依赖和责任。工作分解结构用于范围与交付物组织，不规定具体执行先后；产品结构、技术模块、任务依赖和专业方法步骤可以各自多对多映射。Parnas 1972论文作者机构摘要核对表明模块化效果依分解判据而异；信息隐藏原则作为公认设计思想使用，未核读付费原文全文。

选择：如果复杂度来自需求语义，先拆业务/目标；如果来自跨边界变化，优先梳理技术职责/契约；如果来自交付无法评价，以可观察目标和风险降低形成纵向交付切片；如果来自重复专业工作，拆方法/复用轴而非项目模块。允许在同一交付切片内跨多个技术模块，不规定永远以某一种轴为先。

### 2. 子单元能否独立成立

最小结构：上位目标或义务、范围/非范围、产物、所需输入、责任和授权、依赖、局部判据、与父级组合判据、异常回退。接口不仅是输入输出类型，也含前置、后置、错误、所有权、版本和共享约束。抽象 assume-guarantee：若A的保证不能在边界条件下满足B的假设，则 A 与 B 各自局部正确不足以组合；若存在公共不变量，还须证明双方交互保持它。若双方都假设对方先产出同一前置条件且不存在初始供给，互相声明保证并不能消除循环。

依赖至少区分：必要产物/知识、硬时间先后、资源互斥、写入与责任冲突、接口协商、共同约束。硬先后环可通过找到初始条件、分阶段产出或共同工作包处理；互相协商是迭代而非死锁结论。依赖图强连通分量仅是定位耦合的工具，不意味着每个分量必合为一个技术模块。

### 3. 粒度收敛与反例

每次拆分都问：是否减少认知/失败影响/交付不确定性，是否引入跨边界协调、接口、环境与验收成本？父范围覆盖、无孤儿义务、组合满足、关键依赖有提供者、结果可辨认；不满足则改轴、合并或加集成责任。条件稳定且工作可理解、可安全执行、可独立或组合评价时停止；不按固定任务数量和工时切。反例：按技术层分成A和B，两个子任务均完成，但目标只在A与B契约相容时成立；必须补组合责任而不是按完成率放行。反过来，把所有变化塞进一个大工作包会损失独立并行、边界理解和局部回退价值。
