# 项目多维拆分 · 总体框架 F1

**独立问题：** 怎样把复杂的软件研发对象及工作拆成可理解、可交付、可验证、可复用的单元？不把不同结构混成一个项目目录。

## 1. 多轴拆分地图
| 拆分轴 | 候选层级 | 产生什么 |
|---|---|---|
| 目标轴 | 总目标→子目标→成功条件 | 目标和价值边界 |
| 业务轴 | 业务领域→业务能力→过程/场景/规则 | 业务职责与对象 |
| 产品轴 | 产品→子产品/能力→功能→交互/行为 | 产品范围与用户结果 |
| 技术轴 | 系统→子系统→服务/模块→组件→实现单元 | 技术职责、接口和依赖 |
| 交付轴 | 项目/变更→交付增量→工作包→任务→检查 | 可验收成果与执行依赖 |
| 垂直方法轴 | 专业问题→方法→步骤→输入输出→检查与回退 | 可重复执行的专业工作方法 |
| 横向复用轴 | 共性问题→可复用方法/知识/组件→适配条件→复用实例 | 跨任务、跨项目资产 |
前五类回答不同“拆什么”；后两类回答“如何深化专业工作及复用”。水平、垂直、横向是便于阅读的方向，不是强制物理层级。
 
## 2. 交叉关系（核心）
目标/子目标由多个需求支撑；业务能力可跨产品功能；功能可能跨技术模块；一项交付增量可包括多个模块的差量。任务依赖图描述前置、结果及共享资源，不等于产品树或代码树。
- 优先以用户可见结果/风险降低作为交付切片，再根据内部依赖拆技术任务；不能把所有前端/后端任务完成等同一个业务闭环。
- 拆分边界以语义责任、接口、状态和验证独立性确定。组合变更必须有集成/跨边界验证责任。
- 有循环依赖时识别实际耦合，允许把不可独立验收的任务组成一个工作包、显式迭代，不伪造 DAG 无循环。
- 最小任务需要有目标或需求链接、范围/非范围、输入/前置、产出、验收与失败处理；其表达可以很短。

## 3. 粒度与动态裁剪
| 类型 | 优先粒度 | 禁止的机械做法 |
|---|---|---|
| 新系统 | 目标/领域→可运行业务切片→必要实现 | 先造全量目录及所有基础设施 |
| 跨模块变更 | 受影响行为→接口/状态/数据/兼容→差量任务 | 只拆代码文件不检查集成 |
| 局部缺陷 | 现象/期望→定位→必要修改→定向回归 | 重建整个系统模型 |
| 专业研究 | 待解问题→知识分支→证据与结论 | 把搜索次数当完成 |
| Skill复用 | 共性方法→稳定输入输出→适配和验证 | 每个任务复制一个Skill |
拆分继续的理由是任务不可理解/不可安全执行、依赖不明、验收不可定义或风险跨边界。到足够小且可验证时停止。拆分过度会导致协调、集成、上下文成本高于价值。 

## 4. 框架审查问题
是否有无来源任务、目标未分配、重复任务、输入没人产出、产物无人消费、无验收或跨模块无人负责？是否假设技术树等于业务树？是否混用专业方法步骤与项目任务层级？这些是结构检查，不是完整应用验证。
