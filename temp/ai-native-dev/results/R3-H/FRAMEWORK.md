# 盲区审计与成熟方法 · 总体框架 F1

**独立问题：** 哪些类型的错误、遗漏、冲突和证据缺失需要被发现？什么专业方法适合什么审计对象？当前构建审计地图，不进行产品测试。

## 1. 审计的三维框架
维度一：审计对象（目标/事实→需求/场景→方案/模型→任务/实现→验证/交付→运营/知识）。
维度二：审计领域（原R2八领域）。
维度三：缺陷性质（缺失、错误、歧义、冲突、无依据、越界、不适用、失效、过度设计、不可验证）。例如同一需求可同时有条件遗漏与证据缺口，不能仅按阶段分类。

| 八领域（保留） | 二级审计问题 |
|---|---|
| 价值与目标 | 意图漂移、错误问题、非目标扩展、利益冲突、成功条件不明 |
| 需求与行为 | 必要规则、角色场景、正常/异常/替代/恢复、未分配需求 |
| 状态与时序 | 初始/终止、状态转换、不变量、并发、重复、延迟、顺序、未知结果 |
| 数据与环境 | 身份、归属、生命周期、数据一致性、设备/版本/规模/网络、迁移 |
| 依赖与执行 | 依赖缺失、接口、可行性、输入输出、资源、集成、现有能力与重复建设 |
| 风险与质量 | 安全、隐私、供应链、性能、可靠性、体验、可维护、失败后果 |
| 责任与证据 | 授权、责任空白、裁决权、来源/版本、独立性、真实验收、证据失效 |
| 生命周期 | 变更影响、运营观测、回滚、维护/更新、反馈、知识失效、退役 |
因素A供输入，G供推理，H按目标和风险选择检查，不重复造因素及推理目录。

## 2. 不同阶段的关键审查
| 阶段对象 | 主要审查输出 |
|---|---|
| 目标/来源 | 不一致目标、缺事实、假设及需决策事项 |
| 需求/业务 | 必要需求缺失、冲突、可测判据缺口 |

| 运行/知识 | 事故或长期风险、变更失效、未沉淀/过时经验 |

## 4. 审计输出与停止
问题→影响目标/对象→证据/假设→修正建议→返回对应链路→验证/保留风险。发现类型分为已证实缺陷、待证假设、无效新增、可接受/延期风险；只因缺少文档不自动判缺陷。优先检查不可接受后果、关键约束与高影响未知，按风险控制组合。不以审计数量或专家一致为完成。后续才独立验证命中率、误报、成本及方法适用边界。

## 5. F2：审计方法路由及否决规则

| 缺陷性质 | 优先审查方式 | 输出 |
|---|---|---|
| 目标/需求遗漏 | 目标反推、主体和场景覆盖、需求追溯 | 未覆盖目标、候选补项与依据 |
| 矛盾、边界或例外 | 逻辑一致性、边界值与组合推演 | 冲突条件、反例、修正范围 |
| 局部失效及影响 | FMEA类失效模式分析 | 可能失效、局部及下游影响 |
| 严重后果及系统交互 | STPA类控制约束、系统性分析 | 不安全控制、约束、待查因果 |
| 架构取舍与质量 | 质量属性场景、ATAM类权衡 | 敏感点、风险、取舍依据 |
| 事实或声明错误 | 来源、主张/证据关联、反证检查 | 证据范围及声明上限 |
| 过度设计 | 必要性、替代、裁剪和成本审查 | 可去除、延期或需保留的依据 |

先由 A/C/D 确定审计对象与目标，按风险及未知选择方法，不叠加全部成熟方法。STPA 与 FMEA 视角不同，不互相替代：组件均无局部失效而交互形成危险，单靠局部失效清单未必覆盖。ATAM参照 SEI 公开资料，用于架构质量属性权衡，不直接证明架构正确；NIST SSDF是安全实践指导，不证明任何项目合规。本表是概念性路由。

**否决与回流：** 已知重大逻辑错误、关键遗漏、硬约束冲突、虚假证据或越界声明优先阻断；分数高不能抵消。输出区分发现、证据、严重度、影响对象、可修正范围、待定责任；B 将问题返回对应节点，K 保存反例。审计停止于高影响问题已处置或明确阻断，新增检查不改变结论。框架自审仅验证定义与逻辑，不执行产品测试，也不宣称成熟方法的实际效果。

本节为F2通用结构推导和概念反例，未进行具体应用；重要分类和完整专业知识仍须独立核验。

## 6. F2补证：原15成熟方法的独立作用、选择与限制

本表是对原reference/08的逐项保留和进一步核查。理论来源支持方法的基本作用；“如何组合到AI研发框架”仍是本轮推断。只研究理论，不执行实际应用、模型程序或产品测试。

| 方法 | 在框架中的独立用途与输入→输出 | 适用边界与证据状态 |
|---|---|---|
| KAOS | 从目标、约束、假设及责任主体出发，细化目标、发现冲突及障碍→候选需求与责任 | 不把每个目标直接转成唯一功能；UCL作者项目页核验目标细化、冲突与主体分配；原论文作者机构摘要支持障碍分析 |
| 系统思维/系统动力学 | 当存在反馈、积累、延迟和长期影响时，研究相互作用→结构/动态假设 | 因果环并非因果已证明；MIT Sterman《Business Dynamics》目录支持反馈、动态复杂性与建模 |
| NASA系统工程 | 从利益相关者期望与需求，递归逻辑分解及设计→分层关系和系统边界 | 过程可裁剪，非强制完整文档；NASA SEH 4.0、6.8公开章节核验 |
| GMA形态分析 | 多参数及离散取值→交叉一致性检查→减少不相容组合 | 两两相容未必保证高阶组合全局相容；一致性不是因果或质量保证；Swedish Morphological Society方法页核验 |
| TRIZ | 明确相互冲突的技术要求→借用矛盾分析、分离或创新原则→候选方案 | 提供发散策略，不自动证明可行或最优；Altshuller Institute公开知识介绍核验 |
| 双钻 | 不清楚问题或存在早期方案偏见→发现、定义、发展、交付两次发散收敛 | 不等于每次研发必须四阶段；Design Council官方页核验 |
| 因果/反事实 | 给定变量、假设、机制及观察→区分相关、干预和反事实主张 | 必须陈述因果假设、可识别性和适用范围；Pearl 2010论文HTML摘要核验 |
| Premortem | 从假定计划失败出发→列可能原因→优先调查或控制风险 | 生成的是风险假设，不是故障事实或概率；Klein 2007 HBR公开摘要核验 |
| FMEA | 从组件/接口与失效模式出发→逐层影响、检测及补偿 | 早期仅能做粗粒度分析，依赖对设计和故障模式理解；NASA软件工程手册8.5（历史版本）核验 |
| FTA | 从特定不希望发生的顶事件出发→逻辑条件、可能原因及组合 | 目标是特定顶事件，不覆盖所有其他损失；NASA软件FMEA章明确对照自顶向下FTA；原FTA独立链接403，间接支持 |
| STPA | 从损失、危险、控制结构出发→不安全控制动作、约束及因果场景 | 可分析无组件失效的危险交互；不以STPA单独证明安全；STPA Primer公开页核验 |
| QAW/ATAM | QAW帮助识别质量属性场景；ATAM分析架构候选的取舍、风险与敏感点 | 两者输入及目标不同，不能合并成同一评估；SEI公开方法页核验 |
| Scenario-Based RE | 从角色、目标、条件与交互场景出发→候选正常、替代、异常及恢复需求 | 场景不等于完整需求；原IEEE论文链接418，未读取原文；IREB elicitation、KAOS公开项目页仅支持场景导向调查的部分一般思想，原方法细节仍待核验 |
| NIST组合测试 | 对参数、取值、约束与交互强度建模→选有覆盖保证的组合 | t-way保证的是所设交互覆盖，不保证发现所有故障；SP800-142公开摘要核验 |
| Google SRE | 运行反馈与候选变化→代表性信号、对照、风险限制→可评价的运行证据 | 指标受混杂和样本代表性影响，不证明所有业务正确；SRE Workbook Canarying Releases公开章节核验 |

### 组合选择的结构结论
- 目标缺口优先KAOS及场景研究；问题定义不清用双钻；有技术矛盾再引入TRIZ。
- 参数组合空间大时GMA做候选相容性筛选，NIST组合方法研究后续覆盖策略；两者不等同。
- 局部模式失效→FMEA；已知顶层不可接受事件→FTA；控制交互、时序及社会技术系统风险→STPA；长期反馈与积累→系统动力学。按风险组合，不能以任一方法替代全部审计。
- 质量要求不清用QAW，具体架构权衡用ATAM；因果/反事实校核解释条件；Premortem补风险假设；SRE关注运行信号与反馈。
- 通用理论支持不等于本AI框架实效。当前15个方法均有选择和限制入口，其中13个取得直接相关公开来源层面的支持、FTA取得间接支持、Scenario-Based RE原论文未核验。不是15项完整理论课程或15项已独立验证。完整正式标准和方法内部步骤不在本节伪称已通读。

## R1 深化：成熟方法的独立作用、适用对象与审计结论

### 2. 三种失效视角的理论区分

| 方法 | 分析起点 | 核心操作与产物 | 局限 |
|---|---|---|---|
| FMEA | 单元、行为或数据的故障模式 | 向上推局部/系统影响，形成失效、影响及控制候选 | 仅单故障分析可能漏掉组合、正常交互和边界 |
| FTA | 定义明确的不可接受顶事件T | 按AND/OR条件反推致因，寻找最小致因组合（相对于模型） | 顶事件或因果结构遗漏会漏检；概率推断需可靠分布/依赖 |
| STPA | 损失、危害、控制结构 | 检查控制动作缺失、提供错误、时序、持续时间及反馈，推导控制约束 | 控制模型不完整仍可能遗漏；不是概率排名工具 |

抽象反例：顶事件 T=(a∧b)∨c。只检查a或b单独触发T会漏掉{a,b}；按故障树逻辑可得两个最小致因集合{a,b}与{c}，前提是表达本身充分。若a,b代表各自局部合法的动作，却在某环境时序交互中共同违反系统不变量，则单纯局部故障清单并不足够；STPA关注这类控制条件。三种方法互补，不意味着每个项目都需全部采用。STPA原理核对：https://stamp-institute.org/stpa-primer/ 。

### 3. 审计的选择机制

目标/障碍→GORE；角色与异常路径→场景需求工程；设计备选→形态分析、双钻、TRIZ；复杂反馈→系统思维；质量场景提取与架构权衡分别用QAW和ATAM；故障和控制选择上表；有限交互→NIST组合方法；不确定因果→竞争解释、反事实；计划风险→premortem；运行与服务可靠性→SRE。NASA系统工程作跨层级过程参照。先定位高影响主张和风险，再选能产生独立新信息的方法，不按名称全调用。

形式：审计对象+主张+适用条件+发现类型+反例/来源+影响+处置（已否定、待证、可接受、阻断、不适用）。用正向从条件找结果，用逆向从结果找候选原因，再判断是否存在另一个充分解释。任何建议必须能指出实际改变哪个主张、义务或风险，否则归为低价值重复。重要义务未核实不能靠平均评分关闭。有限t-way覆盖只说明给定域与交互阶数覆盖，不能证明所有故障或安全属性；NIST公开摘要：https://csrc.nist.gov/pubs/sp/800/142/final 。

抽象审查结果：以上T的双条件反例推翻「所有单因素正常即可整体安全」；它只验证逻辑反例，不是实际测试。仍有15方法内部完整条件、方法交叉裁剪与风险度量待专业独立审查；框架期不进入产品实验。
