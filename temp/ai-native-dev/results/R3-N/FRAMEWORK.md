# R3-N AI Project OS 系统价值：框架 F1

## 独占问题
通用研发方法成熟后，哪些问题需要工程系统承载？哪些应继续保持知识、方法、轻量约定？不能从研究专题数量直接推导软件子系统数量。

## 三层判断
1. 方法论层（A–M）：研究对象、模型、推理、协作、治理、证据和知识复用的通用原则。
2. 运行需求层：反复发生的真实任务中，明确的状态、依赖、权限、重复成本、协作冲突和证据问题。
3. 工程载体层：只有运行需求有足够价值和证据时，选择文件约定、现有工具、局部自动化或系统组件。

## 原七个候选组件的职责与替代性（reference/12）
| 组件 | 职责 | 可能的替代方式，非建设决定 |
|---|---|---|
| 目标与真相层 | 目标、需求、约束、决策、事实的可追溯关系 | 明确的来源和版本约定 |
| Reasoning Engine | 推理模式、专业视角、候选方案、反方审查 | 通用方法库及现有模型能力 |
| Workflow Engine | 活动依赖、动态分流、状态与恢复 | 人可读工作流或既有编排工具 |
| Skill Registry | 可复用局部专业能力的索引及选择 | 文档索引、已有能力注册方式 |
| Agent Runtime | 执行主体、模型、工具、权限 | 已有执行平台和工具 |
| Evaluation Engine | 评价、证据、裁决与否决 | 专业方法、检查表及现成验证工具 |
| Knowledge Engine | 来源索引、错误经验、模板、复用与演化 | 版本化知识库及检索工具 |

候选组件并非互斥模块。F/L/H/K 的责任和证据规则贯穿组件，不为治理另建必须的第八引擎。目标/事实供推理和规划，推理产生待决主张，工作流协调能力与执行者，评价独立核查结果，知识记录条件与有效性；这些是概念依赖，不是实现调用图。

未来工程化裁决条件：问题确实重复且高价值、方法边界清楚、已有证据表明轻量方式不足、比较替代成本风险、取得另行授权后才有限验证。当前只保留这些必要性假设，不访问具体项目评估收益、不建设系统。

## 与总体框架的边界
O 整合知识体系，N 研究方法向工程系统迁移的必要性。N 的最终价值裁决依赖 I/J/K/L 与 H 的真实证据，目前尚不具备。F1 仅完成问题分层、候选能力地图和裁决条件，不宣告建设方案已经确定。

## F2：从知识方法到工程化的必要性判断

七个组件的关系不要求一一对应七个服务，也不与A–M专题一一映射。知识方法提出“应该如何思考”；工程系统解决“在已确认条件下如何稳定组织或约束执行”。是否工程化须有独立的必要性及替代性论证。

候选判断顺序：明确问题与适用范围→识别现有方法/文档/工具能否解决→确定是否存在高频、跨任务复用、状态一致性、权限、追溯或协作问题→比较轻量约定、已有工具、局部支持、集成系统→只保留可解释价值的候选能力。实际成本、效果、技术可行性留待另行授权验证，不能在框架期填为已成立。

**抽象反例：** 已有能力X能够满足候选需求，不意味着必须另建X引擎。一个逻辑职责由多个已有工具共同承担，也不必另建独立模块。反之，如果同名能力缺少必要的约束或证据关系，仅有名称不证明其满足需求。治理和评价是贯穿职责，不由软件模块数量决定。

F2结论：保留原七组件概念图及替代方案；删除“研究一个专题就建设一个引擎”的隐含推论。工程化必要性、现有系统实效、架构/实现/部署全数延期，当前没有启动产品建设。
