# AI-Native Dev · R3 深度研究执行规则（编排补充）

本文件补充原 R3 的执行组织方式，不替换任何专题目标、研究任务、验证要求及附录。R2是高价值线索，R3是研究问题，不是已成立的知识或已经完成的项目。允许批判、补充、合并、否决和推翻原结论。

## 1. 原始目标

建立真正可用的 AI 原生软件研发方法，使 AI 从用户不完整的想法、功能变更或缺陷反馈出发，主动理解目标，发现显性、隐性、必要需求与遗漏，研究并选择方案，完成业务与产品设计、技术设计、任务拆分、研发、测试、修复、真实验收和持续演化。最终成果应可阅读、可使用、可复用，而不是增加抽象名词和大量协议。

## 2. 输入读取与隔离

- 仓库 https://github.com/shopable-ai/VizTell ，唯一工作分支 main；独立根目录 `temp/ai-native-dev/`。
- 先读取 README、prompts/00 执行地图、本规则和本批启动文件；每个专题必须从头到尾读取 prompts/ 中对应编号的完整文件（包括关键任务、验证、交付和内嵌R2附录），记录输入提交SHA、路径及未读/截断情况。资料没有完整读取时先补读，不能仅凭目录、标题或总结执行。
- 按需读取 reference/ 的主材料、关联材料、原文备份，及同目录已提交的其他专题结论。R2的00/13/14分别是导航、研究任务、原文追溯，不将其机械地变成独立研究主题；05、11分别由多个专题负责各自独立问题。
- 不扫描或修改 VizTell 其他目录，不默认复用旧正式研究成果。可按专题明确未知项定向查阅公开论文、官方资料、开源源码，以及真实项目参考 opendesk-browser、ai-native-project-os；外部项目只读。本规则和用户本次写入授权覆盖原提示词中定向查找 VizTell 旧目录及默认只读的通用说明。原始资料和 prompts/ 保持不可变。

## 3. 每个专题的实际研究循环（不是写作循环）

1. **恢复与建立问题**：明确原始目标、专题边界、已有高价值结论、待证假设、关键未知和反例。先形成可阅读的总体框架，再深入关键分支；不机械保持既有条目数。
2. **多角度推理与发现**：从目标正向或逆向推导、实际失败溯因、业务/用户场景、因果与约束、跨维组合、反方、边界、价值必要性等视角，按专题选择有效方式。提出候选模型、链路、机制或方法，并说明差异、关系、适用条件及为什么有实际价值。
3. **专业研究**：针对未知问题检索成熟理论、论文、官方文档或源码，核查来源原文与适用边界；记录可追溯链接/版本/具体证据。不得用无关链接凑数量。区分线索、外部事实、本轮推断、桌面推演、真实验证。
4. **真实价值验证**：优先用一个可复核真实项目案例，对比原始/R2方法与候选方法（固定问题、预先定义评价、记录输出、重要遗漏、误报、成本、失败边界）。例如OpenDesk Browser的网页区域选择、消息队列或云同步。只有现成证据不足时设计下一轮实验并标为未执行。专题新增价值以解决问题衡量，不以文档长度衡量。
5. **反方与收敛**：若真实独立Agent可用，给独立审查者原始问题、判据和必要证据，使其先独立判断后再比较；否则明确为单模型自审/桌面推演，不冒称独立专家。逐项处理反例、冲突、证据缺口及不必要设计；必要时返回前面研究环节。
6. **保存与验收**：交付实际新增结论、R2差量、案例/证据、保留/修正/否决/仍未知清单、当前状态及必要后续。每次都留下可复用增量，而非只返回计划、分数和新提示词。

## 4. 编排方式与断点

- 优先利用环境真实具备的独立Agent/云任务机制。主控只负责分派、输入范围、汇总、独立审核和提交；一个专题一个独立上下文和结果目录。不把所有文件拼成一个超长提示词，也不为每个文件固定生成相同篇幅。
- 初次并行建议3个活动专题，受实际工具、上下文、限额和依赖约束。仅在确认真实Agent/任务已启动后报告其任务ID/状态；不得把单对话模拟角色称为独立运行，不伪造后台任务。如果没有并行能力，按专题逐个做实质研究、及时保存，报告确实完成/未完成项；不能要求用户等待不存在的后台作业。
- 批次1：A/B/G；批次2：C/D/E/F/H；批次3：I/J/K/L/M/N（N等待I/J/K/L的必要实证，I/J按必要依赖安排）；批次4：O。允许按已有成果和实际依赖交叉推进，不强制等待无关任务，也不得提前称整合完成。
- 每专题维护自己的 status.md（待处理/研究中/部分成果/待验证/待审查/通过/阻断；标记最后实质进展、输入版本、未完成关键问题及下一动作）。启动时读取本专题状态与已有成果；仅处理未完成的高价值增量，不重复研究。研究是否足够以证据、反例、价值和验收判据决定，而不是耗时或轮数。当前工具时间/额度不足则落盘并明确续跑点。
- 若实际使用脚本，脚本仅负责编排读取、任务分派、响应收集、检查状态、有限重试和落盘；研究由实际模型运行完成。不得用循环或模板冒充深度推理。未经用户另行批准，不新增付费 API 调用、外部服务器任务、凭据、部署或定时作业。环境缺失时不假称脚本已跑。

## 5. 输出与写入

每专题仅写 `temp/ai-native-dev/results/R3-X/`（R3-X替换实际编号），建议最少 README.md（核心结论与完整研究）、evidence.md（来源/案例/对照/反例/验证）、status.md；内容适合时可继续分册。O的总体整合只写 results/R3-O/，不得修改其他专题文件。主控统一提交或每专题独立提交；提交前检查最新main及当前路径变更，只做非强制增量更新，冲突时重新核对并保留已有工作。结果须读回并验证提交差异仅限获授权目录；没有写权限时交付可下载结果并说明。

## 6. 评分及否决

按100分分别评估：目标相关性、知识正确性和证据、研究深度与新增价值、可读性、实际适用性与验证、边界及去重；综合为等权平均。建议每项及综合目标≥95，但只报告有证据支持的分数、评分依据及评审身份；无法评价则标未评并报告覆盖率，不能声称综合完整。关键事实错误、伪造证据、缺少必要真实验证、无实质增量、重复研究、越界修改、未解决高影响反例，一票否决。不能为了满足分数虚增、无限研究或重复写作。输出未达到门槛原因及下一项最有价值的补证工作。

## 7. 工作结束标准

逐专题列出实际已完成、部分完成、待验证/待审查和阻断；提供实质结果与真实提交链接。所有研究完成与否依据状态和证据，不以启动了几个任务、脚本成功退出或文档数代替。没有独立Agent、外部资料或真实环境时报告实际限制。
