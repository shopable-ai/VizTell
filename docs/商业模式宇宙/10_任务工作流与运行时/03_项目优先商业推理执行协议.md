# 项目优先商业推理执行协议

> 状态：对 `02_端到端商业推理Workflow与知识生命周期.md` 的**项目执行层补充协议**。
>
> 触发原因：T01 电子书真实项目运行表明，现有运行时已经能够路由、检索、计算和实验，但用户真正需要的是先看到“项目判断、市场证据、方案排序、第一推荐和下一步”，而不是先看到 Task Router、Atom、Pattern、Schema 或 Benchmark。
>
> 原则：不扩建本体来代替项目决策；只有真实项目暴露 K1/R1/W1 等问题时，才回到底层修复。

---

# 一、默认入口：先做项目判断，不先展示系统内部结构

收到项目以后，第一屏固定输出：

```text
项目判断
1. 我目前怎样理解这个项目
2. 项目现在处于什么阶段
3. 当前真正需要解决的商业问题
4. 接下来会实际研究的 5-10 个问题
```

要求：

- 使用普通商业语言；
- 不展示 Router、Atom、Pattern、Schema 等内部名词；
- 对“已有项目”先做 current-state，不重新从 0 设计；
- 对“只有想法”的项目，先明确谁用、谁付钱、解决什么任务、当前替代方案。

如果用户输入不足，不应立即停下来索取长表单。先按照公开市场、保守/基准/乐观场景继续推进，再只提出**最可能改变决策的 1-3 个未知信息**。

---

# 二、把“真正的商业问题”从主题中分离出来

主题不是决策。

例如：

```text
主题：电子书还能怎样赚钱？

真正问题：
低门槛单本数字商品能否以足够低的成本识别高意向用户，
并通过后端商品/软件/服务形成正的 30/90/180 天 Cohort Contribution？
```

再例如：

```text
主题：AI API 怎样收费？

真正问题：
怎样让 Included Usage / Overage / Commit / Enterprise Contract
在不同用量分位下都覆盖推理成本、渠道分成、支持和容量风险？
```

所有后续研究都必须服务于这个决策问题。

---

# 三、市场研究从“按需背景资料”升级为候选方案的证据层

只要项目依赖现实市场，每个重要候选方案都尽量建立三类证据：

## 1. 成功证据

检查：

- 是否已有持续运营的公司/产品；
- 是否有真实收费；
- 是否有多年续费或复购；
- 是否被多个参与者采用；
- 是否有可观察的单位经济或商业持续性信号。

## 2. 失败证据

检查：

- 关闭、降价、取消收费、转型；
- 免费转付费不足；
- 用户频率不足导致订阅价值弱；
- CAC、退款、补贴、供应成本、平台规则导致模型失效；
- 用户绕平台、供应商绕平台、重度用户负毛利；
- 版权、合同、政策或资格导致不可持续。

## 3. 条件性成功

必须回答：

```text
什么用户成立？
什么场景成立？
什么价格成立？
什么频率成立？
什么渠道成立？
什么成本结构成立？
什么规模成立？
什么地区/平台规则成立？
```

禁止把“某公司成功”直接转写成“当前项目应该复制”。

---

# 四、建立市场验证等级，但避免伪精确评分

默认使用：

```text
A = 已被市场反复验证，且当前项目高度匹配
B = 已被市场验证，但依赖明确条件
C = 经济逻辑合理，但现实证据有限，应作为实验
D = 存在大量失败信号或经济结构脆弱，默认不优先
E = 当前条件明显不成立，淘汰
```

验证等级不能只看“有没有成功案例”，还要同时看：

- 项目匹配度；
- 利润潜力；
- 实施难度；
- 资本要求；
- 获客难度；
- 风险；
- 可逆性；
- 验证成本。

如果没有可靠数据，不给 87.3、92.6 之类伪精确总分；使用等级、区间和条件式结论。

---

# 五、商业机会采用“后台广扫 → 前台严筛”

后台至少扫描：

```text
直接销售 / 订阅 / 会员 / 按量 / 套餐 / 升级
Cross-sell / Upsell / Add-on / 耗材
服务 / 咨询 / 实施 / 培训 / 企业采购
授权 / 白标 / API / 数据
广告 / Affiliate / 分销 / 渠道佣金
平台抽佣 / Marketplace
供应商返点 / MDF / Credits / 账期
预付 / 储值 / Commit / Capacity
上下游 / 相邻商品 / 相邻用户 / 相邻场景
软件 / AI / 知识库 / 硬件
生命周期延伸 / 生态合作
```

但最终只向用户保留 **3-5 个结构明显不同的候选方案**。

候选之间至少在以下一项存在结构差异：

- 谁付钱；
- 卖什么；
- 真正利润池；
- 获客方式；
- 收费计量；
- 风险由谁承担；
- B2C / B2B；
- 自营 / 伙伴 / 平台；
- 一次性 / 订阅 / 按量 / 结果 / 分成。

---

# 六、强制扫描“当前商品之外”的利润

每个项目至少问一次：

> **这个项目获得了怎样的一群用户？这群用户完成同一个任务还需要什么？接下来愿意为什么付钱？**

标准展开：

```text
当前商品
→ 用户真实任务
→ 前置需求
→ 同步需求
→ 后续需求
→ 知识
→ 工具/软件/AI
→ 服务/咨询/实施
→ 实体商品
→ 企业采购
→ 数据/平台/生态
```

这一步用于发现“后端”和“相邻利润池”，而不是为了机械扩商品目录。

---

# 七、上下游与隐藏利润成为固定扫描项

## 上游

检查：

- 内容/货源/模型/API/数据/基础设施；
- 采购价、阶梯价、Credits、返点、MDF；
- 白标、代理、独家、联合营销；
- 账期、预付折扣、容量承诺。

## 下游

检查：

- 用户后续消费；
- 软件、AI、服务、咨询、培训、实施；
- 企业采购；
- Marketplace；
- 复购、续费、升级和推荐。

## 横向

检查：

- 相邻用户；
- 相邻商品；
- 相邻场景；
- 相邻渠道；
- 相邻行业。

任何返点/补贴/平台激励必须标记：

```text
是否已确认
门槛
有效期
Clawback
是否计入基础经济性
```

未确认返点不得作为基础利润成立条件。

---

# 八、候选方案统一用“决策卡”表达

每个最终候选至少回答：

```text
方案一句话
谁付钱
为什么付钱
卖什么
前端入口
真正利润池
进入后端的路径
获客渠道
经济逻辑
市场验证等级
成功证据
失败证据
成立条件
项目匹配原因
不匹配原因
最大假设
当前缺失数据
最小验证
Kill Condition
```

如果无法说明“真正利润在哪里”和“Kill Condition”，候选不得进入前三。

---

# 九、排序不是灵感排序，而是条件式决策

排序顺序：

```text
先排 E / D
→ 再比较 A / B
→ C 只作为实验
→ 在同等级中比较项目匹配、利润、难度、风险、可逆性与验证成本
```

最终必须给：

1. 第一推荐；
2. 第二推荐，以及什么条件下它会超过第一；
3. 第三推荐，以及为什么现在不是第一；
4. 暂时不推荐，并说明淘汰理由。

---

# 十、没有真实数据时，用“阈值”继续推理

禁止因为缺 CAC、LTV、转化率等直接停止。

先建立：

```text
公式
→ 保守 / 基准 / 乐观场景
→ 最敏感变量
→ Break-even Threshold
→ 下一步最值得测的变量
```

例如：

```text
CAC_max
= Front-end Contribution
+ 30/90/180 天后端期望贡献
- 退款/客服/滥用/融资等风险成本
```

真正需要用户补的是：

> **最可能导致方案重排或由正变负的变量。**

而不是一次收集全部字段。

---

# 十一、最终交付先显示“决策面板”

详细分析之前固定展示：

```text
项目一句话判断
当前最重要的商业问题
市场已经验证了什么
市场已经证明哪些方式容易失败
当前项目最值得赚钱的 3 个位置
第一推荐方案
第二推荐方案
暂时不要做什么
当前最大未知
下一步只做哪 1-3 件事
```

然后才展示：

- 市场证据；
- 候选决策卡；
- 经济模型；
- 风险；
- 实验。

用户不阅读后半部分，也应该知道下一步该做什么。

---

# 十二、项目状态必须跨轮继承

每个真实项目维护最小 Project State：

```yaml
project_stage:
current_decision:
validated_facts: []
validated_hypotheses: []
failed_hypotheses: []
current_candidates: []
current_ranking: []
critical_unknowns: []
experiments_running_or_completed: []
new_project_data: []
market_changes: []
next_actions: []
```

下一轮默认从 Project State 继续，而不是重新生成商业模式列表。

只有新数据足以改变决策时才重排方案，并明确：

> 什么信息变了 → 哪个假设变了 → 为什么排序变了。

---

# 十三、真实项目失败后才回到底层系统

输出不好时按以下顺序找根因：

```text
项目信息不足？
↓
市场证据不足/过时？
↓
知识已存在但没有召回（R1）？
↓
知识召回了但没有进入推理（W1）？
↓
经济模型错误（E1）？
↓
方案同质/排序错误（S1）？
↓
现有知识真的无法表达（K1）？
```

只有最后一类才优先新增 Atom / Pattern / Schema。

禁止：

> “项目输出不好 → 先扩建知识库一大层”。

---

# 十四、防偏移关口

每完成一个较大阶段都问：

> **这项工作是否直接帮助当前真实项目做出更好的商业决策？**

如果否：

- 暂停 Schema / CI / Retriever / JSONL / Benchmark 数量扩建；
- 回到项目、市场、经济、排序或实验。

允许进入底层工程的条件只有：

> 当前真实项目已经明确被底层问题阻塞，并能指出修复后会改善哪个商业决策。

---

# 十五、项目级完成标准

一次项目商业推理只有在以下条件满足时才算完成当前轮：

- 用户能用一句话理解项目真正的商业问题；
- 有现实市场证据，不是纯知识库推理；
- 同时看过成功、失败和条件性成功；
- 已广扫利润池和上下游；
- 最终只保留 3-5 个结构不同候选；
- 有明确第一推荐和不推荐项；
- 经济性至少有公式/区间/阈值；
- 关键未知已按信息价值排序；
- 有 1-3 个低成本实验；
- 每个关键实验有 Kill Condition；
- 用户即使只看决策面板，也知道下一步做什么。

系统级评分不能代替这一验收。
