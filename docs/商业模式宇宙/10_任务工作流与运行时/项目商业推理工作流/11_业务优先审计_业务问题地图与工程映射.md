# 项目商业推理工作流：业务优先审计、业务问题地图与工程映射

> 状态：业务架构审计结论与下一版设计基准。
>
> 用途：保存 2026-08-25 对“项目商业推理工作流”进行业务优先审计后确认的高价值结论，作为后续重构 P01-P20、项目状态、Runtime、Skill 映射与 Benchmark 的上游依据。
>
> 重要边界：本文件当前**不直接替代** `01_P01-P20项目商业推理总工作流.md`，也不修改 U01-U27、Atom、Pattern、Product Role、Skill、Schema 或 runtime-v1。后续只有经过更多真实入口验证后，才将确认部分升级为正式业务事实源。

# 一、为什么需要这份文档

当前仓库已经具备：

- P01-P20；
- 现实输入入口；
- 市场研究；
- 成功/失败机制；
- 利润池与上下游；
- 候选方案；
- 商品、价格与经济性；
- 风险、排序；
- 最小验证、实际交易与持续经营；
- 商业现象逆向拆解；
- Router、Retriever、Runtime、Skill、Schema、Trace、Benchmark。

当前最主要的问题已经不是“商业知识明显不足”，而是：

> **用户真正要解决的商业问题、AI 内部必须完成的质量检查、知识调用动作、工程运行机制，被部分放在了同一级结构中。**

因此下一阶段不应优先增加 P21、P22 或大量新 Skill，而应该先建立一套普通创业者能够直接理解和纠错的业务问题地图，再让 Workflow、Skill、State、Runtime、Schema 服从业务需求。

核心原则：

```text
真实商业需求
→ 人工可理解的业务问题地图
→ 按需业务模块
→ AI 内部质量控制
→ 业务到工程映射
→ Workflow / Skill / State / Runtime / Schema
→ Benchmark / Regression
```

而不是：

```text
已经有 Runtime / Skill / Schema
→ 反推用户必须经过哪些业务阶段
```

# 二、现实用户需求分类

项目商业推理系统首先应识别用户真正带来的现实问题，而不是要求用户先理解 P01-P20。

## 2.1 十类主要现实输入

| 现实输入 | 用户真正想解决什么 | 不应该做什么 |
|---|---|---|
| 已有项目 | 现在到底是什么生意，钱在哪里，下一步做什么 | 从零重新讲一遍商业模式 |
| 已有功能 / 技术 / 内容 / 流量等资产 | 这些东西怎样组合成有人愿意买的商品 | 功能直接等于收费项 |
| 一个灵感 | 谁需要、谁付款、能形成哪几种生意 | 先展开大量功能清单 |
| 一个明确经营问题 | 找出利润、转化、获客、复购等真正瓶颈 | 重跑完整商业分析 |
| 一组经营数据 | 算清真实经济性和危险参数 | 只把数据做成总结报告 |
| 几个候选方向 | 比较哪个先做、为什么、什么条件下改变排序 | 所有方向都说“可以” |
| 一个市场 / 行业问题 | 当前市场、价格、竞争、替代和利润结构是什么 | 做不会改变决策的行业百科 |
| 看到别人赚钱的现象 | 他实际上靠什么赚钱，目前能否确认 | 先编一个“隐藏盈利故事” |
| 成功 / 失败案例 | 为什么成立或失败，哪些条件可以复制 | 复制表面动作 |
| 外部变化或新机会 | 新政策、平台、供应商、AI 技术、渠道变化会怎样改变当前项目 | 从头重新做整个项目分析 |

## 2.2 入口设计原则

不同输入不应被迫从同一位置开始。

```text
已有项目
→ 现状、资产、用户、付款、利润池、方案

已有功能
→ 用户任务、商品化、价格、升级路径

灵感
→ 用户问题、付款方、替代、不同商业结构、最小验证

经营问题
→ 直接定位约束与关键参数

真实数据
→ 直接进入经济性、风险、排序和状态更新

商业现象
→ 先逆向拆解，不先设计自己的项目
```

用户第一次回答时，优先让他看到：

```text
我怎样理解你给的对象
它属于哪类商业问题
当前最值得解决什么
最值得先验证哪些假设
哪些暂时不知道但不妨碍继续推进
```

# 三、完整业务问题地图

## 3.1 人工可理解的主业务链

建议将普通用户真正需要理解的商业顾问系统重建为下面 14 个大问题：

```text
一、先看清我现在拿来的到底是什么
↓
二、这一次真正需要做什么商业决定
↓
三、谁在使用、谁在付钱、为什么愿意付钱
↓
四、现在已经拥有什么用户、交易、商品、渠道、数据和能力
↓
五、现实市场已经发生了什么
↓
六、钱真正在哪里，以及上下游还有什么机会
↓
七、有哪些本质不同的商业方案
↓
八、每个方案到底卖什么、怎样收费
↓
九、客户从哪里来、怎样成交、怎样交付
↓
十、这门生意真实赚不赚钱
↓
十一、什么条件下成立，竞争和风险在哪里
↓
十二、现在到底先选哪个，哪些以后再做
↓
十三、怎样最低成本验证最关键的判断
↓
十四、怎样形成真实交易，并根据结果持续经营
```

这是一张**业务问题地图**，不是要求所有项目机械执行 14 个节点。

## 3.2 三个横跨全程的内部控制

下面三类问题非常重要，但不应该伪装成人工业务阶段：

```text
始终检查：哪些是事实，哪些只是推断、假设和未知

始终检查：哪个未知最可能改变当前商业决定

始终检查：出现什么结果就应该继续、修改、停止或扩大
```

## 3.3 商业现象特殊分支

看到别人赚钱的现象时，使用独立的逆向拆解入口：

```text
观察到一个商业现象
→ 只记录真正观察到的事实
→ 判断表面交易能否解释长期利润
→ 如果不能，建立多个解释
→ 分别找支持证据
→ 分别找反证
→ 排除不成立解释
→ 重建可能的真实收入结构
→ 判断可持续性与成立条件
→ 无法确认时明确回答“目前无法确认”
→ 最后才讨论能不能迁移到自己的项目
```

关键纪律：

> 合理的盈利方式不等于现实中的真实盈利来源。

# 四、每个大环节解决什么问题

| 业务环节 | 为什么存在 | 是否必须 | 典型输出 |
|---|---|---|---|
| 1. 看清对象 | 不同输入不能走同一起点 | 新对象首次进入必做 | 项目 / 数据 / 灵感 / 现象 / 案例等输入类型与当前对象 |
| 2. 确定当前决定 | 防止“研究商业模式”无限扩散 | 每轮重大分析必做 | 本轮只解决的 1-3 个商业决定、范围和非目标 |
| 3. 用户与付款 | 使用者、付款者、决策者、受益者经常不同 | 大多数商业设计必做；纯局部财务优化可复用已有结论 | 谁用、谁付、为什么付、当前替代方案 |
| 4. 盘点现状与资产 | 已有项目不能浪费已有用户、流量、技术、内容、数据和渠道 | 已有项目必做；纯灵感按需 | 当前经营底盘、未商品化资产、明显约束 |
| 5. 研究现实市场 | 商业结论不能只来自知识库和模型常识 | 决策依赖现实价格、竞争、规则时必做 | 已确认市场事实、替代、反证、成功和失败条件 |
| 6. 找利润与相邻机会 | 当前商品收入不一定是真利润池 | 商业模式设计、低利润项目重要；局部验证可跳 | 主要利润池、上下游、相邻高价值需求、隐藏和条件性经济 |
| 7. 形成不同方案 | 防止只给同一种模式换三个价格 | 存在方向选择时必做 | 3-5 套结构真正不同的商业方案 |
| 8. 商品与收费 | 商业机制必须最终变成可以买的东西 | 商业化时必做 | 卖什么、买到什么结果/权利、套餐、价格、用量边界、升级路径 |
| 9. 获客—成交—交付 | 好商业模式如果无法获得客户、成交或交付没有意义 | 进入真实执行前必做 | 客户从哪来、销售路径、成交方式、收款、交付和服务方式 |
| 10. 算经济账 | 收入增长可能越做越亏 | 排序和扩大前必做 | 单笔、订单、用户群、现金流、盈亏平衡、敏感变量 |
| 11. 成立条件与风险 | 模式成功通常依赖特定条件 | 重大投入前必做 | 最大脆弱假设、竞争反应、平台/供应/合同/合规等硬约束 |
| 12. 比较并选择 | 用户最终需要的是决定，不是方案百科 | 多候选时必做 | 第一选择、第二选择反超条件、暂不推荐及重新评估条件 |
| 13. 最小真实验证 | 避免先建设完整产品再知道没人买 | 尚有关键未知时必做 | 最小实验、关键指标、预算、继续/修改/停止/扩大条件 |
| 14. 真实交易与持续经营 | 商业最终由真实支付、真实交付和真实贡献检验 | 持续项目必做 | 第一批交易、真实经营数据、状态变化、下一轮决策 |

## 4.1 关于第 9 项的特别说明

“获客 → 成交 → 交付”在现有体系中已经散落在候选、商品、行动卡和持续经营中，但建议在人工业务地图中提升为正式问题。

原因是：

```text
有需求
≠ 能找到客户

找到客户
≠ 能成交

成交
≠ 能稳定交付

稳定交付
≠ 单位经济成立
```

因此商业方案只有连接到真实客户获取、成交与交付，才算进入现实业务。

# 五、P01-P20 审计

## 5.1 总体判断

P01-P20 的业务覆盖率已经较高，但当前存在一个结构问题：

> **业务阶段、入口判断、AI 内部质量控制、知识系统动作，被放在同一级编号中。**

因此下一阶段不建议继续假设“P01-P20 必须稳定作为 20 个同级业务阶段”。

编号可以为了兼容历史引用暂时保留，但业务正确性应优先于编号稳定性。

## 5.2 逐项审计

| 当前 P | 实际解决的问题 | 是否需要 | 是否重复 / 错位 | 建议 |
|---|---|---|---|---|
| P01 项目接收 | 判断用户带来的是什么 | 需要 | 更像入口控制，不是商业分析阶段 | 降为入口层 |
| P02 生意重建 | 看清表面产品背后的真正交易结构 | 需要 | 与 P06 当前现状相邻 | 合并进入“看清对象与现状”业务模块 |
| P03 阶段判断 | 决定当前应该解决哪类问题 | 需要 | 更像路由变量 | 并入入口与当前决策，不必独立成业务阶段 |
| P04 商业问题定位 | 找当前最值得解决的问题 | 核心 | 无明显重复 | 保留为主链 |
| P05 高价值未知识别 | 找会改变当前推荐的未知 | 必须存在 | 更像 AI 内部推理控制 | 从主业务阶段下沉为横切检查 |
| P06 当前经营盘点 | 盘点资产和经营起点 | 已有项目核心 | 与 P02 强相关 | 和“看清现状”组成一个业务模块 |
| P07 用户与支付分析 | 谁用、谁付、为什么付 | 核心 | 无明显重复 | 保留 |
| P08 真实市场研究 | 当前现实市场事实是什么 | 核心 / 按需 | 无明显重复 | 保留正式能力 |
| P09 成功失败机制 | 为什么别人成功或失败 | 重要 | 多数情况下属于市场研究的一部分 | 并入市场研究；案例入口时强化 |
| P10 商业知识调用 | 调用 Atom / Pattern / Product Role 等知识 | 后台需要 | **不是用户商业问题** | 从人工主链删除，转为后台能力 |
| P11 利润池扫描 | 钱在哪里 | 核心 | 与 P12 属于同类机会发现 | 与 P12 合并为“利润池、价值链与相邻机会” |
| P12 上下游与相邻机会 | 当前产品之外还有什么利润机会 | 重要 | 与 P11 强相关 | 与 P11 合并 |
| P13 候选商业方案 | 形成结构不同的方案 | 核心 | 无 | 保留 |
| P14 商品与收费设计 | 卖什么、怎样收费 | 核心 | 对成交与交付表达不足 | 保留，并显式连接获客/成交/交付 |
| P15 经济性分析 | 真正赚不赚钱 | 核心 | 无 | 保留 |
| P16 竞争与风险判断 | 做成后会怎样，最容易在哪里失败 | 核心 | 与 P17 成立条件强相关 | 与 P17 的“成立条件”部分合并 |
| P17 成立条件与证据评级 | 逻辑是否有现实支撑 | 需要 | 当前把证据强度、项目匹配混在一起 | 成立条件并入 P16；证据强度转为横切控制 |
| P18 排序与选择 | 现在先做什么 | 核心 | 无 | 保留 |
| P19 最小行动与验证 | 最便宜怎样知道判断对错 | 核心 | 当前名称弱化真实成交 | 人工层明确拆出“验证”与“真实交易”两层含义 |
| P20 持续经营与更新 | 根据真实结果继续经营 | 核心 | 人工层较完整，机器层还未充分对应 | 保留为持续经营闭环，并升级机器 State |

## 5.3 推荐的新结构关系

不是简单把 20 改成 18 或 14，而是改变层次：

```text
现实输入入口
+
人工业务问题主链
+
按需业务模块
+
AI 内部横切质量检查
+
商业现象等特殊分支
+
持续经营循环
```

P01-P20 可作为历史兼容编号或映射索引，不再强迫其承担业务本体职责。

## 5.4 P17 证据评级特别问题

当前商业验证评级把下面两个维度部分混在一起：

- 市场是否已经验证该商业结构；
- 当前项目是否具备关键成立条件。

后续建议至少拆成三个独立维度：

```text
市场证据强度
当前项目匹配程度
当前项目自身真实验证程度
```

例如：

```text
市场证据：强
项目匹配：未知
当前项目交易验证：未验证
```

这样比一个综合 A/B/C/D/E 更准确。

同时避免与 Benchmark 中另一套 A-E 条件名称发生概念冲突。

# 六、Workflow / Skill / Spec / State / Runtime 等为什么存在

工程对象存在的理由必须从实际业务问题出发，而不是因为系统设计看起来完整。

| 名称 | 普通话解释 | 解决什么实际问题 | 没有它会怎样 | 当前项目是否需要 |
|---|---|---|---|---|
| 工作流（Workflow） | 一类商业任务应该按什么逻辑推进 | 保证重要问题不漏，并允许不同现实输入从不同位置进入 | 每次回答依赖临场发挥，同一项目不同轮次顺序混乱 | 需要，但必须由业务地图决定 |
| 技能（Skill） | 一项反复使用、方法稳定的专业能力 | 例如经济性、风险、模式匹配不必每次重新临时发明方法 | 同一个商业问题每轮计算和判断方法不同 | 需要，但不要“一业务阶段一个 Skill” |
| 执行规范（Spec） | 明确某个工作流或技能到底必须怎样做 | 保证文档、提示词、代码和不同模型遵守同一规则 | 文档说法与实际运行逐渐分叉 | 需要，但应少而稳定 |
| 项目状态（State） | 记录项目当前走到哪里、哪些结论已经被验证或推翻 | 支撑多轮经营、真实实验和新数据继续 | 每次重新从零分析，旧结论无法被新证据更新 | **非常需要，是当前重点缺口** |
| 运行协调器（Runtime） | 根据当前问题和状态决定下一步调用什么能力 | 把路由、检索、研究、Skill、状态更新串起来 | 虽然能力很多，但彼此不会稳定协作 | 需要，但应尽量薄，不自己创造业务阶段 |
| 数据结构约束（Schema） | 规定机器可读对象应该有哪些字段 | 让项目状态、候选、经济性等可以被程序可靠读取和验证 | 字段随意变化，无法稳定测试和复用 | 需要，但只 Schema 化稳定对象 |
| 路由器（Router） | 判断用户这次是什么类型的问题、应该从哪里进入 | 已有数据可直接算经济性，商业现象可进入逆向拆解 | 所有问题都被迫从第一步重新分析 | 需要 |
| 检索器（Retriever） | 从庞大知识库中拿出少量最相关知识 | 不必把 676 Atom、200 Pattern 全部加载 | 上下文噪声增大或关键知识漏召回 | 需要 |
| 推理追踪（Trace） | 记录用了什么事实、知识、计算和判断 | 出错后能知道是知识、检索、推理、证据还是计算问题 | 只能知道答案不好，不知道为什么不好 | 需要 |
| 基准测试（Benchmark） | 用固定问题判断系统是否真的比基线更好 | 比较知识、检索、工作流、研究是否产生增量价值 | 只能凭感觉说“系统更强” | 非常需要 |
| 回归测试（Regression） | 每次修改后重跑旧问题 | 防止修复一个场景却把另一个场景改坏 | 系统越复杂越容易静默倒退 | 需要 |

## 6.1 关键工程原则

> **Skill、Schema、Runtime 不拥有自己的商业需求。**
>
> 它们只是实现已经确认的业务需求的手段。

因此不能：

```text
因为已有一个 Skill
→ 人工创造一个业务阶段去调用它
```

也不能：

```text
因为 Runtime 已经有 S01-S13
→ 要求用户业务流程必须按 S01-S13 理解
```

正确关系应该是：

```text
业务问题
→ AI 内部需要完成的任务
→ 判断是否值得稳定封装
→ Workflow / Skill / State / Schema / Runtime
```

# 七、业务 → 工程映射草图

## 7.1 基本映射

| 用户看到的业务问题 | AI 内部要完成什么 | 是否需要独立 Workflow 节点 | 是否需要 Skill | 是否需要状态保存 | 是否需要外部研究 |
|---|---|---:|---:|---:|---:|
| 我现在拿来的是什么？ | 输入识别、读取已有项目状态、判断入口 | 是，轻量 | 不一定 | 是 | 否 |
| 现在最重要的问题是什么？ | 阶段判断、约束、目标与价值排序 | 是 | 可直接推理或复用规则 | 是 | 通常否 |
| 谁会用、谁会付钱？ | 用户任务、付款关系、替代方案 | 可作为业务节点 | 可复用分析 Skill | 是 | 按需 |
| 现在已经拥有什么？ | 用户、功能、交易、渠道、流量、数据、品牌、技术、供应商等盘点 | 已有项目条件节点 | 不一定 | **是** | 否 |
| 市场现实怎样？ | 研究问题、来源选择、时效、事实核查、成功失败、反证 | 条件节点 | 可封装统一市场研究能力 | 保存关键证据 | **是** |
| 钱在哪里？ | 利润池、价值链、上下游、相邻任务、条件性经济 | 是 | 现有知识检索 + 组合能力 | 保存重要机会 | 按需 |
| 有哪些商业方案？ | 广泛召回、结构变化、去同质、收敛候选 | 是 | 商业模式组合 Skill | 保存候选 | 按需 |
| 到底卖什么、怎么收费？ | 商品角色、价格、用量边界、前后端、升级路径 | 条件节点 | 现有 Offer / 定价 Skill | 是 | 按需 |
| 客户怎么来、怎么成交、怎么交付？ | 渠道、销售动作、交易结构、收款、交付能力 | 建议正式表达 | 未必需要新增 Skill | **是** | 按需 |
| 到底赚不赚钱？ | 单笔、订单、用户群、现金流、敏感性和盈亏平衡 | 是 | 现有经济性 Skill | 保存模型与真实值 | 按需 |
| 什么情况下会失败？ | 竞争反应、反证、成立条件、平台/供应/合同/合规限制 | 是 | 现有风险 Skill | 保存关键风险 | 按需 |
| 先做哪个？ | 多目标排序、反超条件、暂不推荐条件 | 是 | 排序能力 | 保存当前排序 | 通常否 |
| 怎样验证？ | 找最大未知、设计最小实验、定义阈值 | 是 | 现有实验设计 Skill | **必须保存** | 按需 |
| 真实结果出来怎么办？ | 比较新旧状态、更新事实、重新计算、局部回跳 | **必须有** | 不一定 | **核心 State** | 按变化 |

## 7.2 重要结论

> **14 个业务问题 ≠ 14 个 Workflow 节点 ≠ 14 个 Skill。**

合理工程实现可能是：

- 约 8-10 个后台执行节点；
- 一组跨多个业务问题复用的稳定 Skill；
- 一个项目商业画像；
- 一个独立项目经营状态；
- 若干条件模块；
- 一个尽量薄的 Runtime。

例如“市场现在怎样”可以由同一个市场研究能力同时服务：

- 用户与付款分析；
- 市场判断；
- 成功失败机制；
- 风险分析；
- 候选排序。

没有必要为每个业务问题复制一个市场研究 Skill。

# 八、当前最重要的工程推论：项目画像不等于项目状态

当前 `business_model_signature_v4` 更接近：

> **这个商业项目现在长什么样。**

但持续经营还需要回答：

```text
上一轮决定了什么
当前决定是什么
哪些事实发生变化
哪些假设已经被验证
哪些假设已经失败
当前候选排序
哪些候选被淘汰
被淘汰候选重新进入的条件
当前实验
实验结果
最新经营指标
当前最大未知
下一次重新判断的触发条件
为什么本轮结论与上轮不同
```

因此：

> **项目商业画像（Project Signature） ≠ 项目经营状态（Project State）。**

下一阶段工程化优先级应是：

```text
先确认人工业务地图
→ 明确需要跨轮继承的经营状态
→ 设计最小 Project State
→ 再调整 Runtime
```

而不是先扩 Runtime 再寻找 State 应该保存什么。

# 九、后续实施原则

本文件确认的内容后续进入实施时，建议按以下顺序：

## 第一批：先改人工业务层

优先处理：

```text
00 总览
01 核心业务问题地图
02 现实输入入口
03-07 各业务模块边界
08 商业现象逆向拆解
09 模板与经营面板
```

目标：

> 普通创业者完全不知道 Atom、Runtime、Schema、Skill，也可以理解系统为什么这样分析自己的项目。

## 第二批：建立业务 → 工程唯一映射

```text
业务地图
→ 业务问题需要哪些内部任务
→ 哪些是 Workflow 节点
→ 哪些由现有 Skill 支撑
→ 哪些必须保存状态
→ 哪些需要外部市场研究
→ 哪些只需 Runtime 调度
```

## 第三批：补项目经营状态

重点不是继续扩 Project Signature，而是建立跨轮状态：

```text
当前决策
事实变化
假设状态
候选排序
实验
经营数据
决策变化原因
下一触发条件
```

## 第四批：最后调整 Runtime / Schema / Benchmark

业务层稳定后再决定：

- runtime-v1 哪些节点保留；
- 哪些节点合并；
- 哪些只是内部控制；
- 哪些状态必须机器化；
- 哪些 Schema 真正需要增加；
- Benchmark 怎样测试真实业务决策质量。

# 十、当前结论

本轮最重要的结构结论可以压缩为：

```text
现实输入
↓
正确进入方式
↓
人工业务问题地图
↓
按需业务模块
↓
横跨全程的事实/未知/反证/停止条件检查
↓
明确商业选择
↓
最小真实验证
↓
真实交易
↓
项目经营状态更新
↓
局部回跳继续经营
```

后台再提供：

```text
Router
+ Retriever
+ Skill
+ External Research
+ Economics
+ Trace
+ State
+ Runtime
+ Benchmark
```

最终原则：

> **业务需求决定工程结构；工程结构不能反过来决定用户必须怎样理解自己的商业问题。**
