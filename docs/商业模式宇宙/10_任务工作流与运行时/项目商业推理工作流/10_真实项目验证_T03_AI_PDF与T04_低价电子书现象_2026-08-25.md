# T03 AI PDF 与 T04 低价电子书现象：项目商业推理工作流真实验证（2026-08-25）

> 本文件不是为了增加 Case 数量，而是用两种不同现实入口验证新业务 Workflow：
>
> - T03：**我自己的已有项目/功能**；
> - T04：**我看到别人的反常赚钱现象**。
>
> 测试重点是：能否进入正确入口、区分事实与假设、研究现实市场、发现利润池、形成结构不同候选、排序并转成行动。

---

# 一、T03：已有 AI PDF 阅读软件

## 1. 原始输入

> 我已经有一个 AI PDF 阅读软件，包括上传、AI 问答、总结和知识库功能，现在想知道有哪些真正值得做的商业模式和赚钱机会。

## 2. P01-P06：项目理解

### 输入类型

已有项目 + 已有功能资产。

### 当前阶段

已存在产品能力，但没有提供付费用户、活跃频率、CAC、推理成本、转化、团队使用等数据。

因此不能假设已经进入规模增长阶段，更合理的是：

> **已有产品的商业化设计与付费验证阶段。**

### 当前最重要商业问题

不是“还能增加什么功能”，而是：

> **现有上传、问答、总结、知识库能力，应该为哪些高价值用户任务组成什么商品，以及个人订阅、专业工作流、团队/企业、API 中哪条路径最值得先验证。**

### 当前最高价值未知

1. 现有用户主要是谁，最常处理什么 PDF；
2. 用户使用频率和多文档/长期知识库频率；
3. 哪类用户已经表现出明显付费意愿；
4. 单个活跃用户的解析、模型、存储和问答成本；
5. 当前流量来源和可归因 CAC；
6. 是否已经出现团队共享、公司文档、批量处理或 API 需求。

这些未知不会阻止第一轮方案形成，但会直接影响最终排序和价格。

## 3. P08-P09：现实市场证据

本轮只研究会改变商品结构与付款方判断的信息。

### 证据 A：个人 AI 文档能力可以作为付费附加价值

Adobe 当前公开的 Acrobat Pro + AI Assistant Plus 为两个付费组成部分；Acrobat Studio 则把 PDF 工具、AI Assistant、PDF Spaces 等组合到一个更高层套餐。

这说明市场中至少存在：

> **基础 PDF 能力 + AI 理解/工作空间作为高级付费层**

这一已被现实产品采用的结构。

来源：

- Adobe, `Acrobat Pro free trial | Start a free trial`, 2026-08 抓取：<https://www.adobe.com/acrobat/free-trial-download.html>
- Adobe, `Do that with Acrobat: AI-Powered PDF workspaces`, 2026-08 抓取：<https://www.adobe.com/acrobat/campaign/do-that-with-acrobat.html>

### 证据 B：团队用户购买的不只是“AI 问答”

Adobe 当前团队套餐明确额外提供：

- 管理控制台；
- 许可证管理；
- 高级支持；
- 企业拥有文档/资产；
- 更高阶版本包含 AI Assistant、PDF Spaces 等。

这支持一个重要判断：

> **团队/企业商品不能只是把个人 Pro 乘以席位数；治理、资产归属、权限、支持和协作本身就是商品价值。**

来源：

- Adobe, `Acrobat for business pricing & plans`, 2026-08 抓取：<https://www.adobe.com/acrobat/business/pricing-plans.html>

### 证据 C：PDF 能力可以形成独立开发者/API 商品

PDF.ai 当前 API Hub 提供：

- 免费 200 credits/月；
- $49/月 3,000 credits；
- $99/月 10,000 credits；
- $249/月 30,000 credits；
- $599/月 100,000 credits；
- 解析、抽取、Split、Ask 等不同文档处理 API；
- Ask / Parse / Extract 等按页数、能力消耗 credits。

这验证了另一种不同付款方和计量方式：

> **开发者/企业按使用量购买文档处理能力，而不是购买一个个人阅读订阅。**

来源：

- PDF.ai, `API Hub`, 2026-08 抓取：<https://pdf.ai/api-hub>
- PDF.ai, `Credit usage`, 2026-08 抓取：<https://api.pdf.ai/v2/credit-usage>

### 当前不能从市场证据直接得出的结论

以上事实**不能证明当前项目的用户一定愿意买个人订阅、团队版或 API**；它们只证明这些商品结构在现实市场存在。

当前项目匹配仍需真实用户和交易验证。

## 4. P11-P12：利润池与相邻机会

当前功能不应只映射成“一个订阅”。至少出现四个不同利润位置：

1. **个人持续工作流**：高频问答、总结、多文档知识库、高级模型、容量；
2. **垂直专业工作流**：把通用功能包装成科研、法律、财务、学习等结果型流程；
3. **团队/企业知识工作空间**：共享知识库、权限、资产归属、治理、支持、实施；
4. **API / 白标文档能力**：解析、问答、抽取、知识库能力卖给开发者或其他产品。

相邻机会还包括培训、知识库实施、企业咨询等，但当前证据不足，不应全部升为核心候选。

## 5. P13-P18：四套结构不同候选

### 第一推荐：个人 Pro + 成本安全的知识工作流套餐

**方案**：基础阅读/有限 AI 作为入口；持续问答、多文档知识库、高级模型、长期知识工作流进入 Pro；高成本能力设置用量/额度边界。

**为什么第一**：最能复用现有功能，开发增量较小，可直接对已有用户做付费实验；现实市场已验证“PDF 基础能力 + AI 高级层”的商品结构。

**证据等级**：B。市场结构已验证，但当前项目的支付意愿、频率和成本尚未验证。

**最大假设**：现有用户存在足够高频的持续文档任务，而不是偶尔上传一次。

### 第二推荐：垂直专业工作流

**方案**：不再卖“AI PDF”，而卖某一类专业用户完成具体任务的速度和结果，例如多文档研究、证据抽取、文献/合同/报告工作流。

**为什么保留**：更有机会形成差异化、提高支付意愿，并减少与通用 PDF Chat 的直接功能比较。

**证据等级**：C。逻辑强，但尚未证明当前用户集中在哪个垂直任务。

**何时超过第一**：如果高活跃用户明显集中在一个专业场景，且该场景的真实付费意愿显著高于通用用户。

### 第三推荐：团队/企业知识工作空间

**方案**：共享文档/知识库 + 权限/资产归属 + 团队协作 + 管理 + 支持/实施。

**证据等级**：B/C。市场已验证团队 PDF/AI 工作空间的付费结构，但当前项目是否已有组织型需求未知。

**何时超过前两名**：出现持续团队共享、公司文档、权限/安全、集中采购或付费 Pilot 信号。

### 第四推荐：API / 白标

**方案**：把解析、问答、抽取、知识库能力以 credits/usage/commit 方式卖给开发者和其他软件。

**证据等级**：B/C。现实已有明确 API 商品和使用量计价，但当前系统架构、边际成本和开发者需求未知。

**为什么现在不是第一**：会引入独立开发者获客、SLA、成本控制、接口稳定性和支持体系；如果没有现成 B2B/API 需求，不应为了“多一种商业模式”先建设。

### 暂时不推荐：低价“无限 AI”通用套餐

原因：AI 成本会随重度使用变化；如果没有使用边界和 Cohort 成本数据，低价无限量容易把高使用用户变成负贡献用户。

这属于经济结构判断，不代表“低价一定不能做”。正确做法是先测用量分布和 Break-even。

## 6. P15：没有经营数据时如何继续

先不伪造 LTV，建立公式：

```text
月 ARPU
- 单用户文档解析/模型/存储成本
- 支付/渠道
- 支持/退款
- 月度获客摊销
= 月度用户贡献
```

关键敏感变量：

1. 付费转化率；
2. 重度用户 AI 成本；
3. 月活跃频率；
4. 续费/留存；
5. CAC。

下一步只需补真实分布，即可把方案从 B/C 继续升级或降级。

## 7. P19：最小商业行动

### 行动 1：不加新功能，先做现有功能的付费包装实验

对现有活跃用户展示 2-3 个真正不同的 Offer，例如基础版、个人 Pro、专业知识库版，记录真实购买/进入结账，而不是只问“你愿不愿意付费”。

### 行动 2：建立“收入—AI 成本—使用频率”用户群账本

按轻/中/重使用群体计算真实贡献，找到不能被低价无限套餐覆盖的成本边界。

### 行动 3：识别第二付款方

从现有用户中观察团队共享、公司文档、批量处理、API 调用等信号；有真实信号再进入团队/企业或 API paid pilot。

### Continue / Change / Kill / Scale

- **Continue**：目标用户按目标价格真实付费，且重度用户成本可控；
- **Change**：需求强但价格/额度不对，或通用用户付费弱但某垂直用户明显强；
- **Kill 某候选**：多轮真实 Offer 仍无支付，或单位经济需要不现实留存/转化才能转正；
- **Scale**：只扩大已经验证为正贡献的用户群、渠道和套餐。

# 二、T04：闲鱼 0.01～3 元电子书现象

## 1. 原始输入

> 我看到闲鱼有人把电子书卖到 0.01～3 元，这么便宜，他到底怎样赚钱？真实商业模式可能是什么？

## 2. 入口判断

这是“我看到别人的生意”，必须先走商业现象逆向拆解。

禁止先下结论：

> “低价一定是引流。”

---

## 3. 当前能确认的现实事实

### 事实 A：闲鱼技术接入存在虚拟商品订单字段

闲鱼合作方服务端文档的创单 API 明确包含：

- `virtual_item_order`：是否为虚拟商品下单；
- `virtual_item_code`：虚拟商品 code。

这只能证明闲鱼合作方订单系统存在虚拟商品场景，**不能证明某个低价电子书卖家的实际履约方式或利润结构**。

来源：闲鱼开放平台，`闲鱼合作方-服务端接入文档`，2026-08 抓取：<https://open.goofish.com/doc/development/dev/server.html>

### 事实 B：平台规则本身是模式成立条件

当前《闲鱼社区用户服务协议》最新版本日期为 2026-05-27、生效日期为 2026-06-15，并把闲鱼社区规则、淘宝平台规则等纳入服务规则体系；协议还明确涉及用户发布内容及知识产权相关权利。

因此任何依赖内容权利、平台交易或规则边界的方案，都必须把平台/权利条件当作硬约束，而不是普通小风险。

来源：闲鱼，`闲鱼社区用户服务协议`：<https://terms.alicdn.com/legal-agreement/terms/suit_bu1_other/suit_bu1_other201708081618_51146.html>

### 当前没有找到的关键证据

本轮公开研究**没有找到足以证明**：

- 0.01～3 元电子书卖家普遍靠后端商品赚钱；
- 普遍靠网盘拉新赚钱；
- 普遍靠 Affiliate/官方分销赚钱；
- 普遍靠会员、课程、咨询或企业后端赚钱；
- 某一项隐藏收入就是“真正利润来源”。

因此这些都只能保留为 H2-H11 假设，而不是事实。

---

## 4. H1-H12 当前判断

| 假设 | 当前判断 | 原因 |
|---|---|---|
| H1 单本本身赚钱 | 保留 | 数字交付可能有极低边际成本，但缺真实成本、订单量和退款数据 |
| H2 低价入口→后端 | 保留但未验证 | 逻辑成立，但未拿到卖家后端商品/转化证据 |
| H3 高意向 Lead | 保留但未验证 | 购买行为可能识别需求，但缺持续触达与 Lead Value 数据 |
| H4 合集/会员/订阅 | 未验证 | 需要看店铺 SKU、购买后 Offer、复购 |
| H5 Affiliate/官方分销 | 未验证 | 需要正式联盟规则和实际归因路径 |
| H6 软件/AI/工具 | 未验证 | 需要卖家真实后端产品证据 |
| H7 课程/咨询/服务 | 未验证 | 同上 |
| H8 企业后端 | 低先验/未验证 | 单个低价店铺现象不足以推断企业线索链 |
| H9 平台奖励/渠道收益 | 未验证 | 未发现可以直接对应该现象的当前官方收益规则 |
| H10 极低边际成本和自动化 | 结构上较合理，但未证明盈利 | 虚拟商品订单能力存在，但卖家具体自动化和真实成本未知 |
| H11 特殊供应链/内容采购 | 未验证 | 必须取得合法授权/采购证据 |
| H12 不合规/盗版/漏洞/短期套利 | 风险假设必须保留 | 数字内容权利和平台规则是硬约束，但不能在无证据时指称具体卖家侵权 |

---

## 5. 当前最可靠的结论

仅凭“0.01～3 元”这个价格，**无法还原真实核心利润来源**。

当前只能得到：

1. 低边际交付成本使 H1/H10 在结构上可能成立；
2. H2-H9 都是常见的合理盈利假设，但本轮没有足够卖家级证据；
3. H11 只有在合法采购/授权成立时才可进入正式模型；
4. H12 是必须排查的可持续性风险，但不能凭低价直接给具体卖家定性；
5. 因此“低价电子书 = 低价引流”不是一个经过验证的结论。

这正是逆向拆解 Workflow 应该防止的错误。

---

## 6. 下一步怎样把未知变成证据

优先观察一个真实店铺，而不是继续泛搜行业故事：

```text
展示价是否等于成交价
店铺还有哪些高价 SKU
销量/评价结构
交付方式
购买后是否出现下一 Offer
是否有合集/会员/持续更新
是否销售软件/AI/工具/服务
是否有正式 Affiliate/分销路径
是否能够证明内容权利来源
复购和 30/90 天后端贡献
```

拿到这些后才能重新给 H1-H12 排序。

---

## 7. 是否值得迁移

### 当前可迁移的机制

仅作为 C 级实验保留：

> **低摩擦入口 → 识别用户任务 → 自动化交付 → 测试相邻合法 Offer → 看真实 Cohort 贡献。**

### 不应该复制

- 未经确认的版权/内容来源；
- 依赖平台漏洞或短期规则套利；
- 在没有证据时把用户导流价值、平台奖励或网盘收益算进 Base Case。

### 如果迁移到自己的合法数字知识项目

可以把低价入口设计成一个实验，但必须同时记录：

```text
入口真实贡献
Qualified CAC
后端转化
30/90/180 天 Cohort 贡献
退款
合规/权利状态
```

如果低价只增加低价值订单而没有后端贡献，就应停止继续降价。

# 三、两次测试后的总体结论

T03 和 T04 证明它们不能共用一套机械起点：

- T03 应从已有资产、付款方、商品化和真实付费进入；
- T04 必须先逆向拆解与证据排假，再谈迁移。

本轮最重要的 Workflow 改进不是增加商业知识，而是增加五个业务控制：

1. **入口路由**：同一 P01-P20 地图允许局部进入；
2. **证据门**：事实/推断/假设/未知分离；
3. **候选去同质化**：只保留付款方/利润池/计量/渠道等结构不同的 3-5 套方案；
4. **行动门**：推荐必须变成可交易 Offer 与 Continue/Change/Kill/Scale；
5. **状态继承**：P20 保存真实结果，下一轮只重跑受影响阶段。

本轮测试没有发现需要立即新增 U 域、Atom、Pattern 或 Schema 才能表达的问题。

因此下一步优先级仍然是：

> **继续拿真实项目运行 → 收集失败位置 → 先修项目理解/研究/利润池/候选/经济性/排序/行动/状态 → 只有反复出现且现有知识对象无法表达时，才扩本体。**
