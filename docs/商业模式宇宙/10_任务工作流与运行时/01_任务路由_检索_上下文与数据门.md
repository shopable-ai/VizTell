# 商业模式任务路由、检索、最小上下文与数据门

> 本文件定义“用户提出一个商业问题以后，系统怎样决定加载什么”。机器对应：`../08_机器数据与Schema/task_router_v1.json`。
>
> 目标不是把整个商业模式宇宙塞给模型，而是：**在尽量少的上下文里保持足够高的关键知识召回率，并能够在不足时逐级扩检索。**

---

# 一、为什么需要 Task Router

U01-U27 是知识设计域，不是用户意图列表。

真实输入通常是：

- 这个项目怎么赚钱？
- 为什么增长越快越亏？
- 这个产品怎么定价？
- 能不能拿低价商品引流？
- 有哪些隐藏利润？
- 上下游还有什么机会？
- 平台怎么收费？
- 这个行业为什么利润都在某个环节？

如果直接让用户选择 U01-U27，会把知识本体的内部结构泄漏成使用负担。

因此运行入口必须是：

```text
Natural-language Task
→ Task Family
→ Cross-cutting Flags
→ Relevant Domains
→ Knowledge Assets
→ Atom / Pattern / Product Role Retrieval
→ Evidence / Data / Research Gates
```

# 二、8 个核心任务族

## F1 从0设计或重构商业模式

适用：

- 从0设计商业模式；
- 新产品商业化；
- 新业务；
- 创业项目；
- 现有模式整体重构。

典型主域：

> U01/U02/U03/U07/U10/U11/U12/U13/U15/U16/U18/U19/U21

核心问题：

> 谁需要什么 → 谁付钱 → 怎样创造/交付 → 怎样收费 → 成本/现金 → 利润池 → 增长 → 壁垒 → 风险 → 实验。

## F2 已有业务诊断与优化

适用：

- 利润下降；
- 转化差；
- 复购差；
- CAC 太高；
- 业务增长但不赚钱；
- 某个现有模式需要优化。

和 F1 的区别：

> F1 从空白空间生成结构；F2 必须先建立 Current-state Signature，再定位约束、泄漏和错配。

## F3 定价、入口商品、商品组合与 Offer

适用：

- 定价；
- 免费/低价/首单；
- 套餐；
- 订阅；
- 会员；
- 分层；
- 按量计费；
- Credits；
- Commit；
- Upsell/Cross-sell。

这里才强制加载 v4 的：

- Product Role；
- Price Architecture；
- Offer Conversion Graph；
- Cohort Economics；
- Incrementality Guardrail。

**不要把所有商业任务都强制变成 Offer Graph 问题。**

## F4 利润、单位经济、现金流与条件性经济

适用：

- 毛利/贡献利润；
- CAC/LTV/Payback；
- 账期；
- Rebate/MDF/Credits；
- 供应商资金；
- 现金流；
- Cohort Economics；
- 会计口径。

强制检查：

> 标价/收入 ≠ Pocket Price ≠ Net Effective Economics ≠ Contribution ≠ Cash。

## F5 平台、渠道、分销与多方生态

适用：

- Marketplace；
- 多边市场；
- 分销/经销；
- Agent/Broker；
- 渠道设计；
- 平台抽成；
- 合作生态。

必须显式回答：

- 谁创造跨边价值；
- 谁付款；
- 谁被补贴；
- 多归属是否存在；
- 是否容易绕平台；
- 平台真正控制什么；
- 冷启动从哪边开始。

## F6 获客、增长、复购、留存与 LTV

适用：

- 获客；
- 推荐/裂变；
- 留存；
- 唤醒；
- 提高 LTV；
- 降低 CAC；
- 扩张。

必须把：

> 相关性提升 与 真正增量

分开。

## F7 价值链、上下游扩张、竞争与迁移

适用：

- 上游/下游机会；
- 利润池；
- 纵向整合；
- 控制点；
- 竞争重构；
- 商业模式迁移；
- 新市场进入。

优先加载价值链/利润池和迁移，而不是先做商品 Offer。

## F8 案例、行业、市场与竞品研究

适用：

- 行业研究；
- 公司拆解；
- 竞品；
- 事实核查；
- 市场结构。

此任务族默认触发 External Research Gate，因为市场份额、价格、政策、公司动作等会变化。

# 三、Cross-cutting Flags：避免复制 Workflow

## `knowledge_product`

触发：电子书、PDF、课程、知识库、内容产品等。

可能增加：

> U03/U04/U06/U14/U15/U18 + `09_专题商业模式/电子书商业模式.md`

注意：只有真正是电子书/PDF场景才加载电子书专题；普通 SaaS 不应因为“有知识内容”就强行加载。

## `ai_native`

触发：AI/API/Token/模型/Agent/推理成本/算力。

重点：

- U14；
- usage/credits/commit/overage；
- 变量推理 COGS；
- 缓存/路由/模型组合可能改变成本；
- 峰值容量；
- 企业合同。

## `enterprise`

触发：B2B、大客户、企业采购、合同、席位、企业后端。

重点增加：

- 决策者/用户/付款者分离；
- Procurement；
- 合同；
- 账期；
- SLA；
- Minimum Commitment；
- 折扣权限；
- 实施/支持成本。

## `conditional_economics`

触发：返点、返佣、MDF、Credits、账期、年终返利、供应商促销资金。

强制加载 U19 及 06 真实经济层。

## `capacity_perishable`

触发：酒店房间、座位、库存、时段、算力、工时、易腐容量。

增加 U22，并把：

> 未售容量的机会成本 / 边际成本 / 高峰约束

纳入分析。

## `low_price_entry`

触发：低价、免费、首单、试用、入口商品、Loss Leader。

强制检查：

- Qualified CAC；
- Cannibalization；
- Attach；
- True Cohort Contribution；
- 滥用；
- Kill Condition。

# 四、路由不是单标签分类

一个任务可以是：

```text
Family = pricing_offer_portfolio
Flags = [ai_native, enterprise, low_price_entry]
```

另一个任务可以是：

```text
Family = value_chain_expansion_competition
Flags = [conditional_economics, enterprise]
```

若两个任务族分数接近：

1. 选择一个 Primary Family；
2. 保留 Alternate Routes；
3. 把第二任务族的关键模块作为扩展，而不是丢弃。

如果路由置信度很低，不要直接全库加载。应先进行：

> 问题语义重写 / 项目 Signature 建立 / 1 次轻量澄清 / 多路小规模召回

再决定是否扩展。

# 五、最小充分上下文策略

## 5.1 三类上下文必须分开

### A. Runtime Control Context

告诉系统怎样工作：

- Task Router；
- Workflow；
- 证据门；
- 输出协议；
- Benchmark 规则。

它不是商业知识，不应与检索结果混算。

### B. Knowledge Context

真正提供商业机制：

- U 域；
- Atom；
- Pattern；
- Product Role；
- 机会来源；
- 价值链；
- 条件经济；
- 案例/专题。

### C. Project / External Context

- 用户项目数据；
- 当前市场资料；
- 竞争者；
- 平台费率；
- 法规；
- 合同；
- 真实 Cohort。

混在一起会导致两个问题：

1. 无法知道答案来自“通用知识”还是“项目事实”；
2. Benchmark 无法做消融。

# 六、渐进式 Retrieval Pipeline

推荐默认链：

```text
Task Router
↓
Primary U Domains
↓
Atom lexical/semantic recall
↓
Pattern recall
↓
横向系统（机会来源 / Product Role / 价格 / 真实经济）
↓
专题/案例
↓
证据与外部研究
↓
Rerank + Deduplicate
↓
Minimum Sufficient Context
```

## 6.1 第一层：Domain Narrowing

先通过任务族把 27 域缩到约 6-16 个高相关域。

目的：

- 防止“所有 Atom 都很重要”；
- 降低噪声；
- 提高后续 Atom 检索的 Precision。

## 6.2 第二层：Atom Recall

默认目标不是加载整个域，而是每个任务组合召回约 12-30 个高相关 Atom。

召回方法可以演进：

### V0：规则/关键词

优点：

- 无额外基础设施；
- 稳定；
- 可以写 Regression。

用途：作为确定性基线。

### V1：BM25 / FTS

适合稳定 ID、商业术语、返点、Commit、Minimum Guarantee 等精确词。

### V2：Embedding Retrieval

用于表达差异大但语义接近的用户输入。

### V3：Hybrid + Rerank

```text
BM25 Top-N
+
Embedding Top-N
→ Rank Fusion
→ Rerank
→ Top-K
```

这是中期推荐方向，但只有在 Benchmark 证明 V0/V1 召回不足时才值得投入。

## 6.3 第三层：Pattern Recall

Pattern 的用途不是“给模型更多名词”，而是：

> 提供已经稳定组合过的机制结构，减少每次从 Atom 零组合。

应保留来源：

- P001-P130；
- P131-P170；
- P171-P200。

## 6.4 第四层：横向资产

任务满足条件才加载：

- Product Roles；
- Offer/Price Architecture；
- U19/真实经济；
- Opportunity Lens；
- Migration；
- Topic/Case。

## 6.5 第五层：外部研究

只有知识库不能回答“当前事实”时才进入外部研究。

比如：

- 某平台今天的佣金；
- 某供应商返点规则；
- 当前监管；
- 某竞品现在的价格；
- 某公司最近是否改变策略。

这类信息不应硬编码成永久 Atom。

# 七、Context Budget

默认建议：

- 静态知识文件：≤12 个；
- Atom：约 24 个；
- Pattern：约 12 个；
- Product Roles：只加载相关角色族或 top roles；
- 案例/专题：0-3 个；
- 外部研究：按信息缺口加载，不按“越多越好”。

这不是硬上限，真正目标是：

> **Relevant Recall 高 + Context Precision 高 + 关键事实不丢 + 无明显噪声干扰。**

如果任务是全宇宙审计、分类去重或结构完整性检查，可以全量加载机器 Registry；但这属于特殊任务，不是日常商业决策。

# 八、检索失败怎样判断

如果答案遗漏一个已有机制，不能马上记成 K1。

先检查 Trace：

```text
知识库中是否存在？
├─ 不存在 → K1 Knowledge Gap
└─ 存在
   ├─ 没被召回 → R1 Retrieval Failure
   └─ 被召回
      ├─ 没被使用 → W1 Workflow Failure
      └─ 被使用但结论仍错 → E1/F1/S1 等进一步归因
```

这条分层是整个长期演进系统的核心。

# 九、Real Data Gate

## 9.1 通用知识可以推理什么

通常可以先给候选：

- 商业结构；
- 利润池；
- 商品角色；
- 常见成本项；
- 可能的风险；
- 可测试的假设；
- 可能的上下游机会。

## 9.2 哪些不能凭知识库伪造

常见必须用项目数据或实时研究的参数：

```text
采购价 / COGS
渠道费率
返点合同
CAC
真实转化率
Attach Rate
复购
退款
库存
履约成本
支持成本
账期
真实用户 Cohort
实际竞争价格
当前平台政策
```

## 9.3 缺数据时的正确输出

不能：

> “你的 LTV 是 280 元，因此可以把 CAC 提到 90 元。”

应该：

> “缺少真实复购/毛利/流失数据，先用保守/基准/乐观三场景。若 90 天重复贡献分别为 20/60/120 元，则可承受 CAC 上限完全不同；需要用真实 Cohort 替换假设。”

每个数值必须标：

- Actual；
- Contractual；
- Estimated；
- Scenario；
- Unknown。

# 十、Evidence Gate

所有重要结论分成五种状态：

| 状态 | 含义 | 允许怎样说 |
|---|---|---|
| FACT | 项目数据/可靠来源支持 | 可以陈述，但仍需时间/范围 |
| ASSUMPTION | 尚未验证的关键假设 | 必须标注并进入实验 |
| DERIVED | 基于输入计算 | 给公式/输入 |
| JUDGMENT | 分析判断 | 给依据与反方 |
| UNKNOWN | 当前不知道 | 明确说未知，不能补成事实 |

对于时效事实，再增加：

- `as_of_date`；
- `source`；
- `freshness_risk`；
- `recheck_trigger`。

# 十一、External Research Gate

以下情况默认必须研究当前外部信息：

1. 用户问当前市场/竞争；
2. 平台规则/费率/分销政策；
3. 法律法规；
4. 公司当前产品或价格；
5. 返点/合作计划是否仍存在；
6. 新行业进入需要市场事实；
7. Benchmark E 组。

外部研究结果必须进入 Trace，不能无来源写回长期本体。

知识回流时再决定：

> 长期机制 / 案例证据 / 临时事实 / 不入库。

# 十三、输出层：Decision Artifact Contract

商业推理最终交付至少有：

1. 问题与真正要做的决策；
2. 已知事实；
3. 数据缺口与未知；
4. 机会/问题诊断；
5. 3-7 个差异明显候选；
6. 关键经济模型；
7. 条件性经济；
8. 竞争/风险/反方；
9. 关键假设；
10. 最小实验；
11. Pass / Kill / Scale；
12. 推荐方案或需要更多数据才能决定的分支；
13. 下一动作。

禁止把：

- 赚钱方式数量；
- 答案长度；
- Markdown 排版；
- 模型自信程度；

当成决策质量。

# 十四、当前实现边界

当前 `task_router_v1.json` 首先实现的是：

> **确定性任务路由 + 静态资产装配基线。**

这是为了让系统先有可测试的基准。

后续是否升级成：

- BM25；
- 向量；
- Hybrid；
- Reranker；
- Contextual Retrieval；

必须由 Benchmark 的 R1/C1 数据决定。

否则很容易出现：

> “RAG 工程越来越复杂，但商业答案没有可测量提升。”
