# T01 电子书与 T02 AI API：真实项目商业推理运行记录（2026-08-24）

> 本文件不是新增 Benchmark 题库，而是记录一次**真实项目决策输出**：先让用户知道该做什么，再用运行结果检查 Workflow 是否存在直接影响商业决策的缺口。
>
> T01 为主案例；T02 只做跨结构 Canary，检查同一协议会不会退化成“电子书专用答案”。

---

# 一、T01 原始项目

> 我准备在电商平台销售单本电子书/PDF，希望通过单本低门槛商品获得某一领域的高意向用户，并继续研究后端商业价值。这个项目应该怎样设计商业模式？

---

# 二、T01 项目判断

## 1. 当前理解

这不是一个“靠大量低价 PDF 本身赚取主要利润”的项目。

更合理的项目定义是：

> **用合法授权、问题高度聚焦的单本数字知识商品，低成本识别一群具有明确任务和支付行为的用户，再根据他们的后续任务销售更高价值的知识、软件、AI、服务或企业解决方案。**

## 2. 当前阶段

当前信息对应：

> **商业模式设计 / 上线前验证阶段。**

尚没有可靠的真实 CAC、退款、复购、后端转化和 Cohort 数据。

## 3. 真正商业问题

不是：

> “电子书还能有多少种赚钱方式？”

而是：

> **低门槛单本能否成为一个合规、可追踪、经济上成立的 Qualification / Entry Offer，并找到使 30/90/180 天 True Cohort Contribution 为正的后端路径？**

## 4. 当前最有价值的未知信息

按会不会改变决策排序：

1. 内容是否自有、已授权或属于可合法商业传播范围；
2. 具体书籍/领域，对应的用户任务是什么；
3. 准备在哪个电商平台销售，能否在规则允许范围内持续触达和识别购买用户；
4. 入口实际成交价、平台费、退款和 CAC；
5. 用户购买后最自然的下一项高价值任务。

# 三、T01 本轮外部市场证据

## 1. 中国数字阅读：市场还在增长，但增长逻辑已经变化

2026-04 发布的《2025年度中国数字阅读报告》显示：

- 2025 年中国数字阅读市场营收 789.37 亿元，同比增长 19.35%；
- 用户规模 6.89 亿，同比增长 2.95%；
- 行业增长越来越依赖存量用户深度运营，而不是只扩大用户数；
- 单一作品对营收增长的贡献度在下降；
- 大众阅读中广告及其他收入占 51.81%，高于订阅；
- 专业阅读中技术服务收入占 32.54%，说明专业知识业务的价值正在从“卖内容”向“内容 + 技术服务”延伸。

项目含义：

> **把单本书作为入口、把价值延伸到工具/AI/服务，比把“多卖几本低价 PDF”当唯一增长逻辑更符合当前市场结构。**

来源：

- 新华网，《中国音像与数字出版协会副秘书长李弘：我国数字阅读市场已从规模增长阶段迈入高质量发展新阶段》，2026-04-21。
- 中国音像与数字出版协会《2025年度中国数字阅读报告》的公开报道，2026-04-21。

## 2. Leanpub：低价电子书可行，但低价会被固定费用侵蚀

Leanpub 公开规则显示：

- 电子书最低付费价可到 0.99 美元；
- ebook bundle、course、track 最低付费价为 7.99 美元；
- 0.99-7.98 美元区间的版税规则为 80% 再减固定 0.50 美元；
- 7.99 美元以上为 80%。

项目含义：

> **低价可以承担入口作用，但平台固定成本会使价格越低、单位利润率越容易恶化；bundle/course 等后端商品拥有更好的价格空间。**

## 3. Gumroad：同一平台同时支持 ebook、course、membership，但获客方式决定费用

Gumroad 当前公开定价：

- 自有 profile / direct link 成交：10% + 0.50 美元/笔；
- Discover 带来的新客户成交：30%；
- 支持 digital products、ebooks、courses、memberships；
- 明确禁止 copyright infringement / piracy。

项目含义：

> **“单本 → 课程/会员/其他数字品”的商品阶梯是成熟的平台能力；但入口越低价，固定交易费和渠道费越容易成为主要矛盾。**

## 4. Readwise：用户可以为“持续工作流”而不是单本内容持续付费

Readwise / Reader 当前支持：

- PDF、EPUB、RSS、文章、newsletter 等统一阅读；
- highlights、review、Obsidian/Notion 等知识流；
- AI 阅读辅助；
- Full 年付折算 9.99 美元/月，月付 12.99 美元/月；
- 官方公开称其自 2017 年 bootstrapped 且盈利，依赖订阅收入。

项目含义：

> **当产品从“文件”升级成高频、持续的阅读/知识工作流时，订阅可以成立。**

但用户社区也反复出现一个条件性信号：

> 对只是“保存、稍后读”的轻度用户，约 120 美元/年的价格会被认为过高；对 PDF、多来源内容、标注和知识工作流重度用户，付费意愿明显更强。

因此：

> **不要默认所有买书用户都适合订阅；先识别高频知识工作流用户。**

## 5. Pocket：有大量用户也不等于一个阅读工具永远可持续

Mozilla 于 2025-05 宣布 Pocket 在 2025-07-08 关闭。Mozilla 给出的原因之一是用户保存和消费内容的方式已经变化，因此把资源转向更匹配当前浏览习惯的产品。

项目含义：

> **“有用户”“阅读需求存在”都不等于某个独立阅读工具必然具有持续商业价值；必须持续解决一个足够高频、不可轻易被浏览器/平台内置功能替代的任务。**

## 6. 版权是硬门，不是普通风险项

中国《信息网络传播权保护条例》明确：除法律、行政法规另有规定外，将他人作品通过信息网络向公众提供，应取得权利人许可并支付报酬。

因此本项目的 G0 条件是：

> **只使用自有内容、明确授权内容或经确认可合法商业传播的内容。**

未经授权 PDF 不进入正式商业方案，也不能因为它“获客便宜”而作为实验。

# 四、T01 当前最值得赚钱的三个位置

不是按“理论毛利”排序，而是按当前项目与市场证据组合判断。

## P1：单本之后的垂直知识解决方案

```text
授权单本
→ 专题合集 / 模板 / SOP / 案例 / 练习
→ AI 问答 / 专题知识库 / 工作流
→ 会员或年度更新
```

真正卖的是：

> **用户把书中的知识用于完成某个任务的速度和结果。**

## P2：与该领域天然相邻的软件、工具和专业服务

```text
单本
→ 识别用户任务
→ 推荐实际需要的软件 / AI / 硬件 / 数据 / 服务
→ Affiliate / 官方分销 / 自营服务
```

它可以在不先开发大型软件的情况下验证用户后端支付能力。

## P3：专业用户和企业用户的高价值后端

```text
专业主题单本
→ 识别专业用户 / 企业线索
→ 诊断 / 咨询 / 培训
→ AI知识库 / 私有知识库 / 实施
→ 运维 / 年费 / 企业后续项目
```

专业阅读中技术服务收入已经超过三成，是这一方向的现实结构性支持。

# 五、T01 候选商业方案与排序

# 第一推荐：垂直“单本 → 解决方案包 → AI/知识工作流”

## 方案

不是做“电子书商城”，而是从一个非常具体的问题切入：

```text
一份授权单本 / PDF
→ 帮用户理解
→ 帮用户应用
→ 帮用户持续调用
```

后端产品可以是：

- 专题合集；
- 核心知识提炼；
- 模板 / SOP / Prompt / Checklist；
- 练习与案例；
- 专题知识库；
- AI 问书 / AI 导师 / 专题助手；
- 持续更新会员。

## 为什么第一

- 市场验证：A/B，内容 → bundle/course/membership/software 的结构已被多平台验证；
- 项目匹配：高，天然继承当前“单本低门槛入口”；
- 潜在利润：中高，后端数字品边际交付成本低；
- 实施难度：中，可以从人工/半自动专题包开始，不必先开发完整 SaaS；
- 可逆性：高，失败可快速换书、换主题、换后端；
- 验证成本：低。

## 最大假设

购买单本的人存在一个**持续任务**，而不只是一次性拿文件。

## 最小验证

同一主题至少比较两种后端：

```text
A：专题解决方案包
B：AI/知识库型持续产品
```

同时记录：

- 入口转化；
- 用户允许持续触达的比例；
- 7/30 日激活；
- 后端购买率；
- 退款；
- 每入口买家的 30/90 日贡献。

## Kill Condition

在拥有合规触达能力、完成两轮 Offer 优化以后：

> 30/90 日后端期望贡献仍不足以补偿入口补贴 + CAC + 售后，并且用户使用频率不足以形成持续任务，则停止把该主题做成会员/AI订阅。

---

# 第二推荐：单本 → 相关工具 / 软件 / 服务 Affiliate 或官方分销

## 方案

把书当成意图识别器：

```text
用户买“AI Agent”书
≠ 只想再买一本书

可能继续需要：
模型/API、开发工具、托管、课程、数据、模板、咨询等。
```

## 什么时候会超过第一推荐

如果：

- 该领域天然需要购买第三方工具；
- 用户阅读频率不高，不适合订阅；
- 自己开发软件成本过高；
- 官方 Affiliate / Reseller 条件好；

那么第二方案可能比自建 AI 产品更优。

## 最大假设

用户的“知识意图”能够稳定转化为“工具购买意图”。

## Kill Condition

点击和购买行为很弱，或渠道佣金/返点高度不稳定、平台规则限制触达，使 90 日净贡献不足，则不把 Affiliate 当核心利润池。

---

# 第三推荐：专业单本 → 咨询 / 培训 / AI知识库实施 / 企业服务

## 方案

低价商品不追求大规模大众转化，而作为低成本付费资格筛选：

```text
专业主题单本
→ 专业用户
→ 诊断 / Workshop
→ 咨询 / 培训
→ 企业知识库 / AI实施
→ 年费 / 运维 / 二次项目
```

## 什么时候会超过第一推荐

如果一本书对应的核心用户是：

- 企业主；
- 管理者；
- 开发者；
- 专业岗位；
- 有明确业务预算的人；

一个高价值企业成交的贡献可能显著高于大量个人会员，此时应优先走 B2B。

## 最大假设

买书者中存在足够比例的 Budget / Authority / Need / Timing 用户。

## Kill Condition

连续获得一批高意向专业用户后，仍没有可验证的付费诊断、培训或实施需求，或者销售周期和交付成本超过可接受水平，则不继续扩 B2B 销售体系。

---

# 第四候选：作者 / 出版社数字化与白标

这是结构上不同的 B2B 方案：付款方从“读者”变成“内容所有者”。

可销售：

- 电子书制作；
- AI 产品化；
- 作者知识库；
- 分销与销售基础设施；
- 白标阅读 / 知识产品。

当前验证等级：B/C。

原因：逻辑成立，但它更适合作为 T01 获得分发和 AI 产品化能力后的第二增长曲线，不是当前第一步。

# 六、T01 暂时不推荐

## 1. 0.01-3 元极低价作为默认策略

不是永远不能做，而是不应在不知道后端贡献之前先假设“越便宜越好”。

低价会同时带来：

- 固定平台/支付费用占比上升；
- 更低质量流量；
- 退款/套利/售后负担；
- 价格锚定；
- 可能蚕食本来愿意更高价购买的人。

正确做法是把：

> **近免费 / 低价 / 有支付筛选的价格**

作为实验变量，而不是商业模式前提。

## 2. 一开始做“大而全电子书会员库”

原因：

- 版权和内容供给复杂；
- 用户对通用内容已有大量替代；
- 当前市场单品拉动趋弱；
- 轻度用户订阅意愿有限；
- 需要规模、内容库和持续活跃才能成立。

## 3. 把百度网盘/平台返佣当基本盘

当前仓库已经正确把官方分销/推广与账号共享等非正式方式分开。

返点、邀请和活动可以作为：

> **增量补贴 / 渠道经济。**

但具体规则随时间变化，没有确认前不计入基础 Cohort Economics。

## 4. 未授权 PDF

直接淘汰。

# 七、T01 经济模型：当前缺数据时怎样继续

## 1. Front-end

```text
Front-end Contribution
= 实际成交收入
- 内容/版权增量成本
- 平台/支付费用
- 退款
- 客服/交付
- 直接促销成本
```

## 2. Backend Expected Contribution

```text
Backend EV
= Σ（后端产品转化率 × 单次后端贡献）
+ Affiliate / 分销净佣金
+ 服务线索期望贡献
+ 企业线索期望贡献
```

## 3. True Cohort

```text
True Cohort Contribution
= Front-end Contribution
+ Backend EV
- CAC
- 后续客服/退款/滥用
- 其他真实可归因成本
```

## 4. 最重要的 Break-even

```text
CAC_max
= Front-end Contribution + Backend EV - 其他可归因风险成本
```

因此低价入口的关键不是“首单亏几块钱能不能接受”，而是：

> **每个入口买家的后端期望贡献到底是多少。**

### 纯机械敏感性示例

如果一个入口买家平均已经产生 8 元 Front-end Contribution，某后端商品每成交一个贡献 100 元：

- 后端转化 1% → 每个入口买家增加约 1 元期望贡献；
- 后端转化 5% → 增加约 5 元；
- 后端转化 15% → 增加约 15 元。

这不是市场预测，只是说明：

> **后端转化率会直接决定你最多能承受多少 CAC。**

# 八、T01 下一步只做三件事

## 1. 选一个合法、问题高度明确的 Seed Title

不要先铺 1000 本书。

为这一本书明确：

```text
用户是谁
→ 买它解决什么问题
→ 买完下一步做什么
→ 最自然的两个后端 Offer 是什么
```

## 2. 做“价格 × 后端”最小实验

至少比较：

- 一个更低门槛入口；
- 一个更有支付筛选能力的入口；
- 后端 A：一次性专题解决方案；
- 后端 B：持续 AI / 知识工作流。

不以 GMV 为第一指标，优先看：

> Qualified CAC、30/90 日 True Cohort Contribution、退款、后端转化。

## 3. 建立第一版 Cohort Ledger

每个入口 cohort 至少保留：

```text
来源
书籍/主题
成交价
CAC
退款
后端点击
后端成交
Affiliate
服务/企业线索
30/90/180天累计贡献
```

没有这张表，后续会再次退化成“赚钱方式列表”。

# 九、T01 暴露的 Workflow 缺口

本轮没有暴露新的商业知识本体缺口。

`09_专题商业模式/电子书商业模式.md` 已经包含：

- 低价入口；
- 网盘官方分销；
- AI阅读；
- AI知识库；
- 咨询/实施；
- 相关商品；
- 企业业务；
- 作者/出版方。

已有 Retriever 的首轮缺口也已在之前运行时测试中修复。

本次真正暴露的是 **W1 / 输出协议问题**：

1. 现有 Workflow 虽然有 Task Intake，但没有强制第一屏先给用户“项目判断”；
2. External Research 仍容易被理解成按需背景资料，没有强制成功 / 失败 / 条件性成功三类证据；
3. Candidate Generation 有 3-7 个候选，但没有足够强地约束“后台广扫、前台只留 3-5 个”；
4. Rank 没有在用户层明确 A-E 市场验证程度；
5. Decision Artifact 没有强制“决策面板优先”；
6. 跨轮 Project State 没有被单独强调成用户项目资产。

因此本轮没有扩 Atom / Pattern / Schema，而是新增：

> `10_任务工作流与运行时/03_项目优先商业推理执行协议.md`

这是由真实项目输出直接触发的修复。

# 十、修复后复跑 T01 的变化

修复前容易出现：

> “电子书有 A-Q 很多变现方式。”

修复后最终变成：

```text
第一：垂直单本 → 解决方案 → AI/知识工作流
第二：单本 → 相关工具/服务 Affiliate
第三：专业单本 → 咨询/企业知识库实施
第四：作者/出版社白标作为第二增长曲线

暂不优先：
极低价默认策略 / 大而全会员库 / 不确定返佣作为基本盘 / 未授权PDF
```

并且明确了：

- 最大未知；
- 经济公式；
- CAC Break-even；
- 最小实验；
- Kill Condition；
- 下一步只做三件事。

因此这次修复直接改善真实商业决策，而不是增加系统复杂度。

# 十一、T02 跨结构 Canary：AI API

## 原始项目

> 我们提供按调用计费的 AI API，推理成本随用量变化。怎样设计免费额度、commit、overage、渠道和企业后端，避免增长越快亏得越多？

## 项目判断

T02 真正问题不是：

> “API 可以有哪些收费方式？”

而是：

> **怎样把不同用量分位、供应商推理成本、免费额度、缓存/批处理、企业折扣、渠道分成和容量风险放进同一 Contribution Model，并把成本风险合理分配给客户和供应商。**

## 当前市场结构信号

Google Gemini Developer API 当前公开分为：

- Free；
- Paid；
- Enterprise；

并同时提供：

- Context caching；
- Batch API，公开标注可降低 50% 成本；
- Enterprise volume-based discount；
- Provisioned throughput。

这说明现实市场已经不是简单的“一个 token 单价”，而是：

> **免费入口 + 按量 + 成本优化 + 容量/企业合同 + 批量折扣/承诺的组合架构。**

## T02 第一推荐

```text
PAYG 基础价
+ 明确 Included Usage / Credit 上限
+ 超额 Overage
+ 缓存 / Batch / Model Routing 降本
+ Spend Limit / Abuse Guardrail
```

先确保每个用量分位都能计算真实贡献。

## T02 第二推荐

对稳定企业客户：

```text
Minimum Commit / Commit-to-Save
+ Overage
+ SLA / Support Tier
+ 年度或季度用量承诺
```

只有在客户用量足够稳定时，折扣才交换真实承诺，而不是无条件降价。

## T02 第三推荐

对容量敏感的大客户：

> Reserved / Provisioned Capacity + Overage。

让客户为确定性容量付费，而不是平台独自承担峰值成本。

## T02 暂不推荐

- 无上限“无限用量”订阅；
- 没有防滥用的免费 Credits；
- 企业折扣 + 渠道分成叠加后低于风险调整边际成本；
- 把供应商临时 Credits / 返点当长期基础毛利。

## 核心经济式

```text
Contribution by customer / usage decile
= API Revenue
- Model Inference COGS
- Storage / Network / Other Compute
- Free Credits
- Channel Share
- Support
- Fraud / Abuse
- Capacity / Financing Risk
```

## T02 Kill Condition

- 某个主要用量分位持续负贡献且无法通过限额/路由/价格修复；
- Free→Paid 增量贡献不足以覆盖 Free COGS；
- 企业 Pocket Price 低于风险调整后的边际成本；
- 供应商临时折扣消失后模型立即转负。

# 十二、T02 对工作流跨项目能力的结论

T01 与 T02 最终的第一推荐完全不同：

```text
T01：

T02：
```

共同的只有：

- 先定义真正决策；
- 研究市场证据；
- 找条件性成功；
- 建真实经济；
- 排序；
- 做实验；
- 设 Kill。

因此当前 Project-first 协议没有退化成“电子书专用模板”。

# 十三、本轮验收结论

## 已通过

- 能从普通项目描述进入商业决策；
- 能主动使用真实市场而不是只复述知识库；
