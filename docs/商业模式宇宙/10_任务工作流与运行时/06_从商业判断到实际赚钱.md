# 从商业判断到实际赚钱

> 本文件解决第三层问题：**分析完以后，用户现在到底要做什么，怎样把商业判断变成真实交易、真实数据和下一轮经营。**
>
> 它不是项目管理 SOP，也不是工程测试协议，而是商业决策的行动层。

---

# 一、核心链路

```text
已经形成商业判断
→ 选择当前第一方案
→ 明确卖给谁
→ 明确卖什么
→ 明确为什么买
→ 明确多少钱/怎么收费
→ 明确在哪里成交
→ 明确如何交付
→ 用最小成本获得第一批真实交易
→ 收集最关键数据
→ 判断继续/修改/停止
→ 把有效方案扩大
→ 进入下一轮经营
```

最终目标是：

> **不是“我知道可能怎么赚钱”，而是“我知道现在先卖什么、卖给谁、怎么卖、什么结果说明值得继续”。**

---

# 二、第一步：把“第一推荐”改写成一个可成交的 Offer

一个推荐方案如果不能变成下面这张卡，就还没有进入行动层。

## 商业行动卡

```text
目标用户：
用户现在最想完成的任务：
当前替代方案：

我要卖什么：
用户买到的具体权利/结果：
为什么现在愿意付钱：

价格/计费方式：
前端入口：
核心商品：
后端商品：

成交渠道：
交付方式：

当前最大假设：
最关键指标：
预算/时间上限：
继续条件：
修改条件：
停止条件：
```

如果这张卡写不清，说明 P13-P18 仍然没有真正收敛。

---

# 三、第二步：先做“最小可卖商品”，不是最完整产品

行动优先级：

```text
先证明有人愿意付钱
→ 再证明可以稳定交付
→ 再证明单位经济成立
→ 再证明可以重复获客
→ 最后才扩大功能、团队或投入
```

不同项目的最小可卖商品可能是：

- 一个单品；
- 一个专题包；
- 一个服务套餐；
- 一个付费试用；
- 一个按量 API；
- 一个企业 Workshop；
- 一个知识库实施小项目；
- 一个手工完成但用户愿意付钱的结果。

不要因为最终形态可能是 SaaS，就必须先把完整 SaaS 开发完。

---

# 四、第三步：只验证最可能改变决策的假设

商业验证不是“做很多测试”。

先问：

> **如果只能知道一个新事实，哪个事实最可能让我改变第一推荐？**

常见最大假设包括：

```text
需求是否足够强
用户是否愿意付钱
这个价格是否成立
这个渠道能否获得合格用户
低价入口是否真的带来高价值后端
复购/续费是否存在
企业是否愿意进入销售流程
推理/履约成本是否吞掉毛利
供应商返点是否真实可得
平台规则/版权/合同是否允许长期做
```

一个实验只要能显著减少其中一个关键不确定性，就有价值。

---

# 五、第四步：先看真实交易，再看表面互动

指标优先级通常是：

```text
真实付费
> 有购买意向的有效线索
> 进入结账/报价
> 高质量试用
> 点击/收藏/点赞/曝光
```

如果项目目标是商业化，不要因为：

- 浏览很多；
- 点赞很多；
- 下载很多；
- 注册很多；

就认为需求已经验证。

必须继续问：

> **这些行为有没有转成真实支付、真实贡献或明确的企业采购推进？**

---

# 六、第五步：根据项目阶段选择正确的经营指标

## 1. 想法/早期验证

重点：

```text
有多少目标用户真正愿意付钱
成交需要解决什么顾虑
什么价值主张最有效
哪个渠道出现第一批合格客户
```

不急着追求规模。

## 2. 已有产品/已有用户

重点：

```text
付费转化
ARPU/客单
商品组合
使用频率
复购/续费
Upsell/Cross-sell
退款
```

## 3. 已有收入/利润优化

重点：

```text
Contribution Margin
CAC
CAC Payback
LTV / Cohort Contribution
退款/坏账
履约/推理/客服成本
渠道净收入
返点后的真实净经济
```

## 4. 企业业务

重点：

```text
Qualified Lead
Demo/Workshop → Proposal
Proposal → Contract
平均合同额
实施成本
销售周期
续约/扩容
支持成本
账期与现金流
```

## 5. 平台/Marketplace

重点：

```text
供需两侧激活
成交率
GMV
Take Rate
绕平台率
补贴后净贡献
供需密度
复购
```

指标必须服务于当前商业决策，不为了“数据完整”而收集。

---

# 七、第六步：用阈值决定继续、修改还是停止

每个重要方案都需要商业意义上的三类条件。

## Continue：继续

例如：

- 用户愿意按目标价格真实购买；
- CAC 低于当前可承受上限；
- 后端转化达到使 Cohort 为正的阈值；
- 企业客户愿意继续进入采购流程；
- 使用频率足以支持订阅；
- 毛利能够覆盖支持和增长成本。

## Change：修改

例如：

- 有强需求，但价格不对；
- 用户愿意买，但现有渠道 CAC 太高；
- 前端成立，但后端商品错了；
- 企业愿意谈，但交付方式过重；
- 重度用户价值高，但当前定价导致负毛利。

这时修改结构，而不是把整个项目判死。

## Kill：停止

例如：

- 多轮 Offer 优化后仍没有真实支付；
- 必须依赖不可持续补贴或漏洞才能成立；
- 用户价值不足以覆盖获取和履约成本；
- 关键版权、合同、政策或平台条件无法满足；
- 后端价值长期无法覆盖低价入口损失；
- 竞争条件使项目没有合理利润空间且缺少可改变结构。

Kill Condition 的作用是防止：

> **因为已经投入很多，就无限继续一个没有经济基础的方案。**

---

# 八、第七步：有效以后再决定“扩大什么”

验证通过后，不是笼统地“加大投入”。

先判断真正应该扩大的是哪一项：

```text
流量？
成交渠道？
高价值用户群？
某个价格档？
某个后端商品？
某个企业行业？
某个供应商合作？
某个自动化交付环节？
```

扩大之前检查：

- 扩大后 CAC 会不会上升；
- 边际成本会不会变差；
- 客服/履约是否成为瓶颈；
- 渠道是否饱和；
- 供应是否跟得上；
- 返点/优惠是否有规模门槛或上限；
- 现金流能否承受增长。

真正的 Scale 是：

> **扩大已经被验证的正贡献结构，而不是扩大表面销量。**

---

# 九、低价入口项目的行动方式

对于：

> “先用低价商品获得用户，再赚后端的钱”

不要只测试低价能不能卖。

应该同时建立：

```text
入口商品
→ 用户资格
→ 下一 Offer
→ 后端成交
→ 30/90/180 天贡献
```

至少比较：

```text
不同入口价格
不同入口内容
不同用户领域
不同后端 Offer
```

真正要优化的是：

> **Qualified CAC + True Cohort Contribution。**

如果 0.1 元入口带来很多用户，但后端价值低；9.9 元入口带来更少但更高价值用户，那么更低价格不一定是更好的生意。

---

# 十、已有功能项目的行动方式

如果项目已有大量功能，第一轮不要继续开发更多功能。

先做：

```text
功能
→ 用户任务
→ 价值强度
→ 商品角色
→ 套餐
→ 价格
→ 真实付费验证
```

例如可以测试：

- 哪些功能必须免费才能形成入口；
- 哪些功能是用户愿意升级的原因；
- 哪些高成本功能必须按量收费；
- 哪些价值更适合团队/企业而不是个人；
- 哪些功能看起来高级但并不增加支付意愿。

目标是：

> **用现有功能先形成更好的商品结构，而不是用更多功能掩盖商业模式不清。**

---

# 十一、商业现象逆向拆解后的行动方式

当用户从“别人为什么这样赚钱”进入时，分析完成以后要多做一步：

```text
理解别人的模式
→ 找到真正机制
→ 判断是否可持续
→ 判断哪些条件属于对方特有
→ 判断哪些机制可以迁移
→ 变成自己的候选方案
→ 重新做 P15-P19
```

不能因为别人正在做，就直接复制。

最终应该告诉用户：

```text
值得学什么
不要学什么
如果迁移到你的项目，会变成什么
最小应该怎样测试
```

---

# 十二、每轮结束只保留一个简洁经营面板

项目持续推进时，人工最需要看到：

```text
当前阶段：
当前第一方案：
为什么仍然排第一：

已经验证：
已经否定：

当前最重要数据：
当前最大未知：

本轮只做：
1.
2.
3.

达到什么结果继续：
达到什么结果修改：
达到什么结果停止：

下一轮什么时候重新判断：
```

这样下一次用户带来新数据时，可以直接继续经营，而不是重新讨论一遍所有商业模式。

---

# 十三、从商业判断到实际赚钱的完成标准

这一层真正完成，必须满足：

1. 用户知道**先卖什么**；
2. 知道**卖给谁**；
3. 知道**为什么对方会买**；
4. 知道**怎样收费**；
5. 知道**在哪里成交**；
6. 知道**先收集哪几个数据**；
7. 知道**什么结果继续、修改或停止**；
8. 知道有效以后**扩大什么，而不是笼统扩大投入**；
9. 下一轮能够基于真实结果继续 P20，而不是重新从零开始。

最终评价标准不是“分析是否完整”，而是：

> **用户能否根据商业判断直接开始下一步真实行动，并用真实市场结果继续把项目推向正的、可持续的经济结构。**
