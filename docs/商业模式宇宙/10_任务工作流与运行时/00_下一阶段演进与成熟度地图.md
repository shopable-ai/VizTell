# 商业模式宇宙下一阶段：成熟度地图与建设优先级

> 定位：本文件不是 v5 本体，不新增 U/Atom/Pattern/PR ID。它回答一个更高层问题：**当前知识本体下一步怎样变成可检索、可组合、可执行、可测试、可回归、可持续学习的商业推理系统。**
>
> 审计基线：`main` 当前 v4 合并视图；稳定事实为 U01-U27、676 Atom、P001-P200、PR01-PR40，并保留 U19 条件性经济层、v3/v4 Registry、Schema、Validation 与 Skill。

---

# 一、核心结论

当前商业模式宇宙已经不再是“缺分类”的早期知识库，而处在：

> **高成熟度本体 + 较强机器资产 + 多个局部 Skill + 较弱端到端运行时 + 很弱真实任务评测/回归 + 案例/行业/价值链/生态深度不均衡**

因此下一阶段最重要的建设顺序不是：

> 继续增加 Atom → 继续增加 Pattern → 继续增加文档

而应该转成：

> **任务路由 → 最小充分上下文 → 端到端 Workflow → 真实数据/证据门 → 候选方案与经济模型 → 反方/实验 → Benchmark → 错误归因 → Regression → 知识反馈与生命周期治理**

只有在真实任务暴露 `K1 Knowledge Gap` 时，才优先补本体。

---

# 二、成熟度模型

采用 5 个阶段，而不是只看文件数量：

| 阶段 | 定义 |
|---|---|
| M1 文档库 | 能阅读、能查概念，但对象边界和稳定 ID 不完整 |
| M2 知识本体 | 有稳定分类、Atom/Pattern/关系和版本规则 |
| M3 可运行知识系统 | 能识别任务、检索最小上下文、装配 Skill/Workflow、留下 Trace |
| M4 可验证决策系统 | 有真实任务 Benchmark、A-E 对照、消融、错误分类、回归、数据门 |
| M5 持续学习系统 | 真实结果回流，知识有验证/降级/废弃/替换/时效治理，并能长期测量增量价值 |

**当前总体位置：M2 → M3 过渡。**

本体和机器数据已经接近 M3，但端到端运行时与评测仍处在 M1-M2 水平，所以不能用“676 Atom + 200 Pattern”推断整个系统已经 M4/M5。

## 3.1 “文件存在但内容偏薄”的区域

### 02 价值链与利润池

当前总览能提出正确问题，但主要还是：

- 产业链有哪些环节；
- 谁拥有客户；
- 毛利/资本占用/风险如何；
- 利润池如何迁移。

缺少更强的：

- 标准价值链建模协议；
- 利润池计算模板；
- 控制点/瓶颈的证据化判别；
- 前移/后移/横向扩张的候选生成器；
- 跨行业实例和失败反例。

### 03 生态与价值交换

当前主要提供“谁参与、谁拥有、谁缺什么、谁补贴、谁承担风险”等问题框架，尚缺：

- 多方激励可持续性；
- 补贴方向与交叉补贴稳定性；
- 冷启动和鸡蛋问题；
- 去中介/多归属/绕平台；
- 生态权力与规则控制；
- 价值交换矩阵的机器化表达和真实案例。

### 04 案例与行业地图

当前已经定义案例字段和 A/B/C/D 证据等级，这是好基础；但实际案例数量和行业地图深度明显不足。

这里的正确下一步不是机械堆 500 个公司简介，而是优先建立：

> **Benchmark 校准案例 + 能覆盖关键机制边界的反例/失败例 + 高证据案例。**

### 05 失败模式

已经覆盖需求、单位经济、供给生态、现金流资本、增长壁垒、治理风险等主类，但目前仍偏清单。

下一步应由 Benchmark 的真实失败驱动，把失败模式升级成：

> 失败症状 → 根因 → 可观察信号 → 容易误判的解释 → 需要的数据 → 修复动作 → Kill Condition。

# 四、下一阶段建设宇宙

不仅是 Workflow。真正缺少的是一组相互依赖的系统能力。

## P0：运行时与可验证闭环

### N01 Task Router

用户不是按 U01-U27 提问，而是按“我要解决什么”提问。

需要：

> 任务 → 任务族 → 跨切旗标 → 需要的域/Skill/数据/外部研究

### N02 Context Builder / Retrieval

不能默认全量加载 676 Atom + 200 Pattern + 所有 Markdown。

需要：

> Task Router → 一级域候选 → Atom → Pattern → Product Role（如适用）→ 专题/案例 → 真实经济层 → 必要时扩检索

目标是**最小充分上下文**，并记录漏召回率、Token/上下文成本和噪声。

### N03 End-to-End Commercial Reasoning Workflow

把已有局部 Skill 装配成一个真正的任务状态机，而不是再新增一组同义 Skill。

### N04 Real Data Gate + Evidence Gate

把：

- 事实；
- 项目数据；
- 假设；
- 派生计算；
- 分析判断；
- 未知；

强制分离。

缺真实参数时只能输出场景模型，不得伪精确。

### N05 Trace / Observability

这是此前容易遗漏、但对长期演进非常关键的一层。

每次运行至少记录：

- 路由结果；
- 加载域；
- Atom/Pattern/Role；
- 加载文档；
- 实际使用模块；
- 外部证据；
- 假设与未知；
- 候选方案；
- 错误分类；
- 上下文预算；
- 宇宙版本。

没有 Trace，就无法判断“知识不存在”还是“存在但没召回”。

### N06 Benchmark + A-E 对照

必须测试“宇宙有没有增加价值”，而不是“格式有没有满足”。

### N07 Ablation

逐个移除 Atom/Pattern/Product Role/机会来源/价值链/U19/Cohort/案例/外研/反方/实验，测真实下降。

### N08 Regression

每次知识、检索或 Workflow 修改后跑旧任务，不能只看新任务变好。

### N09 Error Taxonomy

至少使用：

- K1 Knowledge Gap
- R1 Retrieval Failure
- W1 Workflow Failure
- C1 Context Failure
- E1 Evidence Failure
- F1 Financial Failure
- S1 Strategy Failure
- T1 Tool Failure
- O1 Output Failure
- B1 Benchmark Failure

其中 **B1 Benchmark Failure** 是本轮新增的重要缺口：测试题本身也会坏，不能把坏 Benchmark 导致的失败归咎于知识系统。

### N10 Feedback + Knowledge Lifecycle

真实任务新发现不能直接变新 Atom。

先判断：已有机制？新组合？案例？证据？专题？短期规则？真正新机制？

并给长期知识对象增加：

> candidate → experimental → verified → stable → deprecated → superseded → historical

# 五、任务宇宙：不要为每个场景复制 Workflow

本轮把常见需求压缩为 8 个核心任务族：

1. **从0设计/重构商业模式**
2. **已有业务诊断与优化**
3. **定价、入口商品、商品组合与 Offer**
4. **利润、单位经济、现金流与条件性经济**
5. **平台、渠道、分销与多方生态**
6. **获客、增长、复购、留存与 LTV**
7. **价值链、上下游扩张、竞争与迁移**
8. **案例、行业、市场与竞品研究**

把下面这些做成**跨切旗标**，而不是独立复制完整 Workflow：

- AI Native；
- Knowledge Product；
- Enterprise/B2B；
- Rebate/Conditional Economics；
- Capacity/Perishable；
- Low-price/Free Entry。

因此：

> “AI 产品商业化”通常不是第 9 套完全独立工作流，而是某个核心任务族 + `ai_native` 旗标。

同理：

> “电子书”不是一套新的宇宙，而是核心任务族 + `knowledge_product` + 可能的 `low_price_entry`。

# 六、建设优先级

采用用户指定思想：

> **价值 × 缺口严重度 × 使用频率 × 对结果质量提升 × 依赖关系 ÷ 实施复杂度**

以下为 1-5 相对量表，只用于排序：

| 工作包 | 价值 | 缺口 | 频率 | 质量影响 | 依赖 | 复杂度 | 相对优先级 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Real Data / Evidence Gate | 5 | 5 | 5 | 5 | 5 | 3 | 1042 |
| End-to-End Workflow + Trace | 5 | 5 | 5 | 5 | 5 | 4 | 781 |
| Benchmark + Regression | 5 | 5 | 4 | 5 | 5 | 4 | 625 |
| Retrieval / Context Builder | 5 | 4 | 5 | 5 | 5 | 4 | 625 |
| Feedback / Lifecycle | 4 | 4 | 4 | 4 | 4 | 3 | 341 |
| 案例与证据校准集 | 4 | 5 | 4 | 4 | 3 | 5 | 192 |
| 价值链/生态深挖 | 4 | 4 | 4 | 4 | 3 | 4 | 192 |
| 继续大规模扩 Atom/Pattern | 2 | 2 | 3 | 2 | 2 | 4 | 12 |

**结论：当前应暂停“为扩而扩”的 Atom/Pattern 增长。**

新增本体的正确触发器应该是 Benchmark 反复出现的 K1，而不是“还能想到一个新名词”。

# 七、第一阶段最小完整闭环

本轮实施目标定为：

```text
现有 v4 本体
↓
Task Router
↓
Context / Retrieval Policy
↓
Commercial Reasoning Runtime
↓
Real Data / Evidence Gate
↓
T01 电子书 + T02 AI API
↓
确定性路由/召回测试
↓
A-E / Ablation 评测协议
↓
Regression
↓
错误分类 + Feedback Router
```

这比“一次把所有未来行业案例和 RAG 基础设施全部做完”更重要，因为它第一次建立了：

> **知识 → 使用 → 测试 → 找根因 → 修系统**

的闭环。

# 八、哪些内容值得继续研究

优先：

- 真实任务 Benchmark 数据集设计；
- 人类/模型评分一致性；
- 检索 Recall 与 Context Precision；
- 路由误判和多任务混合；
- 单位经济/Cohort/现金流计算器；
- 条件性经济证据与合同数据；
- 高证据真实案例；
- 价值链/生态/竞争反应深层协议；
- 时间敏感知识的 freshness/TTL；
- 对象级 provenance；
- Benchmark 质量审计。

暂缓：

- 为了数量扩到 U28+；
- 为了“看起来完整”机械扩 300/500 Pattern；
- 为每个行业复制一套本体；
- 为每个用户问题创建一条高度重复 Workflow；
- 没有 Benchmark 信号时做大规模向量数据库工程。

# 九、外部方法校准

本轮运行时/评测设计参考了以下公开方法，但仓库实现保持模型和供应商中立：

- OpenAI Evals：真实任务、可重复评测以及“指定 → 测量 → 改进”的评测循环；
- OpenAI 2026 年对 SWE-Bench Pro 的质量审计：说明 Benchmark 本身会出现过严测试、需求不充分、覆盖不足和误导性提示，因此新增 `B1 Benchmark Failure` 与测试题质量门；
- Anthropic Contextual Retrieval：说明大型知识库应考虑词法 + 语义召回、融合、重排和 top-K 上下文，而不是无限增加上下文；
- RAGAS 等 RAG 评测工作：提示检索质量和生成质量应分开衡量，避免“答案错了”时无法定位是 Retriever 还是 Generator。

参考：

- https://evals.openai.com/
- https://openai.com/index/separating-signal-from-noise-coding-evaluations/
- https://www.anthropic.com/engineering/contextual-retrieval
- https://arxiv.org/abs/2309.15217

# 十、本轮阶段性验收结论

1. **Workflow 应成为核心，但不是唯一核心。** 与它同级的重要层是 Retrieval、Data/Evidence Gate、Trace、Benchmark、Regression、Feedback/Lifecycle。
2. **当前最大风险不是知识数量不够，而是无法证明哪些知识真正改善结果。**
3. **电子书适合做 T01，但绝不能成为下一阶段唯一场景。**
4. **至少需要一个结构差异很大的 Canary。** 本轮选择 AI API 的 usage/commit/overage/企业后端作为 T02。
5. **A-E 数值提升必须通过真实隔离运行得到。** 在未运行前不填“宇宙提升 20 分”之类虚假数字。
6. **今后新增知识的主驱动应从“想到什么”转成“Benchmark 暴露什么”。**
