> 本文件记录 runtime-v1 第一次真正的“实施 → 测试 → 暴露缺陷 → 修复 → 再测试”闭环。

> 重要边界：这里的 `runtime_harness_score`、Asset Recall、Anchor Recall 都是**运行时/检索工程指标**，不是 A-E 商业答案质量分数。A-E 仍需独立模型 Runner、Judge/Human 和真实项目数据实际运行。

## T01 初始问题

- `U21-A05 Agent模式/Net`；
- `U18-A30 商业贿赂/个人回扣风险`；

- Cohort；
- Affiliate；

## 根因

分类为：

> **R1 Retrieval Failure + C1 Context Precision 风险。**

不是 K1。

知识实际上已经存在，但第一版 V0 只对短用户原句做字符重合，导致：

> “文档级 Context 100% 正确” ≠ “Atom/Pattern 级召回正确”。

这是本轮最重要的真实发现之一。

# 四、第二轮：Route-aware Query Expansion 提高词法信号，但仍未验收

第一次修复把 Retriever 改成：

```text
原始 Query
+ Task Family
+ 触发词
+ Flag
+ 已选 Knowledge Asset 名称
→ V0 Recall
```

结果 T01 的 Top-3 词法信号显著提高：

- Atom Top-3 Mean ≈ 0.221；
- Pattern Top-3 Mean ≈ 0.281。

但仍出现：

- T01 `API-as-a-Product`；
- T02 `Tournament Incentive`；

等语义噪声。

因此没有把“数值变高”视为修复完成。

## 根因进一步定位

> Query Expansion 太宽，通用文件名和通用词把候选空间带入了新的噪声。

这证明：

> **检索分数本身不是质量；Benchmark 必须知道“关键知识是否真的被召回”。**

# 七、首轮静态消融得到什么

当前消融只回答：

> “移除某类知识资产以后，Benchmark 所要求的上下文覆盖下降多少？”

它还不能回答：

> “最终商业答案掉多少分？”

## T01 静态 Coverage Ablation

- 移除 Product Role / Offer / Skill：Required Asset Recall 下降 **28.57 points**；
- 移除 Opportunity Lens：下降 **14.29 points**；
- 移除 Value Chain / Ecosystem：下降 **14.29 points**；
- 移除 Real/Conditional Economics：下降 **14.29 points**；
- 移除 E-book Topic：下降 **14.29 points**；
- 移除 Failure/Counterargument：下降 **14.29 points**。

## T02 静态 Coverage Ablation

- Product Role / Offer 与 Real Economics 都是高依赖资产组。

### 不能错误解读

这些不是“模块商业价值贡献分”。

例如 T01 Product Role/Offer 静态下降 28.57，只说明 T01 Gold Requirements 有 2 个必需资产来自该组，不代表最终答案一定下降 28.57 分。

真正的贡献必须在 D/E 输出上做 Answer-level Ablation。

# 九、当前仍然没有被验证的内容

必须明确：

## 9.1 A-E 商业答案提升尚未测量

目前不能声称：

```text
A = 70
B = 80
C = 88
D = 95
E = 97
```

这样的数字现在都是假的。

还缺：

- 隔离 Model Runner；
- A/B/C/D/E Context Builder；
- Output Archive；
- Deterministic Financial Checker；
- Model Judge；
- Human Calibration；
- 重复运行；
- 真实项目数据。

## 9.2 V0 Retriever 只是可测试基线

当前 `retrieval_concepts` + lexical scorer 的作用是：

> 建立无外部基础设施、稳定、可回归的 baseline。

还没有证明它优于：

- BM25 / FTS；
- Embedding；
- Hybrid；
- Reranker；
- Contextual Retrieval。

未来必须 A/B 测 Retriever，而不是凭技术先进感升级。

## 9.3 当前案例仍太少

T01/T02 只能证明两个结构分支。

还没有覆盖：

- Marketplace；
- 酒店/容量；
- 普通电商 SKU；
- 企业采购/返点；
- 线下服务；
- 知识库实施；
- 创作者。

## 9.4 02/03/04/05 的知识深度问题仍存在

本轮没有为了“顺手补内容”去机械扩这些目录。

应该让后续 Benchmark 先暴露：

> K1 / W1 / S1 到底集中在哪些缺口。

再按真实缺口深化。

# 十一、验收结论

本轮达成的是：

> **“商业模式知识本体 → 可运行、可调试、可回归的商业推理 Runtime 基线”。**

还没有达成的是：

> **“已经实证证明 D/E 商业答案比 A/B/C 高多少”。**

因此当前正确状态应写为：

```text
Ontology v4：稳定
Runtime-v1：第一阶段闭环可运行
Deterministic Regression：PASS
T01/T02 Retrieval Anchors：PASS
A-E Answer Quality：UNMEASURED
Real Project Outcome Validation：UNMEASURED
```

下一阶段不应回到“继续堆 Atom/Pattern”，而应继续推进：

> **A-E Runner → Answer-level Ablation → Retriever Tournament → 新结构 Canary → K/R/W/C/E/F/S/T/O/B 根因修复 → Regression。**
