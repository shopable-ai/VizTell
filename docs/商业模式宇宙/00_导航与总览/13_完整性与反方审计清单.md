# 完整性与反方审计清单

> 本清单同时检查**商业知识完整性**与**仓库结构完整性**。目录重构后不能只确认“文件看起来还在”，还要确认入口、ID、加载顺序、引用和机器资产仍然可解析。

## 一、仓库结构完整性审计

- 是否仍只有一个人类总入口：`../README.md`？
- `00_当前有效版本与加载入口.md` 的路径是否与 main 实际目录一致？
- `MANIFEST.md` 是否覆盖当前全部功能层和关键文件？
- U01-U27、P001-P200、PR01-PR40 的稳定 ID 是否未被重排？
- v2/v3/v4 是否仍采用增量关系，而不是互相覆盖？
- `08_机器数据与Schema/` 中 atoms、patterns、registry、product roles、Schema、Validation 是否齐全？
- Skill 是否加载当前目录中的真实文件，而不是已迁移的旧文件名？
- Markdown 内部引用是否仍指向现存路径？
- 旧目录迁移到新目录后，关键 blob/tree SHA 是否出现非预期变化？
- 人类阅读版与机器事实源是否都有明确主从关系，避免双事实源漂移？
- 专题文件是否进入 `09_专题商业模式/`，没有在根目录再次形成平行入口？
- 研究来源与历史快照是否留在 `90_研究来源与参考/`，没有被误当当前事实源？

结构调整后的机器校验基线见：

> `../08_机器数据与Schema/validation_v4.json`

## 二、商业知识完整性审计

- 是否遗漏参与者？
- 是否遗漏非付款受益者？
- 是否遗漏非货币资源？
- 是否遗漏第三方付款、补贴和多方支付？
- 是否遗漏资金流、账期、预付和资本结构？
- 是否遗漏风险、责任和治理权？
- 是否遗漏价值链位置变化？
- 是否遗漏行业特殊约束？
- 是否遗漏商业模式迁移？
- 是否遗漏 U19 返点、后台利益和 Net Effective Economics？
- 是否把 Front-end、Basket、True Cohort Contribution 分开？
- 是否遗漏商品角色、价格架构、Offer Graph 与 Context Router？
- 是否遗漏库存、容量、Breakage、公共激励、合同和劳动力经济？

## 三、正交性审计

- 是否把 SaaS、订阅、按席位、PLG 放在同一抽象层级？
- 是否存在大量同义词重复？
- 是否把渠道战术误当商业模式？
- 是否把案例名称当成模式类型？
- 是否把 Product、Product Role、Pricing Mechanism、Offer、Pattern、Business Model 混成同一个对象？
- 是否为了一个横向问题机械新增 U28+，而没有先检查现有 U01-U27？

## 四、反方审计

- 需求是否真实？
- 谁愿意付钱，为什么？
- 是否存在绕开平台或脱媒？
- 单位经济是否可能为负？
- 规模扩大后成本是否反而增加？
- 网络效应是否真实而非口号？
- 护城河是否可持续？
- 供应商为何愿意参与？
- 监管、合规、信用或履约风险由谁承担？
- 低价/免费入口是否只是在补贴原本会购买的人？
- 是否存在促销滥用、品牌稀释、渠道冲突、需求前置或容量冲击？
- 哪条证据可以直接推翻当前商业模式假设？

## 五、结构修改后的强制回读

每次移动、拆分、合并或重命名目录后至少重新读取并核对：

```text
README.md
→ MANIFEST.md
→ 00_导航与总览/00_当前有效版本与加载入口.md
→ 07_元数据知识图谱与Skill/02_v4_Skill机器加载与Offer决策协议.md
→ 08_机器数据与Schema/validation_v4.json
→ 08_机器数据与Schema/business_model_signature_v4.schema.json
```

如果发生以下任一情况，不得宣称结构调整完成：

- 必需文件 404；
- 旧路径仍作为当前加载入口；
- Schema/Validation/Skill 的路径与 README 不一致；
- 关键 ID 重排；
- 机器文件数量或范围与当前版本口径不一致；
- 文件已移动但内部引用未更新；
- 只验证 commit 成功，没有回读 main。
