### 2.1 通用变化坐标不是新的因素领域

任何因素族都可按对象/层级、角色/边界、场景/环境、时间/状态、规模/频率、正常/异常/恢复、变化/版本深入。这些是已有[十坐标](../思维与方法宇宙/03_跨宇宙多维推理与节点续研协议.md)与[链路八母维/30维](../通用链路宇宙/19_链路垂直深挖与审计框架.md)的阅读应用，不另起坐标协议。比如设备数从1到2再到大量设备，可能使同步架构、并发规则、运营容量、授权与证据范围同时变化；不能仅把“规模”归 F4 或 F8 然后认为已审查全部影响。

领域层（查哪些问题）→ 因素族（关注什么变量）→ 特定对象的因素与取值（什么条件实际改变决定）→ 机制/规则/证据（为什么、怎样验证）。需求、功能、架构等具体模型和推理方法引用原专题，不要求每个因素都建立新文件。

## 3. 两张地图怎样互相使用

L1–L8 是 [08 链路地图](../通用链路宇宙/08_软件IT与AI原生.md#r2-chain-map) 的生命周期阅读分组。默认优先因素与条件触发因任务调整；未列项不代表无关。F9/F10 不作为每次必须生成的额外材料，分别在授权、交接、共享资源、决策及基线/完成声明等变化时触发。

| 链路 | 默认优先查 | 触发时补查 | 会改变的决定 |
| --- | --- | --- | --- |
| L1 机会与价值 | F1/2/6/8/10 | F3/4/5/7/9 | 需求弱、替代已足够 → 暂缓；价值高但未知 → 最小试验 |
| L2 目标与需求 | F1/2/3/9/10 | F4/5/6/7/8 | 受影响者、决定权或规则条件不同 → 补必要需求/判据，排伪需求 |
| L3 产品与方案 | F1/3/4/5/7 | F2/6/8/9/10 | 小屏/无UI、离线或权限条件不同 → 调整交互/接口，不强制同一方案 |
| L4 技术与计划 | F3/4/5/6/7/8 | F1/2/9/10 | 平台能力缺口、共享owner不明或竞态 → 先验证机制和依赖 |
| L5 开发与集成 | F4/5/6/7/9/10 | F1/2/3/8 | 共享模块影响其他消费者 → 复用并补回归，防并发覆盖 |
| L6 验收与发布 | F4/5/7/8/9/10 | F1/2/3/6 | 候选与正式包不同 → 只接受与身份、环境、用途对应的证据 |
| L7 使用与价值 | F1/2/3/8/10 | F4/5/6/7/9 | 安装量不等于有效使用；结果差或成本过高回采用/需求/价值链 |
| L8 运营与演化 | F4/5/6/7/8/9/10 | F1/2/3 | API变化、事故、升级或退出 → 最小修复、恢复、迁移与验证 |

**反向使用**：变化的因素 → 受影响的业务/工程对象及依赖 → 需要重审的链路 → 最小修正与证据。F5 状态由“确认失败”变成“结果未知”，会影响 L3 的反馈、L4 的副作用/重试设计、L5 的实现、L6 的异常验收和 L8 的恢复；F9 写入责任转移只重审相关接口与交接，不重做全部需求；F10 候选/正式包身份变化影响发布证明，不自动表示业务发生变化。

### 3.1 怎样把地图转为有用的需求判断

从业务/用户链和系统运行链找真实成功点，而非从因素名称机械生成需求：

> 目标结果 → 当前业务/运行步骤 → 找到能改变结果的因素 → 比较正常与变化/异常条件 → 推导必要业务行为或验证义务 → 区分候选实现与必需结果 → 最小证据。

例如云同步中 F5“两个设备同时修改同一规则”让单设备覆盖策略失效；候选必要行为是防静默丢失并有冲突处理，CAS/版本号/具体合并算法是可比较的实现，不自动都成为需求。对 L2 形成条件需求、L3/L4 形成取舍、L6 形成两设备同记录冲突的真实判据。若仅一台设备且不涉及同步，相关规则不强加。

F7 与 F10 特别需要分开：验收中的“确认对应版本、真实对象和实际用户结果”不必成为产品运行时新增回执或数据采集功能。F9 的独立评审/审批义务也不自动变成产品面向用户的审批页面。

每轮只记录：当前问题/链路 → 适用因素及现值/未知 → 改变什么需求/方案/验收决定 → 最小证据。新增项应指出不处理会怎样影响原目标；若只有分类名称变化、无实际决定差异，合并、暂缓或引用既有资产。以上为用法提示，沿用[需求推理](需求推理与需求工程/README.md)、[盲区审计](推理与盲区审计/README.md)、[跨域索引](../02_跨宇宙因素与关系索引.md)和[深挖框架](../通用链路宇宙/19_链路垂直深挖与审计框架.md)，不是新协议。

### 4.2 纵向：从一个因素深入到必要规则和验证

连播助手——视频总时长 D。[需求 K0/K1/F3](https://github.com/shopable-ai/opendesk-browser/blob/e351c1e9bb4dd84b38d3554c118edb6711a09baf/projects/video-auto-skip/REQUIREMENTS.zh-CN.md)，blob 00745575334e1121398b0b26f65a1a92cd6e752d。

F5 当前视频时长 → 未加载/有效有限值/无效或直播/换源过期 → 判断规则适用性（F3/F4）→ 片尾保存相对 N，实际开始 D−N；未知或不合法不执行 → 真实新视频重算并确认跳转（F7）。

- 已有例子：45:00、最后90秒得43:30；48:00重新算46:30。相同时长不证明作品身份或规则兼容。
- 已有 K0 优先：核心视频控制不必先识别作品；K3/K4 是增强。换源、时长变化、原生连播竞争及 UNKNOWN 均已有要求，不能为本轮声称新发现或要求新增 AI 识别。
- 本轮提出的验证视角：只在相应真实视频/规则身份中比较 D 变化、有效与未知条件，核对跳过或安全不跳的结果；实现验收仍属于 OpenDesk。

这说明因素纵向深入不是多列形容词，而是找出条件变化导致的不同业务行为和验证义务。

### 4.5 横向结论：保留、拆分、补足、不升格

- **保留**：F2–F8 的核心问题族、C01–C30、L1–8、原17条专项子链及三个历史案例。以上12个观察点均能在R2的宽泛分类找到落点，不宣称R2完全未覆盖；欠缺主要是直接入口、对象边界与可观察结果链。
- **拆分**：F6中的权责/协作主路由到F9、知识缺口到F10；F7中证据充分性主路由到F10；F5运行数据与F10工程认识分开；F1扩大到所有重要利益相关方。
- **补足**：08 明确五种链路视角，新增8项高价值跨链导航，优先复用T04责任授权、T05证据/追溯/合规、T09变更控制、T11授权监督、T14恢复/迁移。不是C31–C38，也不是新增通用链定义。

### 4.6 从四个案例提取可复用的因素—链路关系（局部纵向示范）

不是再复述案例，而是判断哪些共同考虑项会改变决策。以下是**两个领域因素候选及条件关系**，暂不另分配 VZF ID；与 024/026/029/030/059 等既有因素有关系，尚未证明其跨领域独立性或普遍因果性。

| 对照对象 | 要确认的身份/作用范围（F5/F9） | 成功须确认的不同结果（F3/F10） |
| --- | --- | --- |
| [Web Flow][wf] | 当前会话、文档、安装身份、授权、候选与Run对应 | 任务真实执行、结果持久化、交付原会话、资源释放各自确认 |
| [云同步][cloud] | 账户、产品、设备/记录、同意与记录版本 | 本地保存成功、云端接受、另一设备读回是不同结果；设计尚未实测 |
| [AI New Chat][chat] | 目标项目与新标签身份、原对话范围 | 新tab打开、空composer、用户主动发送后正确归属、原对话未受影响 |
| [Kubernetes Deployment][k8s] | 目标Deployment、目标版本及对应工作负载 | rollout完成、后续可用性及产品真实用途是不同判定 |

共同判断一：**对象与授权范围是否吻合**。即使输出形式正确，如果实际对象错误，目标仍不成立。对象身份未知或授权不成立时，只允许既有授权范围内的安全核查，不猜测执行目标。身份校验能否简化取决于业务风险；并不要求所有软件都增加独立身份服务。

共同判断二：**当前证据能确认哪一级结果**。只有动作请求/ACK，不能据此宣称目标实现；当外部副作用已可能发生、结果却未知，且重复可能造成损失时，优先对账，不自动重放。对于本就可安全重复、已证明幂等或无副作用的操作，按现有策略重试即可，不普遍引入持久账本、跨窗口回执或新的状态机。

相互关系是：真实目标 → 确定目标对象/权限 → 按业务步骤执行 → 观察与该身份对应的真实结果 → 依据证据确认或保留未知。研发侧只在验收要求涉及的层次验证，不把每个QA观察点硬变成产品功能。链路路由：原接口/自动化链、外部副作用与结果对账、T05证据/追溯、C29异常恢复。此结论比记住四个不同产品的历史测试更便于在下一项目中重新检索和推理；没有真实独立应用结果，不宣称已经证明迁移价值。

### 4.7 规模与范围变化：同一个因素可能引出完全不同的链路

以[云同步现有设计][cloud]与[工作流记录][cloud-work]为依据，区分用户数量、设备数量、产品消费者数量，不能把“规模”混为一个指标：

| 条件变化 | 需要重新考虑的因素 | 可能新增或改变的链路/义务 |
| --- | --- | --- |
| 仅本地单设备 → 同一账户两设备 | F3本地可用与同步范围、F5并发/离线、F7数据丢失 | 同意、同步、冲突和删除恢复；实际两设备读回 |
| 单一账户 → 多账户/设备撤销 | F5数据分区、F7泄露、F9授权范围 | 冻结旧队列、隔离账户、撤权与受控清理；不得串账户 |
| 一个产品样板 → 两个独立产品接入 | F4共享能力与适配器耦合、F9责任、F10证明范围 | 共享契约与第二消费者验收；首个样板通过不证明公共平台完成 |
| 小量验证 → 大量用户/记录（未来条件，非已发生事实） | F2成本、F4容量/依赖、F6预算、F7可靠性、F8环境、F9运营职责 | 按实际负载验证配额/监测/支持/恢复和成本；未测阈值前不指定分库、集群或新商业功能 |

这不是强制的项目成熟度阶段，而是沿用19“规模跃迁”和十坐标的方法，说明**因素值的变化为何可能要求改变链路结构**。一般情况下优先研究会影响当前目标的那一项；当条件不存在时，允许不适用。表中的工程义务仍以产品设计或经批准的需求为准，未执行云服务、真实双设备或大规模测试。
