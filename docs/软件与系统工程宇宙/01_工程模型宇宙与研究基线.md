# 工程模型宇宙与研究基线 R1-A

> 原始任务 AI-NATIVE-ENGINEERING-MODEL-UNIVERSE-R1，研究日期 2026-11-26。此文件是对本轮对话研究结论的语义整理，不是逐字聊天转录。所有新分类、规则和元模型仍为候选。目录定义与参考资料的细节只引用 [02](02_工程模型目录与定义卡.md)，研究缺口和评分只维护在 [90](90_研究缺口与续研任务.md)。

## 1. 原始目标、边界与研究原则

- 从原始想法到需求、产品、架构、开发、测试、验收、运营及演化的工程知识，应可读、可验证、可追溯、可计算；解决多个 Agent、对话、设备间的信息遗漏、冲突和目标漂移。
- 工程模型回答项目中有哪些知识、约束与关系；角色体系回答谁判断和负责；工作流回答何时做与怎样推进；Skills 回答如何操作。四者互相提供输入输出契约，不相互替代。
- F01 关系不局限于树或 DAG；F02 区分模型、视图、文档、图表、格式；F03 同一事实应有明确权威来源；F04 分离实现、验证、证据有效性、验收；F05 统一语义不等于统一存储。
- 理论来源：SEBoK/INCOSE、MBSE、MDE/MDA、SysML v2/KerML、ISO 29148/42010/15288/12207/25010、NASA SE Handbook、GORE/KAOS/iStar、DDD、FODA、BPMN/DMN、ArchiMate、C4、ADR、W3C PROV/RDF/OWL/SHACL、SACM、Ecore/EMF、Capella/Arcadia、OSLC、ReqIF、KDM、OCL、Epsilon、Digital Thread、SLSA 等；适用性和局限见 [02 参考索引](02_工程模型目录与定义卡.md)。主要为官方公开简介、规范索引及相关说明，不等于完整标准正文合规审查。正式采用前核验版本、规范条款和适用范围。

## 2. 概念纠偏与候选分类

Entity 是具身份的对象；Relation 是有语义的联系；Model 是围绕关注点的结构化表达；Metamodel 定义类型、属性、关系和约束；Viewpoint 定义观察关注点和表达约定；View 为具体对象按视点组织的表达；Diagram 为可视化表达；Modeling Language 为语法和语义体系；Document 为信息载体；Artifact 为工程活动产生或使用的产物；Evidence 为支持或反驳具体主张的材料；Knowledge Instance 是具体项目中的知识记录。

| 原种子 | 候选修正与原因 |
| --- | --- |
| Goal Tree | Goal and Value Model：存在多目标贡献、替代与冲突 |
| Requirement Tree | Requirement Model：依赖和约束不局限于分解 |
| Feature Tree | Capability and Feature Model：多对多实现、变体约束 |
| Scenario Tree | Scenario and Use Case Model：状态、事件、分支、循环 |
| User Journey | User Journey and Service Experience Model：体验关注点而非完整 UI 模型 |
| UI Tree | Interaction and Information Architecture Model：导航、状态、反馈 |
| Architecture Graph | Architecture Structure and Allocation、Runtime Collaboration、Deployment 等关注点 |
| Data Model | Data Structure and Lifecycle：所有权、流转、版本、迁移 |
| Task DAG | Engineering Task and Resource Plan：可调度依赖可为 DAG，但不是整个知识关系网 |
| Test Matrix | Verification and Validation Specification：矩阵是视图、测试不是唯一验证方法 |
| Evidence Graph | Verification Execution and Evidence + Assurance：运行、证据、论证、验收分离 |

初步 13 个领域 / 32 种候选类型，完整 ID、卡片和典型上游下游只在 [02](02_工程模型目录与定义卡.md) 维护。重点遗漏：问题、质量、约束、业务规则、状态、领域、接口、实现事实、变体、决策、基线、保障论证及演化。候选类型不等于对象类型、数据库表、文件或强制交付物，需进一步拆合及裁剪验证。

## 3. 关系候选与追溯

下列是 R1-A 讨论用语义示例，并非可直接纳入 AI-Project-OS 的关系 allowlist；方向、端点类型、基数、逆关系、传递性、条件与版本适用性尚待定义。

| Problem | affects | Stakeholder |

典型追溯路径：Problem → Goal → Requirement → Feature/Scenario/BusinessRule → Component/Interface/Data/State → Implementation；Requirement → Verification Obligation → TestCase → TestRun → Evidence → Claim → Acceptance。箭头仅表示导航，不等同于上述关系方向。历史证据本身不因新版本被删除；变化影响的是证据对新基线的适用性。implements 不等于 verified，supports 不等于 proves。反馈回路合法，特定执行依赖才需防阻塞循环。

## 4. 元模型与存储候选

四层概念：L3 元元模型（Type/Property/RelationshipType）；L2 工程元模型；L1 具体项目知识；L0 现实对象与运行事实。此处 L0–L3 为建模抽象层，不等于 AI-Project-OS 仓库分层。

统一语义核心：Identity、Type System、Assertion、Provenance、Scope、Revision、Baseline、Authority、Validation、Applicability。独立表达观察事实、假设、推断、未知，以及审批、实现、验证和证据适用状态。用户批准业务规则不意味着外部世界假设已经被证实。

| 候选方案 | 优势 | 风险 |
| --- | --- | --- |
| 多文件独立模型 | Git 友好 | 同一事实重复 |
| 单一统一模型 | 全局查询、校验 | 过重、领域冲突 |
| 多视图模型 | 减少重复、服务多角色 | 派生维护成本 |
| 联邦式模型 | 各领域保留权威 | 身份与映射成本 |
| 知识图谱 | 关系查询与追溯 | 图结构不保证语义正确 |

优先研究：轻量共享语义核心 + 分领域权威模型 + 派生视图。Markdown/YAML/JSON/数据库/图数据库/形式化语言仍是备选，不得从文件格式推导语义。区分人类可读、AI 可读、机器可验证、机器可执行四层；保留用户意图、风险接受、验收等权威决策边界。

## 5. 最小充分模型集合（待验证）

| 类型 | 建议最小知识覆盖 |
| --- | --- |
| 小型功能修改 | 目标、变更需求、相关场景、实现位置、验证义务、证据、基线 |
| Bug 修复 | 问题、复现、根因事实/假设、规则、修复位置、回归 |
| 单功能扩展 | 目标、需求、范围、功能、场景、交互、规则、权限、架构、验证 |
| 中型软件 | 加领域、数据、接口、状态、风险、决策及版本 |
| 复杂系统 | 加运行协作、配置变体、部署、资源、跨模块约束 |
| 高可靠性系统 | 深化威胁、危害、保障论证、独立验证、证据 |
| 持续迭代 | 基线、变更影响、实现事实、历史证据、迁移回归 |

裁剪依据是工程知识充分性，而非文档数量。条件启用应由复杂度、接口、风险、数据及变化范围决定；尚未测量维护成本或证明最小性。

## 6. AI 管理与一致性候选

V01 ID 唯一稳定；V02 端点存在且类型合法；V03 批准需求有来源及验证义务；V04 新功能有依据或批准理由；V05 实现依赖满足批准架构约束；V06 规则冲突或优先级未知不得宣称正确；V07 已实现需求可定位；V08 验收主张关联适用版本证据及论证；V09 不静默覆盖批准知识；V10 证据对新基线失效则重评验收；V11 保留人工/AI 冲突记录；V12 外部事实不足标记未知。以上为候选规则，不是已经实现的检查器。

与工作流交换阶段、活动、完成条件 ↔ 基线、知识缺口、验证义务、阻塞；与角色体系交换身份、权限、专业责任 ↔ 审查对象、冲突和决策；与 Skills 交换输入输出契约和执行回执 ↔ 操作对象、范围和约束；与运行环境交换源码、版本、构建及结果 ↔ 实现目标、影响文件候选、测试范围。
