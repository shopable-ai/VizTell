## 3. 关系对齐（13种旧边+3种旧组）

现行 allowlist 包含 derives_from、governed_by、implements、consumes、produces、produced_by、reviewed_by、identifies_gap_in、verified_by、authorized_by、approved_by、bound_by_baseline、context_bound_by、checkpoint_of、resumes_from、attempt_of、invalidates、supersedes、requests_review_of。正式端点、方向和传播由现行契约及工程元模型 R1-B 核定，不在此新增枚举。

| 旧关系 | 处理 |
|---|---|
| DERIVED_FROM | 候选对应 derives_from；正式合法端点及来源批准不可跳过 |
| DEPENDS_ON | Task/Spec依赖字段、消费/产生关系；不默认同义 |
| CONFLICTS_WITH | 局部冲突记录/Unknown/研究候选；未注册不得写入全局关系 |
| SATISFIES | 领域功能满足需求的候选映射；按现行 Function/Capability/Requirement/Spec 语义追溯，不强改为 implements |
| EXERCISES | 场景→需求 derives_from 或局部覆盖，核对方向及语义 |
| VERIFIED_BY | 同名不等价；先核实现行判据/证据的合法端点，禁止将判据当 PASS |
| CHECKS_SCENARIO | 判据与行为/场景覆盖的局部映射，不注册全局边 |
| IMPLEMENTED_BY | 正式 Task implements Spec；不能直接把 Feature→Task 升格 |
| CONSTRAINS | requirement/治理/授权引用，按 scope 和正式端点裁剪 |
| OBSTRUCTS | 局部异常、未知、研究，非全局枚举 |
| ADDRESSES | 研究/ADR候选选项和需求/Unknown 映射 |
| RESOLVES | 研究→合法裁决→新事实/需求/ADR；选择不等于授权 |
| SUPPORTED_BY | 不能简化独立 Run/Evidence/Verdict；使用正式引用及证据适用性 |
| AND / OR / XOR | 目标分解/替代方案的研究逻辑组，不是三种正式关系；需要端点/基数/条件/选择与必要充分性论证，交 R1-B |

反向必须复用正式 approved_by、bound_by_baseline、context_bound_by、invalidates、supersedes、requests_review_of、produced_by、authorized_by 等权限/版本/运行语义；原实验缺失不表示现有 L1 有缺口。关系传播、命名域及正式改动由工程模型 R1-B 处理，未经批准不修改 allowlist。

## 6. R3 增量：机制独立性与最小充分候选（未做消融）
对固定版本正式工作流、功能卡、需求基线模板、受控对象模型、requirement-design-package-contract、ARTIFACTS_AND_TRACEABILITY 重新定向读取。现有工作流已经明确四段意图、业务状态的正常/异常/恢复、需求→场景→链路→能力→功能、独立审核、决策门及不可变基线；不能把它刻意弱化为“仅写需求树”作为A组。

| 九算子 | R3工作组 | 独立价值假设/相邻重叠 | 裁剪触发（候选） |
|---|---|---|---|
| DECOMPOSE | 理解与展开 | 父目标的必要条件；与REVERSE前提重叠 | 简单单一义务不强制建树 |
| EXPAND | 理解与展开 | 对象/角色/场景覆盖，防单视角 | 多角色、环境差异、权限边界触发 |
| JOURNEY | 理解与展开 | 跨状态/时序/恢复；EXPAND静态覆盖不等于有状态 | 有跨状态、数据生命周期或交接才深入 |
| REVERSE | 反推与发现 | 从可观察成功回推必要前提；与DECOMPOSE互补非等价 | 高风险、未知成功条件必用 |
| DISCOVER | 反推与发现 | 发现是推理结果，未证明独立算法；与EXPAND/JOURNEY/REVERSE/OBSTACLE高度重叠 | 不强制单独一遍，保留可测试算子 |
| OBSTACLE | 质疑与补漏 | 错对象、失败、未知、恢复及滥用 | 核心风险必查，不穷举无关环境 |
| DEPENDENCY | 质疑与补漏 | 区分硬依赖/可选前提；反推可能遗漏错误前置 | 有依赖、异步、授权/版本时深入 |
| CONFLICT | 质疑与补漏 | 目标/角色/规则不可同时满足，需合法决策 | 竞争目标、权限或状态冲突时深入 |
| PRUNE_VERIFY | 裁剪与收敛 | 去重、必要性、验收可见性、未决前沿；不等于批准或验收 | 所有候选均检查，按风险投入 |

最小充分候选输入：原话/稳定引用、当前合法阶段及范围、已知事实、未知、实际版本。输出：在现行功能需求卡及其上游对象中生成可追溯的候选差量（问题/目标、场景/链路、能力/功能、单义务、必要性、失败/风险、验收方向），非目标/待决/停止原因引用原有权威。无需新JSON本体、新项目状态机、每个需求九遍遍历、每项目生成全部图或自动批准。低风险单义务可一次检查；高风险触发对应机制；停止仅表示在给定预算及已知边界内无更多候选，不证明完整。硬未知交现有Unknown与Decision Gate；影响、角色冲突及独立判断沿用既有治理。角色宇宙通过 actor/owner/approver/verifier 与各角色场景/独立审查衔接，尚未核验独立角色专题交付，不自创注册。工程模型宇宙 R1-B 已提交 05/06，候选端点/证据/传播交其后续R1-C；引用 [父专题90](../90_研究缺口与续研任务.md)，不改其阶段。

四组仅是组织和触发方式，九机制没有被实验性否定或删除。A/B 只能检验整体增益；需要 C 与单算子消融才回答独立价值。见 [03](03_R3_盲测规格与冻结基准.md)。旧结构反例的实际证据见 [04](04_R3_检查器反例与复跑.md)；其中C04/C05/C06/C11等属于正式关系、证据和合法裁决的已知边界，不是新L1议案。
