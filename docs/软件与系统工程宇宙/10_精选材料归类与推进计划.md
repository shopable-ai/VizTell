## 3. 已作出的概念纠正

| 原表达/隐患 | 采用的修正 | 为什么会影响使用 |
| --- | --- | --- |
| 工程模型≈工程知识 | 模型是对当前项目某方面的可检查表达；模型目录是可复用知识 | 知道模型名称不等于了解当前系统 |
| “已批准事实” | 有来源的事实、已核验事实、假设和未知项；需求与决策另行批准 | 批准不能使一个未经证实的断言变真 |
| 从目标推导需求叫“正向” | 正向：条件/动作推结果；逆向：由目标或失败反推条件/原因 | 避免不同文档以同一词表达相反操作 |
| Spec → Task → Workflow → Skill/Tool作为时序 | Workflow组织过程；任务调用适用能力与工具；Spec约束相关工作 | 工作流并非任务创建后的最后一步 |
| 研究只在设计前；测试只在编码后 | 研究随关键未知触发；验收方向前置，实际证据随后形成 | 避免设计结束才发现需求无法证明 |
| 四组、13模式、八领域是一套分类 | 四组为操作归组，13模式为分析工具，八领域为检查范围 | 不要求一一对应或做全组合 |
| 核心模型=必建模型文件 | 必要语义要清楚；表达与文件数量按任务选择 | 防止小修改也产生大量文档 |
| 所有研究维度都是P0 | 优先处理当前决定的阻断项、真实遗漏和高影响风险 | “都优先”无法组织执行 |
| 每阶段都必须再次人工确认 | 遵循已有授权与适用决策规则；有实质歧义或越界时再确认 | 保留必要决策，不重复取得同一授权 |
| 有Skill/Agent名称=存在执行能力 | 区分目录建议、规范/模板、实际实现与验证结果 | 防止把规划写成已完成系统 |
| 多专家一致=正确 | 审阅产生待核查发现；事实和产品结果仍需对应证据 | 独立Agent也可能共享错误假设 |
| 静态示例或高分=方法有效 | 分开评价文档质量、独立使用效果和实际产品验收 | 便于真实接续，避免过早结束 |

本文件没有改变现有工程框架的协议、权限规则或状态机；这里是在澄清摘录的阅读与使用方式。各专项中旧版本的阶段叙述须结合其当前状态说明阅读。

## 4. 三张可试用的方法卡

这些卡把已有方法压缩成可以试用的操作说明，仍为候选。它们属于三个方向的阅读用法，不是已注册Skill，也不是新的机器契约。

### 方法1：从已有资料恢复事实，再选择必要模型

- **何时用：** 存量项目开始新任务，或者文档、代码、运行记录互相矛盾。
- **输入：** 原始目标；当前任务范围；仓库/版本；已有需求、真实入口、相关代码和测试/运行资料。
- **操作：** 先写本次要作的决定；沿入口找到实际行为与消费者；分别核对期望、实现和运行证明。缺行为条件时补规则/状态表达，缺数据责任时补数据表达，缺完成依据时补证据对应表。
- **输出：** “要决定什么—事实及来源—缺口—复用/修改/新增/待确认—验证办法”。可写入已有任务或需求文档。
- **停止条件：** 当前决定所需信息已足够，关键冲突已处置，未解决项的影响已说明；缺关键来源时保留阻断，不能把资料缺失当作不适用。
- **何时不用扩大：** 既有表达足以支持决定时，不重画完整架构或重做模型目录。
- **维护位置：** [工程模型README](README.md#当前使用方法r1-b2先决定再选择知识)。R1-B.2方法的独立价值验证已登记为R1-B.3，尚缺独立结果。

### 方法2：按场景反推必要条件，再裁掉无效扩张

- **何时用：** 用户只给出想法、局部功能或一个现象，正常/异常行为仍不清楚。
- **输入：** 原话、目标、相关使用者、现状事实、约束和本轮范围。
- **操作：** 写一条完整成功路径；从成功结果反推必要条件；检查取消、重复、失败、恢复等适用分支；只对存在专业分歧的问题加入相应专家视角。将每个发现分为明确要求、必要条件、候选方案或待验证假设。
- **输出：** 需求差量、理由、反例、验收方向，以及保留/延期/删除/待验证决定。每项说明它改变了哪一项需求、设计或测试。
- **停止条件：** 当前范围的关键成功/失败条件可以观察；重复项与无必要性项已处理；阻断未知明确，不用“需求已完整”掩盖未知。
- **何时不用扩大：** 不为增加条目而引入云同步、商业化或所有专家；无有效新增可以返回空差量。
- **维护位置：** [需求推理](需求推理与需求工程/README.md)、[角色协作](角色与多专家协作/README.md)、[盲区审计](推理与盲区审计/README.md)，各自维护独有内容。

### 方法3：核对完成声明能被哪些证据支持

- **何时用：** 准备声称实现、修复、发布或验收完成，或准备沿用历史测试结果。
- **输入：** 本次范围和事前判据、候选版本、适用环境、实际执行记录。
- **操作：** 为每个重要声明找到对应证据；核对版本、输入、预期和实际结果；区分源码存在、静态检查、局部测试、真实业务运行。对失败和结果未知分别记录，不把未执行写成通过。
- **输出：** “声明—判据—证据—适用范围—结论/缺口”及必要的后续动作。
- **停止条件：** 对当前声明已具备足够证据，或准确报告剩余阻断；只为具体风险补测，不无限扩展检查。
- **何时不用扩大：** 有效旧证据在版本与影响范围上仍适用时可以引用；简单可逆文档修改不需要产品全套验收。
- **维护位置：** [工作流与工程能力关系](07_研发工作流与工程能力关系.md)，正式消费者继续采用既有工程框架；实际产品记录写回对应产品任务。

## 5. 三个推进方向：分别解决什么、怎样汇合

### 方向一：总体框架与工程模型

**独有问题：** 执行者能否从原始目标和现有资产，找到足以支持工程决定的信息？

本轮完成共同入口、材料去向与候选方法1。提交前最新仓库已登记R1-B.3：Cookie Editor同站子路径变化的独立价值验证。**下一项具体产物是按该登记准备允许的固定输入资料包、核对隔离条件，并保存独立首次输出、读取路径、实际成本与审阅结果。** 结果继续回写已有09实验登记及90，不重新选择案例、不增加理论研究任务。完成条件是可核查的使用过程、正确/错误判断、遗漏与成本；登记完成不代表实验完成，环境阻断也不证明方法无效。

### 方向二：需求发现与多角色审查

**独有问题：** 方法带来了哪些必要发现，又产生了哪些错误要求或过度设计？

本轮完成职责归类与候选方法2。下一步使用相同输入，让参与者交付可归因的需求差量、理由、反例和取舍。需求推理的正式效果验证继续使用已登记R3.2；角色和盲区专题补充自身独有发现，不另建第二套36槽实验。完成条件包含有效增量与误报，允许没有改进，不能只展示更长答案。

### 方向三：执行、验收与经验复用

**独有问题：** 前两个方向产生的信息能否被真实下游用于设计、执行、验证和后续接续？

本轮完成能力边界整理与候选方法3。下一步从已有产品任务中明确实际消费者，观察其能否理解输入、形成必要差量并按事前判据验证。仅本轮研究授权不足以把示例自动升级为产品改动指令。完成条件为实际输入输出与运行证明，失败则记录断在哪个环节。对重复发生、已有价值证据的局部步骤，才提出最小自动化接入建议。

### 共同接续纪律

1. 共用原始目标、固定版本、范围和已有结论；各方向只提交自己的新增发现及其影响。
2. 基线先固定，判断和实现可以按依赖并行；任何一方不重复重写完整研发体系。
3. 演示案例可以用已知问题解释方法；效果评测按已登记实验隔离资料与答案。本轮参与素材分析的Agent评审不能充当独立盲测，三个研究方向的共同讨论也不能改变既有A/B组的输入、方法差量或判据。
4. 使用既有任务ID和当前入口。发现旧文“下一步”与当前入口冲突，优先恢复最新有效状态并注明冲突，不能直接重跑旧任务。
5. 每轮接续只需写：原始目标、本轮范围、已完成及证据、未完成/未知、下一项具体产物和完成条件。无需每次重发整套研究提示词。

## 6. 示例：一条反馈怎样转为不同性质的材料

来源为本会话提供的项目历史摘录：“网页剪藏功能优化”，2026-11-26。这里仅使用用户报告与构想；未取得完整复现记录、当前源码和实测结果，不确定根因。

| 材料 | 归类 | 下一步应获得的结果 |
| --- | --- | --- |
| 小区域有时难以选中，有时又正常 | 用户报告的问题现象 | 复现页面、操作、预期与实际选区 |
| 连续选择多个区域加入现有输入框 | 目标/候选行为需求 | 明确追加对象、顺序与原内容保留规则 |
| Ctrl加点击、上方/左方入口、变蓝 | 交互构想 | 与平台行为和现有交互核对后选择方案 |
| 提示浮层可能挡住目标 | 待验证原因假设 | 能区分此原因与其他原因的观察/测试 |

## 7. 保存位置判断

### 为什么继续放在“软件与系统工程宇宙”
