# 模型分类纠偏与收敛方案 R1-A.2

> 2026-11-26；候选研究，未批准。固定输入：VizTell 3ac3bdefae7c8bfccbacd936ef9e4a2009c47929，AI-Project-OS 1a1867640b7ee538bac21cd1a16d50f6a7e19c0f。证据和逐项差异只维护于[03](03_已有工程模型与双向差异矩阵.md)，旧定义卡只维护于[02](02_工程模型目录与定义卡.md)，本文件是增量分类/迁移决策候选，而非替换全部历史卡片或正式契约。

## 1. 结论与选型

不是从32个卡片生成32个内核对象，也不是从42个现有受控对象生成42个知识模型。不同模型可以引用同一个受控对象，一类模型可以跨多种对象、关系、项目事实、工件及外部引用。正式关系和字段仍以 AI-Project-OS 固定版本及经批准的后续版本为准。

候选方案比较（定性，非独立评分）：

| 方案 | 结果 | 反例与取舍 |
|---|---|---|
| A：每个知识模型一份独立可编辑工件/内核对象 | 拒绝 | 目标和功能需求重复身份、证据重复、维护随项目数增长 |
| B：统一语义协议 + 领域权威 + 可追溯派生视图 | 推荐待验证 | 保留薄内核、领域可扩展，必须验证身份/关系映射、局部命名域、源数据与派生一致性 |
| C：仅保留当前L1受控对象，不保留领域知识模型 | 拒绝 | UI焦点、真实业务状态、数据保留、产品变体、利益冲突等无法从L1通用字段推导 |
| D：统一图数据库或建模框架承载所有语义 | 暂不选型 | 查询便利不等于语义正确，缺少迁移、成本、两类真实项目验证；触犯当前薄内核边界 |

推荐B没有修改L1，不要求新增运行时或数据库。已存在的六个薄内核原语保持不变。新增知识关注点仅说明AI需要理解什么，不能自动决定对象注册或文件结构。

## 2. 正交分类轴

| 轴 | 含义与候选值 | 防混淆规则 |
|---|---|---|
| 语义类别（kind） | 工程知识模型、实体/值、关系、工件/记录、视点、视图、表示语言、活动/机制、证据 | 一个术语可有多个角色，但每个定义/实例明确所在类别；模型不是文件；Test Space Modeling是活动，Test Space Model是设计知识，Coverage Matrix是覆盖工件 |
| 工程关注点（concern） | 下节14个主领域；跨域可多标签 | 按主要回答的问题分类，不按流程顺序硬分 |
| 认识与规范性质（epistemic/normative） | 观察事实、来源、候选推断、假设、未知、已批准规范、裁决；不创建正式枚举 | 用户批准并不证实自然事实；同一对象类型可能承载不同主张，具体字段遵循正式契约 |
| 生命周期位置 | 研发R0/S0–S7，业务系统自身运行/退役生命周期 | 工程阶段不等于业务状态，生命周期不推导实现 |
| 抽象层次 | 元元模型、元模型、项目模型、现实事实（研究中的M3/M2/M1/M0记法，避免与仓库L1/L2/L3混淆） | 不映射为仓库层级；抽象越高不等于权限越大 |
| 所有权与适用范围 | 通用理论、L1协议、L2领域、L2默认项目事实/可选L3实例、外部来源 | 仓库所有权、治理scope、框架版本与项目profile分开；需确认L2默认执行记录的路由边界 |
| 用途与可计算性 | 描述、规定、分析、计划、执行、验证/论证；人读/AI读/机器检验/执行 | 设计稿、事实与派生报告分开；可执行性取决于正式契约而非表示语言 |
| 维护形式 | 权威事实/规则、独立证据、版本化引用、可重算视图、外部规范 | 只有同源、同版本、同条件且不含额外事实的内容才可派生；派生结果必须保留源引用、算法版本/参数及未覆盖边界 |

严禁把上表当作新的机器枚举。产品状态机与工程工作状态、业务过程与研发工作流、业务规则与治理Policy、产品变体与治理profile、系统上下文与AI上下文是独立语义。

## 5. 不进入通用薄内核的内容

- 具体业务规则、站点/产品/套餐枚举、UI页面/组件树/交互原型、体验调查、领域实体、业务状态、数据表/字段、接口端点、部署拓扑、SLI/SLO和产品迁移事实：L2/可选L3独占权威。L1可提供稳定引用、必要公共约束、契约和裁剪。
- 流程图、目标/能力/功能/任务树、需求追溯矩阵、项目地图、组合注册、覆盖报表、影响预览：派生或表示工件；不能复制第二份可编辑事实。若含新增独立观察则先归入相应权威模型，而非写入派生视图作为唯一记录。
- UML/SysML/C4/BPMN/DMN/ER等建模语言、图族、图形语法、绘图工具，以及结构化保障论证的完整行业方法：引用专业研究/外部标准，非强制L1技术依赖。
- 全量工作流引擎、图数据库、企业资源/项目组合平台、集中观测平台、独立注册中心不纳入standard强制内核。本研究不选实现框架。
- 六个内核原语仅按既有架构复用；具体受控对象（含已有授权与证据）及专属记录/契约仍由AI-Project-OS注册治理，不用35家族替换42类型矩阵。

## 8. 模拟多专家视角与反方攻击

以下是单AI的八种分析视角，非八位独立专家、无独立评审签名，不构成L1独立反方门禁通过。每个攻击均保留未决验证。

| 视角 | 反方攻击及具体反例 | 方案修正/尚需验证 |
|---|---|---|
| 系统工程 | 只列树会遗漏环路、约束、多目标冲突；系统边界变化后旧接口证据不再适用 | 保留有类型关系与版本；R1-B定义端点、方向、条件及跨界影响 |
| 需求工程 | 目标、业务能力、功能需求多处手写，变更删除一条需求后100%覆盖是假象 | 复用requirement_kind、四段意图、不可变分母及人类scope-change；检查真实功能卡和行为规格的原子事实所有权 |
| 产品设计 | 将用户旅程全部派生自场景会漏真实体验痛点；页面树不等于功能树 | M14独立观察条件，M15领域语义；以真实原型/使用者验证 |
| 软件架构 | 合并M17/18可能丢动态时序；单项目iyf适配逻辑不能进入L1 | 动态独立子面，架构与代码事实分开；需第二异构案例与反例 |
| 领域建模 | M01/M25家族合并会把事故身份当问题假设，M09把业务配置误作治理路由 | 保留子型与不可变事件身份，M09/M34区分，独立性按事实变化理由验证 |
| 测试验收 | 缺少一个批准语义成员仍可pairwise全覆盖；Run成功不等于判据通过 | M26源清单、组合、覆盖分离，M27/28分开；故意漏成员、失效证据、错误裁决反例 |
| 知识工程 | 32→35可能膨胀；用历史JSON与新MD双写产生漂移；重复的规则事实不可知 | 35为家族不等于文件；旧快照只读，新分类唯一增量入口；用固定SHA与内容hash验证派生，实测维护成本 |

**自我否决条件：** 若某候选家族仅重复已有正式语义且无法说明独立关注点、独立变更/风险或用途，则降为引用/视图；若合并丢独立身份或导致错误推理，恢复为独立子家族；若第二项目证明裁剪漏掉关键风险，重新定义触发条件；若没有真实证据则不升级L1，不以设计评分代替事实。当前不接受通用95+或生产就绪声明。
