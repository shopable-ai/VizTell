## 1. 原始目标：最终要解决什么问题

**用户提出一个不完整想法，AI 能结合已有系统，理解目标、发现必要需求、形成方案、组织开发、实际验证，并在出现问题时修正相关部分，直到解决用户问题。**

这套方法要减少需求遗漏、重复开发、目标漂移、上下文丢失和提前声称完成。当前优先判断：哪些内容能帮助作出工程决定、减少返工；哪些只是需要继续验证的想法。

**基础知识地图（R2.2 紧凑阅读，候选）：** [因素与链路关系地图](11_因素宇宙与链路关系地图.md)回答“要考虑什么”；[软件链路总体地图](../通用链路宇宙/08_软件IT与AI原生.md#r2-chain-map)回答“有哪些转化链”。两张地图先看横向分类，再读关键问题与推理思路，最后看一个纵向样本；不替换既有工作流、工程模型、角色或独立实验任务。

**研发内容的八种职责（阅读视角）**：目标；问题；框架；思路；知识；判断；执行；验证与反馈。关键问题决定待解未知，推理思路说明如何推进与收敛，推理模式提供按需使用的方法，事实/知识及证据支撑判断。它们贯穿五阶段，既不是八个新宇宙，也不是八个连续步骤。详见[问题与思路入口](11_因素宇宙与链路关系地图.md#怎样使用框架关键问题与推理思路)。

## 2. 这批材料是什么

它们属于同一个总目标下的不同研究材料，不能整体当成一个业务需求或一份执行任务。

| 内容性质 | 本次材料中的例子 | 怎么使用 |
| --- | --- | --- |
| 目标与原则 | 从不完整想法到真实交付；按复杂度拆分 | 作为后续取舍依据 |
| 总体框架 | 五阶段、工作流关系、各体系职责 | 说明当前在哪里、下一步做什么 |
| 关注点与表达模型 | 角色、场景、约束；目标树、状态模型、测试矩阵 | 前者提醒考虑什么，后者把具体项目内容表达清楚 |
| 分析与评审方法 | 四组推理、正反向推演、盲区审计、多专家协作 | 按当前问题选择使用 |
| 执行能力与系统构想 | Skill、Agent、各类 Engine、AI Project OS | 区分已有能力、候选能力和未来自动化设想 |
| 来源与研究记录 | 参考链接、“已经保存”、待验证效果 | 核对出处、版本和证明范围 |

**“有价值”可以支持保留；“已成为任务”还需要明确目标、范围、输入、产出和完成条件。** 内容的主题与证据状态分开：同一主题中可以同时存在原始要求、候选方案、待验证假设和已核验事实。

## 3. 一件研发工作怎样往前走

沿用已有五阶段框架作为阅读主线。存量项目从恢复当前事实开始，直接处理尚未解决的部分。

| 阶段 | 要回答的问题 | 最少交给下一步什么 |
| --- | --- | --- |
| ① 需求理解与推理 | 为谁解决什么问题？已经有什么？ | 原始目标、现状、范围、场景、未知项和成功方向 |
| ② 工程模型与业务设计 | 在具体场景下，产品应怎样工作？ | 必要需求、能力与功能、正常/异常规则、可观察验收条件 |
| ③ 解决方案与技术设计 | 采用什么办法？怎样实现与验证？ | 必要的方案取舍、交互、状态、数据与接口设计 |
| ④ 工程执行 | 怎样把方案做成可运行结果？ | 有依赖关系的任务、实际变更、构建和定向验证结果 |
| ⑤ 真实验收与持续演化 | 用户问题是否解决？还有哪些缺口？ | 对应版本和环境的证据、结论、修复与经验 |

工程模型可服务全部阶段，第二阶段重点是业务与产品设计。研究由未知项触发；验收条件从需求阶段开始；知识随工作积累。实现有错回实现，设计有错回设计，目标或范围有错才回相应需求；同时复查受到影响的下游内容。

这五阶段是阅读视图，正式阶段、对象与决策规则继续引用现有工程框架。细化关系见[研发工作流与工程能力关系](07_研发工作流与工程能力关系.md)。

**2026-11-27工作流核对：** [R2当前验证记录](07_研发工作流与工程能力关系.md#r2-continuation)保留阶段退出、Skill入口及ADR适用条件的修复与证据，并纠正“局部Skill必须先完成L2接入”和“实施计划已承接真实迁移”的额外前置。AI按指南选择并执行局部维护已有实际记录；专用自动路由、真实L2消费与跨项目通用效果仍分别未证。不重开已有工程模型或产品实验。

## 4. “横向、纵向、模型、方法”怎样分清

| 要看什么 | 对应内容 | 一句话解释 |
| --- | --- | --- |
| 处理哪一部分 | 项目、子系统、模块、功能 | 按业务和责任边界拆范围，不强制每种层级都存在 |
| 怎样推进 | 五阶段及具体工作流 | 组织顺序、依赖、并行、反馈与恢复 |
| 哪些方面容易遗漏 | 角色、场景、状态、数据、约束、风险、商业、生命周期 | 是检查角度，可以跨多个阶段使用 |
| 怎样发现与判断 | 推理模式、多视角分析、反方检查 | 是分析方法，需要产生有理由的修正或明确无新增 |
| 怎样表达结果 | 目标、需求、业务链路、状态、架构、测试等模型 | 是当前项目某方面的可检查表达 |
| 怎样执行和复用 | Task、Skill、Agent、工具、知识与证据 | 分别承载工作、局部方法、执行、工具调用、经验和证明 |

“横向”可用于查看同一项目的不同业务部分或检查角度，“纵向”可用于贯穿一个需求的交付过程；正式记录写出具体含义，避免方向词混用。项目拆分保留[原有结构图](assets/项目结构与分层拆解_用户原图.svg)的思想：拆到结果、边界、依赖和验收可以说明清楚为止。页面与功能可以多对多，局部完成后仍需核对完整业务链路。

**常用模型目录不等于每轮文件清单。** 小任务可以用一张表表达目标、规则和验收。出现异步、重复、暂停或恢复问题时，再补局部状态与时序；涉及数据同步或迁移时，再补数据归属和兼容行为。已有有效资料优先引用，选择依据和停止条件见[工程模型使用方法](README.md#当前使用方法r1-b2先决定再选择知识)。

四组需求推理保留为入口：**理解与展开、反推与发现、质疑与补漏、裁剪与收敛**。13种推理模式回答“怎样分析”，八个审计领域回答“检查哪里”，均为按需参考；具体定义分别维护在[需求推理](需求推理与需求工程/README.md)和[盲区审计](推理与盲区审计/README.md)。

## 5. 分三个方向推进，共用目标和案例

以下是既有研究的分工视图，不是新建三套研发体系。

| 方向 | 独有问题与下一项产物 | 复用位置 |
| --- | --- | --- |
| 方向一：总体框架与工程模型 | 怎样从现有资料恢复足以决策的信息？产出一次真实任务的“已有事实—缺口—选用表达—工程决定”记录 | 本入口、工程模型使用方法及[当前任务记录](90_研究缺口与续研任务.md) |
| 方向二：需求发现与多角色审查 | 怎样发现必要遗漏，又剔除伪需求？产出候选增量、理由、反例、保留/延期/删除决定 | 需求推理、[角色协作](角色与多专家协作/README.md)、盲区审计 |
| 方向三：执行、验收与经验复用 | 已确定工作能否被执行、验证和接续？产出任务输入输出、实际结果、证据缺口及可复用经验 | 工作流与工程能力关系、已有正式框架和产品任务 |

方向一提供共同基线；方向二围绕同一问题提交需求与判断增量；方向三检验这些增量能否用于设计、实施和验收。知识与证据贯穿三者。独立分析适合可拆分的问题，涉及同一目标、术语和当前状态的结论统一回写已有入口。

本轮已经完成资料归位，并在[附录](10_精选材料归类与推进计划.md#4-三张可试用的方法卡)给出三张候选用法卡。

**现在先推进哪一项：** 方向一已有[Cookie Editor独立实验登记](09_工程模型独立价值实验登记_CookieEditor.md)。先按登记准备允许的固定输入资料包，并核对执行隔离条件，再保存各组首次结果、实际成本与独立评审。已有登记未取得这些结果，本轮未复测其执行环境。无需重新选案例或扩写模型清单；方向二、三只在既有范围内提供各自增量。

共用案例可以帮助理解衔接；正式比较须按原登记隔离资料与答案，不能让共同讨论污染首次判断。进一步工具化取决于方法实际收益和重复使用成本。

## 6. 用“网页选区追加剪藏”看出实际用途

示例来自本会话提供的2026-11-26“网页剪藏功能优化”历史反馈：小区域有时难以选中，希望能追加选区，并有清楚的模式提示。**下面是阅读演示；本轮未读取该功能源码、未复现故障、未修改产品或执行浏览器验收。**

| 内容 | 怎样整理成有用结果 |
| --- | --- |
| 原始目标 | 准确选中需要的内容，并能连续收集多个区域 |
| 已报告现象 | 有时只能选大区域，有时又可以选小区域；实际原因待复现 |
| 候选方案 | 修饰键加点击、工具条入口、蓝色提示；这些是待比较的交互选择 |
| 推导出的候选行为 | 选区预览与实际提取一致；替换/追加意图明确；追加保留已有内容；取消不改写草稿，均需结合场景核对 |
| 待验证假设 | 是否有浮层拦截、命中目标提升过度或其他原因，需用页面和代码证据判断 |
| 最少表达 | 一张交互状态与规则表，加一份验收清单，可先承载本次讨论 |
| 验收方向 | 小区域可选；追加顺序正确且不丢旧内容；取消保持原文；模式提示与最终动作一致 |

由此可见，同一句反馈中同时存在问题、目标、候选设计和待验证假设。把它们拆清后，才知道要复现什么、决定什么、实现什么以及如何验收。通用能力名称或专家意见不能替代这些具体结果。
