# AI 原生研发：总体框架与关键结论

> 更新：2026-11-26。用途：整合历史思考、需求推理、工程模型及执行框架，提供一个可读的总体入口。
> 状态：候选方法与阅读导航；本轮完成资料核对和关系整理，方法效果、最小充分性与跨项目适用性仍待真实验证。正式对象、状态及决策规则以现有工程框架为准。

## 先看目标和主线

**原始目标：用户提出一个不完整想法，AI 能逐步理解问题、发现必要需求、选择方案、组织执行、验证结果，并在出错后局部修正，直到解决用户问题。**

这套方法要减少需求遗漏、目标漂移、重复研究、上下文丢失和提前声称完成。判断价值看它是否帮助作出更准确的决定、减少返工并交付可验证结果。

| 推进阶段 | 要回答的问题 | 当前阶段应交给下游什么 |
| --- | --- | --- |
| ① 需求理解与推理 | 为谁解决什么问题？什么结果算成功？ | 有来源的目标、问题、角色、场景、候选需求、非目标、未知项和验收方向 |
| ② 工程模型与业务设计 | 业务怎样运行？系统必须提供哪些能力和行为？ | 按需选取的业务链路、能力/功能、规则与异常；经现有审核和决策流程形成需求基线 |
| ③ 解决方案与技术设计 | 哪种方案满足需求？边界和取舍是什么？ | 必要的资料研究、方案比较、基线范围内的 MVP 实现方案、交互设计、架构、数据/接口契约及执行规格 |
| ④ 工程执行 | 怎样把确定的方案做出来？ | 有依赖关系的任务、代码和构建产物、实际执行记录、测试与修复结果 |
| ⑤ 真实验收与持续演化 | 用户问题是否解决？变化后哪些部分需要重审？ | 对照事前判据的真实证据、验收结论、未完成项、局部修正、决策与经验沉淀 |

五阶段是便于阅读的推进视图。工程模型可用于所有阶段；第二阶段重点是业务与产品模型。研究由具体未知项触发；验收条件从需求阶段开始建立；知识随工作持续积累。发现实现缺陷回到实现，发现方案问题回到设计，发现目标或范围错误再回到需求。方案比较若需要改变已接受的目标或需求范围，应回到相应决策流程更新基线。

正式工程框架已有自己的阶段、推进/追溯/状态/配置规则；此表不重新定义它们。相关接口见[需求推理专项](需求推理与需求工程/README.md)和[现有需求设计工作流](https://github.com/shopable-ai/ai-native-project-os/blob/1a1867640b7ee538bac21cd1a16d50f6a7e19c0f/docs/workflows/REQUIREMENT_DESIGN_WORKFLOW.md)。

## 一、把范围结构、推进流程和复用能力分清

历史资料中“水平、垂直”曾有不同含义。后续使用具体名称，避免仅靠方向词传达结构。

| 维度 | 回答什么 | 正确用法 |
| --- | --- | --- |
| 范围结构 | 当前处理项目的哪一部分？ | 项目可按实际复杂度划分子系统、模块和功能；允许省略不必要层级 |
| 推进流程 | 这一部分接下来怎样推进？ | 对当前范围应用上面的五阶段；已有成果先恢复，直接处理剩余问题 |
| 工程模型 | 用什么表达需要理解的事实？ | 按问题选择目标、场景、功能、架构、测试等模型，并保留相互关系 |
| 复用能力 | 哪些做法能反复使用？ | 有重复价值的局部方法形成 Skill、脚本、工具或模板；多步过程可形成 Workflow |
| 规格与知识资产 | 哪些内容需要长期保存？ | 保存目标、需求、规则、契约、规格、决策和经验的来源、版本及适用范围 |
| 验证与证据 | 怎样判断工作合格？ | 事前定义判据，事后保留对应版本、环境、结果与剩余缺口 |

用户上传的[项目结构与分层拆解原图](assets/项目结构与分层拆解_用户原图.svg)表达了“逐步拆小、明确输入输出、能够验收”的重要思想。使用时需要补充以下解释：

- 页面是交互组织方式，一个页面可能包含多个功能，一个功能也可能跨页面或模块，不能强制一一对应。
- Task 是要完成的工作；Workflow 组织顺序、依赖与恢复；Skill 提供局部可复用能力；Agent 承担执行。它们通过关系连接，不是同一级目录节点。
- 目标、输入输出、边界与验收要求约束每项必要工作，不能等到最后一层才补充。
- 模块可以按边界拆分；交付时仍应跑通必要的端到端业务链路，避免各模块分别“完成”却无法协同。

## 二、最小需求推理：四组方法、八个检查问题

保留四组候选方法：**理解与展开 → 反推与发现 → 质疑与补漏 → 裁剪与收敛**。它们主要服务第一阶段和第二阶段上游，也用于后续变更的局部复审。

用户提供的八步链路可以作为四组方法的检查顺序：原始想法、目标与问题、角色与场景、业务链路、能力与功能、规则与异常、审计与收敛、需求与验收结果。第六项明确为“规则、异常与隐含条件”，因为前五项已经在进行需求推理。

四组操作、八个检查问题及九种细分推理机制的对应关系统一保存在[需求推理专项入口](需求推理与需求工程/README.md)。这里不另维护一套算法。

**推理结果必须区分：已有事实、候选解释、待研究事项和已接受决定。** 从成功结果反推的是必要条件；具体技术方案还需要比较。例如，“进入正确下一集”是期望结果；识别并核对候选目标是必要能力；点击站点原生按钮、解析列表或用户指认属于待比较的实现办法。

收敛时至少说明本轮范围、排除内容、关键规则、可观察验收方向、未解决问题及其影响。停止生成新条目，不代表需求已经完整或自动得到批准。

## 三、15 个直观工程模型：按问题选择

下表是15种常用工程模型的阅读入口。树、图、矩阵是表达形式，同一模型可以有多个视图；不要求建立15份文件。不同模型可以引用同一条事实，一个视图也可能引用多个模型。具体类型、关系及权威对象仍引用既有定义。

| 工程模型 | 主要回答的问题 |
| --- | --- |
| 目标树 Goal Tree | 为什么开发？成功结果怎样逐步分解？ |
| 问题模型 Problem Model | 谁遇到什么问题？哪些是现象、哪些是待证原因？ |
| 利益相关者模型 Stakeholder Model | 谁使用、付费、维护或受影响？各自关切和责任是什么？ |
| 需求树 Requirement Tree | 必须满足哪些结果、规则、质量要求和约束？ |
| 场景模型 Scenario Model | 谁在什么条件、状态和环境下使用？ |
| 用户旅程 User Journey | 用户从开始到完成任务，会经过哪些触点和困难？ |
| 业务链路 Business Flow | 业务状态、参与者和责任怎样衔接？ |
| 能力树 Capability Tree | 要实现业务结果，系统必须具备什么能力？ |
| 功能树 Feature Tree | 用户或调用方能够观察、使用哪些功能？ |
| 界面树 UI Tree | 信息、页面和交互组件怎样组织？ |
| 架构图 Architecture Graph | 系统怎样分工、协作和处理边界？ |
| 数据模型 Data Model | 数据怎样定义、归属、流转、保存和删除？ |
| 任务依赖图 Task DAG | 哪些工作可以并行，哪些必须先完成？ |
| 测试矩阵 Test Matrix | 哪些场景、输入、状态、异常和判据需要验证？ |
| 证据关系图 Evidence Graph | 哪项结果支持哪个版本、范围和条件下的结论？ |

这15项对应已有35个候选家族中的常用关注点；是阅读选择，不是重新分类或删减原目录。详细映射继续维护在[04_模型分类纠偏与收敛方案](04_模型分类纠偏与收敛方案.md)；35家族和14主领域也仍是候选分类。

选取方法很简单：**先问当前决定缺什么信息，再选能补足它的模型。** 例如，时序复杂时补状态/事件模型；外部调用较多时补接口契约；数据迁移时补保留、兼容与回滚。它们不必挤进这个15项入口表。

需求说明必须达到什么结果；能力说明系统能做什么；功能说明向使用者提供什么行为；方案说明如何实现；任务说明本轮做哪项工作。相邻模型之间可能是多对多关系，不能凭树形展示推断全部关系。测试矩阵定义验证义务，真实执行记录及证据才能支持验收。

## 四、角色、方法和执行工具怎样配合

| 体系 | 负责什么 | 应留下什么有用结果 |
| --- | --- | --- |
| Role 角色 | 识别受影响者、专业判断、执行责任、决定与验收责任 | 当前问题所需的角色与责任，不机械召集全部角色 |
| Model 工程模型 | 表达需要理解的工程事实及关系 | 当前决定真正需要的模型或已有模型引用 |
| Reasoning 推理方法 | 从来源推导必要条件、查找反例和遗漏 | 有理由、有来源的需求差量、冲突与未知项 |
| Workflow 工作流 | 组织任务顺序、依赖、反馈、恢复和退出 | 可执行的推进安排 |
| Skill 技能 | 复用一种局部任务的执行方法 | 输入、输出、适用条件及失败返回 |
| Agent 智能体 | 在当前任务与授权范围内分析、调用能力并执行 | 实际工作结果和可核验记录 |
| Knowledge 知识 | 保存和复用事实、决策、经验与方法 | 能找到来源、版本和适用边界的知识 |
| Evidence 证据 | 支持特定结论或验收判据 | 可以定位的验证材料及其证明范围 |

项目利益相关者与参与分析的专家不是一组名单。先辨认谁受影响，再按当前问题选择专业视角，最后明确谁执行、谁决定和验收。同一 AI 切换视角可以帮助自检；独立审核需说明实际审核者、输入及隔离方式，多开几个角色名称不足以证明独立性。

研究、竞品、开源、商业和可行性分析由具体未知项触发。例如，不清楚用户是否需要该能力，进入需求研究；不清楚现成工具能否满足约束，进入方案研究。研究应输出“影响了哪个决定、依据是什么、还不知道什么”，再更新对应需求或设计。

## 五、让 AI 接得住：一项工作的最小闭环

以下信息可以写在已有需求卡、规格或任务记录中，避免另建重复表格：

| 必须说清的内容 | 具体问题 |
| --- | --- |
| 来源、目标与范围 | 为什么做？依据哪条原话、需求或缺陷？本轮处理哪里？ |
| 输入与前置条件 | 读取哪个版本？依赖什么信息和环境？哪些尚未核实？ |
| 输出与下游用途 | 交付什么？下一步由谁消费、如何使用？ |
| 边界、规则与失败处理 | 哪些行为允许？异常怎样处理？什么情况下应停止或恢复？ |
| 验收与证据 | 怎样观察成功和失败？现在实际验证到了什么范围？ |
| 状态与接续 | 已完成、未完成、待决和下一步分别是什么？ |

“输入输出优先”包括语义、业务规则和失败行为；字段格式正确只是其中一部分。规格、契约、测试清单、代码、运行证据都可以是资产，但职责不同。Markdown 是文件格式，不能据此判断内容已经批准或实现有效。

拆分在能够独立说明结果、边界、依赖和验收时停止。还含多个独立结果或不同失败责任时继续拆；只是内部判断步骤时可以留在规则或子流程中。不要仅为凑层级或控制文件数量拆分。

## 六、用连播助手看一次完整衔接

下面依据已有需求作阅读示例，未执行新的功能开发或真实验收。固定案例见[OpenDesk 连播助手历史版本](https://github.com/shopable-ai/opendesk-browser/tree/91239889481bad3f42edb30e84e1012aa1901fc0/projects/video-auto-skip)；原有静态案例映射见[工程模型专题入口](README.md)。

| 环节 | 针对“自动进入正确下一集”的具体内容 |
| --- | --- |
| 目标与范围 | 减少连续看剧时的手动操作；本次只分析下一集切换 |
| 角色与场景 | 观看者；正常顺序、倒序列表、分页、最后一集及无法判断目标等场景 |
| 业务链路 | 满足切换条件 → 确定候选下一集 → 核对身份 → 导航 → 观察是否进入目标正片并开始播放 |
| 能力与需求 | 找到目标、判断是否可继续、执行切换并反馈结果；目标不明确时不猜测跳转 |
| 方案与规格 | 比较原生按钮、列表识别或用户指认的适用性；选定方案后定义站点适配、输入输出及失败行为 |
| 执行与验收 | 形成有依赖的实现和验证任务；检查实际进入正确集并起播，同时验证目标不明时的停止行为 |

此例需要目标、场景、业务链路、需求/能力/功能、局部接口、任务、测试与证据的关联信息，可以复用已有文档；不必创建全套模型文件。“点击执行成功”不能单独证明“进入正确下一集”。若失败来自候选目标错误，回查识别和规则；若目标正确却未起播，检查执行与播放器状态。
