# 工作流装配方法与 L4 模板

> **最小装配链**：识别触发 → 明确结果与标准 → 选择最少必要基础链 → 衔接输入输出 → 挂接必要控制 → 设定失败返回与停止条件 → 按风险选择轻量／标准／严格档 → 运行并保留必要证据 → 验收、评估并进入生命周期状态。

> 导航：[返回总览](00_总览与核心结论.md)｜[基础链库](02_通用基础链路库.md)｜[术语与编号索引](12_术语、边界与编号索引.md)｜[场景验证](13_场景验证与覆盖矩阵.md)

## 一、L4 的职责

L2 基础链说明跨领域稳定复现的状态转化；L3 组合链说明某类场景通常怎样调用基础链；L4 工作流把组合落实到具体组织、对象、人员、工具、时限、阈值和证据。

L4 不是把所有字段填满，而是回答：

1. 谁在什么情况下启动？
2. 必须拿到什么输入，产生什么可交付输出？
3. 哪些步骤顺序、并行、分支或调用其他链？
4. 谁执行、谁决定、谁批准、谁接收？
5. 用什么证据判断继续、返工、升级、暂停或停止？
6. 异常怎样旁路，完成后进入什么状态？

## 二、装配八步法

### 1. 定义场景边界

> 触发 → 对象 → 使用者／受影响者 → 期望结果 → 不适用条件 → 生命周期范围

先说清楚“这一个工作流解决哪一种重复情境”，不要把整个部门、整个生活或整个产品生命周期塞进一张流程。

### 2. 选择主链

从《02_通用基础链路库》选择能够产生目标输出的最少基础链。普通任务通常从下面的最小闭环开始：

> **C02 需求澄清 → C04 目标设定 → C05 标准设定 → C09 任务执行 → C14 提交验收 → C30 维护更新退出**

只有缺少价值判断、计划资源、信息证据、多人协作、风险控制或复盘沉淀时，才增加相应链。

### 3. 建立输入输出契约

对每次链路交接明确：

- 上游输出名称和版本；
- 下游必需字段与可选字段；
- 来源、责任人和有效期；
- 缺失、冲突或过期时的返回位置；
- 接收者确认方式。

前链输出不能满足后链输入时，不得靠默认猜测继续运行。

### 4. 挂接横向控制

控制强度按实际风险选择：

- 记录：哪些事实必须留存；
- 监测：哪些状态和趋势必须观察；
- 沟通：哪些接口和变化必须同步；
- 质量：哪些缺陷必须在下游前阻断；
- 风险：哪些未来不确定性需要触发器和预案；
- 合规安全：哪些法律、隐私、伦理和安全边界必须审查；
- 变更版本：谁能改基线，怎样迁移和回退。

### 5. 明确责任与决策权

至少区分：

- 执行者：完成具体工作；
- 负责人：对整体结果和闭环负责；
- 决策者／批准者：对取舍、例外和重大风险作决定；
- 接收者：验证、确认并接管成果；
- 被告知者：需要获得状态或影响信息的人。

责任、权限和资源不匹配时，必须返回授权或资源配置，不得只给责任不给权力。

### 6. 定义关口与阈值

为关键节点规定：判断问题、证据、判定人、通过标准、容差、失败去向和最迟决定时间。不能量化的事项可以采用可观察条件，但不能只写“视情况处理”。

### 7. 设计失败、异常和退出

- 普通偏差 → 返回最近根因层修复。
- 风险发生 → 切换 C29 异常恢复，先安全止损。
- 价值或目标失效 → 暂停投入并返回 C03／C04／C22。
- 无法恢复或净价值为负 → C30 有序终止、归档或淘汰。

每个循环必须有预算、时限、次数、升级点和停止条件，避免研究、返工和改进无限循环。

### 8. 试运行与发布

> 桌面推演 → 小范围试运行 → 记录耗时错误返工 → 验证输入输出和责任接口 → 修订 → 批准发布 → 培训采用 → 监测真实效果 → 更新或撤回

文档完成不等于工作流有效；至少要经过一次真实运行或代表性推演，并明确尚未验证的部分。

## 三、三档流程强度

| 判断维度 | 轻量 | 标准 | 严格 |
| --- | --- | --- | --- |
| 典型情境 | 低风险、个人、可逆、影响小 | 普通工作、项目、OPC交付 | 高风险、不可逆、多人、生产、合规 |
| 目标与标准 | 一句话结果＋完成条件 | 目标、范围、标准、证据 | 正式基线、独立评审、版本控制 |
| 计划与责任 | 下一动作、期限、本人负责 | 任务、依赖、负责人、检查点 | 权责矩阵、授权、容量和升级链 |
| 记录 | 最小状态和结果 | 关键决定、过程、问题和版本 | 全程追溯、审计与保留规则 |
| 质量 | 自检 | 同行或接收者检查 | 独立验证、分层测试和放行授权 |
| 风险 | 简单备选和停止条件 | 风险清单、触发器、责任和预案 | 正式安全合规审查、演练和连续性 |
| 变更 | 直接调整并记录结果 | 评估影响、更新基线并通知 | 授权审批、迁移、回退和审计 |
| 验收 | 自己或直接使用者确认 | 有权接收者验收 | 验证、确认、验收相互区分并留证 |

### 强度选择规则

任一条件显著上升时提高强度：人身或健康安全、法律合规、隐私数据、金额、不可逆性、外部承诺、影响人数、运行持续时间、恢复成本和权限敏感度。

如果增加控制的成本高于潜在损失且事项可快速恢复，可以降档；降档决定仍需由承担风险的人确认。

## 四、输入输出契约模板

| 字段 | 填写要求 |
| --- | --- |
| 交接名称 | 使用稳定、可检索的产物名称 |
| 上游链与责任人 | 写明链路 ID、负责人和联系方式／角色 |
| 下游链与接收者 | 写明使用该输出的链路和接收责任 |
| 必需内容 | 缺少任何一项就不能继续的字段 |
| 可选内容 | 有助于判断但允许缺失的字段 |
| 格式与位置 | 文件、系统、表单或可访问地址 |
| 版本与有效期 | 当前版本、批准状态和过期条件 |
| 质量与证据 | 完整性、准确性、来源和检查结果 |
| 缺失或冲突处理 | 返回、补证、升级、保留未知或停止 |
| 接收确认 | 谁在何时以什么方式确认可用 |

## 六、轻量工作流模板

低风险日常事项可以只保留：

> **触发／需要 → 期望结果 → 完成条件 → 下一动作与期限 → 必要资源 → 执行 → 检查结果 → 继续／调整／结束**

最小记录：事项、下一动作、完成条件、结果、异常和后续状态。没有实际风险时，不要求制作权责矩阵、完整风险清单和正式审批记录。

## 七、装配质量检查

发布前逐项判断：

1. 是否可以在一分钟内说清楚这个工作流解决什么？
2. 每个步骤是否指向真实存在的基础链或领域动作？
3. 前一步输出是否足够作为下一步输入？
4. 是否存在责任空白、重复责任或有责无权？
5. 正常路径之外是否有信息不足、资源不足和质量失败返回？
6. 风险发生后是否切换到异常响应，而不是继续讨论风险概率？
7. 是否区分验证、确认、验收、效果和价值？
8. 是否有暂停、停止、回退、交接和生命周期出口？
9. 控制强度是否与真实风险匹配？
10. 是否能通过运行证据判断工作流有效，而非只判断文档完整？
