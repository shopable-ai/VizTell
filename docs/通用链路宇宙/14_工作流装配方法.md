# 工作流装配方法与 L4 模板

> **核心结论**：工作流装配的重点是“从现有基础链中选对最少必要链，并把输入输出、返回和退出接起来”，不是把所有任务都填成复杂工程表单。工具、角色、时间、权限和参数只在真实场景需要时补充。

> **最小装配链**：识别场景 → 明确结果和完成标准 → 选择基础链 → 排顺序／并行／分支 → 接好输入输出 → 设计失败返回 → 挂接必要控制 → 运行 → 验收评价 → 进入生命周期

> 导航：[返回总览](00_总览与核心结论.md)｜[基础链库](02_通用基础链路库.md)｜[运行关系](03_链路关系、关口与运行协议.md)｜[场景验证](13_场景验证与覆盖矩阵.md)

## 一、L4 到底是什么

- L2 说明一种稳定状态转化；
- L3 说明一类场景通常怎样组合多条基础链；
- L4 只是把组合落到真实环境。

所以 L4 首先要回答的仍然是：

1. 什么情况下开始？
2. 输入是什么？
3. 想得到什么结果？
4. 中间需要哪几条链？
5. 哪些可以并行，哪些必须先后？
6. 失败时回哪里？
7. 怎样算结束？
8. 结束后进入什么状态？

只有这些问题回答完后，才按需要增加人员、工具、期限、权限、表单或参数。

## 二、装配七步法

### 1. 定义真实场景

> 谁／什么对象 → 在什么情境 → 遇到什么需要／问题／任务 → 希望得到什么结果 → 哪些情况不属于这个流程

不要一开始就从工具或步骤出发。

### 2. 明确输入、输出和完成

- 输入：开始前必须已经具备什么；
- 输出：结束时真正交给下一环节什么；
- 完成标准：什么事实可以证明这一段已经结束；
- 下一去向：完成、继续、返回、暂停还是进入另一链。

### 3. 选择最少必要基础链

简单事项先从最小闭环开始：

> **需求／结果 → 标准 → 执行 → 检查／验收 → 结束**

复杂度增加时再补：

- 不知道值不值得做 → C03；
- 目标不清 → C04／C05；
- 事情太大 → 目标拆解、C06；
- 问题不清 → C20；
- 信息不足 → C23；
- 原因不清 → C21；
- 多方案选择 → C22；
- 资源不足 → C07；
- 多人合作 → C25／C26；
- 高风险 → C28；
- 已发生异常 → C29；
- 长期维护或退出 → C30。

### 4. 对复杂任务补齐研究与选择

复杂任务尤其容易从“目标”直接跳到“计划”。建议先检查是否需要：

> **现状差距 → 拆目标／拆问题 → 找已有解法 → 生成多方案 → 查失败／反例 → 必要咨询 → 验证关键未知 → 比较 → 决策**

这些都是对现有基础链的组合，不另造一套“项目专用基础链”。

### 5. 设计返回路径

至少判断：

- 动作错 → 回执行；
- 质量错 → 回质量／执行；
- 计划错 → 回计划；
- 资源不足 → 回资源／优先级；
- 关键事实不足 → 回研究；
- 方案错 → 回方案和决策；
- 目标错 → 回目标；
- 需求理解错 → 回需求澄清；
- 重大异常 → 切换异常恢复。

只有正常路径没有返回路径的工作流，通常只是一张理想化流程图。

### 6. 挂接必要控制

按真实影响选择：

- 需要追溯时才增加记录；
- 容易延期时增加监测；
- 多人接口时增加沟通；
- 结果不能出错时增加质量控制；
- 不确定性影响较大时增加风险管理；
- 有法律、安全或隐私要求时增加相应控制。

控制不是越多越好。低风险事项应保持轻量。

### 7. 运行、评价和更新

> 运行 → 看实际卡点 → 检查输入输出是否衔接 → 检查返回是否有效 → 评价结果和负担 → 删除无价值步骤／补真正缺口 → 更新版本

工作流有效性的证据是“帮助实际事情更好地完成”，而不是文档字段填得完整。

## 三、三档使用强度

| 强度 | 适用情况 | 最少内容 |
| --- | --- | --- |
| 轻量 | 个人、低风险、可逆的小事 | 结果、完成条件、下一动作、检查和结束 |
| 标准 | 普通工作、项目、多人协作 | 输入输出、主要步骤、责任、返回、验收和必要控制 |
| 严格 | 高风险、不可逆、强合规或重大外部影响 | 在标准档基础上补正式证据、授权、独立检查、恢复与审计 |

强度不是按照“是不是 AI／软件”决定，而是按照真实影响、可逆性和责任决定。

## 五、轻量模板

对于多数低风险事项，只需要：

> **发生什么 → 想得到什么 → 怎样算完成 → 下一动作 → 执行 → 看结果 → 调整／结束**

如果这个版本已经足够，就不要为了“完整”继续加角色矩阵、预算表、Agent 重试次数、阈值或审批流程。

## 六、装配质量检查

1. 这条工作流解决什么状态转化或场景？
2. 是否先明确结果再列动作？
3. 复杂任务是否漏了现状、拆解、已有解法、多方案和关键未知验证？
4. 前一步输出是否真的能作为后一步输入？
5. 正常路径之外是否知道失败回哪里？
6. 是否把工具或参数误写成了通用步骤？
7. 是否为了形式完整加入了低价值控制？
8. 验收后是否还检查真实效果和价值？
9. 长期对象是否有维护、迁移和退出？
10. 实际使用后能否删掉无价值步骤并保留真正有效的链？

## 七、复杂工作流的可选追溯区

简单、低风险工作流不需要填写完整追溯表；当项目跨多人、跨模块、跨版本，或出现“任务越来越多但不知道为什么存在”时，再启用本区。

建议按需增加：

```markdown
## 8. 追溯关系（复杂项目按需）
- 上游目标：
- 解决的问题／机会：
- 来源需求：
- 当前需求状态／基线版本：
- 关联能力：
- 关联产品／解决方案对象：
- 关联技术对象：
- 预期交付物／工作包：
- 实现对象／版本：
- 验证方式：
- 验证证据：
- 真实用途确认：
- 验收人／接收者：
- 实际效果与价值证据：
- 失败时最近返回层：
```

### 7.1 追溯不是增加表单，而是回答两个问题

从任意下游 Task、页面、接口、代码或自动化动作向上追问：

> **为什么存在？它服务哪个交付物、能力、需求、问题或目标？**

从任意已批准／基线需求向下追问：

> **由什么方案承载、什么工作交付、什么实现完成、什么测试证明、什么真实场景确认？**

如果回答不了，优先修复关系或返回上游，不要继续制造更多任务。

### 7.2 工作流关系与对象追溯关系要分开

- `A → B` 的**流程关系**表达执行先后或状态转化；
- `Task belongs_to Work Package` 的**父子关系**表达工作归属；
- `Feature satisfies Requirement` 的**追溯关系**表达为什么存在；
- `Test verifies Requirement` 的**证据关系**表达怎样证明；
- `A depends_on B` 的**依赖关系**表达前置约束。

只有关系语义清楚，复杂工作流才能在变更和失败时找到正确返回位置。
