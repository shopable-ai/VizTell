# 链路垂直深挖与审计框架

> **核心用途**：把“继续深入想一想”变成可重复执行的正式方法。对任意 C01—C30、扩展基础链、L3 场景组合或 L4 工作流，从专业性、完整性、系统性、结构性、时序性、规模跃迁、AI／软件分工、失败与生命周期等多个方向进行纵向深挖，发现原有平面链路中尚未显式表达的状态、分支、机制、基础设施和新组合。

> **核心结论**：深度不是把步骤写得更长，而是同时增加**语义深度、结构深度、时间深度、规模深度、价值深度、执行深度、韧性深度和系统深度**。当数量、频率、持续时间、复杂度、风险、参与者、自动化程度或环境变化速度发生跃迁时，应重新检查原链路是否需要切换运行模式或形成新的 L3/L4 架构。

## 一、为什么需要“垂直深挖”

C01—C30 解决的是跨领域稳定存在的**状态转化骨架**。但同一条基础链进入真实场景后，可能因为规模、时间、主体、AI 占比、风险、知识状态或工具条件不同，展开成完全不同的运行系统。

典型例子是 C23 信息处理与 C24 个人学习：

> **找资料 → 阅读 → 提取 → 去重 → 学习**

经过连续垂直深挖后，会进一步暴露：

> **信息注意力 → 已有知识基线 → 知识原子化 → 语义关系 → 知识增量 → 当前／未来价值 → 阅读调度 → 人学习／AI 使用分流 → Wiki／RAG／Skill／Workflow → 被动信息自动采集 → 主动信息发现 → 主动研究 → 来源与人物图谱 → 弱信号 → 试错情报 → 增量维护与生命周期**

因此，基础链的“短”不代表问题简单；它只是稳定语义骨架。垂直深挖负责发现其在高价值现实场景中的完整运行形态。

## 二、八个深挖母维度

| 母维度 | 主要覆盖 | 核心问题 |
| --- | --- | --- |
| **A 语义深度** | 专业性、机制、证据、边界、不确定性 | 这条链真正处理的专业对象和底层机制是什么，怎样判断正确 |
| **B 结构深度** | 完整性、结构、分类、接口、抽象层级 | 输入、步骤、分支、输出和上下游是否完整，是否层级混乱 |
| **C 时间深度** | 时序、状态、动态、生命周期、演化 | 事前／事中／事后怎样变化，状态怎样迁移和重新激活 |
| **D 规模深度** | 数量、频率、持续时间、复杂度、条件跃迁 | 规模扩大后原方法是否失效，何时需要切换架构 |
| **E 价值深度** | 价值、优先级、注意力、成本、停止条件 | 什么值得做、现在是否值得做、做到什么程度应停止 |
| **F 执行深度** | 角色、人机分工、工具、AI、自动化、验证 | 谁做什么，哪些可自动化，怎样证明执行结果真实有效 |
| **G 韧性深度** | 风险、失败、异常、回退、恢复、反例 | 正常路径失败时怎么办，怎样提前发现并控制损失 |
| **H 系统深度** | 上下游、组合、反馈、迁移、涌现、复用 | 与其他链组合后出现什么新能力、新风险和新闭环 |

执行深挖时先用 A—H 保证方向完整，再用第三节 30 个细分维度逐项审查。

## 三、链路深挖 30 维度框架

| # | 维度 | 核心要解决的问题 |
| --- | --- | --- |
| 01 | **专业性** | 专业领域真正关键的对象、机制、标准、术语、最佳实践、反例和专业判断是什么 |
| 02 | **完整性** | 从触发到完成是否缺输入、步骤、判断、分支、异常、反馈、退出或维护 |
| 03 | **系统性** | 该链与目标、需求、资源、风险、执行、决策、知识、组织、生命周期等系统怎样连接 |
| 04 | **结构性** | 对象怎样分类、分层、分型；哪些属于主链、支链、并行链、反馈链和组合链 |
| 05 | **时序性** | 事前、事中、事后分别做什么；即时、近期、中期、长期有什么差异 |
| 06 | **规模性／量变质变** | 1 个、10 个、1 万个对象时，原方法是否仍成立，何时必须切换为另一种架构 |
| 07 | **状态性** | 对象有哪些稳定状态，状态如何迁移，什么条件触发下一状态、回退、暂停或退出 |
| 08 | **增量性** | 已经处理、知道、完成或验证过以后，下一轮怎样只处理新增、变化、冲突和异常 |
| 09 | **动态性** | 目标、需求、环境、数据、资源和风险变化后，链路怎样重新评分、重排和调整 |
| 10 | **因果与机制性** | 为什么这些步骤有效，真正改变结果的底层机制是什么，哪些只是表面相关 |
| 11 | **价值性** | 哪些动作真正创造价值，哪些可以跳过、降级、延迟、委托、合并或删除 |
| 12 | **决策性** | 哪些节点需要判断；选项、标准、阈值、证据、可逆性和复查条件是什么 |
| 13 | **角色性** | 谁提出、谁负责、谁执行、谁审批、谁使用结果；责任和权限如何转移 |
| 14 | **工具与自动化性** | 哪些步骤适合人工、软件、AI、Agent、Workflow 或自动监测，自动化边界在哪里 |
| 15 | **数据与证据性** | 每个关键判断需要什么数据、证据、来源、版本、可信度和追溯关系 |
| 16 | **不确定性** | 哪些结论未知、概率性、争议性或信息不足，怎样表达置信度和保留未知 |
| 17 | **风险与失败性** | 最可能怎样失败，失败前有哪些信号，怎样预防、止损、回退、恢复和复发防控 |
| 18 | **边界性** | 什么条件下成立、不成立；有哪些例外、反例、禁区、适用范围和外推限制 |
| 19 | **成本与效率性** | 时间、注意力、Token、算力、金钱、人力、切换成本和长期维护成本怎样优化 |
| 20 | **反馈与学习性** | 执行结果怎样反向更新规则、模型、知识、Skill、流程和下一次行为 |
| 21 | **生命周期性** | 对象怎样创建、使用、维护、升级、替代、暂停、交接、归档、淘汰和重新启用 |
| 22 | **复用与迁移性** | 机制能否跨人、跨项目、跨行业、跨组织复用；哪些内容只能留在特定场景 |
| 23 | **接口与依赖性** | 上游必须提供什么，下游需要消费什么，与哪些链、数据、角色、工具和版本依赖耦合 |
| 24 | **抽象层级性** | 哪些是原则、机制、状态转化、基础链、场景组合、工作流步骤和工具实现，避免层级错位 |
| 25 | **场景差异性** | 同一链在生活、工作、OPC、公司、软件、研究、AI Agent 等场景中怎样变化 |
| 26 | **消费端差异性** | 最终给人、AI、Agent、组织或外部客户使用时，产物结构和处理方式如何变化 |
| 27 | **主动性** | 能否从事后响应升级为提前感知、监测、预测、主动发现、条件触发或授权自动行动 |
| 28 | **组合与涌现性** | 多条链组合后是否出现单链没有的新能力、新风险、新状态、新反馈回路或系统行为 |
| 29 | **饱和与停止性** | 什么时候继续搜索、分析、执行、优化或监测的边际价值已经低于成本，应结束或转观察 |
| 30 | **演化性** | 技术、市场、组织和环境长期变化后，这条链本身怎样升级，旧范式何时失效或被替代 |

## 四、条件跃迁：不仅检查“量变”

规模扩大只是导致链路质变的一种原因。以下条件任一发生明显跃迁，都要重新审查运行方式：

| 跃迁因素 | 典型变化 | 可能导致的架构变化 |
| --- | --- | --- |
| **数量** | 1 个对象 → 1 万个对象 | 人工处理 → 聚类、索引、批处理、自动化 |
| **频率** | 偶尔一次 → 每分钟持续发生 | 临时处理 → 持续监测、事件流、自动路由 |
| **持续时间** | 一次任务 → 跨月／跨年运行 | 临时上下文 → 状态持久化、版本、复查和生命周期 |
| **复杂度** | 单对象 → 多依赖网络 | 线性步骤 → 依赖图、分支、检查点、回退 |
| **风险** | 可逆低损失 → 高损失／高监管 | 自动执行 → 人工关口、证据、审批、双重验证 |
| **参与者** | 个人 → 团队 → 公司 → 多组织 | 自我管理 → 权责、接口、协商、治理和组织采用 |
| **自动化程度** | 人工 100% → AI／Agent 90%+ | 人执行 → 人设边界、处理例外、监督和验收 |
| **环境变化速度** | 稳定 → 每日快速变化 | 静态知识 → 主动监测、增量更新、过期与替代管理 |
| **不可逆性** | 可轻松撤销 → 难回退 | 快速试错 → 前置验证、沙盒、分阶段发布和退出方案 |
| **数据／证据不确定性** | 高确定 → 高噪声／冲突 | 单一路径 → 多源验证、置信度、反证和人工复核 |
| **依赖密度** | 少量独立依赖 → 高耦合生态 | 局部调整 → 影响分析、迁移、兼容和系统回归 |

### 4.1 规模跃迁审查

每条高频链至少问一次：

> **如果对象数量扩大 10 倍、100 倍、10,000 倍，原来的人工步骤还能运行吗？如果不能，新的核心机制是什么？**

典型模式：

- 1 本书：人工阅读；
- 20 本同类书：知识基线＋增量阅读；
- 1,000 本书：原子化＋关系判定＋阅读调度；
- 百万文档：索引＋RAG＋主动采集＋增量维护。

关键判断不是“怎样把旧流程执行更多次”，而是“何时旧流程本身应该被另一种架构替代”。

## 五、链路垂直深挖执行协议

> **选择基础链／场景 → 明确当前语义边界 → 收集代表性真实场景 → 按 A—H 八个母维度扫描 → 用 30 维度逐项找缺口 → 放大规模、频率、时间、风险和 AI 占比做条件跃迁测试 → 识别新增状态、对象类型、判断关口和上下游 → 区分人工／AI／软件／Agent 角色 → 补证据、失败、回退、停止和生命周期 → 判断应修改核心链、增加扩展链、建立 L3 组合还是下沉 L4 → 用真实场景回归测试 → 收敛并更新版本**

### 5.1 十二步深挖法

1. **选对象**：指定一条 C 链、扩展链、L3 场景或 L4 工作流。
2. **定边界**：明确它当前解决什么、不解决什么，避免把相邻链全部吞入。
3. **找场景**：收集普通、复杂、大规模、高风险、AI 高占比等代表性场景。
4. **做分型**：识别输入对象、使用主体、消费端、风险等级和生命周期阶段的差异。
5. **建状态**：列处理前状态、中间状态、完成状态、暂停／失败／退出状态。
6. **找增量**：判断是否存在“每次从零开始”的低效，建立基线与差额机制。
7. **做跃迁**：放大数量、频率、持续时间、复杂度、风险、参与者和自动化比例，寻找质变点。
8. **做人机分工**：区分必须由人判断、适合 AI 辅助、适合软件批处理和适合 Agent 自动执行的部分。
9. **补韧性**：增加证据、反例、失败模式、预警、回退、恢复和人工关口。
10. **补上下游**：检查入口是否缺失、输出是否可被下一链消费、是否产生新的组合能力。
11. **定资产化**：判断结果应成为知识、Wiki、RAG、Skill、Workflow、SOP、模板、数据状态或组织能力。
12. **验证收敛**：用真实场景压力测试，合并重复内容，只保留真正具有独立状态转化或组合价值的结果。

## 六、强制追问清单

每次垂直深挖至少回答以下问题：

1. **如果没有明确目标，这条链还能否启动？入口是什么？**
2. **如果已经执行过 20 次，第 21 次是否还需要从头处理？**
3. **如果输入扩大 100 倍、10,000 倍，处理架构是否必须变化？**
4. **如果 AI／软件承担 90% 工作，人真正应该保留哪些判断和责任？**
5. **如果最终消费者从“人”变成“AI／Agent／组织”，产物是否应该变化？**
6. **如果环境和需求发生变化，过去低优先级对象能否被重新激活？**
7. **如果多个候选只是换语言、换案例、换包装，怎样识别底层机制是否相同？**
8. **如果多个来源结论相同，但证据、边界或反例不同，怎样保留有效增量？**
9. **如果当前没有答案，系统应该继续搜索、试验、咨询、观察还是停止？**
10. **别人是否已经支付过类似试错成本，能否提前获取失败路径、弱信号和反例？**
11. **哪些步骤适合主动监测和条件触发，而不必等用户再次想起来？**
12. **什么条件满足后应该停止继续优化，转向执行、观察、维护或退出？**

## 七、深挖结果的层级归属

垂直深挖发现的新内容必须先判断应该落在哪一层，而不是全部升级为新基础链。

| 发现类型 | 优先归属 |
| --- | --- |
| 跨领域稳定的新状态转化 | 候选 L2 基础链，进入严格准入审计 |
| 已有 L2 的独立子机制／伴随机制 | 扩展基础链 |
| 多条基础链在某类现实场景中的稳定组合 | L3 场景组合／领域宇宙 |
| 具体角色、阈值、模型、API、数据库、表单、Prompt | L4 工作流配置 |
| 横跨多条链的统一要求 | 运行协议／横向控制 |
| 人／AI／Agent 的实现差异 | 运行模式或 L3/L4，不复制第二套 C 编号 |
| 工具或平台特有逻辑 | 领域／实现层，避免污染通用本体 |

### 7.1 新链准入门

只有同时满足以下条件，才考虑新增核心链：

- 输入／输出状态与已有链存在结构性差异；
- 核心转化机制不同；
- 完成标准和失败返回不同；
- 不是仅仅因为对象、行业、角色、工具、规模或 AI 使用方式不同；
- 经过多个场景验证，确实无法通过现有链组合稳定表达。

## 八、深挖输出模板

每次深挖不应只给长篇解释，至少产出以下结构：

### 8.1 一级框架

| 模块 | 解决的问题 |
| --- | --- |
| …… | …… |

用于保留完整问题空间，防止后续压缩时把已推导结论丢失。

### 8.2 收敛后的解决方案表

| 模块 | 问题 | 核心机制 | 核心输出 | 上游 → 下游 | 体系归属 |
| --- | --- | --- | --- | --- | --- |
| …… | …… | …… | …… | …… | …… |

### 8.3 正式紧凑链

> **链名**：输入／触发 → 核心判断 → 状态转化 → 分支 → 输出／下一链。

### 8.4 状态模型

明确：

> **未处理 → 处理中 → 已验证／待验证 → 已使用 → 更新／过时／暂停／归档／重新激活**

具体状态按对象调整。

### 8.5 条件跃迁表

至少检查：数量、频率、持续时间、复杂度、风险、参与者、自动化程度和环境变化速度。

### 8.6 场景压力测试

至少覆盖：

- 普通小规模；
- 重复执行；
- 大规模；
- 高 AI 占比；
- 高风险；
- 信息不足／冲突；
- 异常和回退；
- 长期运行与生命周期。

## 九、深度等级

为了区分“写得长”和“真正挖得深”，使用以下等级：

| 等级 | 特征 |
| --- | --- |
| **D0 名称级** | 只有链名或一句描述 |
| **D1 标准卡级** | 有输入、步骤、输出、完成标准和返回 |
| **D2 场景级** | 能覆盖主要场景分型、分支和上下游 |
| **D3 系统级** | 覆盖规模跃迁、人机分工、状态、增量、风险、基础设施和生命周期 |
| **D4 演化级** | 能持续监测环境变化、主动发现新机制、重新激活旧资产并推动链路自身升级 |

高价值、高频、可规模化、AI 能显著改变成本结构的链，优先推进到 D3；持续运行的战略性链路再考虑 D4。

## 十、95 分深挖验收矩阵

| 维度 | 权重 | 合格要求 |
| --- | ---: | --- |
| 专业与机制 | 15 | 专业对象、机制、证据、边界清楚，不只罗列步骤 |
| 完整与结构 | 15 | 入口、状态、分支、输出、失败返回和上下游完整 |
| 时间与生命周期 | 10 | 事前事中事后、更新、替代、暂停和退出明确 |
| 规模与条件跃迁 | 15 | 至少验证数量、频率、复杂度、风险和 AI 占比变化 |
| 价值与效率 | 10 | 有优先级、成本、注意力和停止机制 |
| 人机执行与自动化 | 10 | 人、AI、软件、Agent 的职责和关口明确 |
| 风险与韧性 | 10 | 有失败、异常、反例、回退、恢复和剩余风险 |
| 系统与复用 | 10 | 与其他链、资产、组织和不同场景关系明确 |
| 验证与证据 | 5 | 能用真实场景、证据或测试验证，不用自评代替事实 |

**目标：≥95／100。**

高分不代表内容越多越好。若出现大量同义重复、层级混乱、工具细节污染通用层、无限增加新链或无法说明实际状态转化，应扣分。

## 十一、优先深挖顺序

优先深挖同时满足“高频＋高重复＋高规模＋AI 可显著改变成本＋会形成长期资产”的链。

### P0

- **C09 任务执行**：Agent、Skill、检查点、长任务、恢复和人机责任。
- **C10 过程记录**：全量日志 vs 状态差额、自动记录、长期记忆和恢复入口。
- **C16 反馈处理**：单条反馈 vs 万条反馈、聚类、趋势、异常和旧问题匹配。
- **C17 总结提炼**：全量总结 vs 增量总结、变化摘要和消费端差异。
- **C19 经验沉淀**：与已有方法库比较，只沉淀新机制、新边界和失败模式。
- **C22 决策选择**：大量候选方案的机制去重、证据、反方路线、试验和动态重决策。
- **C23 信息处理／C24 个人学习**：已完成第一轮深挖，继续通过真实场景验证。
- **C30 维护更新退出**：环境变化后自动判断受影响知识、Skill、Workflow、流程和资产。

### P1

- **C02 需求澄清**：显性／隐性需求、多方冲突、行为信号、需求版本和 AI 辅助发现。
- **C03 价值排序**：北极星、组合价值、机会成本、动态优先级和自动重排。
- **C06 计划制定**：滚动计划、依赖变化、动态重排和多 Agent 调度。
- **C15 评估判断**：持续评估、多指标、不确定性、反事实和自动评估边界。

## 十四、结构类型审计：先判断当前画的到底是什么图

垂直深挖最常见的错误之一，是看到多个对象之间都可以画箭头，就把它们误认为同一种“层级”。今后结构审计先回答：**当前表达的究竟是流程、状态、对象父子、交付、产品、技术、时间、责任、数据还是追溯关系？**

### 14.1 十种常见结构视图

| 结构视图 | 核心问题 | 典型关系 | 常见误区 |
| --- | --- | --- | --- |
| **生命周期／流程图** | 先发生什么、后发生什么 | `A → B` | 把时间先后误当成父子分解 |
| **状态机** | 对象当前是什么状态、怎样迁移 | `state A → state B` | 把对象种类当成状态 |
| **对象分类／本体** | 有哪些对象类型、边界是什么 | `is_a / type_of` | 把分类树当执行流程 |
| **成果／WBS 树** | 项目要交付什么、工作怎样归属 | `deliverable → work package → task` | 把产品模块直接当工作包 |
| **产品／解决方案结构树** | 产品由什么能力、功能、模块组成 | `capability / feature / module` | 把技术服务当产品模块 |
| **技术结构树** | 系统如何按实现职责分解 | `system → subsystem → service/component` | 要求与页面或产品模块一一同名 |
| **时间轴** | 何时进入阶段、达到里程碑 | `phase / milestone / release` | 把里程碑当任务父节点 |
| **责任图** | 谁负责、批准、执行、接收 | `owned_by / accountable_to` | 用组织层级代替工作依赖 |
| **数据／领域模型** | 业务对象、数据、关系是什么 | `entity / relation / schema` | 把数据库表直接当业务对象 |
| **追溯图** | 为什么存在、由什么实现和证明 | `derived_from / satisfies / implemented_by / verified_by` | 只保留一个 `parent_id` 丢失关系语义 |

### 14.2 强制结构判别问题

当发现“模块、页面、任务、目录、阶段”等概念混在同一长链时，至少追问：

1. 这个箭头表达**先后**、**父子**、**依赖**、**实现**、**满足**、**验证**还是**时间覆盖**？
2. 两个节点是否真的处于同一抽象维度？
3. 如果换成后端/API、数据项目或无 UI 自动化，这一层是否仍然必须存在？
4. 当前对象属于通用 L2、场景 L3、真实工作流 L4，还是仅是具体工具／代码实现？
5. 是否因为某一种项目管理或软件开发方法常用，就错误提升为全领域规律？

### 14.3 结构审计纪律

- **流程完整 ≠ 对象结构完整**：知道“下一步做什么”不代表知道当前处理什么对象以及对象之间为何关联。
- **父子完整 ≠ 追溯完整**：知道 Task 属于哪个 Work Package，不代表知道它满足哪个需求。
- **实现完整 ≠ 价值完整**：代码与测试全部完成，不代表真实用户用途和净价值已经实现。
- **UI 完整 ≠ 产品完整**：页面地图很完整，也可能需求、功能或目标本身错误。
- **一张图不必解决所有关系**：复杂系统应允许多视图并通过稳定 ID 和明确关系连接，而不是追求一棵“万能树”。
