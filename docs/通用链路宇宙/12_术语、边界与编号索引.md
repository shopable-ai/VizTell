# 术语、边界与编号索引

> **最快使用方法**：先判断当前对象属于“信号、需求、问题、机会、目标、任务、风险还是异常”，再按核心链编号进入唯一正式定义。相同概念可以有多个日常说法，但只能有一个正式名称和一个稳定编号。

> 导航：[返回总览](00_总览与核心结论.md)｜[查看三十条基础链](02_通用基础链路库.md)｜[装配 L4 工作流](14_工作流装配方法.md)｜[查看场景测试](13_场景验证与覆盖矩阵.md)

## 一、术语使用规则

1. **正式名称唯一**：基础链以 `C01`—`C30` 和《02_通用基础链路库》的名称为准。
2. **别名只用于检索**：旧称、口语和领域术语必须指回正式名称，不建立第二份定义。
3. **对象、动作和链路分开**：任务、计划、证据是对象或产物；“任务执行链”“计划制定链”才是状态转化模块。
4. **通用与领域分开**：角色、工具、法规、数值阈值和行业术语进入 L3/L4，不因换了对象就新增基础链。
5. **相邻概念按判断问题区分**：不能仅凭词语相似合并，也不能仅凭名称不同拆分。

## 二、高频概念边界

| 概念 | 核心判断 | 主要输出 | 不等于 |
| --- | --- | --- | --- |
| 信号／触发 | 发生了什么，是否值得进入处理系统 | 已分类且有去向的事项 | 已确认需求、已定义问题 |
| 需求 | 谁在什么场景需要什么结果，为什么 | 经相关方确认的需求说明 | 用户提出的手段、预设功能 |
| 问题 | 当前状态与期望状态之间有什么重要差距 | 有对象、边界和影响的问题陈述 | 症状、情绪、未经验证的原因 |
| 机会 | 什么变化可能产生尚未满足的价值 | 待验证的受益者、价值和窗口假设 | 已证明的商业模式、普通待办 |
| 目标 | 期望在约束内达到什么状态 | 结果、范围、指标、期限和责任 | 任务清单、行动口号 |
| 要求 | 成果必须满足什么约束或能力 | 可追溯的必须项 | 成功后的全部价值 |
| 标准 | 用什么维度、阈值和证据作判断 | 可测量且可解释的判定规则 | 单一指标、事后随意改变的口径 |
| 计划 | 怎样组织成果、任务、依赖、资源和检查点 | 可启动、可监测的行动基线 | 目标本身、简单愿望列表 |
| 任务 | 由责任主体在约束内产生具体成果的工作单元 | 可提交的成果和状态 | 完整流程、长期系统 |
| 记录 | 对发生事实和状态的有上下文留存 | 可检索的事实记录 | 已证明某项主张 |
| 数据 | 按口径采集或生成的观测值 | 可处理的数据集 | 自动成为可靠证据 |
| 证据 | 能够支持或反驳特定主张的信息 | 主张—来源—可信度映射 | 所有记录、所有数据 |
| 未知 | 当前证据不足以判断的事项 | 已标注的知识边界和补证决定 | 错误、可以任意猜测的空白 |
| 假设 | 能够产生可检验预测的候选解释 | 待验证的预测和判定条件 | 已确认事实、正式需求 |
| 风险 | 尚未发生但可能影响目标的不确定性 | 等级、责任、触发器和应对 | 已经发生的异常或问题 |
| 问题事项 | 已出现并需要常规处理的差距或阻碍 | 分析、纠偏或改进任务 | 必须进入应急状态的事件 |
| 异常／事件 | 已发生且超出正常控制范围的情况 | 安全、止损、隔离和恢复状态 | 风险清单中的未来可能性 |
| 验证 | 是否符合规定要求 | 符合／不符合及证据 | 是否适合真实用途 |
| 确认 | 是否满足用户和真实情境用途 | 适用／不适用及证据 | 有权接收者已经接管 |
| 验收 | 有权者是否接受成果并承担后续责任 | 接受、拒收或条件接受 | 已产生长期效果和价值 |
| 效果 | 采取行动后实际发生了什么变化 | 结果、影响和副作用 | 变化一定由本行动造成 |
| 价值 | 效果相对成本、风险、副作用和分配是否值得 | 继续、扩大、调整或退出决定 | 指标达标、收入增长 |
| 监测 | 状态和趋势是否正在偏离 | 当前状态、趋势和预警 | 最终评价或原因解释 |
| 检查 | 当前对象是否存在缺陷或不符合项 | 缺陷和处置决定 | 长期效果评价 |
| 评估 | 依据标准和证据形成什么判断 | 带限制和置信度的结论 | 复盘原因、直接采取调整 |
| 反馈 | 外部或内部返回了什么信息 | 已核验、分类并分派的反馈项 | 已经完成修改 |
| 纠偏 | 怎样恢复当前有效基线 | 已验证的最小调整 | 改变目标或建立新基线 |
| 变更 | 是否应正式修改范围、计划、标准或版本基线 | 被批准的新基线 | 未经批准的临时调整 |
| 改进 | 怎样改变机制，使未来表现更好 | 待验证的新做法 | 单次恢复原计划 |
| 总结 | 发生了什么，核心结论是什么 | 准确压缩的事实和结论 | 原因复盘、可复用方法 |
| 复盘 | 为什么得到这一结果，下次改变什么 | 原因、边界和改进试验 | 只回顾过程或归档资料 |
| 沉淀 | 怎样把经验证经验转为可复用资产 | 方法、模板、流程、工具或课程 | 发布一份无人能用的文档 |
| 标准化 | 什么做法已跨人或跨场景复现，可成为统一做法 | 受控流程、标准和版本 | 将一次成功直接强制复制 |
| 维护 | 怎样保持既有有效状态 | 健康状态、周期、责任和记录 | 吸收重大变化的新版本 |
| 更新 | 怎样吸收变化并形成新版本 | 经验证和迁移的新版本 | 日常保持、随意覆盖旧版 |
| 迁移 | 怎样把对象或能力转到新环境 | 依赖已转移且验证通过的新状态 | 简单复制、扩大规模 |
| 归档 | 怎样退出活跃使用但保持必要检索 | 受控保留状态 | 继续运行、彻底删除 |
| 淘汰 | 怎样有序停止正式使用 | 已迁移依赖并安全停用的状态 | 暂停等待、直接删除记录 |
| 终止 | 目标尚未达成但决定停止投入 | 止损、责任结算和经验留存 | 已正常完成、暂时暂停 |
| 重启 | 怎样重新启用暂停或归档对象 | 重新核验后可用的活跃状态 | 无检查地恢复旧做法 |

| 坐标 | 回答的问题 | 例子 |

## 五、别名与改名治理

1. 正式名称变更时，稳定编号原则上不变。
2. 旧称至少保留一个版本周期，并明确“旧称 → 新正式名称”。
3. 领域文件可以使用更贴近业务的名称，但首次出现时标注对应核心链编号。
4. 同一编号不得在不同文件中指向不同状态转化。
5. 新名如果只是表达更自然，不构成新增基础链的理由。
6. 无法确认归属的候选词先进入审计记录，不直接建立正式编号。

## 六、项目、产品、设计与工程高频边界

这一组术语用于解决复杂项目里最常见的混层问题：**同一个箭头不能同时代表流程先后、父子分解、实现关系、依赖关系和时间关系。** 先判断当前描述的是“需求对象、产品／解决方案结构、技术结构、项目交付结构、时间结构还是代码组织”，再决定关系。

| 概念 A | 概念 B | 核心区别 | 层级建议 |
| --- | --- | --- | --- |
| 产品模块 | 技术模块 | 产品模块按用户／业务能力与职责组织；技术模块按软件实现职责、边界和依赖组织 | 软件 L3/L4 |
| 产品结构 | 项目结构 | 产品结构回答“产品由什么能力、模块、功能组成”；项目结构回答“为了交付要产生哪些成果和工作” | 前者软件 L3，后者项目 L3 |
| 信息架构／导航目录 | 文档目录 | 前者帮助用户寻找、理解和进入信息／功能；后者组织知识文件 | 软件/内容产品 L3/L4 vs 文档实现 |
| 文档目录 | 代码仓库目录 | 前者组织文档知识；后者组织源代码、配置、测试和构建资产 | L4 实现 |
| 页面／Screen | 组件／Component | 页面是用户交互上下文和任务承载面；组件是界面实现或复用单元 | UI 产品 L3/L4 |
| 用户流程 | 系统流程 | 用户流程描述人怎样完成目标；系统流程描述软件、服务和数据怎样内部处理 | 软件 L3/L4 |
| 产品需求 | 技术需求 | 产品需求说明用户／业务需要什么结果与约束；技术需求说明所选解决方案必须满足的技术属性与约束 | 软件 L3/L4 |
| 业务对象 | 数据表 | 业务对象是领域中的人、物、事件或关系；数据表只是可能的持久化实现 | 领域模型 vs L4 数据实现 |
| 功能拆解 | 任务拆解 | 功能描述产品／系统能做什么；任务描述人、团队、AI 或 Agent 为交付成果要做什么 | 产品结构 vs 项目执行 |
| 项目阶段 | 里程碑 | 阶段是一段生命周期／工作区间；里程碑是一个重要状态点或时间点 | 项目 L3/L4 |
| 交付物 | 工作包 | 交付物是需要得到和验收的结果；工作包是为了产生某部分交付物而可负责、可估算、可管理的工作单元 | 项目 L3/L4 |
| Story／用户故事 | Task／任务 | Story 是软件敏捷场景中的需求／价值切片表达；Task 是产生具体成果的执行单元 | Story 仅软件 L3/L4，Task 跨领域 |
| Subtask／子任务 | 最小执行动作 | 子任务仍是可管理、可分派、可验收的工作单元；最小动作只是执行时足够清楚的下一行为 | L4 执行 |

### 6.1 四种结构不要强行合成一棵树

复杂项目通常同时存在至少四种结构：

1. **价值／需求结构**：目标 → 问题／机会 → 用户需要 → 需求 → 能力／要求。
2. **产品／解决方案结构**：能力 → 功能 → 产品／业务模块 → 流程 → 页面／接口等交互面。
3. **技术实现结构**：系统 → 技术子系统 → 服务／组件／模块 → 接口 → 数据／代码实现。
4. **项目交付结构**：项目目标 → 成果 → 交付物 → 工作包 → 任务 → 子任务。

阶段、里程碑、发布日期、Sprint、Deadline 等属于**时间与运行视图**，通常挂接在交付物、工作包或任务上，不应再冒充上述结构的统一父节点。

### 6.2 UI、Story 与代码目录不是通用必经层

- 页面、导航、组件只在存在交互界面的产品中展开；后端、API、数据处理和自动化项目可以完全没有页面。
- Story 是一种特定软件／敏捷需求表达，不是所有项目都必须经过的通用层。
- 代码仓库目录是实现组织方式，不能要求与产品模块、业务模块或页面一一同名对应。
- 数据表是数据实现方式，不能直接替代业务对象或领域模型。

### 6.3 关系名称要表达真正语义

复杂项目不要只保存一个含糊的 `parent_id`。按需明确：

- `derived_from`：从什么上游需要／结论派生；
- `satisfies`：满足什么目标、需求或标准；
- `realized_by`：由什么产品／解决方案对象承载；
- `implemented_by`：由什么技术对象、任务或代码实现；
- `verified_by`：由什么检查、测试或证据证明符合要求；
- `validated_by`：由什么真实场景证据证明满足用途；
- `depends_on`：依赖什么前置对象；
- `owned_by`：谁对对象或结果负责；
- `supersedes`：替代哪个旧对象或版本。

这些是复杂场景的对象关系，不新增 C31，也不把对象关系误写成新的基础链。
