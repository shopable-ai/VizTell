# 软件 IT 与 AI 原生链路宇宙

> **定位**：本文件只说明软件、AI 和 Agent 怎样调用通用基础链。它是领域应用，不反向定义“通用链路宇宙”。模型参数、token、最大尝试次数、Agent 框架、数据库或部署平台等属于具体 L4 配置，不应进入通用总链。

> **软件业务总链**：用户问题与机会 → 需求与价值 → 调研已有产品／技术／项目 → 多方案比较 → 产品与技术方案 → 规格和任务 → 实现 → 测试 → 发布 → 运行 → 用户效果和商业价值 → 迭代、维护或下线 → 工程经验沉淀

> 导航：[返回总览](00_总览与核心结论.md)｜[基础链库](02_通用基础链路库.md)｜[通用总地图](01_通用总链与Level1-3总地图.md)｜[场景验证](13_场景验证与覆盖矩阵.md)

## 一、软件项目的主要组合链

### 1. 从想法到问题

> 模糊想法／观察 → 还原目标用户和场景 → 区分诉求、问题、机会和预设功能 → 明确价值 → 形成待验证的问题与需求

调用：C01、C02、C03、C20。

### 2. 从问题到方案

> 明确问题和约束 → 调研现有产品、开源项目、技术方案、组件、服务和案例 → 查失败案例与限制 → 形成多个结构不同的方案 → 验证关键假设 → 比较用户价值、实现难度、长期维护、依赖和风险 → 选择／组合／试验／放弃

调用：C23、C21、C22、C28。

软件场景尤其容易“看到需求就开始写代码”；本链要求先判断是不是已经有更便宜、更成熟或更可维护的解法。

### 3. 从方案到实现

> 目标与验收标准 → 业务流程和系统能力 → 功能／非功能要求 → 架构与接口 → 拆成果、任务和依赖 → 实现 → 测试 → 集成验证 → 提交发布

调用：C04—C14。

### 4. 从发布到真实价值

> 上线 → 监测运行 → 收集用户行为和反馈 → 判断是否真的解决问题 → 评价成本、质量和商业结果 → 继续迭代／维护／迁移／暂停／下线

调用：C11、C15、C16、C18、C30。

## 二、需求层级边界

软件项目至少要区分：

1. 原始信号；
2. 用户诉求；
3. 问题场景；
4. 业务需求；
5. 业务目标；
6. 业务链；
7. 系统能力；
8. 功能要求；
9. 非功能要求；
10. 接口和数据要求；
11. 验收标准；
12. 实现规格。

AI、产品经理或开发者提出的解释只能先作为候选，不能因为表达完整就自动升级为正式需求。

## 三、软件项目三条基线

- **意图基线**：用户、问题、价值、目标、范围、输入输出、约束、标准和主要未知。
- **框架基线**：主要模块、职责、业务流、数据流、接口、关键取舍和风险。
- **执行基线**：规格、任务、依赖、里程碑、测试、发布和回退安排。

三条基线是软件场景的 L3/L4 组织方式，不是新的通用基础链。

## 四、AI／Agent 作为执行方式

### AI 原生任务链

> 人明确问题、结果和标准 → 提供必要上下文 → AI 检索／分析／生成／执行 → 读取真实结果 → 核查事实或测试产物 → 人或规则在关键点判断 → 修改、接受或停止 → 沉淀可复用经验

这里最重要的边界是：

- AI 生成候选，不等于事实成立；
- 工具调用成功，不等于任务完成；
- Agent 声称完成，不等于已经验证、确认或验收；
- 自动化适合降低重复劳动，不自动获得目标、价值和责任的决定权。

### 多 Agent

只有在任务确实可以分解、并行收益大于协调成本、输入输出接口清楚时才需要多个 Agent。否则单一执行者通常更简单。

多 Agent 的通用逻辑仍然是 C26 分工协作：

> 共同成果 → 拆工作包 → 明确接口 → 并行执行 → 汇合检查 → 冲突处理 → 整体验收

具体 Agent 数量、模型、上下文长度、调用费用、重试次数、超时和框架实现全部属于 L4，不进入通用层。

## 五、人机责任边界

| 场景 | AI 可以辅助 | 不能自动替代的判断 |
| --- | --- | --- |
| 研究 | 搜索、整理、对比、提候选解释 | 问题边界、关键来源可信度、最终事实判断 |
| 需求 | 归纳诉求、生成候选需求 | 用户和业务确认 |
| 方案 | 生成选项、比较资料、找遗漏 | 重大取舍和责任承担 |
| 开发 | 代码、测试、重构、文档 | 需求正确性、发布责任、关键安全判断 |
| 测试 | 生成用例、执行检查、归类失败 | 验收标准和高风险最终判定 |
| 运营 | 归纳告警、提出诊断候选 | 重大事件指挥、对外承诺和不可逆操作 |

## 六、软件与 AI 常见失败返回

| 现象 | 优先返回 |
| --- | --- |
| 功能做出来但用户不要 | C02／C03／C04 |
| 需求不断变化 | 需求场景、目标和范围，而不是只加任务 |
| 技术方案实现困难 | C23 调研已有解法 → C22 重选方案 |
| 测试总失败 | 规格、实现或质量控制 |
| 上线正常但没有价值 | C15 效果价值 → 返回需求／目标／方案 |
| 自动化频繁出错 | 降低自动化范围，回到可检查步骤 |
| 供应商／模型依赖失效 | C28 风险 → 必要时 C29 恢复 → C30 迁移 |

## 七、软件生命周期出口

> **继续迭代／维护稳定／扩大使用／技术迁移／暂停开发／交接转移／归档／下线淘汰／重新启用**

下线不是“代码不再开发”这么简单，还应处理用户、数据、依赖、权限、文档和替代方案。

## 八、需求推理链：自然语言不能直接升级为正式需求

软件项目应把“用户说了什么”“现实是什么”“分析者怎样解释”“最终批准做什么”拆成不同状态。推荐链：

> **原始方向／要求 → 目标使用者 → 使用场景 → 当前做法 → 问题／痛点 → 用户真正想完成的任务／Job → 期望结果 → 约束 → 事实／明确表达／观察／推断／假设／未知 → 候选需求 → 补证／访谈／数据／原型／实验 → 已确认需求／已否定需求／暂缓需求 → 已批准需求 → 当前需求基线**

### 8.1 知识与证据状态

| 状态 | 含义 | 允许直接升级为正式需求吗 |
| --- | --- | --- |
| **事实 Fact** | 有足够证据支持的现实陈述 | 否；事实只是需求判断输入 |
| **用户明确表达 Explicit Statement** | 用户确实说过或明确要求过 | 否；表达可能是手段、误诊或局部需要 |
| **观察 Observation** | 看到了行为、数据或现象 | 否；尚未解释原因和价值 |
| **推断 Inference** | AI、产品经理、研究者从材料推出的解释 | 否；必须保留推断身份 |
| **假设 Assumption／Hypothesis** | 为推进决策暂时采用、可验证的候选前提 | 否；需要验证或显式接受风险 |
| **未知 Unknown** | 目前证据不足 | 否；应补证、保留未知或降低承诺 |
| **争议 Disputed** | 来源、利益相关者或证据冲突 | 否；需要处理冲突和决策权 |

### 8.2 需求生命周期

> **原始信号 → 候选需求 → 待补证 → 已验证需求 → 已批准需求 → 基线需求 → 实现中 → 已实现 → 已验证 → 已确认用途／已验收 → 维护／变更／替代／退休**

旁路状态包括：**已否定、暂缓、无法判断、被替代**。

### 8.3 AI 需求纪律

1. AI 可以归纳、聚类、改写和提出**候选需求**，但不能把自己的推断标成用户明确表达。
2. “用户没有反驳”不能当成需求批准；需要按项目风险采用明确确认、证据或有权者决策。
3. 完整、专业、技术细节丰富的描述仍可能只是错误假设，不能因表达质量自动提升可信度。
4. 基线不是“永远不变”，而是当前被批准、可以用于下游设计、实现和测试的受控版本；变化后需要更新追溯关系和影响分析。
5. 下游发现问题时，要判断是实现错误还是需求本身错误，不能只通过增加任务修补上游误判。

## 九、从需求到能力、功能与产品结构

推荐软件产品的主分解视图：

> **业务目标 → 用户／利益相关者需要 → 场景／Job／Use Case → 已确认需求 → 产品／系统能力 Capability → 功能与质量要求 → 产品／业务模块**

注意：这不是要求每层严格一对一。能力、功能和模块是不同视图：

- **能力**回答“为了满足需求，系统整体必须具备什么能力”；
- **功能**回答“系统必须能够做什么”；
- **质量／非功能要求**回答性能、安全、可靠性、可用性、可维护性等“做到什么程度”；
- **产品／业务模块**按用户心智、业务职责、ownership 或产品边界组织能力和功能。

一个功能可能横跨多个模块，一个模块也可能承载多个能力。不要为了画树强制一对一映射。

### 9.1 范围与 MVP

方案被选择后，在进入细结构前至少明确：

> **目标价值 → 当前必须验证／交付的能力 → MVP／首期范围 → 明确不做事项 → 后续候选范围 → 变更条件**

MVP 的意义是用最小范围验证关键价值和风险，不是简单把完整产品随机删成功能更少的版本。

## 十、有 UI 的交互产品分支

只有当产品确实存在面向人的交互界面时，才展开页面与信息架构：

> **功能／用户任务 → 用户旅程／用户流程 → 信息架构 → 导航／入口结构 → 页面地图 → 页面／Screen → 页面区域 → UI 组件 → 状态 → 操作 → Loading／Empty／Error／Permission 等异常与权限状态**

关键边界：

- **用户旅程**描述用户跨时间和触点的整体经历；**用户流程**描述完成一个具体目标的行为路径；
- **信息架构**组织用户如何理解、寻找和进入信息／功能，不等于仓库文件夹目录；
- **页面**是用户交互上下文，不等于代码组件；
- **组件**是界面实现／复用单元，不应反向决定产品模块；
- 页面很多但用户不用时，可能需要返回用户流程、功能、需求、问题甚至目标，而不是默认继续改 UI。

页面不是软件项目的通用必经层。后端、API、数据管道、Agent 和自动化项目可以完全跳过本节。

## 十一、无 UI、后端、数据与自动化分支

对于没有页面或页面不是主要交付面的系统，推荐：

> **功能／系统能力 → 服务／系统流程 → API／Command／Event／Job／Trigger → 输入输出 Contract → 数据处理与状态变化 → 异常／Retry／Idempotency／权限 → 输出／副作用 → 监测与证据**

按项目实际情况选择，不要求同时具备 API、Event、Job 和数据库。

典型分支：

- **后端/API**：Use Case → API Contract → Domain／Service Logic → 数据／外部依赖 → 响应与错误 → 测试；
- **数据处理**：输入源 → 校验 → 转换／计算 → 质量检查 → 输出数据集／指标 → 血缘和运行证据；
- **无 UI 自动化**：Trigger → 条件判断 → 动作 → 异常／重试 → 结果 → 通知／记录；
- **Agent 系统**：任务与边界 → 上下文 → 工具／模型调用 → 状态更新 → 人工关口／例外 → 可验证输出。

## 十二、产品结构到技术结构

产品结构回答“需要提供什么”，技术结构回答“用什么职责边界实现”。推荐逐层建立：

> **产品／解决方案需求 → 技术需求与约束 → 技术方案 → 系统架构 → 技术子系统 → 服务／技术模块／组件 → 接口与依赖 → 数据／状态模型 → 代码与部署实现**

必须保持以下边界：

- **产品模块 ≠ 技术模块**；
- **业务对象 ≠ 数据表**；
- **页面／功能 ≠ 代码目录**；
- **领域模型 ≠ ORM／数据库 Schema**；
- **系统能力 ≠ 单个微服务**。

代码仓库目录是 L4 实现组织方式，可以按语言、框架、构建、部署和团队 ownership 组织，不要求与产品模块同名或一一对应。

## 十三、软件项目四棵树与一张追溯图

复杂软件项目不要把所有对象强行塞进一棵树。至少区分：

1. **价值／需求树**：业务目标 → 用户问题／机会 → 需要 → 需求 → 能力；
2. **产品／解决方案结构树**：能力 → 功能／质量要求 → 产品模块 → 用户流程／页面或 API／Job；
3. **技术实现树**：系统 → 技术子系统 → 服务／组件 → 接口 → 数据／代码；
4. **项目交付树**：项目成果 → 交付物 → 工作包 → Task → Subtask；
5. **双向追溯图**：连接上述对象与测试、验收和实际价值。

项目交付树的通用规则见 [15_项目与复杂任务链路宇宙.md](15_项目与复杂任务链路宇宙.md)。

### 13.1 核心追溯链

> **目标 ↕ 用户问题／机会 ↕ 需求 ↕ 能力 ↕ 功能／质量要求 ↕ 产品模块 ↕ 页面／API／Job／Event ↕ 技术模块 ↕ 实现／代码 ↕ 测试 ↕ 验证证据 ↕ 真实用途确认 ↕ 验收 ↕ 用户效果 ↕ 净价值**

复杂场景按需使用：

- `derived_from`：从何种上游需要／结论派生；
- `satisfies`：满足哪个需求／标准；
- `realized_by`：由哪个产品／解决方案对象承载；
- `implemented_by`：由什么技术模块、工作包、任务或代码实现；
- `verified_by`：由什么测试／检查证明符合规定要求；
- `validated_by`：由什么用户／真实场景证据证明满足用途；
- `depends_on`：依赖什么；
- `owned_by`：谁负责；
- `supersedes`：替代什么旧对象／版本。

任何 Task 都应能向上回答“为什么存在”；任何基线需求都应能向下回答“由什么实现、由什么测试证明、由谁验收”。

## 十四、从实现失败和价值失败返回正确层

软件项目的返回不只按 C 链，还可以利用追溯图定位对象层：

| 现象 | 优先检查／返回 | 不应默认做什么 |
| --- | --- | --- |
| 局部代码错误 | 实现／代码 | 重做整个需求 |
| 接口／集成失败 | Interface／Architecture／Technical Module | 只增加前端补丁 |
| 性能、安全、可靠性不达标 | 非功能要求／技术方案／架构 | 把测试阈值调低掩盖问题 |
| 页面局部难用 | 页面／交互／用户流程 | 自动新增更多页面 |
| 页面很多但用户不用 | 用户流程 → 功能 → 需求 → 问题 | 只做 UI 美化 |
| 功能正确但用户不需要 | 需求／用户问题 | 继续堆功能 |
| 测试持续失败 | 实现／设计；必要时返回需求质量 | 只反复重跑测试 |
| 验收通过但真实效果差 | Solution／Requirement／Problem | 把“按规格完成”当成价值实现 |
| 用户效果好但经济性差 | 成本／商业价值／范围／方案 | 仅优化局部代码 |
| AI 自动化频繁失败 | 自动化边界／流程／模型与工具选择 | 无限增加重试次数 |

最终仍遵守《03_链路关系、关口与运行协议》的**最小充分返回**：先回最近能解释根因的有效层；只有根因确实在上游时才继续上溯。
