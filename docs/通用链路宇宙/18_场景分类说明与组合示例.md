## 一、为什么“场景分类”和“领域分类”必须分开

现实中的一句话通常同时包含两类信息：

- **现在发生了什么／我要解决什么**：决定从哪条链进入；
- **事情发生在哪里**：决定调用哪个领域知识、规则和具体工作流。

例如：

> “公司最近客户流失严重。”

它可以同时标记为：

- 主场景：S05 问题／障碍；
- 次场景：S07 信息／研究、S06 决策／选择；
- 领域：D05 公司组织；
- 主体：P04/P05；
- 复杂度：R03；
- 生命周期：L03/L04。

如果把“公司”“问题”“研究”“项目”混成同一级分类，就会出现重复目录：公司问题链、软件问题链、生活问题链、学习问题链……而它们的很多核心转化其实相同。

因此：

> **主场景决定入口，领域提供上下文，主体决定协作强度，复杂度决定展开程度，生命周期决定对象当前所处阶段。**

## 二、为什么同一条链会被不同场景调用

基础链是稳定的状态转化，现实场景是这些转化的组合和入口。

例如 C22 决策选择可以出现在：

- 买电脑；
- 选工作；
- 选择项目方案；
- 选择供应商；
- 是否继续维护一个产品；
- 公司是否进入新市场。

对象完全不同，但共同状态都是：

> **多个可行动选项 → 基于目标、证据和约束作出选择。**

所以场景分类不能为了“看起来具体”而复制基础链。

## 三、十五类主场景的边界说明

### S01 信号／变化 vs S03 机会／想法

**信号／变化**只回答“发生了什么、是否值得进一步处理”。

> 数据变了 → 用户行为变了 → 身体状态变了 → 市场出现变化

**机会／想法**已经包含潜在价值假设：

> 这个变化能不能创造价值 → 是否值得探索 → 要不要变成目标或项目

因此：

> S01 可以流向 S03，也可以流向 S05、S13 或直接忽略。

### S02 需求／请求 vs S04 目标／改变

需求是：

> 谁在什么情境下需要什么结果，为什么？

目标是：

> 在明确边界、标准和期限下，要达到什么状态？

“我想减肥”仍可能只是愿望；当结果、边界和判断标准明确后，才进入目标状态。

### S04 目标／改变 vs S05 问题／障碍

目标从期望状态出发：

> 我要达到 X。

问题从差距或障碍出发：

> 为什么现在达不到 X？

两者经常同时出现，但处理顺序不同：

- 目标不清 → 先 C04/C05；
- 已有清楚目标但出现障碍 → C20/C21；
- 发现目标本身错误 → 从问题链返回目标链。

### S05 问题／障碍 vs S07 信息／研究

问题是待解释或待解决的差距；研究是为了减少未知而采取的认知活动。

> “销量下降”是问题。  
> “调查销量下降的原因、用户行为和竞品变化”是研究。

因此通常是：

> S05 → S07 → 原因模型／方案 → S06。

### S07 信息／研究 vs S08 学习／能力

研究改变的是**外部知识状态**：

> 不知道 → 有可用知识模型。

学习改变的是**人的能力状态**：

> 不会 → 能理解、回想、辨别、应用和迁移。

所以“资料看完了”不能自动升级成“已经掌握”。

### S09 任务／执行 vs S10 项目／复杂任务

任务通常具有清晰成果、范围和近期完成条件：

> 写报告、提交报价、修复一个明确缺陷。

项目／复杂任务通常具有以下至少一项：

- 多阶段成果；
- 多个关键未知；
- 多种可能方案；
- 多依赖；
- 多人协作；
- 较高试错成本；
- 需要多轮验证和阶段决策。

一个人也可以运行复杂项目，不要求一定有团队。

### S11 沟通／协作／交接 vs S09 执行

执行回答“成果怎样产生”；协作回答“多个主体怎样形成同一结果”。

如果一个任务没有明显多人接口，就不必强行增加协作流程。

### S12 监测／反馈／偏差／改进 vs S13 风险／异常／恢复

S12 仍在正常控制范围内：

> 延期、普通质量问题、用户反馈、效果下降。

S13 表示未来高影响不确定性或已经超出正常控制范围的事件：

> 重大故障、数据泄露、人身危险、严重供应中断。

普通偏差走 C13；事件发生后切 C29，不继续把它当“风险概率”讨论。

### S14 验证／验收／价值评估 vs S15 生命周期

S14 判断：

> 做对了吗？有用吗？被接收了吗？值得吗？

S15 决定：

> 接下来继续、维护、扩大、迁移、暂停、交接、归档、淘汰还是重启？

所以通常：

> S14 评价 → S15 延续决定。

## 四、常见的复合场景模式

### 1. 想法变项目

> **S03 机会／想法 → S02 需求 → S04 目标 → S07 研究 → S06 决策 → S10 项目 → S14 价值评估 → S15 生命周期**

典型：新产品、创业想法、个人大型计划。

### 2. 问题解决

> **S05 问题 → S07 研究 → 原因分析 → S06 决策 → S09/S10 执行 → S14 评估**

典型：效率下降、销量下降、学习效果差、系统性能问题。

### 3. 反馈驱动改进

> **S12 反馈 → 核验事实 → 判断层级 → 动作问题回 S09｜计划问题回 S10/C06｜方案问题回 S06｜目标问题回 S04｜需求问题回 S02**

这比“收到反馈就改需求”更稳定。

### 4. 学习服务于真实任务

> **S09/S10 真实任务 → 发现能力缺口 → S08 学习 → 练习 → 回到 S09/S10 → S14 能力与结果评估**

学习不是独立无限循环，而是解决真实表现差距。

### 5. 风险变事件

> **S13 风险识别 → 预防与预案 → 事件发生 → S13 异常恢复 → S05 原因问题 → S12 改进 → S15 更新维护**

### 6. 成果进入生命周期

> **S09/S10 完成 → S14 验证／验收／价值 → S15 维护／扩大／迁移／退出**

交付不是长期对象的终点。

## 六、从自然语言快速识别入口

### “我有个想法……”

优先检查 S03；如果事情预计会持续多阶段，再加 S10。

### “我想做到……”

优先检查 S04；如果只是一句愿望，先回 S02/S03 判断真实需要和价值。

### “为什么会这样……”

优先检查 S05；如果缺资料，再调用 S07。

### “A 和 B 哪个更好……”

优先检查 S06；信息不足时先 S07，不要直接凭偏好选。

### “我不知道……”

若缺外部信息 → S07；若知道但不会 → S08。

### “这件事已经定了，帮我做完……”

如果输入、结果和标准清楚 → S09；如果包含多阶段、多未知 → S10。

### “做着做着不对了……”

优先 S12，并判断偏差根因在哪一层。

### “已经出事故了……”

优先 S13/C29，不从普通任务链重新开始。

### “做完了，接下来怎么办……”

先 S14 判断真实结果，再 S15 决定生命周期。

## 七、场景分类不是互斥标签体系

现实事件通常是动态迁移的：

> **机会 → 目标 → 项目 → 执行 → 偏差 → 问题 → 研究 → 决策 → 再执行 → 评估 → 生命周期**

所以不能要求一个对象从开始到结束只能属于一个场景分类。

正确理解是：

> **场景标签描述“此刻最主要的工作状态”，它可以随状态变化而切换。**

## 八、什么时候才值得建立新的独立场景宇宙

新场景文件只有同时满足以下条件时才值得建立：

1. 跨多个领域高频出现；
2. 需要多条 C 链形成稳定组合；
3. 有独特的入口、返回、停止和生命周期特征；
4. 仅靠 `17` 的一行入口已经难以直接使用；
5. 能承担独立职责，而不是复制已有领域文件或基础链。

目前已经满足这一条件的典型跨域场景有：

- [15_项目与复杂任务链路宇宙.md](15_项目与复杂任务链路宇宙.md)；
- [16_阅读学习与知识研究链路宇宙.md](16_阅读学习与知识研究链路宇宙.md)。

普通决策、沟通、反馈、异常、验收、生命周期等虽然高频，但已有 C 链、09 文件和领域场景能清楚承载，因此暂不机械拆成新的“宇宙”。

## 九、对后续维护的纪律

- `17` 保存**稳定分类结论、入口规则和五维坐标**；
- `18` 保存**解释、边界、案例和组合模式**；
- `13` 负责**用基准场景验证结构是否跑通**；
- `15/16` 负责**需要深度展开的跨域 L3 场景**；
- `04—08` 负责**领域中的具体场景组合**；
- `02` 始终是 C01—C30 的唯一正式基础链定义。

如果未来大量例子继续增加，应优先扩展本文件或建立案例索引，不要把解释性内容重新塞回总览和基础链库。
