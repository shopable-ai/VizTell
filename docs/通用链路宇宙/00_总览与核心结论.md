# 通用链路宇宙：总览与核心结论

> **最重要的总链**  
> **发现信号 → 澄清需要／问题／机会／任务 → 判断价值与优先级 → 明确目标、边界与完成标准 → 了解现状与关键差距 → 拆解目标和问题 → 搜集信息、已有解法与经验 → 形成多个可行方案 → 核查证据与失败条件 → 用必要的小试验降低关键未知 → 比较效果、成本、风险与可逆性 → 选择方案 → 制定计划、配置资源与责任 → 执行〔记录＋监测＋沟通＋质量＋风险〕→ 发现偏差并按根因返回 → 提交、验证、确认与验收 → 评估实际效果与价值 → 总结、复盘、沉淀 → 维护／扩大／迁移／暂停／交接／归档／淘汰／重启**

## 一、核心结论

1. 通用链路宇宙首先研究的是：**人在生活、学习、工作、项目和组织活动中反复经历哪些状态转化，以及这些转化怎样连接、分支、循环和退出。**
2. L0 提供完整生命周期；L1 提供十一类功能系统；L2 保存 C01—C30 稳定基础链；L3 把基础链组合成项目、学习、决策、软件、OPC 等场景；L4 才加入具体角色、工具、规则和环境参数。
3. **目标设定、目标拆解、问题定义、信息处理、方案生成、决策选择、计划、执行、评估、复盘和生命周期**是链路本体；模型名称、Agent 最大尝试次数、接口参数、某个软件工具或某个行业表单不是通用链路。
4. 大任务和项目不能直接从“目标”跳到“执行”。中间通常还需要：了解现状 → 拆目标／拆问题 → 找已有解法 → 形成多方案 → 查失败经验 → 必要时咨询实践者 → 验证关键未知 → 比较方案 → 再决策和计划。
5. “找别人已经解决过什么”是研究和决策的重要组合：产品、工具、开源项目、服务、论文、标准、案例和有经验的人都可以成为输入，但它们不是新的基础链。
6. 咨询不是权威替代判断。咨询得到的是经验和证据输入，仍需结合目标、情境、反例和实际验证决定是否采用。
7. 评估不能只在最后出现。立项前评估值不值得做，方案阶段评估哪个更合适，执行中评估是否偏离，完成后评估真实效果与净价值。
8. 记录、监测、沟通、质量、风险、合规和变更可以与执行并行；它们的强度由场景决定，不应把所有任务都工程化。
9. 验证、确认、验收、效果和价值必须分开：符合要求不等于适合真实用途，被接收不等于产生长期价值。
10. 完成不是唯一终点。长期对象还会进入维护、扩大、迁移、暂停、交接、更新、归档、淘汰或重新启用。
11. **项目／复杂任务**和**阅读学习／知识研究**都是跨生活、工作和行业反复出现的高频 L3 场景，因此分别建立独立场景宇宙；它们不新增 C 编号，也不复制 C23、C24 等正式定义。
12. **现实场景入口和领域分类必须分开**：现实场景回答“现在发生了什么、从哪里进入”，领域回答“事情发生在哪里”。同一个问题场景可以发生在健康、工作、公司或软件领域。
13. 现实场景采用五维坐标：**主场景类型 × 领域 × 主体规模 × 复杂度／风险 × 生命周期阶段**。一个现实事件可以有多个标签，但只选当前最需要改变状态的主场景作为入口。
14. 稳定分类结论与解释性内容分开维护：`17` 保存 15 类主场景入口和五维坐标，`18` 保存边界解释、复合场景和大量例子，避免总览与基础链库被解释性内容淹没。
15. **复杂项目不能只靠一条越来越长的流程表达。** 除了“状态怎样变化”的链路，还要区分价值／需求结构、产品／解决方案结构、技术实现结构和项目交付结构，并用双向追溯关系连接目标、需求、实现、测试、验收证据和实际价值。
16. **AI 推断不能自动升级为真实需求。** 软件／数字项目应区分事实、用户明确表达、观察、AI／分析者推断、假设、未知和争议，并让候选需求经过补证、确认／批准和基线管理后才进入稳定下游实现。
17. **页面、导航、Story、Sprint、数据库表和代码目录不是通用必经层。** 有 UI 的产品按需展开页面和信息架构；后端、API、数据 Pipeline、无 UI 自动化和 Agent 可以走独立分支。
18. **项目分解优先拆成果和交付物，再拆工作。** 通用项目交付视图采用“成果 → 交付物 → 工作包 → Task → Subtask”，阶段、里程碑和 Release 属于时间视图；高未知工作先通过调研／原型／实验获取证据，不制造虚假的远期精确任务树。
19. **流程关系、父子关系、依赖关系、实现关系和验证关系必须分开。** 一个箭头不能同时承担所有语义；复杂项目需要明确 `depends_on`、`satisfies`、`implemented_by`、`verified_by` 等关系，并在失败时按照最近根因层返回。

## 二、十一类运行系统

> **感知与定向｜研究与认识｜选择与验证｜计划与配置｜执行与创造｜沟通与协作｜记录与保障｜评估与改进｜学习与能力｜沉淀与复制｜运维与退出**

十一系统用于回答“现在处在哪类问题里”；它们不是一条固定顺序，也不是十一套互相重复的流程。

## 三、重要的通用组合链

### 1. 普通事项

> 发生什么 → 想得到什么 → 是否值得做 → 下一动作 → 执行 → 检查结果 → 继续／调整／结束

### 2. 复杂问题

> 定义问题 → 收集事实 → 拆解问题 → 分析原因与未知 → 搜索已有认识和解法 → 形成解释／方案 → 验证关键假设 → 决策 → 执行 → 评估

### 3. 项目或较大任务

> 明确价值 → 目标与标准 → 现状与差距 → 目标拆解＋问题拆解 → 调研已有方案／产品／工具／案例 → 生成多方案 → 查失败路径和限制 → 必要时咨询有经验者 → 小试验证关键未知 → 比较方案 → 选择 → 计划资源 → 分阶段执行 → 阶段评估与纠偏 → 验收 → 效果价值 → 复盘沉淀 → 延续或退出

详见 [15_项目与复杂任务链路宇宙.md](15_项目与复杂任务链路宇宙.md)。

### 4. 学习与知识

> 明确想解决的问题／达到的能力 → 找资料 → 筛选 → 阅读与提取 → 对比旧知 → 去重、冲突与增量判断 → 理解 → 回想与练习 → 场景应用 → 反馈 → 掌握评估 → 更新知识

详见 [16_阅读学习与知识研究链路宇宙.md](16_阅读学习与知识研究链路宇宙.md)。

### 5. 从现实描述找到入口

> **自然语言描述 → 识别主场景 → 标记次场景 → 叠加领域／主体／复杂度／生命周期 → 映射 C 链入口 → 打开对应深度场景文件 → 运行最短必要组合**

现实入口的 15 类主场景和五维坐标见 [17_现实场景分类与入口地图.md](17_现实场景分类与入口地图.md)；相邻场景边界、复合模式和跨领域例子见 [18_场景分类说明与组合示例.md](18_场景分类说明与组合示例.md)。

### 6. 复杂项目的纵向追溯

> **目标／价值 ↕ 问题／机会 ↕ 需求 ↕ 能力／方案 ↕ 产品／技术结构 ↕ 交付物／工作包／任务 ↕ 实现 ↕ 测试与证据 ↕ 确认／验收 ↕ 实际效果与净价值**

这不是新的固定流水线，而是把复杂项目中不同对象连接起来的追溯视图。项目交付结构见 `15`，软件产品／技术结构与需求状态见 `08`，总图见 `01`。

## 四、层级边界

- **L0**：任何长期事项从触发到退出的生命周期。
- **L1**：按功能寻找当前位置和下一类动作。
- **L2**：完成一种跨领域稳定复现的状态转化；正式核心仍为 C01—C30。
- **L3**：把多个 L2 组合成“项目推进”“文章处理”“软件需求”“经营机会”等场景链，并提供现实场景入口导航。
- **L4**：具体的人、工具、软件、参数、时间、权限、行业规则和表单。

判断一项内容是否应该进入通用层时，先问：**它是在描述一种普遍状态转化，还是只是在描述某种实现方式？** 后者默认下沉。

## 六、统一结束状态

| 状态 | 含义 |
| --- | --- |
| 完成 | 目标达成、成果被接收、遗留责任明确 |
| 继续 | 当前路径有效，进入下一周期 |
| 扩大 | 已验证做法应用到更多对象或规模 |
| 维护 | 保持既有有效状态 |
| 更新 | 吸收变化形成新版本 |
| 迁移 | 转到新环境并验证可用 |
| 暂停 | 暂停投入并保存恢复条件 |
| 交接 | 转移资料、责任、权限和关键知识 |
| 转向 | 保留有价成果，改变目标、用户或方案 |
| 归档 | 退出活跃使用但保留检索和证据 |
| 淘汰 | 有序停止使用并处理依赖 |
| 重启 | 重新检查后恢复活跃使用 |
| 终止 | 目标未完成但有理由停止继续投入 |
