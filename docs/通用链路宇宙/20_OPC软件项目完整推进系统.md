# OPC 软件项目完整推进系统

> **状态**：高召回候选版。当前目标是先尽量完整覆盖一个人／OPC 从原始需求到真实交付、运行、价值验证和生命周期退出的全过程，后续再做去重、裁剪、必选／条件／可选分类与阶段关口收敛。
>
> **定位**：本文件是 [06_OPC链路宇宙.md](06_OPC链路宇宙.md)、[08_软件IT与AI原生.md](08_软件IT与AI原生.md)、[15_项目与复杂任务链路宇宙.md](15_项目与复杂任务链路宇宙.md) 的高颗粒度组合专题。它不新增 C 编号，不替代 C01—C30 的正式定义，也不要求所有项目机械走完每个步骤。

## 一、核心结论

一个人／OPC 的软件项目不应被压缩成：

> 需求 → 方案 → 任务 → 写代码 → 测试 → 发布

更完整的结构应理解为：

> **1 条主生命周期 + 1 条向下分解链 + 1 条向上实现与集成链 + 1 条向上验证链 + 多条横向治理链。**

### 1. 主生命周期

> **触发／需求 → 需求发现 → 价值与机会判断 → 需求验证与基线 → 立项 → 项目定义 → 方案研究 → 技术可行性验证 → 方案决策 → 产品／系统设计 → 架构设计 → 逐层分解 → 任务与技术单元设计 → 开发实现 → 单元验证 → 模块与系统集成 → 系统验证 → 真实场景确认 → 发布准备 → 部署发布 → 运行监测 → 反馈与问题处理 → 价值验证 → 迭代维护 → 复盘沉淀 → 迁移／暂停／下线／退出**

#### 1.1 主生命周期快速执行地图

> **阅读方式**：上面的主生命周期负责看顺序；本节负责快速理解“每一阶段主要做什么”；后面的 A01—Y17 用于真正执行时再展开。

**触发／需求：** 原始想法、问题、用户反馈、客户要求、功能想法、商业／技术机会、外部变化；保留原始表达并区分问题、需求、目标、功能想法和方案想法。

**需求发现：** 明确用户、使用者、付费者、场景、当前做法、问题、痛点、原因假设和期望结果，区分表面诉求与真正需要。

**价值与机会判断：** 判断用户价值、商业价值、战略／资产价值、学习价值、机会成本和不做的后果，初步决定是否值得继续投入。

**需求验证与基线：** 扫描现状、竞品、替代方案和已有技术，扩展候选需求，通过正常／边界／反例场景和最小实验补证，筛选要／不要／暂缓项，形成当前需求基线。

**立项：** 判断正式做、暂缓、放弃、先调研还是先实验；确认主要风险、关键未知、资源承载能力、停止条件和转向条件。

**项目定义：** 明确项目目标、非目标、范围、MVP／首期范围、成功标准、完成标准、版本目标以及时间、资金、AI／API 和个人注意力预算。

**方案研究：** 搜索产品、开源项目、API、SaaS、框架、模型、服务和实践案例，比较直接使用、购买、改造、组合、自建、外包或不做等候选方案。

**技术可行性验证：** 找出高风险技术点，用 PoC、Prototype、Benchmark 或最小实验验证能不能做、效果够不够、性能和成本能否接受、关键依赖是否可靠。

**方案决策：** 比较价值、技术难度、开发／运行／维护成本、性能、安全、扩展性、锁定风险、可逆性和失败模式，选定方案并保留关键决策记录。

**产品／系统设计：** 将正式需求转成系统能力、功能要求、质量要求、业务对象、用户流程、服务流程以及有 UI／无 UI 的交付表面。

**架构设计：** 明确系统边界、子系统、服务／技术模块、组件、接口、数据、状态、依赖、权限、安全、错误恢复、可观测性、部署、配置和备份策略。

**逐层分解：** 区分价值／需求树、产品结构树、技术实现树和项目交付树，从项目目标逐层拆到成果、交付物、工作包、Task／Subtask，并保持上下游追溯。

**任务与技术单元设计：** 判断 Task 是否继续抽成 Skill、Script、Tool、Component、Adapter、Prompt 等独立技术单元；实现前明确职责、输入、输出、格式、Schema、依赖、权限、异常、副作用、性能、成本、测试样例和完成条件。

**开发实现：** 读取上游需求、设计、接口和 Task 契约，完成最小可工作实现，实际运行、读取真实输出、测试、自检、修复、Review、提交并保存执行证据。

**单元验证：** 对函数、组件、Skill、Script、Tool、API 等独立单元执行静态检查、正常／边界／错误样例和契约测试，确认结果不是“能运行”而是真正符合约定。

**模块与系统集成：** 将实现逐级组装为技术单元、Component、Module、Subsystem 和 System，检查接口、数据、状态、权限、错误、超时、重试、并发、依赖、配置和日志。

**系统验证：** 按项目风险执行集成、系统、端到端、回归、异常、权限、安全、性能、负载、恢复、迁移和兼容性测试，确认完整系统符合规定要求。

**真实场景确认：** 用真实用户、真实任务、真实数据和真实使用条件验证系统是否满足最初用途；区分“按规格做对”与“做了真正需要的东西”。

**发布准备：** 确认发布范围、版本、Changelog、配置、数据迁移、Feature Flag、权限、Secret、备份、回滚、监控、告警、文档、Support、已知问题和发布清单。

**部署发布：** Build、Package、Deploy、Migration、Smoke Test、Health Check、流量切换、功能开启、发布后测试和监测，必要时执行回滚。

**运行监测：** 持续观察 Logs、Metrics、Trace、用户行为、错误率、性能、成本、容量、告警、用户反馈、漏洞以及 Model／API／供应商和依赖变化。

**反馈与问题处理：** 收集 Bug、异常、新需求、UX、性能、安全、架构、数据、成本和商业问题，先定位最近根因层，再止损、修复、回归、发布和防复发，而不是默认新增 Task。

**价值验证：** 检查真实使用、任务完成率、用户结果、留存、付费／续费、口碑、支持负担、基础设施／模型成本、创始人时间成本、毛利和机会成本，区分技术成功、产品成功和商业成功。

**迭代维护：** 根据运行证据和价值结果决定修 Bug、优化体验／性能／成本、增加能力、重构、更新依赖／模型／数据／架构或调整范围，并同步更新基线和回归测试。

**复盘沉淀：** 还原目标、假设、决策、成功、失败、返工和隐藏成本，将可复用部分沉淀为代码、Skill、Script、Tool、Template、Prompt、Fixture、Dataset、Benchmark、Workflow、Checklist、Decision Record 和文档。

**迁移／暂停／下线／退出：** 根据长期净价值选择继续开发、稳定维护、扩大、重构、重写、技术迁移、替换依赖、暂停、归档、开源、出售、交接、合并、下线、数据迁移、删除或重新启用。

### 2. 向下分解链

> **目标／价值 → 用户问题／机会 → 已确认需求 → 系统能力 → 功能与质量要求 → 产品／解决方案结构 → 技术结构 → 交付物 → 工作包 → Task → Subtask → 独立技术单元〔按需〕 → 输入输出契约 → 测试规格 → 实现**

### 3. 向上实现与集成链

> **实现 → 独立技术单元 → Component → 技术模块 → 子系统 → System → Product／Solution**

### 4. 向上验证链

> **单元验证 → 契约／组件验证 → 模块集成测试 → 子系统集成测试 → 系统验证 → 用户真实用途确认 → 验收 → 用户效果验证 → 商业／净价值验证**

### 5. 横向治理链

贯穿全程的至少包括：

- 需求追溯；
- 决策；
- 风险；
- 质量；
- 安全与隐私；
- 配置与版本；
- 资源与成本；
- 证据；
- 变更；
- 知识沉淀。

因此，本文件不是一条越来越长的平面流程，而是一套项目推进结构。

## 二、A：触发与原始需求

### A01 原始触发

来源可以包括：

- 一个灵感；
- 自己遇到的问题；
- 用户反馈；
- 客户要求；
- 想增加一个功能；
- 想开发一个软件；
- 商业机会；
- 技术变化；
- 竞品变化；
- 现有系统缺陷；
- 运营或故障信号。

### A02 保存原始表达

先保留：

- 用户原话；
- 原始上下文；
- 触发时间；
- 当前期望；
- 已知事实；
- 明确未知。

不要一开始就让 AI 把自然语言自动改写成正式需求。

### A03 区分触发类型

至少区分：

- 问题；
- 需求；
- 目标；
- 功能想法；
- 方案想法；
- 商业机会；
- 技术机会；
- 外部约束。

### A04 明确目标对象

确认：

- 谁遇到问题；
- 谁真正使用；
- 谁付费；
- 谁验收；
- 谁承担风险；
- 是否只有自己使用。

### A05 描述发生场景

至少回答：

- 什么时候发生；
- 在什么环境发生；
- 什么触发；
- 当前流程怎样；
- 当前使用什么替代方式；
- 为什么不满意。

### A06 初步问题定义

区分：

- 观察到的现象；
- 症状；
- 真正问题候选；
- 原因假设；
- 解决方案假设；
- 尚未知道的信息。

### A07 期望结果

明确用户真正想得到的结果，而不是只记录“想增加哪个按钮”。

## 三、B：外部扫描与候选扩展

### B01 当前做法扫描

调查：

- 当前人工流程；
- 现有软件；
- 现有脚本；
- 现有内部系统；
- 当前成本与主要问题。

### B02 直接竞品扫描

关注：

- 服务相同用户；
- 解决相同问题；
- 提供相同核心结果的产品。

### B03 间接竞品与替代方案

包括：

- Excel；
- 人工操作；
- 外包；
- 通用 AI；
- 其他类别软件；
- 什么都不做。

### B04 技术与开源扫描

按需搜索：

- 开源项目；
- Library；
- SDK；
- API；
- SaaS；
- AI Model；
- Agent Framework；
- 数据集；
- Benchmark；
- 标准；
- 可购买组件。

### B05 成功案例

寻找：

- 什么方法已经被证明可行；
- 成功需要哪些条件；
- 实际成本；
- 真正收益。

### B06 失败案例

寻找：

- 为什么失败；
- 为什么停止使用；
- 隐藏成本；
- 长期维护困难；
- 锁定风险；
- 常见误判。

### B07 行业与外部约束

按需检查：

- 法律；
- 合规；
- 隐私；
- 平台规则；
- API 限制；
- 地区限制；
- 内容安全；
- 授权和许可。

### B08 AI 候选扩展

AI 可以根据原始材料和调查结果扩展候选：

- 问题；
- 用户；
- 场景；
- 需求；
- 功能；
- 质量要求；
- 约束；
- 风险；
- 机会；
- 边界情况；
- 潜在商业模式。

所有新增项默认只是候选，不自动成为正式事实或需求。

### B09 人工筛选

候选项进入：

- 要；
- 不要；
- 未确定；
- 后续版本；
- 需要补证。

### B10 初步价值判断

检查：

- 用户价值；
- 商业价值；
- 战略价值；
- 学习价值；
- 技术资产价值；
- 数据资产价值；
- 品牌或渠道价值。

## 四、C：需求验证与正式需求基线

### C01 正常场景验证

检查需求在主要用户场景中是否成立。

### C02 高频场景验证

优先验证实际发生频率高、影响大的场景。

### C03 边界场景验证

检查：

- 极端输入；
- 极端用户；
- 大数据量；
- 低网络质量；
- 权限不足；
- 外部服务失效。

### C04 反例验证

主动寻找：

- 什么情况下用户根本不需要；
- 什么情况下旧方案更好；
- 什么情况下产品会制造额外负担；
- 什么情况下需求解释是错误的。

### C05 假设清单

至少区分：

- 事实；
- 用户明确表达；
- 观察；
- 推断；
- 假设；
- 未知；
- 争议。

### C06 关键未知识别

找出：

- 如果结论变化，会改变是否做项目的未知；
- 如果判断错误，会导致大量返工的未知；
- 成本最低但信息价值最高的验证点。

### C07 设计最小验证

验证方式按需包括：

- 用户访谈；
- 数据分析；
- 竞品试用；
- Prototype；
- Demo；
- 技术实验；
- Landing Page；
- 预售；
- 小规模真实使用；
- 人工模拟服务。

### C08 执行验证

记录：

- 输入；
- 假设；
- 方法；
- 结果；
- 证据；
- 是否改变判断。

### C09 更新候选需求状态

至少使用：

- 候选；
- 待补证；
- 已验证；
- 已否定；
- 暂缓；
- 被替代；
- 已批准。

### C10 明确范围边界

形成：

- 做什么；
- 不做什么；
- 当前版本做什么；
- 后续可能做什么；
- 哪些仍然未知。

### C11 形成需求基线

当前版本正式允许进入下游设计与实现的需求，形成受控基线。

需求变化后，不应只增加 Task，而要同步更新追溯关系及受影响设计、实现和测试。

## 五、D：立项与项目定义

### D01 立项判断

选择：

- 正式做；
- 暂缓；
- 放弃；
- 先调研；
- 先做实验；
- 先做人工服务验证；
- 先购买或复用现有方案。

### D02 项目价值声明

明确为什么值得投入。

### D03 项目目标

描述希望达到的结果状态。

### D04 非目标

显式写出当前不解决什么。

### D05 项目范围

确定：

- 用户；
- 能力；
- 场景；
- 系统边界；
- 交付边界。

### D06 MVP／首期范围

MVP 的目标是以最小范围验证关键价值和关键风险，不是随机删除完整产品的功能。

### D07 成功标准

回答：什么结果表明这个项目成功。

### D08 完成标准

回答：什么状态表明当前项目／版本可以进入验收或结束。

### D09 时间预算

明确可投入时间和关键窗口。

### D10 金钱预算

包括一次性成本和持续成本。

### D11 AI／API／计算成本预算

按需包括：

- Token；
- GPU；
- 推理；
- 存储；
- 第三方 API；
- SaaS；
- 带宽。

### D12 创始人注意力与能力预算

OPC 尤其需要判断：

- 是否超过一个人的持续承载能力；
- 哪些工作必须本人做；
- 哪些可以自动化、外包或购买。

### D13 主要风险

列出最可能改变项目命运的风险。

### D14 主要未知

保留项目启动后仍需继续降低的不确定性。

### D15 停止条件

提前定义什么时候不再继续投入。

### D16 转向条件

提前定义什么证据出现时要改变需求、方案、用户或商业方向。

立项不等于承诺完整开发。项目本身也可以只是“验证某个关键技术或商业假设”。

### E01 再次搜索已有解决方案

从正式需求出发重新判断：

- 直接使用；
- 购买；
- 开源改造；
- API；
- 外包；
- 合作；
- 自建；
- 组合；
- 不做。

### E02 生成结构不同的方案

候选方案应尽量在机制、资源结构、技术路线或交付方式上存在真实差异。

- 框架；
- 模型；

- 协议；
- 开源组件；
- 云服务；
- 部署方式；

- 运行成本；
- 模型／API 成本；

- 数据成本；
- 迁移成本。

## 十、I：四种结构树与双向追溯

复杂软件项目不要把所有对象强行塞进一棵树。

至少区分：

### I01 价值／需求树

> **业务／项目目标 → 用户问题／机会 → 用户需要 → 正式需求 → 系统能力**

### I02 产品／解决方案结构树

> **能力 → 功能／质量要求 → 产品模块 → 用户流程／页面或 API／Job 等交付表面**

### I03 技术实现树

> **System → Subsystem → Service／技术模块 → Component → Interface／Data → Code／Deployment**

### I04 项目交付树

> **Project → 阶段／版本 → 成果 → Deliverable → Work Package → Task → Subtask**

### I05 双向追溯图

连接：

> **目标 ↕ 问题／机会 ↕ 需求 ↕ 能力 ↕ 功能／质量要求 ↕ 产品结构 ↕ 技术结构 ↕ 工作包／Task ↕ 实现 ↕ 测试 ↕ 验证证据 ↕ 用户确认 ↕ 验收 ↕ 用户效果 ↕ 净价值**

关键关系按需包括：

- `derived_from`；
- `satisfies`；
- `realized_by`；
- `implemented_by`；
- `verified_by`；
- `validated_by`；
- `depends_on`；
- `owned_by`；
- `supersedes`。

任何 Task 都应该能向上回答“为什么存在”；任何正式需求都应该能向下回答“由什么实现、由什么证明、由谁确认”。

## 十一、J：项目交付与任务拆分

### J01 阶段／版本拆分

### J02 目标成果拆分

### J03 Deliverable 拆分

明确可检查、可提交的交付物。

### J04 Work Package 拆分

把较大的交付物拆成可管理工作包。

### J05 Task 拆分

Task 应尽量满足：

- 边界清楚；
- 结果可判断；
- 依赖可识别；
- 足够小，可独立推进；
- 能追溯到上游成果或需求。

### J06 Subtask

只有当 Task 仍然过大、包含多个明显动作时继续拆。

### J07 依赖关系

区分：

- 硬依赖；
- 软依赖；
- 数据依赖；
- 接口依赖；
- 人工决策依赖；
- 外部供应商依赖。

### J08 优先级

优先处理：

- 会解锁大量后续工作的事项；
- 会降低关键未知的事项；
- 价值高且窗口短的事项；
- 高风险前置验证。

### J09 里程碑

里程碑是时间／进度检查视图，不与产品模块或 Task 层级混为一谈。

## 十八、Q：Verification、Validation、Acceptance 与 Value 分离

> **有没有做真正需要的东西？**

### Q03 Acceptance｜有权者是否接收

回答：

> **是否由有权验收的人接管／认可当前成果？**

回答：

> **实际效果是否值得投入这些成本、时间和风险？**

因此可能出现：

> Verification ✓
>
> Validation ✗

或者：

> Verification ✓ → Validation ✓ → Acceptance ✓ → Value ✗

测试通过不能自动证明商业价值成立。

### Q05 镜像验证关系

推荐保留：

> **需求 ↔ 用户／真实场景验证**

## 二十九、适用性与裁剪规则

本文件刻意采用高召回设计。真实项目必须裁剪。

### 1. 必经思想，不等于必建文件

例如“明确输入输出”是重要思想，但不代表每个小 Task 都要创建独立 Spec 文件。

### 2. Page 是条件层

只有存在实际人机 UI 时才展开页面、导航和组件。

### 3. Skill 是条件层

只有独立、可复用、可验证或需要单独治理的技术能力才值得拆成 Skill／Tool／Script。

### 4. 测试按风险裁剪

小型低风险脚本不需要完整企业级测试矩阵；高风险系统不能只跑 Happy Path。

### 5. 架构按复杂度裁剪

简单程序可把多个架构对象合并，但仍要知道职责、接口、依赖和错误边界。

### 6. 高未知项目先验证，不先拆到底

关键未知没有消除前，远期精细 Task 树大多是假精确。

### 7. 下游失败按最近根因返回

不从头重做，也不默认用补丁掩盖上游错误。

### 8. OPC 关注机会成本

一个技术上正确但持续占用创始人大量时间的系统，仍可能是不合格方案。

## 三十、后续收敛方向

本文件下一阶段不宜继续无限增加环节，应开始做以下治理：

1. 对所有环节去重；
2. 标注“必选／条件必选／可选”；
3. 按项目规模提供极简版、标准版、完整版；
4. 把约 50+ 关键执行环节压缩成 OPC 高频 15—25 个核心关口；
5. 明确每一阶段的进入条件、核心动作、输出、完成条件和返回路径；
6. 为 UI、API／后端、数据 Pipeline、Agent／Workflow、CLI／Script 等建立分支模板；
7. 专门建立 Task／Skill／Script／Tool 最小执行契约；
8. 建立需求—实现—测试—用户效果—商业价值的双向追溯最小格式；
9. 用真实软件项目做端到端压力测试；
10. 最后再判断哪些内容需要并入 `08_软件IT与AI原生.md`、`15_项目与复杂任务链路宇宙.md` 或其他正式文件。

当前阶段的目标是：**先确保项目推进宇宙没有因为过早简化而遗漏关键环节，再做收敛。**
