# 项目与复杂任务链路宇宙

> **核心主链**：**判断价值 → 建立目标与完成标准 → 了解现状与差距 → 拆解目标 → 拆解问题 → 搜索已有解法 → 生成结构不同的方案 → 调查失败、反例与限制 → 必要时借力实践经验 → 验证关键未知 → 比较方案 → 决策 → 拆成果与任务 → 排依赖和优先级 → 配置资源 → 分阶段执行〔记录＋监测＋沟通＋质量＋风险〕→ 阶段判断 → 按根因返回 → 验收 → 评估效果与价值 → 总结复盘 → 沉淀复用 → 继续／扩大／转向／暂停／交接／归档／终止**。

> 导航：[返回总览](00_总览与核心结论.md)｜[总地图](01_通用总链与Level1-3总地图.md)｜[基础链库](02_通用基础链路库.md)｜[运行关系](03_链路关系、关口与运行协议.md)｜[场景验证](13_场景验证与覆盖矩阵.md)

## 一、本文件的职责与边界

本文件承担**跨领域的 L3“项目／复杂任务”场景组合**。它适用于大型个人任务、工作项目、研究任务、产品创造、采购选型、流程改进、组织变更等需要多阶段推进的事情。

它不新增 C31，也不重新定义 C01—C30。下面的“目标链、目标拆解链、问题拆解链”等名称都是为了快速使用而建立的**场景子链**；其正式状态转化仍由已有 C 链和扩展动作承担。

项目并不等于“多人＋甘特图”。只要一个事项存在多个成果、多个未知、多个可能方案、明显依赖、较高试错成本或需要多轮验证，即使只有一个人，也可以采用本文件的组合链。

## 二、三种项目主链

### 1. 最小项目链

> **目标 → 完成标准 → 下一阶段成果 → 任务与依赖 → 执行 → 检查 → 验收 → 结束／继续**

适用于目标清楚、方案成熟、风险较低的项目。

### 2. 标准项目链

> **价值 → 目标与标准 → 现状差距 → 目标拆解 → 方案选择 → 计划资源 → 分阶段执行 → 监测纠偏 → 验收 → 效果评估 → 复盘沉淀 → 生命周期**

适用于普通工作项目和较大的个人任务。

### 3. 高不确定项目链

> **触发／想法 → 价值判断 → 目标与边界 → 现状与未知 → 目标拆解＋问题拆解 → 找已有解法 → 多方案 → 失败研究／反例 → 咨询实践者 → 小试关键未知 → 重新比较 → 决策 → 阶段成果与任务 → 资源与风险 → 执行 → 阶段门 → 返回或继续 → 验收 → 效果与净价值 → 沉淀／转向／退出**

不确定性越高，越应该把资源放在“减少关键未知”上，而不是过早把所有细节计划到底。

## 三、高频场景子链

### 1. 目标建立组合链

> **模糊想法／外部要求 → 谁真正需要 → 为什么值得做 → 想达到什么状态 → 包含什么／不包含什么 → 什么叫完成 → 有哪些硬约束 → 目标确认**

- 主要输出：价值成立、边界明确、可评价的目标与完成标准。
- 主要映射：C02 需求澄清＋C03 价值排序＋C04 目标设定＋C05 标准设定。
- 关键返回：价值不成立回放弃／延后；真实需要不清回 C02；完成标准不可判断回 C05。

### 2. 目标拆解链

> **最终目标 → 阶段成果 → 子目标 → 关键交付物 → 前后依赖 → 里程碑 → 近期结果 → 下一步行动**

拆解的对象首先是“成果”，其次才是动作。不能把一长串待办误当成目标拆解。

- 主要输出：成果树、依赖关系、阶段里程碑和近期可启动结果。
- 主要映射：C04＋C05＋C06，以及“目标拆解”扩展动作。
- 关键返回：发现子目标无法解释上位价值时回目标；依赖不可实现时回方案或范围。

### 3. 问题拆解链

> **当前障碍／差距 → 分离事实、症状和猜测 → 拆成子问题 → 标注关系与依赖 → 找关键未知 → 判断哪些最影响结果 → 排研究顺序 → 形成可回答的小问题**

问题拆解回答“**我们到底不知道什么、卡在哪里**”，目标拆解回答“**要产出哪些结果**”，两者不能混成同一张任务列表。

- 主要输出：子问题、关键未知、研究顺序和待验证假设。
- 主要映射：C20 问题定义＋C23 信息处理＋C21 原因分析。
- 关键返回：问题边界错误回 C20；事实不足回 C23；原因假设混乱回 C21。

### 4. 现状与差距链

> **读取目标状态 → 描述当前状态 → 收集必要证据 → 对照差距 → 区分资源差距／知识差距／能力差距／方案差距／环境约束 → 识别关键差距 → 决定先研究还是先行动**

现状调查只做到足以支持下一决定，不以“资料越多越好”为完成标准。

### 5. 已有解法搜索链

> **明确待解决问题 → 搜知识与先例 → 搜产品／工具／开源项目／服务／标准／案例 → 判断成熟度和适用条件 → 找缺口与锁定风险 → 比较直接采用／采购／改造／组合／自建／不做 → 形成候选解法集**

这条链的意义是先问：**别人是否已经付过试错成本？**

- 主要映射：C23 为 C22 提供决策输入。
- 停止条件：已经找到足够支持当前方案选择的候选；继续搜索的预期收益低于等待成本。

### 6. 经验借力与咨询链

> **识别高试错成本或隐性经验问题 → 找真正做过的人 → 准备具体问题 → 获取实践过程、失败、成本、边界和例外 → 区分经验、观点与事实 → 与其他证据交叉核对 → 转成方案输入／验证假设**

免费交流、社区询问、同行访谈和付费咨询只是不同获取方式。咨询结果不是自动正确的决定。

- 主要映射：C23＋C25＋C22。
- 适用：试错昂贵、经验难公开检索、行业隐性知识强、决策窗口短。

### 7. 多方案生成链

> **明确目标和硬约束 → 找不同作用机制 → 生成结构不同的方案 → 增加复用／购买／合作／自建／改变上游／不做等候选 → 为每个方案写核心机制和前提 → 排除明显不可行项**

“方案 A 改措辞、方案 B 换措辞”不算多方案。真正的候选应在机制、资源结构、交付方式或风险承担上存在差异。

### 8. 失败预演与反例链

> **假设方案最后失败 → 倒推可能原因 → 搜真实失败案例 → 找隐藏成本、依赖、维护难点、反例和退出困难 → 区分可预防／可缓解／必须接受的风险 → 修改方案或预案**

不仅问“怎样成功”，还应问：**什么时候这个方法不成立？为什么别人最后停止使用？**

- 主要映射：C23＋C28＋C22。

### 9. 关键未知验证链

> **列出仍会改变决定的未知 → 按影响和验证成本排序 → 选择最关键未知 → 设计最小验证 → 获取真实结果 → 更新假设 → 保留／修改／淘汰方案**

验证对象可以是用户行为、技术可行性、成本、耗时、供应能力、学习难度或其他关键未知。实验只是手段，核心是让决定获得新证据。

### 10. 方案评估链

> **读取目标和硬约束 → 选择真正有区分度的评价维度 → 收集必要证据 → 比较预期效果、投入、时间、难度、长期负担、风险、可逆性和机会成本 → 做敏感性／最坏情况检查 → 形成选择建议**

不是所有项目都需要同一张评分表。评价维度应该由目标和场景决定。

- 主要映射：C15 评估判断＋C22 决策选择。

### 11. 优先级与资源链

> **汇总成果、问题和任务 → 判断价值与紧迫性 → 识别关键路径和前置依赖 → 优先处理会解锁后续或降低重大未知的事项 → 删除／延后低价值工作 → 配置时间、人员、资金、信息、工具和能力**

优先级不是简单按“看起来重要”排序，还要考虑依赖、窗口、风险和是否能解锁后续工作。

- 主要映射：C03＋C06＋C07。

### 12. 计划建立链

> **读取已选方案和成果树 → 拆近期可交付成果 → 建任务与依赖 → 估资源和时间 → 设置阶段检查点 → 明确需要同步的相关方 → 识别主要风险和变更条件 → 形成可启动计划**

计划只需要详细到足以可靠推进当前阶段；新证据会推翻远期细节时，不必假装能够提前精确预测全部任务。

### 13. 执行控制链

> **选择下一有效动作 → 执行 → 记录关键事实 → 检查成果和进度 → 发现偏差 → 判断偏差属于动作、计划、方案、目标还是需求 → 返回最近根因层 → 更新后继续**

- 主要映射：C09〔C10＋C11＋C12＋C25＋C28〕→ C13。
- 防止：只因为“做了很多动作”就判定项目在前进。

### 14. 阶段决策链

> **到达检查点／出现重大新证据 → 汇总完成成果、剩余未知、成本、风险和价值 → 判断继续／扩大／缩小／改方案／转向／暂停／交接／终止 → 更新基线 → 进入下一阶段**

阶段门的作用是避免沉没成本把项目锁在已失效的路径上。

### 15. 验收、效果与价值链

> **形成成果 → 验证是否符合要求 → 确认是否满足真实用途 → 有权者验收接管 → 观察实际效果和副作用 → 对照投入与风险判断净价值 → 决定继续、扩大、维护或退出**

“按规格做完”“用户真正能用”“产生了值得的结果”是三个不同判断。

### 16. 复盘、沉淀与复用链

> **还原目标与关键假设 → 总结发生了什么 → 分析为什么 → 区分机制与偶然 → 提炼适用条件、失败边界和例外 → 形成方法／清单／模板／案例／工具 → 在新场景复用验证 → 更新或淘汰**

- 主要映射：C17＋C18＋C19＋C30。

## 四、常见项目场景变体

### 1. 大型个人任务

> **想法／需要 → 判断价值 → 目标标准 → 拆成果 → 查已有方法 → 选择路线 → 安排时间精力 → 分阶段执行 → 检查调整 → 完成评估 → 沉淀**

重点控制注意力、时间、健康和机会成本，避免把个人项目做成沉重的企业流程。

### 2. 陌生领域项目

> **目标 → 知识缺口 → 问题拆解 → 调研已有解法和实践者 → 建知识地图 → 关键未知验证 → 选方案 → 边做边学 → 项目反馈反哺学习 → 交付与复盘**

学习服务真实任务，而不是无限研究后再开始行动。

### 3. 购买／选型／采购

> **真实需要 → 必须条件 → 搜候选 → 查评价与失败 → 必要试用／询价／咨询 → 比较全周期成本和锁定风险 → 选择 → 验收 → 使用效果评估 → 保留／更换／退出**

### 4. 研究项目

> **研究问题 → 已知／未知 → 资料和现有研究 → 假设 → 方法 → 取证／试验 → 分析 → 反例与限制 → 结论 → 复现／应用 → 更新知识**

### 5. 多人项目

> **共同结果 → 目标和标准 → 成果拆解 → 任务依赖 → 分工接口 → 资源权限 → 并行执行 → 同步与冲突处理 → 集成 → 验收 → 交接复盘**

多人项目额外强调 C25 沟通和 C26 分工协作，但不改变项目基本状态转化。

### 6. 改进／转型项目

> **现状问题 → 目标状态 → 原因与利益相关方 → 候选改变 → 小范围试点 → 效果和副作用 → 修订 → 分批采用 → 监测 → 固化／撤回／继续改进**

### 7. 暂停、转向与重启

> **发现原路径失效 → 保存事实和成果 → 判断剩余价值 → 暂停／转向／终止 → 记录恢复条件 → 条件满足后重新核查目标、环境和依赖 → 重启或保持退出**

## 五、评估不是单独的末尾步骤

| 时点 | 核心问题 | 常见去向 |
| --- | --- | --- |
| 立项前 | 值不值得投入？ | 做／延后／委派／放弃 |
| 方案前后 | 哪条路线更合适？最关键未知是什么？ | 补证／试验／选择 |
| 执行阶段 | 还在正确路径上吗？ | 继续／纠偏／重计划／换方案 |
| 验收阶段 | 做对了吗、能用吗、被接管了吗？ | 接受／返工／重澄清 |
| 运行后 | 是否真正产生值得的效果？ | 扩大／维护／转向／退出 |

## 六、失败后的返回地图

| 发现的问题 | 优先返回 |
| --- | --- |
| 真实需求理解错 | C02 需求澄清 |
| 事情本来不值得做 | C03 价值排序 |
| 目标或范围错 | C04／C05 |
| 成果拆错、依赖错 | C06 计划制定／目标拆解 |
| 不知道真正问题在哪 | C20／C23／C21 |
| 方案机制不成立 | C22 重新生成和选择方案 |
| 缺资源 | C07，必要时回 C03 缩减优先级 |
| 执行动作错 | C09／C13 |
| 质量不过 | C12 → C09 |
| 已发生重大异常 | C29 先止损恢复 |
| 项目长期无净价值 | C30 暂停、转向或终止 |

原则是**按根因返回最近的有效层**。不能用“增加任务、加班、继续投入”修补上层目标或方案错误。

## 七、停止、继续与升级条件

项目至少在以下时点重新决定是否继续：

- 价值或目标明显变化；
- 关键假设被否定；
- 出现能显著改变路线的新证据；
- 必要资源长期无法获得；
- 继续成本明显超过剩余价值；
- 风险超过可接受边界；
- 阶段成果已完成，需要决定是否进入下一阶段；
- 外部环境变化导致旧方案失效。

停止不等于失败。及时放弃低价值路线、迁移已获得的成果，也属于有效项目决策。

## 八、层级与去重决定

本文件没有创造新的核心基础链：

- “目标建立”是 C02＋C03＋C04＋C05 的场景组合；
- “目标拆解”主要由 C04／C05／C06 及扩展动作表达；
- “问题拆解”由 C20＋C23＋C21 表达；
- “已有解法搜索”属于 C23 为 C22 提供输入；
- “咨询实践者”属于 C23＋C25；
- “失败预演”属于 C23＋C28＋C22；
- “方案评估”属于 C15＋C22；
- “执行控制”属于 C09—C13 的组合；
- “阶段决策”属于 C15＋C22＋C30；
- “复盘沉淀”属于 C17—C19＋C30。

只有未来真实场景反复出现一种现有 C 链无法表达、且具有独立输入、输出、完成标准和失败返回的跨领域状态转化，才重新评估是否需要 C31。

## 九、项目分解模型：成果树、执行树与时间视图

项目拆解不能把“目标、阶段、里程碑、交付物、模块、任务”机械串成一棵长树。跨领域更稳定的做法是把**要交付什么、为了交付做什么、什么时候检查**分开。

### 9.1 成果／交付结构：先拆 WHAT

> **项目目标 → 预期成果／Outcome → 交付物 → 子交付物 → 工作包／Work Package**

- **预期成果**：项目结束后希望真实世界达到的状态变化，不只是“做出一个东西”。
- **交付物**：可被检查、提交、接收或使用的具体结果。
- **子交付物**：当交付物过大时按独立结果继续分解。
- **工作包**：最低层的可管理交付范围；应足够明确到可以负责、估算、安排、监测和判断完成。

工作包不是产品模块，也不是技术模块。一个工作包可以为了同一交付物同时涉及研究、设计、开发、采购、沟通或其他工作。

### 9.2 执行结构：再拆 HOW

> **工作包 → 活动／Activity → 任务／Task → 子任务／Subtask → 必要时下一最小行动／Next Action**

任务是为了产生具体成果而存在的工作单元，不应脱离上游工作包和交付物独立增长。对于简单项目，可以直接从交付物进入任务，不要求为了形式完整创建 Activity 或 Subtask。

### 9.3 时间结构不是父子结构

以下对象主要回答“何时发生、何时检查、何时切换”，通常作为成果／工作的覆盖视图：

- 项目阶段／Phase；
- 里程碑／Milestone；
- Release／发布批次；
- Sprint／迭代周期；
- Deadline／截止时间；
- 阶段门／Gate。

不能默认使用“阶段 → 里程碑 → 交付物 → 工作包 → Task”作为统一父子树。里程碑可以由多个工作包共同达成，一个工作包也可能跨越多个时间检查点。

### 9.4 产品结构、技术结构与项目结构不能互相替代

复杂软件项目可能同时拥有：

1. **价值／需求树**：目标 → 问题／机会 → 用户需要 → 需求；
2. **产品／解决方案结构树**：能力 → 功能 → 产品／业务模块 → 页面／接口等承载面；
3. **技术结构树**：系统 → 技术子系统 → 服务／模块／组件 → 接口 → 实现；
4. **项目交付树**：项目成果 → 交付物 → 工作包 → 任务。

四棵树通过追溯关系连接，而不是要求节点一一同名。软件领域的具体产品和技术分解见 [08_软件IT与AI原生.md](08_软件IT与AI原生.md)。

## 十、什么时候停止继续拆任务

任务或工作包已经同时满足下列条件时，通常可以停止继续细拆：

1. **输出清楚**：知道这一单元具体产生什么结果；
2. **完成可判定**：存在明确完成条件或可检查证据；
3. **责任清楚**：有单一主要责任主体，必要协作接口已知；
4. **前置清楚**：关键依赖、权限和输入已经能够识别；
5. **足以安排**：当前已经能够估算、排序或放入近期计划；
6. **下一步明确**：执行者拿到任务后知道如何启动，而不是继续猜目标；
7. **风险可控**：再细拆不会显著降低重要未知、质量风险或协作风险；
8. **管理收益递减**：继续细拆的维护成本已经高于带来的执行收益。

不要为了“原子化”把知识工作拆成“打开软件 → 找文件 → 输入字符 → 保存”之类没有独立成果和管理价值的动作。最小执行动作是**当下足够清楚的下一行为**，不是项目计划必须长期保存的最底层节点。

## 十一、高未知工作：先把未知变成证据，不制造假精确任务树

当路径、可行性、用户行为、成本或技术机制仍高度未知时，不应假装远期任务已经可以可靠预测。

推荐母式：

> **关键未知 → 调研／Spike／原型／小试／实验 → 获取证据 → 更新假设与方案 → 重新建立近期成果和任务**

例如“不知道某模型能否在目标成本下稳定完成任务”时，当前工作的成果应先是**可复现的验证结果和选型结论**，而不是直接生成“开发 → 集成 → 上线”的完整确定计划。

这与第三节“关键未知验证链”和“计划只详细到足以可靠推进当前阶段”的原则一致。高不确定项目允许滚动规划；得到新证据后，应正式更新当前基线，而不是把旧任务树继续向下扩充。

## 十二、项目节点的五种最小关系

对于复杂项目，只有父子树仍不足以表达真实运行。每个重要成果、工作包或任务至少按需记录：

| 关系 | 回答的问题 | 示例 |
| --- | --- | --- |
| **父子／belongs_to** | 它属于哪个上位成果或工作范围 | Task → Work Package |
| **依赖／depends_on** | 哪个前置未完成就不能可靠推进 | 集成测试依赖接口实现 |
| **责任／owned_by** | 谁对这个结果的完成负责 | 工作包 → 负责人 |
| **完成／done_when** | 什么证据证明该节点结束 | 测试通过、文档被接收 |
| **返回／returns_to** | 失败后最近应回到哪一层纠正 | 技术不可行 → 方案／范围 |

复杂软件项目还可以进一步使用 `derived_from`、`satisfies`、`implemented_by`、`verified_by`、`validated_by` 等追溯关系，术语边界见 [12_术语、边界与编号索引.md](12_术语、边界与编号索引.md)。

> **最终纪律**：任何任务都应能回答“为了哪个工作包／交付物／目标而存在”；任何长期无法解释上位成果的任务都应被删除、合并、重新归属或返回上游重新判断。
