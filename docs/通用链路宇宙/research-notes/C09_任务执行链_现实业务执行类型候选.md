## 一、为什么单独保存

这类内容不是普通 TODO，也不是已经验证的 Reference。它属于“值得保留、需要继续研究、可能晋级为正式结构”的候选知识。

建议统一放在 `docs/通用链路宇宙/research-notes/`：

- `reference`：保存外部来源、事实材料、案例和可引用证据；
- `research-notes`：保存内部推理得到、尚待验证的分类、假设、候选模型和思考角度；

## 二、候选问题

C09 任务执行链在真实业务中，是否需要按照“执行对象 / 任务性质 / 风险与规模”进一步形成一组稳定的现实业务执行类型？这些类型是否互斥、完备、可组合，是否应该成为正式分类，目前尚未验证。

## 三、现实业务执行类型候选

| 候选类型 | 初步含义 | 示例 |
| --- | --- | --- |
| **事务型执行** | 规则较明确、步骤相对稳定、以完成事务状态变更为主 | 填表、审批、支付、录入、通知 |
| **知识型执行** | 主要依赖分析、判断、表达、设计或知识生产 | 研究、分析、写作、设计、编程 |
| **服务型执行** | 围绕外部或内部服务对象持续完成交互和交付 | 客服、咨询、交付、售后 |
| **交易型执行** | 涉及价值交换、报价、合同、采购、结算等交易状态 | 销售、采购、合同、结算 |
| **生产型执行** | 把输入转化为标准化或可验收产物 | 制造、内容生产、软件发布 |
| **探索型执行** | 目标大致明确，但路径、机制或解法未知，需要试错 | 新产品探索、科研、陌生问题求解 |
| **长期型执行** | 跨天、跨月或持续运行，需要状态持久化和周期复查 | 长期运营、持续研究、维护工作 |
| **多人协作型执行** | 多角色共同完成，存在接口、依赖、交接和责任边界 | 项目协作、跨部门交付 |
| **高风险型执行** | 错误可能造成较大损失、法律/安全影响或不可逆后果 | 资金操作、生产变更、法律审批 |
| **批量型执行** | 同类任务数量、频率显著增加，可能触发自动化和架构跃迁 | 大量客服、批量内容处理、批量数据操作 |

## 四、当前需要验证的问题

1. 这些类型是否处于同一分类维度，还是混合了“任务性质、组织形态、风险、时间和规模”等不同轴？
2. `长期型 / 多人协作型 / 高风险型 / 批量型` 更像横向条件，而非与 `事务型 / 知识型 / 服务型 / 交易型 / 生产型 / 探索型` 同层类型，是否需要拆成二维或多维模型？
3. 是否缺少现场作业型、决策型、协调型、监测型、维护型、创作型等重要类别？
4. 每类任务是否真的会导致不同的 C09 执行机制、状态、关口和完成标准？如果只是行业名称不同，不应晋级为通用分类。
5. 当数量、频率、风险、持续时间、参与者和自动化比例发生跃迁时，哪些类别会发生架构质变？
6. M0 人工、M1 AI 辅助、M2 AI 原生在各类业务执行中的分工是否不同？
7. 这些类型最终应属于 C09 的正式扩展、L3 场景分类、19_链路垂直深挖方法中的案例，还是仅保留为研究笔记？

## 五、暂定的更稳妥结构假设

后续验证时优先考虑把“业务任务性质”和“运行条件”拆开，而不是强行做成一张单轴分类表：

> **任务性质轴**：事务 / 知识 / 服务 / 交易 / 生产 / 探索 / ……  
> **运行条件轴**：单人或多人 / 短期或长期 / 低风险或高风险 / 单件或批量 / 人工或 AI 原生 / 稳定或高变化。

一个现实任务可以同时拥有多个标签，例如：

> “10 万条客服请求的 AI 自动处理” = 服务型 × 批量 × 持续 × M2 AI 原生 × 中高风险。

这种多轴表示是否优于单一类型表，需要通过真实业务场景验证。

## 六、晋级规则

只有同时满足以下条件，候选内容才从 `research-notes` 迁入正式体系：

1. 能解释多个领域的真实任务，而不是只适用于单一行业；
2. 类型之间的边界、重叠和组合规则清楚；
3. 分类会实际改变链路步骤、判断、状态、关口或完成标准；
4. 经过生活 / 工作 / OPC / 公司 / 软件或其他代表性场景压力测试；
5. 通过 `19_链路垂直深挖与审计框架.md` 的专业性、完整性、结构性、规模跃迁和层级归属审查；
6. 明确最终应进入 L2、扩展链、L3 场景还是 L4 工作流。

若验证后发现只是方便思考的标签，则继续留在本目录，不提升为正式链路。
