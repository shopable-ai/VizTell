# 通用链路宇宙：持续优化母提示词

> **使用方式**：在新的对话中连接或粘贴代码仓库 `https://github.com/shopable-ai/VizTell`，然后复制本文件“母提示词正文”部分。目标是让新对话先完整读取现状，再持续审计、修改、验证和提交，而不是重新生成一套互相冲突的体系。

## 母提示词正文

请作为一个跨学科的“通用链路建模、系统工程、流程设计、复杂问题解决、项目与产品管理、组织运营、质量风险、知识工程、软件工程和AI协作”专家团队，对下面的代码仓库进行一次长时间、连续、多轮的优化：

> 仓库：`https://github.com/shopable-ai/VizTell`  
> 主要范围：`docs/通用链路宇宙/`

### 一、任务性质

这是在现有成果上的继续完善，不是从零重新创作。

你必须先完整读取仓库中的 README、`00—11` 和 `90` 文件，建立当前目录、概念、编号、主链、基础链、领域链和交叉引用基线，然后再提出或实施修改。

不得只给建议、目录或评分后停止。只要权限和资料允许，就应继续完成审计、修改文件、校验链接、回读结果并提交仓库。

### 二、必须保留的现有成果

1. 重要结论和最重要链路放在文件顶部。
2. 8节点、20节点和完整生命周期三种总链并存，各自服务不同复杂度。
3. Level 0—4 分层：生命周期、系统、基础链、领域组合、具体工作流。
4. 十一类运行系统作为全局导航。
5. 30条核心基础链作为可复用模块，每条包含：解决、输入、核心步骤、输出、完成标准、返回、可调用、应用。
6. 生活、工作、OPC、公司、软件IT和AI原生分别建模，不混为同一分类维度。
7. 记录、监测、沟通、质量、风险、合规和变更与执行并行。
8. 验证、确认、验收、效果和价值保持概念边界。
9. 失败按根因返回最近的有效控制层，异常优先安全、止损、隔离和恢复。
10. 完成后仍需进入维护、扩大、暂停、交接、更新、归档、淘汰或重启。

除非有明确证据和场景测试，不要推翻这些结构。需要修改时必须说明问题、证据、替代方案、影响范围和迁移方式。

### 三、核心目标

把当前体系从“内容较完整的知识地图”继续提升为：

- 容易扫读和检索；
- 概念边界清楚；
- 链路之间可以装配；
- 输入输出能够衔接；
- 正常、失败和异常路径可运行；
- 能按风险选择流程强度；
- 能下沉为生活、工作、OPC、公司和软件IT的具体工作流；
- 能通过测试、证据和版本记录持续改进。

### 四、必须完成的多轮工作

#### 第0轮：现状基线

1. 列出仓库文件树、每个文件职责和主要标题。
2. 提取所有总链、L1系统、L2核心链、扩展链和领域链。
3. 建立编号、名称、输入、输出、完成标准和调用关系清单。
4. 标记重复、冲突、断链、孤立链、缺失引用和层级错误。

输出：当前基线、结构图、问题清单和修改优先级。

#### 第1轮：架构与完整性审计

分别检查：

- 是否覆盖感知、价值、目标、研究、决策、计划、资源、执行、协作、控制、验收、评估、学习、沉淀、运维和退出；
- 是否遗漏机会、边界、证据、权限、预算、容量、变更、风险、合规、安全、隐私、数据、连续性、交接和退役；
- 是否把行动、角色、工具、产物、指标或行业差异错误升级成基础链；
- 是否存在相同输入输出、相同转化和相同完成标准的重复链；
- 是否有名称相似但职责不同的链未说明边界。

对每个候选遗漏给出：是否真缺失、应处于L1/L2/L3/L4哪一层、是否需要新文件、为什么。

#### 第2轮：可用性与快速导航

1. 每个长文件顶部提供最重要结论、紧凑链或速览。
2. 为30条核心链提供分组速查、按卡点选链和主闭环。
3. 建立术语、编号、别名、上游、下游和常见组合索引。
4. 检查目录排序，使重要内容在前，审计、模板和提示词在后。
5. 保持链路采用紧凑水平形式：`A → B → C`；只有比较和精确映射才使用表格。

#### 第3轮：运行化

设计统一L4工作流模板，按需包含：

- 目的、范围、触发器和不适用条件；
- 输入、输出、角色、责任、决策权；
- 步骤、并行控制、依赖和交接；
- 时间、预算、容量、指标、阈值和容差；
- 工具、表单、证据、版本和追溯；
- 风险、安全、隐私、合规与升级；
- 验证、确认、验收、效果和价值；
- 失败返回、异常旁路、暂停、退出和重启。

不要把所有字段强塞给低风险日常事项；设计轻量、标准、严格三个强度档位。

#### 第4轮：场景与反方验证

至少使用以下高相关基准：

1. 个人一周计划与健康维护；
2. 普通工作任务从接收到验收；
3. 软件需求从用户问题到上线运营；
4. AI重度软件OPC从机会到现金回收；
5. 成功项目经验转成公司流程并被采用；
6. 生产故障的止损、恢复和防复发；
7. 产品或流程的暂停、交接、淘汰和重启。

每个场景都要测试：最小正常路径、信息不足、资源不足、质量失败、风险事件、需求或目标错误、停止条件和生命周期出口。

反方必须挑战：体系过大、官僚主义、生活过度项目化、指标替代价值、研究无限循环、标准化复制错误、AI放大错误、组织激励与权力阻碍采用。

#### 第5轮：实施修改

按照“先P0、再P1”的优先级直接修改仓库：

1. 先修正明显错误、断链、重复、命名和导航。
2. 再增加术语索引、工作流模板和场景测试。
3. 新文件必须具有独立职责，不能只是把同一内容换一种说法。
4. 修改现有文件时保留其核心价值，避免整篇覆盖造成信息丢失。
5. 每一批修改形成清晰提交，并记录新增、合并、降级、改名和删除原因。

如果仓库已有并发修改，先重新读取最新版本，禁止覆盖未知更新。若具有写入权限，允许直接更新 `main`；若权限或保护规则阻止写入，则给出精确补丁或创建分支与PR。

#### 第6轮：自动校验与远端回读

至少检查：

- 每个Markdown只有一个一级标题；
- 标题层级没有跳级；
- 相对链接全部有效；
- 30条核心链编号唯一、字段齐全；
- 总览导航覆盖所有正式文件；
- 没有未完成占位、缺失正文、无内容标题和失效引用；
- 通用层没有被软件、AI或公司场景绑架；
- README、目录和最终提交能从远端读取。

### 五、判断与去重规则

新增核心基础链前必须同时回答：

1. 是否有不同于已有链的输入和输出？
2. 是否有独立的核心状态转化？
3. 是否有不同的完成标准？
4. 是否有不同的失败返回？
5. 是否在多个领域高频复现？

如果差异只是对象、角色、工具、术语、风险强度、行业法规或数值阈值，应下沉为L3/L4；如果由多条基础链组合而成，应定义为组合链。

### 六、边界与表达要求

- 以中文为主，必要英文放在中文后，不要用英文堆砌。
- 结论先行，关键链路紧凑展示，避免长篇重复解释。
- AI是技术模式和执行增强器，不是通用体系的唯一中心。
- 不把休息、关系、体验和所有日常生活强制项目化。
- 不追求虚假的“绝对完整”；明确已完成、部分完成、待验证和不适用。
- 不用主观自评分代替测试；可以评价成熟度，但必须给证据和剩余边界。
- 不引用无法核实的权威标准；需要外部资料时优先官方标准、原始研究和正式文档。

### 七、最终交付

完成后必须给出：

1. 总结性结论；
2. 修改前后差异；
3. 新的完整目录树；
4. 真正遗漏、被降级内容和拒绝新增内容清单；
5. 场景覆盖与失败返回矩阵；
6. 自动校验结果；
7. 提交记录和可直接访问的仓库链接；
8. 仍需真实数据或行业专家验证的边界；
9. 下一轮最多五项、按价值排序的工作。

### 八、完成条件

不要在给出初步分析或计划后停止。持续推进到：P0问题已经修复、P1基础运行模板和代表场景已经形成、校验通过、远端可读取，并且继续扩充通用层的边际收益明显低于维护成本。此时才结束本轮任务。
