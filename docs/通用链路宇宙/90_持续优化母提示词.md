# 通用链路宇宙：持续优化母提示词

> **使用方式**：连接仓库 `https://github.com/shopable-ai/VizTell` 后使用本提示词。任务重点是继续发现、校准、去重和验证“通用链路本体”，不是不断增加 Agent、软件工程字段或仓库操作细节。

> 导航：[返回总览](00_总览与核心结论.md)｜[总地图](01_通用总链与Level1-3总地图.md)｜[优化路线](11_优化路线与遗漏清单.md)｜[场景验证](13_场景验证与覆盖矩阵.md)

## 母提示词正文

请作为“通用链路建模、复杂问题解决、项目与执行、学习科学、知识工程、组织管理、风险质量和生命周期”跨学科专家团队，继续完善仓库：

> `https://github.com/shopable-ai/VizTell`  
> 主要目录：`docs/通用链路宇宙/`

### 一、真正的核心任务

本项目研究的核心问题是：

> **人在生活、学习、工作、项目、经营和组织活动中，会反复经历哪些关键状态转化？这些链路如何组合、分支、循环、返回和退出？**

因此优先完善：

- 触发、需求、价值和优先级；
- 目标、标准、目标拆解和问题拆解；
- 现状、差距、信息、证据和原因；
- 已有解法搜索、成功经验、失败案例和反例；
- 多方案生成、比较、验证和决策；
- 计划、资源、执行、记录、监测和纠偏；
- 验证、确认、验收、效果和价值；
- 总结、复盘、学习、经验沉淀和组织转化；
- 维护、扩大、迁移、暂停、交接、归档、淘汰和重启。

不要把“通用链路宇宙”逐渐写成 Agent 工程手册、软件研发规范或项目管理模板库。

### 三、必须保留的稳定结构

1. L0—L4 分层；
2. 八节点、二十节点和完整生命周期三种总链；
3. 十一类运行系统；
4. C01—C30 稳定编号；
5. L2 负责稳定状态转化，L3 负责场景组合，L4 负责具体实现；
6. 记录、监测、沟通、质量、风险、合规和变更可以与执行并行；
7. 验证、确认、验收、效果和价值保持区分；
8. 失败按根因返回最近有效层；
9. 生命周期不以“交付完成”为唯一终点；
10. 长文件顶部保留核心结论和紧凑链路。

### 四、每轮首先做“链路缺失审计”

不要先问“还能增加哪些字段”，而要问：

1. 是否遗漏了高频状态转化？
2. 是否有常见场景需要多条基础链组合，却还没有明显入口？
3. 是否有链只有正常路径，没有失败返回？
4. 是否有输出无法作为下一链输入？
5. 是否把结果、任务、工具、角色、参数误当成链？
6. 是否存在不同名字但输入输出和转化相同的重复链？
7. 是否存在名字相似但实际职责不同、却没有说明边界的链？
8. 是否遗漏维护、迁移、暂停、交接和退出？

### 五、重点验证复杂任务和项目链

至少反复检查下面这组高频组合是否完整：

> **价值判断 → 目标与标准 → 现状与差距 → 目标拆解＋问题拆解 → 查已有解法 → 生成多方案 → 查失败案例和反例 → 必要时咨询实践者 → 验证关键未知 → 比较效果、资源、时间、难度、长期负担、风险和可逆性 → 选择方案 → 拆成果任务 → 排依赖优先 → 配资源 → 执行 → 阶段评估 → 按根因返回 → 验收 → 效果价值 → 复盘沉淀 → 生命周期**

注意：这是一条 L3 组合链，不应为了它机械新增 C31。

### 六、已有解法、咨询和失败研究的正确归属

#### 已有解法搜索

> 问题 → 搜知识／产品／工具／开源项目／服务／案例／标准 → 判断可直接采用、改造、组合还是自己做

通常由 C23 信息处理为 C22 决策提供输入。

#### 咨询实践者

> 识别高试错成本或高隐性经验问题 → 找真正做过的人 → 获取经验、边界和失败条件 → 与其他证据核对 → 吸收进方案或试验

这是 C23＋C25 的组合，不是独立基础链。付费与否只是资源和交易方式。

#### 失败案例和反例

> 搜失败路径 → 找隐藏成本、限制、反例和退出困难 → 进入风险与方案评价

这是研究、风险和决策的组合。

### 七、评估必须贯穿而不是只放末尾

至少区分：

- **立项评估**：值不值得投入；
- **方案评估**：哪个方案更合适；
- **阶段评估**：是否继续当前路径；
- **成果评估**：是否达到要求和用途；
- **价值评估**：实际效果相对投入、风险和副作用是否值得；
- **长期评估**：是否维护、扩大、迁移或退出。

不要制造统一虚假精确评分；比较维度和证据强度随场景变化。

### 八、严格防止工程化漂移

以下内容即使重要，也默认属于 L4 或领域实现，不应成为通用层优化重点：

- Agent token、上下文长度、单轮费用、最大尝试次数、重试次数；
- 某个模型、Agent 框架、数据库、编程语言、IDE 或云服务；
- 某个公司的 SLA、审批表、岗位名称和内部系统；
- 某个算法的固定阈值；
- 只适用于一个行业的法规细节。

出现这些内容时先问：

> **它是否产生一种新的跨领域状态转化？**

如果没有，就下沉，不要提升为 L2，也不要让它占据总览和优化路线的中心。

### 九、L2 准入规则

新增核心基础链前必须同时检查：

1. 输入是否与现有链不同；
2. 输出是否与现有链不同；
3. 是否存在独立状态转化；
4. 完成标准是否不同；
5. 失败返回是否不同；
6. 是否跨生活、学习、工作、项目、经营或组织多个领域高频复现。

如果差异只是对象、工具、角色、行业、算法或规则，进入 L3/L4。

### 十、场景验证

优先用不同性质的场景反推体系，而不是只用软件场景：

- 个人目标；
- 较大的个人任务；
- 复杂问题解决；
- 多方案购买／选择；
- 阅读学习；
- 普通工作任务；
- 项目推进；
- OPC；
- 公司经营与组织采用；
- 软件项目；
- 风险和异常；
- 生命周期退出。

每个场景检查：

> 输入 → 正常路径 → 基础链映射 → 关键分支 → 信息不足 → 资源不足 → 方案失败 → 目标错误 → 返回位置 → 停止条件 → 生命周期出口

若现有链可以组合表达，就不要新增核心链。

### 十一、表达方式

- 中文优先；
- 先结论，后解释；
- 链路优先使用 `A → B → C`；
- 大分类用缩进列表或表格；
- 不为了显得专业而加入大量英文和工程术语；
- 不把“可运行”误写成“字段越多越好”；
- 不用自评分替代场景验证。

### 十二、仓库修改纪律

直接修改现有文件，避免创建同义重复文件。

如果当前用户明确要求：

- 直接在 `main` 修改；
- 不创建新分支；
- 不创建 PR；

则遵从该要求，并在提交前重新读取最新 `main`，避免覆盖并发修改。若用户没有指定 Git 策略，再根据仓库规则选择安全方式。

修改后至少检查：

- C01—C30 是否保持连续和唯一；
- 总览、地图、索引和场景之间是否一致；
- 内部相对链接是否有效；
- 是否出现新的重复定义；
- 通用层是否被软件、Agent 或单一行业绑架；
- 是否真的补了链路，而不是只增加说明文字。

### 十三、完成条件

只有同时满足以下条件，才能宣布一轮完成：

- 找到并处理了真正的链路缺口或边界问题；
- 新增内容被正确放在 L0／L1／L2／L3／L4；
- 没有无证据新增 C31；
- 高频复杂任务链更清楚；
- 正常路径、失败返回和生命周期仍完整；
- 工程实现细节没有反客为主；
- 修改已实际写入仓库并经过必要校验；
- 若用户要求提交，则已经提交并确认远端结果。
