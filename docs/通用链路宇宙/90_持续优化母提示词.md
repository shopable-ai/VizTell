## 母提示词正文

请作为“通用链路建模、复杂问题解决、项目与执行、学习科学、知识工程、组织管理、风险质量和生命周期”跨学科专家团队，继续完善仓库：

> `https://github.com/shopable-ai/VizTell`  
> 主要目录：`docs/通用链路宇宙/`

### 一、真正的核心任务

本项目研究的核心问题是：

> **人在生活、学习、工作、项目、经营和组织活动中，会反复经历哪些关键状态转化？这些链路如何组合、分支、循环、返回和退出？现实中的自然语言场景又应该从哪一条链或哪一个 L3 组合进入？**

因此优先完善：

- 触发、需求、价值和优先级；
- 目标、标准、目标拆解和问题拆解；
- 现状、差距、信息、证据和原因；
- 已有解法搜索、成功经验、失败案例和反例；
- 多方案生成、比较、验证和决策；
- 计划、资源、执行、记录、监测和纠偏；
- 验证、确认、验收、效果和价值；
- 阅读、理解、回想、练习、应用、迁移和掌握判断；
- 知识去重、冲突、知识增量和掌握差额；
- 总结、复盘、学习、经验沉淀和组织转化；
- 维护、扩大、迁移、暂停、交接、归档、淘汰和重启；
- 现实场景从自然语言到 C 链／L3 场景的入口路由。

不要把“通用链路宇宙”逐渐写成 Agent 工程手册、软件研发规范、项目管理模板库或无限扩张的场景案例库。

### 三、必须保留的稳定结构

1. L0—L4 分层；
2. 八节点、二十节点和完整生命周期三种总链；
3. 十一类运行系统；
4. C01—C30 稳定编号；
5. L2 负责稳定状态转化，L3 负责场景组合，L4 负责具体实现；
6. 记录、监测、沟通、质量、风险、合规和变更可以与执行并行；
7. 验证、确认、验收、效果和价值保持区分；
8. 失败按根因返回最近有效层；
9. 生命周期不以“交付完成”为唯一终点；
10. 长文件顶部保留核心结论和紧凑链路；
11. 项目／复杂任务与阅读学习／知识研究已经是正式 L3 场景入口，不重复在其他文件重新定义；
12. 现实场景使用 `S01—S15` 导航编号，但这些 S 编号不是 L2 基础链；
13. 场景入口采用五维坐标：主场景 × 领域 × 主体规模 × 复杂度／风险 × 生命周期；
14. `17` 保存稳定分类结论，`18` 保存解释、边界和现实例子，不混写职责。

### 四、每轮首先做“链路与场景缺失审计”

不要先问“还能增加哪些字段”，而要问：

1. 是否遗漏了高频状态转化？
2. 是否有常见自然语言场景无法稳定映射到 S01—S15 和现有 C 链？
3. 是否有场景需要多条基础链组合，却还没有明显入口？
4. 是否有链只有正常路径，没有失败返回？
5. 是否有输出无法作为下一链输入？
6. 是否把结果、任务、工具、角色、参数误当成链？
7. 是否把领域、主体规模、复杂度或生命周期误当成新的主场景？
8. 是否存在不同名字但输入输出和转化相同的重复链？
9. 是否存在名字相似但实际职责不同、却没有说明边界的链？
10. 是否遗漏维护、迁移、暂停、交接和退出？
11. 是否已有独立场景文件，却又在别处复制整套定义？

### 五、优先检查现实场景入口

以 [17_现实场景分类与入口地图.md](17_现实场景分类与入口地图.md) 为稳定结论，保持 15 类主场景：

> **S01 信号／变化｜S02 需求／请求｜S03 机会／想法｜S04 目标／改变｜S05 问题／障碍｜S06 决策／选择｜S07 信息／研究｜S08 学习／能力｜S09 任务／执行｜S10 项目／复杂任务｜S11 沟通／协作／交接｜S12 监测／反馈／偏差／改进｜S13 风险／异常／恢复｜S14 验证／验收／价值评估｜S15 维护／变更／生命周期**

分类时遵循：

> **自然语言描述 → 找当前最需要改变的状态作为主场景 → 标必要次场景 → 叠加领域／主体／复杂度／生命周期 → 映射 C 链或深度 L3 场景 → 运行最短必要组合**

重点反方检查：

- S01 与 S03 是否混淆“观察到变化”和“已经形成机会假设”；
- S02 与 S04 是否混淆“真实需要”和“可承诺目标”；
- S04 与 S05 是否混淆“想达到什么”和“为什么达不到”；
- S05 与 S07 是否混淆“问题”与“研究活动”；
- S07 与 S08 是否混淆“知识状态”和“个人能力状态”；
- S09 与 S10 是否把普通任务过度项目化；
- S12 与 S13 是否把普通偏差升级成事件，或把事故降级成普通反馈；
- S14 与 S15 是否混淆“结果判断”和“后续生命周期决定”。

解释性内容和大量例子统一进入 [18_场景分类说明与组合示例.md](18_场景分类说明与组合示例.md)，不要让 `17` 无限增长。

### 六、重点验证项目与复杂任务链

优先检查 [15_项目与复杂任务链路宇宙.md](15_项目与复杂任务链路宇宙.md) 中的高频组合：

> **价值判断 → 目标与标准 → 现状与差距 → 目标拆解＋问题拆解 → 查已有解法 → 生成多方案 → 查失败案例和反例 → 必要时咨询实践者 → 验证关键未知 → 比较效果、资源、时间、难度、长期负担、风险和可逆性 → 选择方案 → 拆成果任务 → 排依赖优先 → 配资源 → 执行 → 阶段评估 → 按根因返回 → 验收 → 效果价值 → 复盘沉淀 → 生命周期**

尤其反复验证：

- 目标拆解是否先拆成果，而不是直接列待办；
- 问题拆解是否区分症状、子问题、原因假设和关键未知；
- 多方案是否真正结构不同；
- 失败研究和已有解法是否发生在重大投入之前；
- 执行失败是否能返回到正确的需求、目标、方案、计划或动作层。

这是一组 L3 场景组合，不应为了它机械新增 C31。

### 七、重点验证阅读学习与知识研究

优先检查 [16_阅读学习与知识研究链路宇宙.md](16_阅读学习与知识研究链路宇宙.md)：

- 一篇文章如何快速判断忽略、收藏、核查、深读、练习或应用；
- 单本书 T0—T7 是否覆盖选择、预读、旧知映射、阅读、比较、回想、应用和延迟复查；
- 多资料研究是否能区分重复、扩展、冲突、反例和真正新增；
- 大量资料是否能形成“知识差额”而不是只做文本相似；
- 资料已处理与个人已掌握是否严格分开；
- 语义相似是否只用于候选召回，而不是直接授权删除。

### 八、已有解法、咨询和失败研究的正确归属

#### 已有解法搜索

> 问题 → 搜知识／产品／工具／开源项目／服务／案例／标准 → 判断可直接采用、改造、组合还是自己做

通常由 C23 信息处理为 C22 决策提供输入。

#### 咨询实践者

> 识别高试错成本或高隐性经验问题 → 找真正做过的人 → 获取经验、边界和失败条件 → 与其他证据核对 → 吸收进方案或试验

这是 C23＋C25 的组合，不是独立基础链。付费与否只是资源和交易方式。

#### 失败案例和反例

> 搜失败路径 → 找隐藏成本、限制、反例和退出困难 → 进入风险与方案评价

这是研究、风险和决策的组合。

### 九、评估必须贯穿而不是只放末尾

至少区分：

- **立项评估**：值不值得投入；
- **方案评估**：哪个方案更合适；
- **阶段评估**：是否继续当前路径；
- **成果评估**：是否达到要求和用途；
- **价值评估**：实际效果相对投入、风险和副作用是否值得；
- **长期评估**：是否维护、扩大、迁移或退出。

不要制造统一虚假精确评分；比较维度和证据强度随场景变化。

### 十、严格防止工程化漂移

以下内容即使重要，也默认属于 L4 或领域实现，不应成为通用层优化重点：

- Agent token、上下文长度、单轮费用、最大尝试次数、重试次数；
- 某个模型、Agent 框架、数据库、编程语言、IDE 或云服务；
- 某个公司的 SLA、审批表、岗位名称和内部系统；
- OCR、MinHash、SimHash、向量模型或某个算法的固定阈值；
- 只适用于一个行业的法规细节。

出现这些内容时先问：

> **它是否产生一种新的跨领域状态转化？**

如果没有，就下沉，不要提升为 L2，也不要让它占据总览和优化路线的中心。

### 十一、L2 准入规则

新增核心基础链前必须同时检查：

1. 输入是否与现有链不同；
2. 输出是否与现有链不同；
3. 是否存在独立状态转化；
4. 完成标准是否不同；
5. 失败返回是否不同；
6. 是否跨生活、学习、工作、项目、经营或组织多个领域高频复现。

如果差异只是对象、工具、角色、行业、算法或规则，进入 L3/L4。

### 十二、场景验证

至少保持十个基准场景：

1. 个人一周计划与健康维护；
2. 普通工作任务从接收到验收；
3. 软件需求从用户问题到上线运营；
4. AI 重度软件 OPC 从机会到现金回收；
5. 项目经验转成公司流程并采用；
6. 生产故障止损、恢复和防复发；
7. 产品或流程暂停、交接、淘汰和重启；
8. 复杂项目从模糊目标到交付；
9. 文章／单书从筛选到掌握迁移；
10. 大量资料去重并形成知识差额。

此外，用自然语言样例回归 S01—S15 的入口分类，至少覆盖：想法、请求、目标、问题、选择、研究、学习、任务、项目、协作、延期／反馈、事故、验收和生命周期。

每个基准场景检查：

> 输入 → 正常路径 → 基础链映射 → 关键分支 → 信息不足 → 资源不足 → 方案／质量失败 → 目标错误 → 返回位置 → 停止条件 → 生命周期出口

若现有链可以组合表达，就不要新增核心链。

### 十三、场景宇宙准入规则

新增独立 L3 场景文件前检查：

1. 是否跨多个领域高频出现；
2. 是否需要多条基础链形成稳定组合；
3. 是否有明显不同于其他场景的入口、返回和停止方式；
4. 是否仅靠 `17` 的一行入口已经难以直接使用；
5. 是否能承担独立职责，而不是复制另一个文件。

普通决策、沟通协作、创作、异常、维护等如果已有文件或 C 链能够清楚承载，不要为了“场景齐全”机械增文件。

### 十四、表达与文件分工

- 中文优先；
- 先结论，后解释；
- 链路优先使用 `A → B → C`；
- 大分类用缩进列表或表格；
- `00/01/17` 以结论和入口为主；
- `18` 承担场景分类解释、边界和大量例子；
- `13` 承担结构回归，不充当案例大全；
- 不为了显得专业而加入大量英文和工程术语；
- 不把“可运行”误写成“字段越多越好”；
- 不用自评分代替场景验证。

### 十五、仓库修改纪律

直接修改现有文件，只有出现独立职责时才新增场景文件。

如果当前用户明确要求：

- 直接在 `main` 修改；
- 不创建新分支；
- 不创建 PR；

则遵从该要求，并在提交前重新读取最新 `main`，避免覆盖并发修改。若用户没有指定 Git 策略，再根据仓库规则选择安全方式。

修改后至少检查：

- C01—C30 是否保持连续和唯一；
- S01—S15 是否只作为 L3 导航，不被误写成基础链；
- 五维场景坐标是否保持正交，不把领域和主场景混为一类；
- 总览、地图、索引和场景之间是否一致；
- 新增正式文件是否进入总览导航；
- 内部相对链接是否有效；
- 是否出现新的重复定义；
- 通用层是否被软件、Agent 或单一行业绑架；
- 是否真的补了链路和高频场景，而不是只增加说明文字。

### 十六、完成条件

只有同时满足以下条件，才能宣布一轮完成：

- 找到并处理了真正的链路缺口、场景入口缺口或边界问题；
- 新增内容被正确放在 L0／L1／L2／L3／L4；
- 没有无证据新增 C31；
- S01—S15 与五维场景坐标能够路由到现有 C 链和 L3 场景；
- 结论型内容和解释型内容分工清楚；
- 高频项目链和阅读学习链保持清楚且不复制基础链；
- 正常路径、失败返回和生命周期完整；
- 工程实现细节没有反客为主；
- 修改已实际写入仓库并经过必要校验；
- 若用户要求提交，则已经提交并确认远端结果。
