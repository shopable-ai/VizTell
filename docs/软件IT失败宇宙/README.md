# 软件与 IT 失败宇宙（V0.1）

> **独立行业研究域**。研究软件、IT、AI、平台、数字产品、工程组织与线上系统的失效机制、前兆、恢复和预防。既可收集真实失败案例，也可形成风险模式库。**失败案例是证据，不是自动禁用某项技术或做法的理由。**

## 1. 失败有不同对象和结果

必须说明到底什么失败：技术实现、工程交付、产品使用、商业经济性、运行可靠性、安全合规、生态依赖还是组织能力。交付成功 ≠ 产品成功 ≠ 商业成功；**提前止损或验证后终止**也不必然是失败。

每条记录标记：失败 / 部分失败 / 近失事件（near miss）/ 修复挽救 / 经证据支持的成功 / 战略性退出 / 尚不明确。保留事实与解释两层，切忌根据标题贴“失败原因”。

## 2. 首批研究分区（行业维度）

| 研究域 | 常见现象 | 首先核实的事实 |
| --- | --- | --- |
| IT-01 产品与需求 | 做出功能但缺少用户价值 | 用户研究、采用、留存与替代品 |
| IT-02 技术可行与架构 | 性能瓶颈、扩展性不足、技术债 | 负载、架构决策、约束和测试 |
| IT-03 工程交付 | 延期、范围膨胀、回归缺失 | 需求基线、进度、质量证据 |
| IT-04 运行可靠性 | 故障、数据丢失、恢复失败 | 时间线、影响面、监控、变更 |
| IT-05 安全、权限与隐私 | 漏洞、越权、隐私风险 | 威胁模型、授权路径、日志 |
| IT-06 AI 模型与 Agent | 幻觉、工具误用、不可复现 | 数据、评测、权限、回滚 |
| IT-07 平台与依赖生态 | 第三方 API 变化、渠道锁定 | 合同/规则变更、替代方案 |
| IT-08 商业模式与单位经济 | 高获客成本、盈利路径失效 | 收入、毛利、留存、现金消耗 |
| IT-09 组织与协作 | 责任不明、知识孤岛、技术路线漂移 | 决策记录、所有权、交付边界 |
| IT-10 竞争与时机 | 技术替代、市场窗口错失 | 市场阶段、竞争举措、时间证据 |

这些分区不互斥。一宗故障可涉及技术、管理、资金和市场，但应区分直接触发、促成条件、深层机制与结果。

## 3. 失败模式记录模板

- **failure_mode_id / 名称**：具体可观察的失效模式，不以含糊的“管理不善”结案。
- **对象和范围**：产品、系统、功能、组织、运行环境及版本。
- **目标与实际偏差**：预期服务/性能/用户价值/回报与实际差距。
- **时间线和阶段**：首次预兆、触发、发现、影响、恢复、复发。
- **事实 / 待验证假设 / 竞争性解释**：显式分离。
- **机制链**：前提 → 失效路径 → 触发 → 影响 → 反馈扩散。
- **可观测信号**：测试失败、错误率、留存、成本、单点依赖、风险阈值。
- **失败边界和反例**：什么条件下同一技术路线能够成功？
- **响应**：预防、检测、隔离、缓解、恢复、迁移、退出。
- **证据与归属**：原始来源、上下文、置信状态、记录者、版本、关联 ID。

真实事故需要真实时间线与可核来源；模拟案例必须显著标注 hypothetical，不能混入事实统计。

## 4. 排除因素 ≠ 一票否决

风险知识用于三类决策：
1. **解释**：理解已发生的结果；
2. **预警**：提示调查和测试；
3. **约束**：只有违反明确安全/合规硬约束，或经证据确认的不可承受风险时，才考虑暂停/阻断。

例：AI 自动生成代码且缺少回归测试 → 这是质量风险，应补验收/权限/回滚；不能由此得出“禁止 AI 编码”。未观察到故障也不代表系统已经安全。

## 6. MVP 研究闭环与验收

优先选择一个可靠性事故、一个需求/产品失败、一个 AI/自动化交付风险，且各自找成功或险情对照。对每例：确认原始来源 → 时间线 → 证据/主张分离 → 至少一种替代解释 → 映射模式 → 可执行的预警/测试 → 回读修订。**V0.1 未导入真实案例，也未验证预测精度；不得据此声称已防止 IT 失败。**
