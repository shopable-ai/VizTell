# 开源营销软件与数据工具生态

> 状态：RESEARCHED_REFERENCE_BASELINE
> 核查日期：2026-11-19
> 目的：从真实软件的能力边界、数据结构和运营流程反向理解营销职能；不是要求部署所有工具，也不是软件推荐榜单。

## 一、为什么要研究开源营销软件

- 专业知识地图描述“需要做什么”。
- 行动手册描述“怎样完成”。
- 软件系统揭示真实运营中需要哪些数据、角色、状态、权限、自动化和反馈。
- 开源项目还可以提供：
  - 可观察的真实工作流。
  - 数据对象与事件模型。
  - API 和集成方式。
  - 运营边界和权限机制。
  - 实验、报告和复盘机制。
  - 可复用的工程实现。

但软件功能不等于营销理论。一个软件只覆盖某类任务，不代表其产品分类就是完整营销分类。

## 二、软件许可必须先分类

不要把所有源码可见项目都称为“开源”。

- OSI 意义上的开源软件：
  - 需要核对 LICENSE 是否符合开源定义。
- Open Core：
  - 核心部分开源，企业版或特定目录可能采用商业许可。
- Fair-code / Source-available：
  - 源码可见、自托管或可扩展，但使用权可能受额外限制。
- 托管 SaaS：
  - 即使客户端或部分组件开源，托管服务、数据、品牌和 API 仍可能受商业条款约束。

当前已核查的许可提示：
- PostHog：仓库说明大部分为 MIT expat，EE 目录有单独许可；若要求纯 FOSS，应检查其 posthog-foss 发行仓库。
- GrowthBook：核心部分 MIT，部分 Enterprise 目录有单独商业许可。
- Formbricks：仓库包含 Enterprise 目录的单独许可，不能把全仓库简单标记为单一许可证。
- n8n：采用 Sustainable Use License 和 Enterprise License，属于 fair-code / source-available，不应直接标记为 OSI 开源。
- listmonk：仓库标示 AGPL-3.0。
- Umami：GitHub 仓库标示 MIT。
- Google Meridian：GitHub 仓库使用 Apache License 2.0。
- Meta Robyn：GitHub 仓库标示 MIT。

以上为仓库快照信息；实际采用、分发、商业集成前，必须核对当前 commit 的 LICENSE、NOTICE、子目录许可和第三方依赖。

## 三、按营销能力分类的软件参考地图

### 1. 用户研究、问卷与反馈

- Formbricks：
  - https://github.com/formbricks/formbricks
  - 调查问卷、产品内反馈、体验研究和用户反馈。
  - 值得研究：
    - 问卷与受访者对象。
    - 触发条件。
    - 反馈事件。
    - 同意与数据管理。
    - 从反馈到产品/营销决策的闭环。
  - 注意：
    - Enterprise 目录存在单独许可。
- 其他研究方向：
  - LimeSurvey。
  - SurveyJS。
  - Open-source qualitative coding / research repositories。
  - 采用前需检查维护状态、许可和数据保护能力。

### 2. CRM、线索与营销自动化

- Mautic：
  - https://github.com/mautic/mautic
  - 营销自动化、联系人、分群、Campaign、邮件和行为触发。
  - 值得研究：
    - Contact / Segment / Campaign / Event。
    - 触发器、条件、评分和生命周期状态。
    - 同意、退订和数据保留。
- EspoCRM：
  - https://github.com/espocrm/espocrm
  - CRM、账户、联系人、线索、商机和销售流程。
  - 值得研究：
    - 客户关系对象。
    - 销售活动与商机阶段。
    - 角色权限和审计。
- Twenty：
  - https://github.com/twentyhq/twenty
  - 现代 CRM 项目，可作为 CRM 对象和可扩展性参考。
- 重要边界：
  - CRM 不是完整营销系统。
  - 联系人数量不等于有效客户关系。
  - 自动化触达必须遵守同意、隐私和退订规则。

### 3. 邮件、Newsletter 与生命周期沟通

- listmonk：
  - https://github.com/knadh/listmonk
  - 自托管 Newsletter、邮件列表和活动管理。
  - AGPL-3.0。
  - 值得研究：
    - 订阅者、列表、Campaign、模板、发送状态和退订。
- Mautic 也覆盖营销邮件和自动化。
- 研究重点：
  - 邮件触达许可。
  - 分群与频率控制。
  - 投递、退信、投诉和退订。
  - 邮件带来的行为与商业结果。
- 不把打开率单独当作收入或真实注意力证明。

### 4. 网站分析与产品行为分析

- PostHog：
  - https://github.com/PostHog/posthog
  - 产品分析、Web Analytics、Session Replay、Feature Flags、Experiments、Surveys 等。
  - 值得研究：
    - Event / Person / Group。
    - Funnel / Cohort / Retention。
    - Session Replay 与用户行为解释。
    - Feature Flag 和实验。
    - 事件数据与业务结果连接。
  - 许可：大部分 MIT expat，EE 目录另有许可。
- Umami：
  - https://github.com/umami-software/umami
  - 隐私优先的网站和产品分析。
  - MIT。
  - 值得研究：
    - 页面访问、来源、活动、转化和隐私友好型分析。
- Matomo：
  - https://github.com/matomo-org/matomo
  - 网站分析与自托管分析能力。
  - 需核查当前发行版本和插件许可。
- 重要边界：
  - Web Analytics 不等于用户研究。
  - Session Replay 不等于因果解释。
  - 产品分析需要事件定义、身份规则、同意机制和数据质量。

### 5. A/B 测试、实验与功能发布

- GrowthBook：
  - https://github.com/growthbook/growthbook
  - Feature Flags、A/B/n Testing、实验统计和产品分析。
  - 核心 MIT，部分企业功能单独许可。
  - 值得研究：
    - 实验分配。
    - 指标定义。
    - 样本比例异常（SRM）。
    - CUPED、贝叶斯和序贯方法。
    - 实验结果与决策的连接。
- PostHog Experiments：
  - 可与其产品分析和 Feature Flags 联动研究。
- 重要边界：
  - 实验平台不能自动解决实验设计错误。
  - 多重比较、样本污染、干扰效应和外部效度仍需专业判断。

### 6. BI、数据探索与管理报告

- Metabase：
  - https://github.com/metabase/metabase
  - 商业数据查询、可视化和仪表盘。
  - 需核查开源核心与商业许可边界。
- Apache Superset：
  - https://github.com/apache/superset
  - Apache 2.0；数据探索、SQL Lab 和可视化。
- 值得研究：
  - 指标定义与语义层。
  - 数据源与权限。
  - 仪表盘和自助分析。
  - 业务指标与行动决策之间的连接。
- 边界：
  - BI 只呈现数据，不自动保证口径正确。
  - 仪表盘数量不等于组织的数据决策能力。

### 7. CDP、事件管道与数据连接

- RudderStack：
  - https://github.com/rudderlabs/rudder-server
  - 客户事件数据管道和数据集成参考。
  - 需要核查当前许可和 Cloud / Enterprise 边界。
- 相关研究方向：
  - Event Collection。
  - Identity Resolution。
  - Consent / Preference。
  - Event Routing。
  - Warehouse。
  - Data Quality。
- 边界：
  - CDP 不等于 CRM，也不等于完整客户视图已经可信。
  - 身份合并、跨设备关联和数据用途必须受到隐私规则约束。

### 8. 营销组合模型与预算优化

- Google Meridian：
  - https://github.com/google/meridian
  - Apache 2.0。
  - Bayesian Marketing Mix Modeling。
  - 使用聚合数据评估渠道影响、ROI 和预算分配。
- Meta Robyn：
  - https://github.com/facebookexperimental/Robyn
  - MIT。
  - 半自动化 MMM，包含回归、时间序列分解、优化和渠道响应曲线等能力。
- 值得研究：
  - Adstock。
  - Saturation / Diminishing Returns。
  - Channel Contribution。
  - Baseline / Incrementality。
  - Budget Allocation。
  - Geo-level Data。
- 边界：
  - MMM 不是一键生成真相。
  - 数据粒度、混杂因素、模型设定、校准、先验和业务解释决定结果质量。
  - 不应把平台归因 ROAS 与 MMM 估计直接混为同一种指标。

### 9. 自动化与系统集成

- n8n：
  - https://github.com/n8n-io/n8n
  - Fair-code 工作流自动化，具备大量集成和 AI 节点。
  - 不属于 OSI 意义上的传统开源许可。
- 值得研究：
  - 事件触发。
  - 数据同步。
  - 审批。
  - 周期报告。
  - 多系统任务编排。
  - 错误重试和状态管理。
- 边界：
  - Workflow 自动化不等于 Agent。
  - 外部副作用必须有授权、幂等、重试边界和人工审批。

## 四、从软件反推营销知识节点

每个软件研究至少提取：

- 软件解决的营销任务。
- 目标用户和角色。
- 核心业务对象。
- 输入数据。
- 输出数据。
- 工作流和状态机。
- 触发条件。
- 指标和报表。
- 权限与治理。
- 集成接口。
- 许可和商业边界。
- 失败模式。
- 适用规模与不适用场景。

软件中存在某个功能，不代表该功能就是通用营销最佳实践；需要结合理论、研究和真实任务判断。

## 五、工具采用与集成决策

- 不默认自建。
- 先比较现有工具是否满足任务。
- 优先考虑集成，而不是重复开发。
- 检查总拥有成本、许可、托管费用、维护、迁移和供应商依赖。
- 检查隐私、数据驻留、删除、权限和审计。
- 只有在多种工具无法覆盖、数据/流程需要独特控制或长期成本合理时，才考虑自建。
- 对工具进行分类：
  - REFERENCE：只用于研究和学习。
  - CANDIDATE：可能试用。
  - PILOT：小规模试点。
  - ADOPTED：已正式采用。
  - REJECTED：不采用并记录原因。
  - DEPRECATED：已停止使用。

## 六、后续维护

- 每个项目记录最近核查日期、默认分支、版本、活跃度和许可证。
- 商业许可、Fair-code、Open Core 和第三方依赖需要单独审查。
- 不把 GitHub Star 数量当作成熟度或安全证明。
- 不把自托管能力等同于隐私合规。
- 任何工具进入真实业务前，需进行安全、数据、成本和业务验收。
