# AI 自动检查器、组合筛选器与能力分级

> 核心目标：把前面的专业检查方法转成可组合的 AI Checker 能力，同时明确自动化上限、外部核验要求、冲突处理和错误放大风险。

本文件仍属于**能力设计层**，不是产品页面、API、Agent 或数据库方案。

---

## 一、AI Checker 的基本单位

一个 Checker 不是“一段提示词”，而是一个可评测的判断能力：

```yaml
checker:
  id:
  name:
  purpose:
  professional_fields: []
  framework_refs: []
  applicable_claim_types: []
  target_nv_families: []
  input_requirements: []
  detection_questions: []
  positive_signals: []
  risk_signals: []
  required_evidence: []
  missing_information: []
  alternative_explanations: []
  counterexample_test: []
  false_positive_conditions: []
  false_negative_conditions: []
  boundary_cases: []
  external_search_required:
  calculation_required:
  domain_expertise_required:
  human_review_required:
  case_refs: []
  benchmark_refs: []
```

## 二、自动化能力必须拆成五维

```text
Detect
发现候选风险

Explain
解释为什么值得检查

Verify
获取或计算支持判断所需证据

Judge
在当前证据下做可靠裁决

Act
据此自动执行阻断、合并、删除、入库或其他动作
```

同一个 Checker 可能：

```text
Detect = high
Explain = high
Verify = medium
Judge = low
Act = none
```

不能因为 AI 很会解释，就假设它也能可靠 Judge / Act。

## 四、Checker 不应全部串行运行

错误做法：

```text
每篇文章
→ F01
→ F02
→ ...
→ F24 全部跑完
```

会导致：

- 成本高；
- 延迟高；
- 大量无关报警；
- False Positive 增加；
- 用户无法理解优先级。

正确方式：

```text
内容类型 + Claim 类型 + 当前目标 + 风险
↓
生成 Checker Route
↓
只调用相关检查器
```

例如：

```text
因果 Claim
→ F03/F04/F08
→ 若引用研究，再 F10/F11/F13/F14/F15
```

## 五、组合筛选器候选

组合筛选器不是新的认识论工具，而是按任务装配多个 Checker。

### 5.1 快速文章筛选器

```text
F01 + F02 + F03 + F13 + F19 + F21 + F22
```

目标：快速发现值得深入核验的 Claim 与阅读价值。

### 5.2 因果主张筛选器

```text
F02 + F04 + F08 + F09 + F10 + F11 + F13 + F14
```

### 5.3 科研二手解读检查器

```text
F02 + F04 + F10 + F11 + F13 + F14 + F15 + F16
```

### 5.4 网络谣言辅助核验器

```text
F02 + F13 + F14 + F17 + F18 + F23
```

### 5.5 书籍预审器

```text
F01 + F02 + F03 + F04 + F13 + F19 + F21 + F22 + F23
```

根据书籍类型再动态加入专业 Checker。

### 5.6 AI 回答审查器

```text
F02 + F04 + F13 + F14 + F21 + F23 + F24
```

对数据/因果问题再加入 F08—F12。

## 六、外部检索是独立能力，不是 LLM 内部知识替代品

遇到下面任务必须触发外部核验：

- 论文是否真实存在；
- 最新指南/法规/版本；
- 原始引用；
- 撤稿/更正状态；
- 作者专业身份；
- 原始图像/视频来源；
- 当前科学共识。

因此 Checker 输出至少需要：

```yaml
verification_plan:
  external_search_required: true
  target_sources: []
  freshness_requirement:
  primary_source_priority: true
```

不能把模型记忆当作“已检索”。

---

## 七、数学计算与文本判断分开

例如 F11：

```text
LLM 识别问题
→ Calculator / Statistical Tool 计算
→ LLM 解释结果
```

不要让语言模型仅凭自然语言心算承担所有数值核验。

同理，图表检测需要视觉/数据工具时，应显式标记所需能力。

---

## 八、Checker 冲突处理

不同 Checker 可能得出：

```text
F19：修辞强
F14：引用忠实
F15：整体证据强
```

正确结果不是：

> “修辞强，所以文章低可信。”

而是：

> “表达高度说服性，但核心 Claim 证据仍然较强。”

因此结果聚合必须保留多维状态，不能做简单多数投票。

---

## 九、风险信号聚合原则

优先级考虑：

- Claim 重要性；
- 风险严重性；
- Checker 可靠度；
- 证据状态；
- 是否独立信号；
- 是否只是同一根因被多个 Checker 重复报警。

例如：

```text
F04 相关→因果升级
F08 因果支持不足
F14 原研究只说相关
```

可能是同一个根因，不应该显示成“三个独立错误”。

## 十、AI 转换失真 F24

当 AI 做：

- 摘要；
- 改写；
- 翻译；
- 多文档合并；
- 知识原子化；
- Canonicalization；

至少检查：

1. 原 Claim 是否存在；
2. 条件是否保留；
3. 量词/概率是否升级；
4. 因果强度是否升级；
5. 不确定性是否消失；
6. 来源是否仍然正确对应；
7. 多个来源是否被错误合成为同一事实；
8. 模型是否自行补了不存在的桥梁解释；
9. 引用是否错配；
10. 原文冲突是否被模型“顺滑地消除”。

有原文时，F24 的自动检测潜力很高。

---

## 十一、AI Checker 必须允许 Abstain

至少支持：

```text
insufficient_information
external_verification_required
human_review_required
```

系统不应被奖励为“每条都必须给确定答案”。

正确拒判是能力，而不是失败。

---

## 十二、错误放大风险

单条误判 × 海量自动处理会形成：

- 错误知识批量拒绝；
- 正确资料批量降权；
- 大规模错误 merge；
- 系统性偏向某类表达风格；
- RAG 入库污染；
- 用户过度依赖自动评分。

因此：

> **规模化前必须先有 Checker-level Benchmark。**

---

## 十三、Act 权限默认最保守

第一阶段建议：

```text
Detect / Explain
→ 可自动

Verify
→ 有工具和来源时条件自动

Judge
→ 按 Checker 与风险分级

Act
→ 默认只建议，不做不可逆动作
```

尤其以下动作默认需更强 Gate：

- 删除知识；
- 覆盖 Canonical；
- 标记作者/来源为“虚假”；
- 高风险内容执行；
- 自动阻断关键业务资料。

正式权限与风险进入现有 `10`。

## 十五、Benchmark 要求

每个 Checker 和组合筛选器都必须测：

- TP / FP / TN / FN；
- Boundary；
- Insufficient Evidence；
- Abstain；
- Overclaim Rate；
- Appropriate Abstention Rate；
- latency / cost；
- 人工复核量；
- 高风险错误严重度。

具体进入 `21` 和现有 `13/22`。
