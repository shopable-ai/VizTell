# 论证结构、非形式逻辑与逻辑谬误工具

> 核心目标：把自然语言中的“前提 → 推理 → 结论”显式化，再判断支持关系是否合理；不以“谬误标签大全”为中心。

---

## 一、专业来源

主要来自：

- Critical Thinking；
- Informal Logic；
- Argumentation Theory；
- Toulmin Model；
- Argument Mapping；
- Argumentation Schemes + Critical Questions；
- 形式逻辑中的明确有效/无效形式；
- Structured Analytic Techniques 的关键假设与反方检查。

---

## 二、第一步永远不是“找谬误”，而是标准化论证

面对一段自然语言，先提取：

```yaml
argument:
  claims: []
  premises: []
  implicit_premises: []
  evidence_refs: []
  conclusion:
  inference_type:
  qualifiers: []
  rebuttals: []
```

至少做四件事：

1. 去掉与推理无关的重复、情绪铺垫和修辞噪声；
2. 把问句、比喻和隐含表达还原成可分析命题；
3. 补出没有明说但结论依赖的隐含前提；
4. 区分作者真正的结论与读者可能自行推出来的结论。

如果无法稳定提取论证结构，应输出 `insufficient_information`，而不是强行贴谬误标签。

---

## 三、通用论证三问

一个最小可用的自然语言论证检查器至少问：

### 3.1 前提是否可接受？

- 前提本身是事实、假设、价值判断还是定义？
- 是否需要外部证据？
- 是否存在明显错误、过时或争议？
- 是否把“尚未验证”写成“已知事实”？

### 3.2 前提是否相关？

- 即使前提为真，它与结论真的有关吗？
- 是否通过人物身份、情绪、群体归属转移了问题？
- 是否只证明了一个旁支命题？

### 3.3 前提是否足够？

- 这些前提最多能支持多强的结论？
- 是否少了关键桥梁前提？
- 是否从个案跳到普遍规律？
- 是否从“可能”跳到“必然”？

## 四、Toulmin 结构检查

适合复杂现实论证：

- **Claim**：最终主张；
- **Data / Grounds**：作者提供了什么资料；
- **Warrant**：为什么这些资料能支持 Claim；
- **Backing**：Warrant 凭什么成立；
- **Qualifier**：结论强度和条件；
- **Rebuttal**：什么情况下例外或失败。

高价值检查动作：

> **强制显式化 Warrant。**

很多弱论证的问题不在 Data 本身，而在“Data → Claim”的桥梁从未被证明。

## 五、Argumentation Schemes + Critical Questions

### 5.1 专家意见

不要直接判“诉诸权威”。继续问：

1. 专家是否真的属于相关领域？
2. 专业范围是否与当前 Claim 对齐？
3. 专家原话是什么？
4. 专家是否有明显利益冲突或可信度问题？
5. 其他相关专家/证据是否大体一致？
6. 该专家的结论是否基于可核查证据？

只有关键问题无法得到合理回答时，才把它标成弱专家论证风险。

### 5.2 类比论证

检查：

1. A 与 B 在哪些关键机制上相似？
2. 相似的是表面还是因果机制？
3. 有没有会改变结论的重要差异？
4. 类比只是帮助理解，还是被当成证明？
5. 是否存在更接近目标场景的直接证据？

### 5.3 案例 / Example

检查：

1. 案例是教学例子、存在性证明、反例还是普遍证据？
2. 需要支持“存在”还是“普遍规律”？
3. 一个案例是否被扩张成总体概率？
4. 是否存在选择案例/幸存者偏差？

### 5.4 因果论证

只做论证层路由，具体进入 `04`。

### 5.5 人身可信度

“讨论人”不自动等于 ad hominem 谬误。

若当前问题本身涉及：

- 证人可靠性；
- 专业资格；
- 利益冲突；
- 反复错误记录；

人物信息可能与证据评价直接相关。

真正要检查的是：

> 对人的攻击是否与目标 Claim 的真假或可信度有关？

## 七、几个可较可靠自动化的明确检查

### 7.1 肯定后件候选

```text
如果 A → B
观察到 B
所以 A
```

AI 可高召回检测形式，但仍需检查自然语言中是否遗漏其他前提。

### 7.2 否定前件候选

```text
如果 A → B
非 A
所以非 B
```

### 7.3 明显循环论证候选

检测结论是否只是换词后重新作为自己的前提。

### 7.4 明显错误两难候选

检测是否把多种可能压成 A/B 两项，并搜索文本内或常识层可见的第三选项。

这些适合 `Detect=high`，但 `Judge` 仍要保留上下文。

## 八、反方压力测试工具

至少包括：

### Key Assumptions Check

- 当前结论依赖哪些未明说的假设？
- 哪个假设最脆弱？
- 什么新信息会迫使我们放弃它？

### Competing Explanations

- 至少生成 2—3 个能解释同一现象的替代解释；
- 找真正能够区分这些解释的证据；
- 不只搜索支持当前首选解释的信息。

### Counterexample Test

- 什么具体情况一旦出现，就说明当前普遍命题过强？
- 是否已经存在这样的反例？

---

## 九、AI Checker 边界

### 适合自动化

- Claim / premise / conclusion 候选提取；
- 明显逻辑形式；
- 缺失 Warrant 提醒；
- 论证模式候选；
- 生成 Critical Questions；
- 生成替代解释与反例搜索方向。

### 只能提示风险

- 某个专家意见是否最终可靠；
- 类比是否足够；
- 某种人身信息是否真正相关；
- 稻草人是否成立；
- 作者是否满足举证责任。

### 常需外部证据

- 前提真伪；
- 专家领域和原话；
- 现实反例；
- 领域共识。

---

## 十、误报 Benchmark 必测

1. 合理专家意见被误判“诉诸权威”；
2. 合理人物可信度信息被误判“人身攻击”；
3. 教学类比被误判“类比证明”；
4. 风险管理中的合理 worst-case 被误判“滑坡”；
5. 真的只有两个选项却被误判“错误两难”；
6. 一个真实反例合理推翻全称命题，却被误判“以偏概全”。

目标不是“谬误识别数量最大”，而是**论证裁决更接近真实结构**。
