# 验证计划、样本清单与数据边界

> 本文件规定 AI 原生知识系统什么时候可以读取真实知识资产、允许读取什么、为什么读取、如何记录以及何时停止。

当前阶段的默认规则：

> **先完成通用框架、协议、Schema 与合成 Benchmark；未经显式 Validation Sample Manifest，不读取或处理现有书库、论文库、个人知识库或 `temp/` 真实资料。**

---

## 1. 为什么需要独立的数据使用协议

真实资料很容易让研究过程产生三种偏差：

1. **样本偏置**：因为手头恰好有某类书，就把整个知识系统设计成适合这类书；
2. **目标漂移**：本来在设计通用框架，却逐渐变成整理具体资料；
3. **不可观察的数据使用**：人工无法判断 AI 到底读取了哪些资料、为了验证什么、结论是否被特定样本污染。

因此：

> **真实资料不是默认上下文，而是受治理的测试输入。**

---

## 2. 三个验证阶段

### V0：框架与合成案例阶段

只允许使用：

- 现有正式框架文档；
- 通用链路参考；
- 人工设计的 synthetic case；
- 公开专业标准与正式方法论。

目的：

- 检查 L1/L2/L3 完整性；
- 检查正交性；
- 定义 Knowledge Atom；
- 定义关系、去重、增量和路由；
- 建立 Schema 和 Benchmark 结构。

**当前默认处于 V0。**

### V1：受控小样本验证

前提：

- V0 核心语义已经基本稳定；
- 已明确要验证的具体能力；
- 已建立 Validation Sample Manifest。

只读取少量代表性样本，验证特定问题。

### V2：规模化真实语料 Benchmark

只有在 V1 证明协议可运行后，才考虑：

- 更大样本；
- 自动采样；
- 批处理；
- 真实检索/去重性能；
- 成本、延迟、错误率和人工复核率。

## 3. Validation Sample Manifest

每次真实资料验证之前，必须先生成一份 Manifest。

最小字段：

```yaml
validation_manifest:
  manifest_id: VM-...
  status: proposed
  validation_goal:
    - "验证命题等价与新增条件是否可区分"

  sample_selection:
    strategy: purposive
    rationale: "需要一组明确的等价、扩展和冲突样本"

  samples:
    - sample_id: VS-001
      source_path: "..."
      source_type: document
      allowed_range:
        mode: explicit_section
        value: "..."
      purpose: "..."

  prohibited_scope:
    - "未列入 samples 的其他资料"

  allowed_operations:
    read: true
    derive_atoms: true
    compare_semantics: true
    modify_source: false
    delete_source: false

  output_location:
    - "docs/AI原生知识系统/research-notes/..."

  promotion_rule:
    framework_changes_require_cross_case_support: true

  stop_conditions:
    - "目标测试完成"
    - "发现样本选择不足，需要重新审批样本设计"
```

---

## 4. 样本选择必须说明“为什么是它”

不能采用：

> “看起来这个文件挺合适，所以顺便读一下。”

应该先定义测试类别，再选择样本。

例如：

| Benchmark 类别 | 需要的样本性质 |
|---|---|
| 文件完全重复 | 同内容不同路径或复制文件 |
| 近似文本重复 | OCR、格式、轻微编辑差异 |
| 同义改写 | 文字差异大、命题等价 |
| 新条件 | 主命题相同但新增成立条件 |
| 新边界 | 原规则被限制适用范围 |
| 新证据 | 原命题不变但证据新增 |
| 伪多源 | 多个二手来源来自同一上游 |
| 真冲突 | 条件相同但结论相反 |
| 同名异义 | 名称相同、语义对象不同 |
| 异名同义 | 名称不同、Canonical 身份相同 |
| 版本替代 | 明确的新版本替代旧版本 |
| 非版本关系 | 文件名像版本但实际不是修订关系 |

先有类别，后有样本。

---

## 5. 当前阶段禁止的行为

在 V0 阶段默认禁止：

- 扫描整个 `temp/` 以寻找有趣内容；
- 为完善框架随机打开书籍；
- 把具体书中的观点直接提升为系统规则；
- 未建立 Manifest 就进行跨书语义比较；
- 把书库内容生成正式 Canonical Knowledge；
- 修改、清洗、删除原始资料；
- 因为某一批资料的结构而改变总体 L1。

## 6. 允许的元数据级盘点也要有边界

未来如果只做文件级 inventory，仍需区分：

### Metadata-only

允许读取：

- 文件名；
- 路径；
- 大小；
- hash；
- 类型；
- 修改时间等非内容元数据。

不读取正文。

### Content-sampling

只读取 Manifest 明确授权的内容范围。

### Full-processing

只有进入正式批处理实验后，才允许对指定数据集进行全文解析、Atom 提取或跨资料比较。

三种模式不能混淆。

## 7. 数据使用日志

未来每次真实验证至少记录：

```yaml
data_usage_log:
  run_id: VR-...
  manifest_id: VM-...
  started_at: "..."
  samples_read: []
  ranges_read: []
  operations_performed: []
  derived_artifacts: []
  source_modifications: []
  anomalies: []
  stopped_reason: "..."
```

目标是人工能够回答：

> **这一次 AI 到底看了什么、做了什么、没有看什么。**

---

## 8. 样本结论不能自动升级为框架结论

单个或少量样本只能产生：

- observed phenomenon；
- candidate issue；
- candidate relation；
- failure case；
- hypothesis。

只有经过：

```text
多个不同类型案例
→ 能被现有理论解释或暴露稳定缺口
→ 对照反例
→ 证明不是数据集偶然特征
→ 再修改正式框架
```

才允许升级为正式规则。

## 9. 合成 Benchmark 应先于真实书库

在框架阶段可以先构造人工可控案例：

### SYN-DUP-01

A：`当输入 X 且条件 C 时，方法 M 提高结果 Y。`

B：`在 C 成立时，使用 M 可以改善 X 对 Y 的结果。`

预期：`paraphrase_equivalent`。

### SYN-COND-01

A：`方法 M 通常提高 Y。`

B：`方法 M 只在条件 C 成立时提高 Y。`

预期：不能合并为完全等价；B 至少产生 `adds_condition` 或对 A 的范围修正。

### SYN-EVID-01

A 与 B 均引用同一上游研究 E1。

预期：raw source count=2，但 independent evidence group count=1。

### SYN-CONFLICT-01

A：在相同条件 C 下，M 提高 Y。

B：在相同条件 C 下，M 降低 Y。

预期：进入 `conflicts_with`，不得平均成“效果不确定”而丢失两侧证据。

合成测试可以先验证协议逻辑，不产生真实资料偏置。

## 10. Validation Gate

从 V0 进入 V1 前至少满足：

- [ ] L1/L2 边界已完成一次正式审计；
- [ ] Knowledge Atom 与 Canonical Knowledge 已定义；
- [ ] Relation Assertion 已定义；
- [ ] 去重/增量关系宇宙已定义；
- [ ] 可信度与来源独立性协议已定义；
- [ ] 学习/消费路由已定义；
- [ ] 实现能力路由已定义；
- [ ] Benchmark Case Schema 已定义；
- [ ] 已先通过一组合成回归测试；
- [ ] 已创建 Validation Sample Manifest；
- [ ] 人工能够明确看到真实资料范围与目的。

未满足时保持 V0。
