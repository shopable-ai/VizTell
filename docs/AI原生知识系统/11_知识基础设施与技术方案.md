# 知识基础设施与技术方案

> 本文件属于 **Solution Space**。只有上游需求、知识属性、价值、风险与人机分工明确后，才选择具体技术。技术是实现手段，不是问题定义。

## 一、技术层总图

| 层 | 解决的问题 | 代表技术／形态 |
| --- | --- | --- |
| 原始资料层 | 保存原文、版本和来源 | 文件系统、对象存储、数据库 |
| 解析标准化层 | 把不同载体转成可处理结构 | 文档解析、字幕／音频转写、OCR、元数据抽取 |
| 全文检索层 | 精确关键词、术语、短语查询 | Elasticsearch、OpenSearch、BM25 类检索 |
| 语义检索层 | 找到不同表述但含义接近的候选 | Embedding、向量索引 |
| 混合检索层 | 同时利用关键词、语义、元数据和关系 | Full-text + Vector + Metadata + Rerank |
| 标准知识层 | 维护去重后的知识单元和来源关系 | Canonical Knowledge Store、Claim／Evidence 数据模型 |
| Wiki／浏览层 | 让人和 Agent 浏览整体结构 | OpenWiki 类 Wiki、主题页、领域地图 |
| RAG 层 | 任务发生时组装最小充分上下文 | Query 理解、召回、重排、压缩、引用、上下文预算 |
| 关系层 | 表达知识、实体、证据、依赖、冲突 | Knowledge Graph、关系索引 |
| AI 能力层 | 把稳定知识变成可调用能力 | Prompt、Rule、Skill、Tool、Workflow、Agent |
| 人工学习层 | 把知识变成人的理解与能力 | 学习地图、主动回忆、题库、案例、间隔复查 |
| 观测维护层 | 监测质量、变化和能力退化 | 日志、评测、版本、增量更新、回归测试 |

## 二、检索技术的分工

- **全文检索**：术语、名称、精确短语、代码、编号和结构化过滤强。
- **语义检索**：同义表达、改写、跨表述召回强，但只能提供候选。
- **关系检索**：回答“依赖什么、冲突什么、有哪些证据／反例”等关系问题。
- **混合检索**：海量知识场景默认应允许多路召回和重排，而非单一向量搜索包打天下。

## 三、RAG 的位置

RAG 解决的是“任务发生时怎样找到并组装相关外部知识”，不自动解决：

- 知识是否正确；
- 是否新瓶装旧酒；
- 人是否值得学习；
- 是否应该 Skill 化；
- 是否已经有成熟工具替代；
- 知识是否过期；
- 多来源是否独立。

因此 RAG 位于标准知识与消费端之间，而不是整个知识系统的总架构。

## 四、Wiki／OpenWiki 类系统的位置

Wiki 更适合承担：主题浏览、领域地图、知识关系、版本说明、来源追溯与人工编辑。它与全文搜索、RAG、知识图谱可以并存，不应被理解为互相替代。

## 五、技术选型的上游输入

任何技术选型至少读取：数据规模、查询类型、更新速度、来源格式、关系复杂度、延迟要求、准确率要求、可追溯性、权限、成本、维护能力、人／AI 消费方式。

## 六、暂不冻结的实现细节

具体模型、向量数据库、Chunk 大小、Embedding、Reranker、ES/OpenSearch 版本、Wiki 产品、阈值与部署方式属于 L4 工程配置，应通过代表性场景 Benchmark 决定，不在当前框架阶段提前固定。
