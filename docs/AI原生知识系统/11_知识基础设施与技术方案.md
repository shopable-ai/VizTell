# 知识基础设施与技术方案

> 本文件属于 **Solution / Implementation Space**。只有上游需求、知识属性、来源证据、主体价值、学习适配、风险与能力归属明确后，才选择具体技术。

历史编号 `L1-12` 为兼容现有结构继续保留，但它不是与“知识质量、主体价值”同类的评价轴。

---

## 一、技术层总图

| 层 | 解决的问题 | 代表技术／形态 |
| --- | --- | --- |
| 原始资料层 | 保存原文、版本和来源 | 文件系统、对象存储、数据库 |
| 解析标准化层 | 把不同载体转成可定位结构 | 文档解析、转写、OCR、元数据抽取 |
| Provenance 层 | 记录来源、派生、处理活动、版本 | Source Registry、lineage、PROV-compatible model |
| 全文检索层 | 精确关键词、术语、短语查询 | Elasticsearch、OpenSearch、BM25 类检索 |
| 语义检索层 | 找到不同表述但含义接近的候选 | Embedding、向量索引 |
| 混合检索层 | 关键词、语义、元数据、关系联合召回 | Full-text + Vector + Metadata + Rerank |
| 标准知识层 | 维护 Canonical Knowledge、Evidence、Relation | Canonical Store、Claim/Evidence/Relation model |
| Wiki／浏览层 | 让人浏览稳定知识结构 | Wiki、主题页、领域地图 |
| RAG 层 | 任务发生时组装最小充分上下文 | Query 理解、召回、重排、压缩、引用 |
| 关系层 | 查询依赖、支持、冲突、版本、证据 | Knowledge Graph 或关系索引 |
| 能力层 | 把稳定知识变成可调用任务能力 | Skill、Rule、Tool、Workflow、Agent |
| 人工学习层 | 把必要知识变成人的真实能力 | 学习地图、练习、反馈、迁移验证 |
| 观测维护层 | 监测质量、变化、成本和能力退化 | 日志、评测、版本、回归、增量更新 |

## 二、技术选型必须经过 Implementation Routing

不再采用：

> “这是知识问题，所以用 RAG。”

而采用：

```text
Problem / Requirement
→ Capability Ownership
→ Task Characteristics
→ Candidate Implementations
→ Compare lowest sufficient complexity
→ Select + record rejected alternatives
```

正式路由见 `19_知识到Search-RAG-Skill-Workflow-Agent-软件的能力路由.md`。

## 三、检索技术的分工

- **全文检索**：术语、名称、精确短语、代码、编号、错误码和结构化过滤强。
- **语义检索**：同义表达、改写、跨表述召回强，但只提供候选。
- **关系检索**：回答依赖、支持、冲突、证据、版本和影响传播问题。
- **混合检索**：海量知识默认应允许关键词、语义、元数据、时间和权限联合检索，而不是向量搜索包打天下。

## 四、RAG 的位置

RAG 解决：

> **任务发生时怎样找到并组装外部知识，让模型在有限上下文中完成当前任务。**

RAG 不自动解决：

- 知识是否正确；
- 是否新瓶装旧酒；
- 来源是否独立；
- 人是否值得学习；
- Skill 是否正确；
- 知识是否过期；
- 是否允许自动执行。

因此 RAG 位于检索/标准知识与消费端之间，不是整个知识系统的总架构。

---

## 五、Wiki 的位置

Wiki 更适合承担：

- Human Browse Surface；
- 主题导航；
- 概念地图；
- Canonical Knowledge 人工可读视图；
- 来源/版本/边界展示；
- 人工修订入口。

Wiki 不应要求把每个原始文件手工整理成页面。

---

## 六、Knowledge Graph 的位置

先保证：

> Canonical ID + typed Relation Assertion

只有在显式关系、多跳、依赖、影响传播等需求证明图式查询有价值后，再决定底层是否采用图数据库。

“有关系”不等于“必须部署图数据库”。

---

## 七、Skill / Workflow / Agent 的技术边界

- **Skill**：稳定、可重复、输入输出较清晰的方法或判断能力。
- **Workflow**：多步骤、顺序/依赖/关口相对稳定的任务图。
- **Agent**：需要持续观察环境、动态分支、重规划和多工具推进的开放任务。

如果稳定 Workflow 能覆盖，就不应为了 AI 原生而强行 Agent 化。

详细路由见 `19`。

---

## 八、首批工程底座候选

在真实产品需求尚未验证前，优先考虑最小基础对象与能力：

1. Source Registry；
2. Raw Fragment provenance；
3. Knowledge Atom / Canonical Store；
4. Evidence / Relation Assertion；
5. Hybrid Retrieval；
6. Increment Report；
7. Human Review Queue；
8. Routing Decision Store；
9. Benchmark Runner。

这些底座稳定后，再考虑 Tutor、主动研究 Agent、Skill Mining、完整 Wiki 和产品 UI。

---

## 九、技术选型的上游输入

至少读取：

- Requirement Pattern；
- 数据规模；
- 查询类型；
- 更新速度；
- 来源格式；
- 关系复杂度；
- latency；
- accuracy/recall 要求；
- provenance 要求；
- 权限和风险；
- 人/AI 消费方式；
- 维护能力；
- 总拥有成本；
- Benchmark 结果。

## 十、暂不冻结的实现细节

具体模型、向量数据库、Chunk 大小、Embedding、Reranker、ES/OpenSearch 版本、Wiki 产品、阈值与部署方式属于 L4 工程配置。

它们必须通过代表性 Benchmark 决定，不在框架阶段提前固定。
