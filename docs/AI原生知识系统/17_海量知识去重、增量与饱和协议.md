# 海量知识去重、增量与饱和协议

> 本文件定义从几十万本级资料中识别“重复、换皮、扩展、证据变化、边界变化、真正新增”的正式协议。

核心原则：

> **语义相似只能召回候选，不能直接授权删除、合并、覆盖或替代。**

---

## 1. 去重不是一个问题，而是八层判定链

```text
G0 文件与版本身份
→ G1 文本完全重复
→ G2 近似文本重复
→ G3 语义候选召回
→ G4 命题/机制对齐
→ G5 关系裁决
→ G6 知识增量裁决
→ G7 证据独立性与证据增量
→ G8 饱和与停止策略
```

任何层都不得把后续语义问题偷换成前面的字符串问题。

---

## 2. G0：文件与版本身份

### 2.1 文件级完全重复

可使用：

- cryptographic hash；
- byte size；
- MIME/type；
- normalized archive member hash。

文件 hash 一致可判定文件字节级重复。

但文件不同并不代表内容不同。

### 2.2 版本号只能作为候选信号

文件名中的：

- v1/v2；
- 1.0/2.0；
- 修订版；
- PDF版/文字版；
- 完整版/精简版；

都不能单独证明：

> `new_file supersedes old_file`

必须继续判断：

- 内容重合率；
- 章节对应；
- Canonical Knowledge 集合变化；
- 删除/新增内容；
- 来源元数据；
- 是否只是不同载体表示。

可能的关系包括：

- revision_of；
- alternate_representation_of；
- partial_overlap；
- expanded_from；
- independent_collection；
- unrelated_despite_name。

---

## 3. G1：文本完全重复

在统一编码、换行、空白、页眉页脚等**可逆规范化**后，可计算文本级 hash。

注意：

- 原始文件必须保留；
- normalization 规则必须版本化；
- OCR 纠错前后不能丢失原始来源；
- 图片、表格、代码等非纯文本信息不能因为正文相同就被忽略。

---

## 4. G2：近似文本重复

适合发现：

- OCR 少量差异；
- 页码/广告/页眉差异；
- 段落微调；
- 轻微删改；
- 大段复制。

候选技术可以包括：

- n-gram / shingles；
- MinHash；
- SimHash；
- edit distance；
- rolling hash；
- chunk-level overlap。

输出应该是：

> **candidate pair / candidate cluster**

而不是：

> **自动删除列表。**

---

## 5. G3：语义相似候选召回

Embedding / Semantic Search 主要解决：

> 文本不同，但可能在说同一件事。

它适合发现：

- 同义改写；
- 翻译；
- 换一种叙事重讲；
- 同一机制不同作者命名；
- 同一方法在不同场景中的表达。

但高语义相似仍可能是：

- 条件不同；
- 结论方向相反；
- 一个是一般规则，一个是反例；
- 一个是机制，一个只是案例；
- 一个适用于 A 人群，一个只适用于 B 人群；
- 一个是旧版本，一个是新证据修订。

因此：

> `semantic_similarity >= threshold` 只能进入 G4，不得直接 merge。

---

## 6. G4：命题、机制与条件对齐

需要把候选知识拆成可比较结构：

```yaml
proposition:
  subject: "..."
  predicate: "..."
  object: "..."
  qualifiers: []
  conditions: []
  scope: []
  time: null
  mechanism: null
```

至少比较：

1. 主体是否相同；
2. 关系/结论是否相同；
3. 量词和强度是否相同；
4. 条件是否相同；
5. 适用范围是否相同；
6. 时间是否相同；
7. 机制是否相同；
8. 证据是否相同；
9. 是否只是例子不同。

---

## 7. G5：正式关系宇宙

### 7.1 高重复关系

- `exact_duplicate`：知识结构与限定条件等价；
- `textual_variant`：主要只是文本/OCR/格式变体；
- `paraphrase_equivalent`：命题语义等价；
- `alias_of`：概念异名同义；
- `same_mechanism`：不同命名但核心机制相同。

### 7.2 包含与扩展

- `contains`；
- `is_contained_by`；
- `refines`；
- `supplements`；
- `adds_condition`；
- `adds_boundary`；
- `adds_scope`；
- `adds_mechanism`；
- `adds_method_step`。

### 7.3 证据与案例关系

- `adds_evidence`；
- `adds_independent_evidence`；
- `adds_case`；
- `adds_counterexample`；
- `supports`；
- `weakens`；
- `refutes`。

### 7.4 时间与替代

- `updates`；
- `supersedes`；
- `replaces`；
- `obsolete_because_of`。

### 7.5 其他

- `conflicts_with`；
- `depends_on`；
- `unrelated`；
- `uncertain_pending_review`。

## 8. “新瓶装旧酒”的判定

不能按标题判断。

一个新命名模型如果满足：

- 核心命题已有；
- 机制已有；
- 条件没有新增；
- 范围没有新增；
- 方法步骤没有实质新增；
- 证据没有新增；

那么更可能是：

> alias / paraphrase / repackaging

而不是新 Canonical Knowledge。

但如果同一机制在新场景中提供了**新的有效边界、条件、实施步骤或可验证证据**，则应保留对应增量，而不是把整段内容全部删除。

## 9. G6：知识增量账本

每次新资料处理后，不只输出“重复率”，还要输出：

```yaml
increment_decision:
  source_id: S-...
  canonical_targets: []
  new_canonical_nodes: []
  increments:
    new_concept: 0
    new_fact: 0
    new_claim: 0
    new_mechanism: 0
    new_method: 0
    new_condition: 0
    new_boundary: 0
    new_evidence: 0
    new_independent_evidence: 0
    new_case: 0
    new_counterexample: 0
    new_version: 0
    decision_changing_increment: 0
  unresolved_relations: []
```

## 10. 什么才算高价值知识增量

通常从弱到强：

1. 新措辞；
2. 新名称；
3. 新例子；
4. 新案例；
5. 新细化；
6. 新条件；
7. 新边界；
8. 新机制；
9. 新反例；
10. 新独立证据；
11. 更强方法学证据；
12. 改变决策的冲突或更新。

这不是固定全局排名；不同任务下权重不同。

---

## 11. 新案例什么时候算真正增量

Case 可能有四种状态：

### A. 纯教学例子

只帮助理解，不改变知识本体。

→ 教学价值增量，知识命题增量低。

### B. 新场景应用

证明方法可以迁移到新的有效场景。

→ 可能增加 `scope` 或 `transfer evidence`。

### C. 边界案例

显示原规则在某些条件下失效。

→ 高价值 `boundary/counterexample` 增量。

### D. 独立经验材料

只有在来源独立、记录充分、能支持目标主张时，才可能形成证据增量。

> 新故事 ≠ 新证据。

---

## 12. G7：新证据与“伪多源”

十个来源都写同一句话，可能只是复制同一个上游来源。

因此 Evidence 必须判断：

- 是否独立产生；
- 是否引用同一原始研究/案例；
- 是否只是二次转述；
- 方法是否不同；
- 数据是否独立；
- 样本是否重合；
- 是否存在利益关联；
- 是否能回到 primary source。

建议保留：

```yaml
evidence_lineage:
  evidence_id: E-...
  primary_source: S-...
  derived_sources: []
  independence_group: EG-...
  method_family: "..."
  data_overlap: unknown
```

统计“来源数”时，至少同时报告：

- raw source count；
- primary source count；
- independent evidence group count。

---

## 13. 冲突不能用平均值消失

发现冲突时需要保留：

- 冲突命题；
- 各自条件；
- 适用范围；
- 时间；
- 证据；
- 来源；
- 可能原因；
- 是否可通过分层解释消解。

常见冲突类型：

- 真正逻辑冲突；
- 条件不同造成的表面冲突；
- 人群/地域不同；
- 时间版本不同；
- 定义不同；
- 指标不同；
- 证据质量不同；
- 机制层与经验层混淆。

禁止：

> LLM 生成一段“综合起来双方都有道理”就算完成冲突处理。

---

## 14. G8：知识饱和不是“没有新文档”

知识处理的停止判断应看 **边际 Canonical Increment**，而不是资料数量。

建议按主题/任务窗口观察：

- 每百万 token 新 Canonical Node 数；
- 新 Mechanism 数；
- 新 Condition 数；
- 新 Boundary 数；
- 新 Counterexample 数；
- 新 Independent Evidence Group 数；
- 新 Conflict 数；
- Decision-changing Increment 数；
- 处理成本；
- 人工复核成本。

---

## 15. 饱和曲线与停止策略

不预设一个全球统一阈值。

更合理的是：

```text
按主题建立时间窗/批次
→ 观察边际增量趋势
→ 连续多个批次低于任务相关阈值
→ 检查来源多样性是否充分
→ 检查是否仍存在高风险未决冲突
→ 决定暂停、降频或继续主动研究
```

需要使用 hysteresis，避免一次低增量就停止、下一批又重新启动造成抖动。

停止也不是永久结束，可以进入：

- Monitor；
- 低频更新；
- 条件触发重启；
- 新证据出现时重启。

---

## 16. 20 万本级规模的计算原则

不应让所有知识两两比较。

推荐逻辑：

```text
文件/版本快速层
→ 结构/文本近似召回
→ 主题/实体/概念分区
→ 向量/Hybrid Top-K 候选召回
→ 只对候选做昂贵命题裁决
→ 高风险或不确定关系进入人工复核
```

核心是：

> **Cheap Recall → Expensive Adjudication**

而不是：

> 全库 LLM 两两比较。

---

## 17. 合并、删除与替代纪律

### 17.1 可以自动做的

在高置信、低风险情况下：

- 建候选重复 cluster；
- 建 alias；
- 建 exact-text duplicate；
- 标记 alternate representation；
- 建议 canonical merge。

### 17.2 需要谨慎或人工关口的

- 删除唯一来源；
- 合并条件不同的 Claim；
- 用新版本覆盖旧版本；
- 把冲突结论压成一个结论；
- 删除反例；
- 把 weak evidence 升级为 fact；
- 高风险知识的自动替代。

### 17.3 永远保留的

即使逻辑合并，也应保留：

- Source provenance；
- 原始片段；
- 版本链；
- Relation Assertion；
- merge decision；
- rollback 信息。

---

## 18. 真实资料验证的进入条件

本协议当前属于**通用框架与协议设计阶段**，不得为了完善协议而自动扫描、读取或处理现有书库。

真实资料只在后续验证阶段进入，并且必须先建立显式的 `Validation Sample Manifest`，至少记录：

- 为什么选择这些样本；
- 样本路径/来源；
- 只读取哪些范围；
- 要验证哪一条协议能力；
- 是否允许生成派生知识；
- 是否允许修改原始资料；
- 输出写入哪里；
- 验证结束后哪些结论可以进入正式框架。

在 Manifest 建立前：

> **禁止把 `temp/` 或其他现有知识资产作为默认研究数据源。**

真实资料只能用于验证已经形成的通用假设，不能反过来用少量资料塑造总体问题空间。

---

## 19. 最小验收问题

给任意一个新资料，系统必须能回答：

1. 文件是不是已有文件的字节/文本/近似版本？
2. 它召回了哪些可能相同的 Canonical Knowledge？
3. 相似是文字相似、概念同义、命题等价还是机制相同？
4. 条件、边界、范围是否发生变化？
5. 新增了什么？
6. 新证据是否独立？
7. 是否产生冲突或反例？
8. 是否改变已有决策？
9. 是否已经接近知识饱和？
10. 是否可以安全合并、替代或停止继续处理？

如果只能回答“相似度 0.93”，本协议视为未完成。
