# 时间、版本与知识生命周期

> 研究知识随时间如何变化、什么时候对现实有效、什么时候进入系统、何时需要重新验证，以及变化如何传播到下游知识和能力。

核心原则：

> **一个 `updated_at` 不足以表达知识生命周期。**

---

# 一、L2 二级维度

- **发布时间**：来源何时公开/发布。
- **观察时间**：事实或现象何时被观测。
- **有效时间（Valid Time）**：知识描述的结论在现实世界何时成立。
- **系统时间（Transaction/System Time）**：系统何时知道、记录或修改这条知识。
- **验证时间**：何时完成最近一次证据核查。
- **新鲜度**：刚产生、近期、稳定旧知、历史知识。
- **变化速度**：稳定、慢变、中速、快变、实时。
- **有效期**：长期、阶段、短期、事件窗口。
- **版本状态**：当前版、旧版、新版并存、分支版本、历史版本。
- **过时程度**：当前有效、可能过时、部分过时、已过时。
- **替代状态**：未替代、部分替代、完全替代、场景替代。
- **重新验证需求**：无需、低频、定期、事件触发、每次使用前验证。
- **维护成本**：低、中、高、持续高维护。
- **重新激活条件**：项目阶段、目标、外部事件、需求出现、旧知识失效。
- **退出方式**：降级、归档、冻结、淘汰、保留历史版本。
- **影响传播**：知识变化会影响哪些 Claim、方法、Skill、Workflow、路由和学习内容。

---

# 二、至少区分六类时间

```yaml
temporal:
  source_published_at: null
  observed_at: null
  valid_from: null
  valid_until: null
  ingested_at: null
  verified_at: null
```

此外 Relation Assertion、Routing Decision、Implementation 也需要自己的 `created_at / reviewed_at / superseded_at`。

---

# 三、Valid Time 与 System Time 分离

例：

- 某政策 2026-01-01 起生效；
- 系统 2026-01-10 才采集到；
- 2026-01-12 才完成验证。

如果只保存 `updated_at=2026-01-12`，就无法正确回答：

> “2026-01-05 当时什么规则有效？”

因此需要区分：

- **Valid Time**：现实世界什么时候成立；
- **System Time**：系统什么时候知道/保存。

---

# 四、版本关系不是文件名关系

版本判定需要 provenance 和内容关系支持。

可能关系：

- revision_of；
- supersedes；
- partial_update；
- parallel_branch；
- alternate_representation；
- historical_version。

文件名、版本号和时间戳只能作为候选信号。

---

# 五、知识变化速度应影响消费方式

## 稳定知识

例如基础数学/长期稳定原理：

- 重验证频率低；
- 人工内化价值可能更高；
- 长期缓存和 Wiki 更合理。

## 快变知识

例如价格、API、产品能力、政策细节：

- 需要更频繁验证；
- 人类记忆投入下降；
- Search/RAG/Monitor 权重上升；
- 使用前时间过滤更重要。

因此变化速度影响路由，但不改变知识本体类型。

---

# 六、L3：过时风险

优先展开：

- source age；
- domain change rate；
- known successor exists；
- last verified age；
- dependency sensitivity；
- cost of stale use；
- usage frequency；
- external trigger presence。

不能仅用“发布日期距今多少天”判断是否过时。

---

# 七、L3：重新验证触发器

触发器可能包括：

- 新版本发布；
- 新证据；
- 新反例；
- 法规变化；
- 工具/模型变化；
- 失败反馈；
- 项目阶段变化；
- 高风险使用前；
- 超过最大验证间隔。

---

# 八、Impact Propagation

当基础知识变化时，不应全库重跑，而应沿依赖关系寻找受影响对象。

```text
Changed Knowledge
→ dependent Claims / Models / Methods
→ Wiki / Search metadata / RAG contexts
→ Skill / Workflow / Agent policy
→ Routing Decisions
→ Human Learning Material
→ Benchmark / Regression Cases
```

需要分别记录：

- direct impact；
- transitive impact；
- uncertain impact；
- review required。

---

# 九、局部更新原则

新资料进入后：

```text
找到对应 Canonical / Relation
→ 更新受影响字段或新增版本
→ 重新计算相关 Evidence State
→ 找到依赖对象
→ 只重算受影响 Routing / Capability
→ 触发必要 Benchmark
```

而不是：

> 每加入一篇新资料就重新处理整个知识库。

---

# 十、历史知识不等于无价值

旧知识可能有：

- 历史解释价值；
- 旧项目复盘价值；
- 版本迁移价值；
- 风险/错误案例价值；
- 研究思想演进价值。

因此 superseded 通常意味着：

> 当前默认消费降级

而不是：

> 物理删除。

---

# 十一、重新激活

Deferred/Dormant Knowledge 应允许记录：

```yaml
reactivation_triggers:
  - project_stage: "..."
  - topic_event: "..."
  - new_evidence: true
  - demand_pattern: RP-...
```

“暂时不需要”不等于永久无价值。

---

# 十二、L3 质量指标

- stale knowledge detection latency；
- valid-time query accuracy；
- version lineage completeness；
- impacted object recall；
- false impact propagation rate；
- revalidation backlog；
- local update correctness；
- rollback correctness；
- historical traceability。

---

# 十三、边界

- 版本/语义替代关系见 `04/17`；
- provenance 见 `03/16`；
- 系统状态与回滚见 `10`；
- 路由重算见 `18/19`；
- 时间变化相关 Benchmark 见 `22`。
