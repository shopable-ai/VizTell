# 知识原子、标准知识与关系模型

> 本文件回答：**知识的最小可管理单位是什么，以及不同来源中的表达如何归一成可追踪、可比较、可验证的 Canonical Knowledge。**

书籍、论文、网页、视频和课程只是 Source Container，不是最终知识单元。

---

## 1. 三层对象：Raw → Normalized → Canonical

### 1.1 Raw Knowledge Fragment

`Raw Knowledge Fragment` 是可回到来源定位的原始片段。

它必须保留：

- Source ID；
- 文件/页面/章节/时间戳/代码位置；
- 原始文本或媒体引用；
- 提取方法；
- 提取时间；
- 原始语言；
- 解析/OCR 状态；
- 来源版本。

Raw Fragment 的任务是保证：

> **任何归一化知识都可以回到原始证据位置。**

Raw Fragment 本身不代表“知识已经正确”。

---

### 1.2 Normalized Knowledge Atom

`Normalized Knowledge Atom` 是从 Raw Fragment 中提取出的最小可独立判断语义单元。

它至少应满足：

1. 能独立表达一个概念、主张、条件、机制、方法、证据或边界；
2. 能与其他 Atom 建立关系；
3. 可以单独判断来源、可信度、时间、适用范围；
4. 不因为来源文风不同而改变核心语义；
5. 仍保留对 Raw Fragment 的 provenance。

Normalized Atom 是**候选知识**，不是已经去重后的标准知识。

---

### 1.3 Canonical Knowledge

`Canonical Knowledge` 是经过身份归一、关系判定、证据绑定和版本治理后，知识库内部用于稳定引用的标准对象。

它不是：

> “把十本书的相似段落拼成一段摘要”。

而是：

> 一个稳定语义身份 + 多个来源表达 + 条件/边界/证据/反例 + 版本与关系。

Canonical Knowledge 的核心作用：

- 消除同义改写造成的伪知识数量；
- 保留真正新增的条件、边界、证据和反例；
- 允许一个知识有多个名称；
- 允许同一个名称对应多个不同知识；
- 支持局部更新而不是全库重建；
- 为 Wiki、Search、RAG、Skill、Workflow、Agent 提供共同知识身份。

## 2. Knowledge Atom 类型不是一个万能文本块

建议保留以下主要类型：

| 类型 | 主要回答 |
|---|---|
| Concept | 这是什么概念？ |
| Fact | 在指定范围/时间内发生或成立的可核事实是什么？ |
| Claim | 某来源提出了什么可真可假的陈述？ |
| Principle | 较稳定的一般原则是什么？ |
| Mechanism | 为什么/通过什么机制发生？ |
| Theory | 一组系统解释命题是什么？ |
| Model | 如何抽象表示对象或关系？ |
| Framework | 如何组织多个维度/组件？ |
| Method | 达成目标的一般方法是什么？ |
| Technique | 方法中的局部技巧是什么？ |
| Procedure | 按什么步骤执行？ |
| Decision Rule | 在什么条件下应做什么判断？ |
| Evidence | 什么观测/数据/研究支持或反驳某主张？ |
| Condition | 结论成立需要什么前提？ |
| Scope | 适用于哪些对象、场景、时间或地域？ |
| Boundary | 从哪里开始不应外推？ |
| Exception | 一般规则在哪些已知情况下不成立？ |
| Counterexample | 哪个实例直接挑战某个一般化主张？ |
| Case | 一个具体实例发生了什么？ |
| Skill | 人或 AI 能稳定完成的能力是什么？ |
| Tacit Knowledge | 难以完全语言化但影响判断/动作的经验结构是什么？ |

> `Fact` 与 `Claim` 必须严格区分。任何来源中的陈述默认先是 Claim；只有满足相应事实核验条件后，才能获得 Fact 状态。

## 3. 不同 Atom 类型需要不同最小槽位

### 3.1 Concept

最小字段：

- canonical label；
- aliases；
- definition；
- distinguishing features；
- broader/narrower/related；
- scope note；
- provenance。

### 3.2 Claim / Fact

最小字段：

- subject；
- predicate/relation；
- object/value；
- qualifiers；
- conditions；
- scope；
- time validity；
- evidence links；
- counterevidence；
- provenance；
- epistemic status。

### 3.3 Mechanism

最小字段：

- input/state；
- causal/process steps；
- mediators；
- outcome；
- required conditions；
- known boundaries；
- competing explanations；
- evidence。

### 3.4 Method / Technique / Procedure

最小字段：

- goal；
- prerequisites；
- inputs；
- steps or operating logic；
- outputs；
- success criteria；
- failure modes；
- boundary conditions；
- required tools/resources；
- evidence/validation state。

### 3.5 Decision Rule

最小字段：

- decision context；
- trigger；
- conditions；
- action/recommendation；
- exceptions；
- expected consequence；
- confidence/evidence；
- override/human gate。

### 3.6 Evidence

最小字段：

- evidence object；
- evidence type；
- target claim；
- direction：support / weaken / refute / neutral；
- method；
- sample/data；
- directness；
- independence；
- quality limitations；
- source/provenance。

### 3.7 Case

最小字段：

- entity/context；
- event/action；
- outcome；
- source；
- whether independently verified；
- linked principle/mechanism/method；
- what this case adds。

案例不能自动升级为一般规律。

## 4. Canonical Knowledge 的身份问题

### 4.1 一个知识多个名字

常见情况：

- 中英文名称；
- 缩写；
- 俗称；
- 行业术语；
- 不同作者重新命名；
- 错拼但高频搜索词。

应建立：

```yaml
canonical_label: "..."
aliases:
  - label: "..."
    type: synonym
    language: zh
  - label: "..."
    type: acronym
    language: en
```

字符串不同并不代表知识不同。

---

### 4.2 一个名字多个知识

例如同一个“杠杆”“模型”“第一性原理”在不同领域可能指向完全不同对象。

因此 canonical identity 不能只依赖名称，还必须结合：

- 类型；
- 定义；
-核心命题；
- 机制；
- 条件；
- 范围；
- 上下位语境。

字符串相同并不授权合并。

---

## 5. Concept 与 Claim 不应共用同一种“相同”关系

需要区分：

### 概念身份关系

- `alias_of`：不同标签指向同一概念；
- `broader_than`；
- `narrower_than`；
- `related_to`；
- `overlaps_with`。

### 命题语义关系

- `equivalent_to`；
- `paraphrase_of`；
- `contains`；
- `refines`；
- `adds_condition`；
- `adds_boundary`；
- `supports`；
- `weakens`；
- `conflicts_with`；
- `counterexample_to`；
- `supersedes`。

### 来源/版本关系

- `derived_from`；
- `quoted_from`；
- `revision_of`；
- `alternate_representation_of`；
- `has_primary_source`。

### 能力依赖关系

- `prerequisite_of`；
- `depends_on`；
- `complements`；
- `substitutes_for`；
- `implemented_by`。

不同关系族不能混成一个 `similar_to`。

---

## 6. Relation Assertion 必须是独立对象

关系不是永久真值；它本身也需要证据与版本。

建议：

```yaml
relation_assertion:
  relation_id: R-...
  subject_id: K-...
  relation_type: adds_boundary
  object_id: K-...
  adjudication_status: confirmed
  confidence: high
  evidence_refs:
    - E-...
  rationale: "..."
  adjudicated_by:
    type: human_ai
  created_at: "..."
  valid_from: "..."
  supersedes_relation: null
```

这样才能处理：

- AI 一开始判断为等价，后续发现条件不同；
- 新证据证明两个模型并非同一机制；
- 旧版本关系被新版本替换；
- 人工复核推翻自动合并。

---

## 7. Canonical Knowledge 不等于“唯一正确版本”

Canonical 的含义是：

> **知识库内部稳定身份。**

不是：

> **它已经被证明为真。**

同一个 Canonical Knowledge 可以处于：

- unsupported_claim；
- weak_evidence；
- contested；
- supported；
- strongly_supported；
- falsified；
- obsolete；
- superseded；
- unresolved。

这允许知识库保存：

- 重要但尚未证实的假说；
- 市场上流行但证据薄弱的观点；
- 已被反驳但具有历史或风险价值的旧知识。

## 8. 标准知识的建议结构

```yaml
canonical_knowledge:
  knowledge_id: K-...
  knowledge_type: mechanism
  canonical_label: "..."
  aliases: []

  canonical_statement: "..."
  mechanism: "..."
  conditions: []
  scope: []
  boundaries: []
  exceptions: []

  evidence_refs: []
  counterevidence_refs: []
  source_refs: []
  raw_fragment_refs: []

  relation_refs: []
  provenance:
    derived_from_atoms: []
    created_by_activity: A-...

  epistemic_status: unresolved
  temporal_state: current
  version: 1

  quality_state: {}
  subject_value_state: {}
  learning_fit_state: {}
  routing_state: null
```

评分与路由不应直接覆盖 canonical content，而应作为可更新状态或独立 decision object。

## 9. Raw → Normalized → Canonical 处理协议

```text
Source Container
→ 解析并建立定位
→ Raw Fragment
→ 提取候选 Atom
→ 类型识别
→ 术语/单位/时间/实体归一
→ 候选 canonical 召回
→ 概念身份或命题关系判定
→ 证据与来源独立性判断
→ 合并到已有 Canonical / 建立新 Canonical / 保留待判定
→ 生成 Relation Assertion
→ 生成 Increment Decision
→ 后续价值与消费路由
```

### 关键禁止项

- 不能因为 embedding 很近就自动合并；
- 不能因为标题相同就认为版本替代；
- 不能因为十个来源重复同一句话就当成十份独立证据；
- 不能把 Case 自动提升为 Principle；
- 不能把作者的强语气当作 Evidence；
- 不能删除被替代知识的 provenance。

## 10. 与主流知识组织标准的兼容方向

不要求现阶段把系统强制转换为 RDF/OWL，但字段语义应尽量兼容成熟模型：

- 概念首选名、别名、上下位与相关关系可映射 SKOS；
- Entity / Activity / Agent、派生、修订、原始来源等 provenance 可映射 W3C PROV；
- 机器校验优先采用 JSON Schema；
- 未来若进入知识图谱，可从 Canonical ID 和 Relation Assertion 平滑映射，而不需要重做知识身份。

具体主流框架校准记录见 `research-notes/2026-08-25_主流框架校准.md`。
