## 一、本轮先给结论

本轮最重要的结论不是“再增加问题”，而是：

1. **17 个 P-L1 当前可以保留，不新增、不合并。**
2. **现有 P-L2 的最大风险已经从“漏很多”转成“类型不纯、边界重叠、状态/类型被写成问题”。**
3. **本轮不恢复旧 P-L1-18。** 问题去重、问题状态、Problem Graph、问题生命周期属于治理与能力候选，不应该因为需要管理问题就创造一个新的用户问题一级空间。
4. **旧候选池里的 AI 上下文多少、模型处理成本、批处理放大错误等内容，不直接晋升 P-L2。** 用户可感知后果留在 Problem Space；上下文组织进入 Capability；错误率和成本进入 Benchmark / Error Taxonomy。
5. **P-L2 正式增加“准入 Gate”。** 以后类型、状态、属性、关系、实现载体、系统错误不能仅凭一个名词占用 P-L2 编号。
6. **覆盖验证从 Coverage Test 升级为 Coverage + Classification Boundary Test。** 以后不仅问“有没有位置”，还要问“为什么必须在这里，而不是相邻分类”。
7. **能力层不按 P-L2 一对一增长。** 17 类问题被压缩成少量可复用能力族，再进入验证和实现。

## 二、为什么当前不应该继续增加 P-L1

当前 17 类已经形成一条相对完整的专业问题链：

```text
真实问题
→ 知识需求
→ 来源发现
→ 资料筛选
→ 重复判断
→ 增量识别
→ 关系与结构
→ 冲突与边界
→ 来源与证据
→ 时间与版本
→ 整理与压缩
→ 主体价值
→ 理解与掌握
→ 判断与行动
→ 本人/AI/工具分工
→ 规模与停止
→ 反馈与再判断
```

这 17 类并不是为了“流程完整”而机械凑齐，而是分别回答不同问题。

### 2.1 不能合并 01 / 02 / 03

- 01：真正要解决什么；
- 02：为解决它需要知道什么；
- 03：这些知识应该去哪里找。

真实信息需求会在搜索过程中变化，但“需求变化”不意味着问题、知识缺口、来源发现应该成为同一类。

### 2.2 不能合并 05 / 06

这是整个海量知识系统里非常关键的边界：

```text
05：是不是同一个？
06：不是完全同一个时，真正多了什么？
```

“相同原理换案例”通常首先属于 05；但如果新案例增加新适用边界、新反例或独立证据，则相应部分又会进入 06 / 08 / 09。

### 2.3 不能合并 07 / 11 / 13

三个空间都可能出现“没有整体结构”，但机制不同：

- 07：知识本身的关系是否清楚；
- 11：外部整理产物是否形成可理解结构；
- 13：用户自己脑中是否真正形成结构模型。

一个系统可以在 07 上完全正确，但仍在 11 和 13 上失败。

### 2.4 不能合并 09 / 10 / 17

- 09：证据本身支持什么；
- 10：哪个版本/时间状态有效；
- 17：这些变化是否要求过去的判断、优先级和行动重新检查。

### 2.5 不能合并 13 / 14

- 13 主要看人的能力形成：理解、主动提取、判断、迁移；
- 14 主要看现实任务：识别何时调用、选择方法、形成方案、执行与调整。

“换场景就想不到用哪个原则”主要是 13；“已经知道该用哪个原则，但仍无法形成现实方案”主要是 14。

### 2.6 不能合并 04 / 16

- 04：局部资料值不值得读、读多深；
- 16：资料规模扩大后，整体注意力预算、边际收益、停止和重启。

一本书不知道精读还是浏览，不需要创造规模问题；两万份资料即使每份只看五分钟也不可持续，才真正进入 16。

## 三、本轮发现的 P-L2 类型污染

### 3.1 原 P-L1-06 大量是“增量类型”，不是问题

原表达类似：

- 增加新概念；
- 增加新机制；
- 增加新步骤；
- 增加新案例或证据。

这些都是 Knowledge Increment Type。

正式问题应该写成：

> **出现这种差异时，为什么难以判断它是否构成真实、有价值、值得保留的知识增量？**

因此 `01` 已把 06-01 ～ 06-10 统一改成判断困难/失败形式，同时保留原编号以减少不必要的映射震荡。

### 3.2 原 P-L1-13-01 ～ 13-06 大量是“掌握深度状态”

原表达类似：

- 只需要知道其存在；
- 需要理解；
- 需要主动记忆；
- 需要判断；
- 需要应用；
- 需要形成技能。

这些更接近 `mastery_depth` 枚举。

当前正式处理方式是：

> 不把状态本身当问题，而把“**不知道某项知识究竟应该达到哪个掌握深度**”作为问题。

这也与 `14_术语、编号与Schema.md` 中 Requirement Instance 的 `mastery_depth` 属性保持一致。

### 3.3 原 P-L1-12 部分表达只是价值状态

例如：

> “有价值但当前无需使用。”

这本身可能只是合理状态，而不是问题。

正式 P-L2 应描述：

> “无法判断应该现在投入还是延后。”

因此 12 已统一改成主体价值判断困难、错误排序和机会成本问题。

### 3.4 09 / 10 / 17 存在时间与变化传播重叠

本轮通过重新写法收敛：

```text
09-10：新证据本身是否足以改变主张？
10-08：版本具体改了什么、什么仍有效？
17-03 / 17-06：哪些既有判断需要因为变化而重新检查？
```

### 3.5 11 / 16 原来共享“什么时候研究充分”

本轮把责任分开：

- 11：综合产物能否说明覆盖范围、剩余不确定性与未解决问题；
- 16：用户什么时候真正应该停止继续搜索/阅读/分析。

## 四、旧 P-L2 候选池的正式处置

旧 Research Note 的六个 P0 问题群仍然有研究价值，但不应按旧编号原样晋升。

### 4.1 “知识原子化以后人工看不懂”

不新增 P-L1。

用户后果已可由：

- `11-08` 外部整理没有形成可理解模型；
- `11-11` 粒度过细/过粗；
- `13-11` 用户没有形成内部结构模型；
- `13-12` 认知负荷过高；

共同解释。

后台知识原子的表示方式进入 `16_知识原子、标准知识与关系模型.md`；人工消费能力进入 `18 / 20`。

### 4.2 “知识拆多细、组合多粗”

“粒度”是跨层属性，不应该天然成为一级问题。

需要分别判断：

- 后台语义单元粒度；
- 外部整理与阅读粒度；
- 当前任务调用粒度；
- 人的学习与认知粒度。

因此优先作为多个问题/能力的属性，而不是创造 `P-L1 知识粒度`。

### 4.3 “人和 AI 应该以不同方式使用同一知识”

这是重要设计原则，但它不是新的用户问题一级空间。

正确分层：

```text
用户可感知后果
→ 11 / 13 / 15

人工学习消费能力
→ H

AI 知识消费能力
→ I

实现与界面
→ 19 / 产品层
```

### 4.4 “AI 每次到底拿哪些、拿多少知识”

这组旧候选最容易重新污染 Problem Space。

本轮正式判断：

- 用户看到错误、遗漏、无法核验等结果 → 仍可以进入 P；
- “如何构造最小充分上下文” → `CAP-I02 Minimal Sufficient Context Pack Builder`；
- 漏取率、噪声率、成本、延迟 → `13 / 22`；
- 是否使用 RAG / Hybrid Retrieval → `19`。

### 4.5 “20 万本书应不应该全部深加工”

拆开以后分别属于：

- 04：单份资料处理深度；
- 12：当前主体价值；
- 16：规模与停止；
- 20：注意力预算和饱和能力；
- 13 / 22 / 19：模型、存储、调用和工程成本。

因此不创建“处理成本 P-L1”。

### 4.6 “问题本身怎样保存、去重和演化”

这是重要系统治理问题，但不能因为“需要 Problem Registry”就恢复 P-L1-18。

用户侧已有：

- 16-04 重复研究浪费；
- 17-05 历史判断依据无法恢复；
- 17-07 已解决问题条件变化后重新出现。

问题 ID、状态、依赖、Problem Graph、State Machine 是否必要，应该在 Capability / Implementation 层继续验证。

## 五、当前覆盖审计

`01B` 当前正式列出 94 个 SUP。

本轮重新阅读后的状态是：

- `COVERED`：90；
- `PARTIAL`：2；
- `MISPLACED`：2；
- 正式 SUP 行中没有 `MISSING`。

其中两个 `MISPLACED` 本身就是刻意的负例：

- AI 大规模处理错误/成本；
- RAG / Skill / Workflow / Agent 实现选择。

它们不应该因为“没有 P-L2”被视为缺口。

两个 `PARTIAL`：

1. 学习动机、焦虑囤积、自我控制；
2. 长期行为改变维持。

另外 `01B` 还保留两类尚未正式形成完整 SUP 集合的 `MISSING Candidate`：

1. 团队 / 组织共同学习与知识协作；
2. 无障碍与特殊认知需求。

### 5.1 覆盖率为什么不能作为唯一质量分

即使一个 SUP 能同时挂到三四个 P-L2，也可能存在：

- 分类边界错误；
- P-L2 是状态而非问题；
- 同一机制重复命名；
- 为了覆盖而强行映射。

所以当前体系应该从：

> **Coverage-first**

进入：

> **Coverage + Boundary Correctness + Type Purity + Traceability**

## 七、能力推导后的结构收敛

当前不建议为 183 个 P-L2 建 183 个功能。

`20` 已将用户问题能力收敛为 14 个前台通用能力：

```text
P01 用户需求澄清
P02 问题框定与范围控制
P03 问题分解与任务结构化
P04 知识需求推导
P05 已知/未知/误解诊断
P06 研究问题与搜索策略生成
P07 资料选择与阅读优先级
P08 多来源综合与知识压缩
P09 方案形成与比较
P10 决策支持
P11 知识到行动转化
P12 结果验证、反馈与新缺口发现
P13 注意力预算、研究停止与重启
P14 委托、人工验收与责任边界支持
```

再由 A-M 后台能力共同支撑。

### 7.1 为什么新增 P13

旧 CAP-P06/P12 虽然分别涉及搜索和反馈，但 `P-L1-16` 的核心需求比“搜索策略”更大：

- 注意力预算；
- 边际增量；
- 研究饱和；
- 停止；
- 重新启动。

因此需要一个实现无关的通用能力承接。

### 7.2 为什么新增 P14

原 G02 `Learning vs Delegation Router` 是后台路由能力，但 P-L1-15 还有明显的人工前台需求：

- 本人至少理解什么；
- 如何验收 AI；
- 什么必须人工复核；
- 谁承担责任；
- 隐私/版权/权限是否允许委托。

所以增加一个直接面向用户任务的 P14，比把这一整类问题隐藏在后台 Router 更合理。

## 八、外部专业框架校准

外部资料只用于校准，不取代仓库当前正式事实源。

### 8.1 信息行为与搜索：需求会演化

Marcia Bates 的 Berrypicking 模型强调：真实搜索并不是一次静态 Query → 一次结果集，而是用户每看到新的信息以后都会改变对问题和查询的理解。

这支持：

- P-L1-01 需求会变化；
- P-L1-02 知识需求会变化；
- P-L1-03 搜索需要迭代；
- P-L1-17 变化后要重新判断。

参考：

- Bates, *The Design of Browsing and Berrypicking Techniques for the Online Search Interface* (1989): https://pages.gseis.ucla.edu/faculty/bates/berrypicking.html
- Wilson, *Models in information behaviour research* (1999), DOI: 10.1108/EUM0000000007145

### 8.2 学习科学：理解、提取、迁移、元认知不是同一个状态

National Academies 的 *How People Learn II* 强调：

- retrieval practice；
- spaced / varied practice；
- self-explanation；
- metacognition；
- self-regulation；
- transfer。

这支持 P-L1-13 不应被压缩成“记住知识”，也支持把掌握深度状态与具体学习问题分开。

参考：

- https://www.nationalacademies.org/read/24783/chapter/6
- https://www.nationalacademies.org/read/24783/chapter/7

### 8.3 人机系统：角色、监督与责任需要区分

NIST AI RMF / Playbook 明确要求区分 AI 使用者、监督者、责任角色和不同 Human-AI Configuration，并根据上下文定义人工监督。

这支持 P-L1-15 继续独立保留，而不是被“AI 能力足够”简单替代。

参考：

- https://www.nist.gov/itl/ai-risk-management-framework
- https://airc.nist.gov/airmf-resources/playbook/govern/
- https://airc.nist.gov/airmf-resources/playbook/map/

### 8.4 人本设计：先理解使用情境和用户需要

ISO 9241-210:2019 把 human-centred design 放在系统生命周期中，并强调围绕使用情境与人的需要进行设计。

这与当前正式链：

```text
01A 用户世界
→ 01B SUP
→ 01 Problem
→ Capability
→ Implementation
```

方向一致。

参考：

- https://www.iso.org/standard/77520.html

## 九、本轮架构成熟度判断

如果只从“专业问题宇宙本身是否已经可以作为下一阶段事实源”进行内部工程审计，而不是声称获得外部行业认证：

| 维度 | 当前判断 |
| --- | --- |
| 用户世界与专业问题分层 | 强 |
| Problem / Solution 分离 | 强 |
| 17 个 P-L1 上位覆盖 | 强 |
| P-L2 类型纯度 | 本轮显著改善，仍需继续回归 |
| 相邻分类边界 | 本轮首次正式建立对抗测试 |
| SUP → P 可追踪 | 强 |
| P → Capability 可追踪 | 本轮显著改善 |
| 真实用户数据验证 | 仍不足 |
| 团队/组织知识协作 | 尚未正式覆盖 |
| 无障碍/特殊认知需求 | 尚未正式覆盖 |

因此当前体系已经从“不断补概念”进入：

> **Taxonomy Stabilization + Boundary Validation + Capability Compression**

阶段。

不应再以“还有没有更多 P-L1”作为主推进指标。

## 十一、本轮最终人工可读结论

1. **17 类专业问题目前已经够用，当前不要继续加一级分类。**
2. **真正需要治理的是 P-L2 的质量，而不是 P-L2 的数量。**
3. **“新概念、新机制、需要记忆、海量、因果关系”都不天然是问题，它们很多只是类型、状态或属性。**
4. **同一个现象可以跨多个 P-L1，但必须知道每个 P-L1 分别解释哪个失效机制。**
5. **AI 一次应该读多少知识、用什么 RAG、成本多少，不要重新混进用户问题宇宙。**
6. **问题层可以细，能力层必须压缩复用，产品功能更不能和 P-L2 一对一。**
7. **今后判断 Taxonomy 好不好，不能只看“覆盖率”，还要看边界正确性、类型纯度和可追踪验证。**
