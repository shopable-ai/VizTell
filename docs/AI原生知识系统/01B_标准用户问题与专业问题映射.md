# 标准用户问题与专业问题映射

> 状态：正式上游标准化桥梁
>
> 本文件连接 `01A_用户旅程、需求与高频问题现象宇宙.md` 与 `01_需求宇宙.md`。
>
> 核心链路：**用户原话 → 标准用户问题（Standard User Problem, SUP）→ P-L1 / P-L2。**
>
> 本文件只做问题标准化、语义去重、覆盖审计和轻量优先级，不设计产品功能或工程实现。

---

## 一、三层表达正式定义

```text
A. 用户原话
↓
B. 标准用户问题 SUP
↓
C. 专业问题 P-L1 / P-L2
```

- **用户原话**负责保留真实情境和普通用户语言。
- **SUP**负责把大量近似说法归一成稳定问题。
- **P-L1 / P-L2**负责专业归类，不负责表达所有用户说法。

三层不能互相替代。

---

## 二、去重与拆分规则

1. 核心困难相同，只是措辞不同 → 合并成一个 SUP。
2. 同一问题出现在单书、多书、海量等不同规模 → SUP 可共享，但阶段/规模信息不能丢。
3. “想不起来”“想起来但不会用”“用了却失败”根因不同 → 必须拆分。
4. 一句话同时包含压缩遗漏、AI 偏离、熟悉感错觉、主动提取失败 → 拆成多个 SUP。
5. “需要 RAG / Skill / Agent / 软件”不是 SUP，而是实现选择。
6. “系统 false merge / 路由错误 / 模型成本过高”属于 Benchmark / System Error，不是标准用户问题；若用户能感知其后果，则只保存用户后果。

## 三、覆盖状态

| 状态 | 含义 |
| --- | --- |
| `COVERED` | 当前 `01` 已有 P-L2 可以解释 |
| `PARTIAL` | 只能解释一部分，仍需研究边界 |
| `MISSING` | 当前专业问题宇宙没有合适位置 |
| `MISPLACED` | 表达实际属于解决方案、实现或系统错误，不属于用户问题层 |

## 五、本轮覆盖审计结论

### 5.1 正式 P-L1 已收敛为 17 类

本轮不再保留原 `P-L1-16 实现载体选择`。原因很简单：它回答的是“怎么实现”，而不是“用户遇到什么问题”。

正式边界现在是：

```text
01A 用户世界
→ 01B SUP
→ 01 P-L1 / P-L2
→ 后续 Capability
→ 19 Implementation
```

不再经过“P-L1 里的实现桥”。

### 5.2 原系统错误项已移出问题宇宙

原来类似以下表达：

- 系统去重判断错误；
- 增量判断错误；
- 路由判断错误；
- AI 大规模处理把错误放大；
- 高成本模型使用过度；

现在进入 `13 / 22` 的 Error Taxonomy 与 Benchmark。

这不代表用户后果消失。用户可感知的“AI 偏离原意、漏掉边界、给错引用、找不到知识”等仍保留为 SUP 和 P-L2。

### 5.3 仍保留的 PARTIAL / MISSING

- 学习动机、焦虑囤积、自我控制：`PARTIAL`；
- 长期行为改变维持：`PARTIAL`；
- 团队 / 组织共同学习与知识协作：`MISSING Candidate`；
- 无障碍与特殊认知需求：`MISSING Candidate`。

这些候选不因为“目前没有 P-L1”就被强行塞入现有分类。

## 六、轻量优先级原则

只使用人工容易判断的标签：

- 频率：高 / 中 / 低；
- 痛感：强 / 中 / 弱；
- 时间浪费：高 / 中 / 低；
- 错误风险：高 / 中 / 低；
- 规模：单书 / 多书 / 领域 / 百本 / 海量 / 长期。

当前优先关注：真正知识缺口、资料筛选、整体结构、重点提取、可信度、条件边界、多书重复与真增量、主动提取、迁移与行动、失败诊断、长期失效与再判断。

## 七、正式边界

任何后续能力或功能都应该能向上追踪：

```text
用户原话
→ SUP
→ P-L1 / P-L2
→ 后续才进入 Capability / Validation / Implementation
```

如果一个候选条目只能写成“应该用 Agent”“需要向量库”“模型成本太高”“false merge 率高”，它就不属于本文件。
