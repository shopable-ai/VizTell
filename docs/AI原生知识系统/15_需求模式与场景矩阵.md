# 需求模式与场景矩阵

> 本文件把大量自然语言需求压缩成稳定的 Requirement Pattern（需求模式），并映射到 `01_需求宇宙.md` 的 17 个 P-L1 专业问题空间。
>
> Requirement Pattern 是**现实任务入口**，不是产品功能，也不是实现方式。

---

## 一、为什么需要需求模式

现实需求表达方式近乎无限，但真正改变知识处理策略的任务模式有限。

```text
用户原始表达
→ 需求归一化
→ Requirement Pattern
→ 命中的 P-L1 / P-L2
→ 必须完成的判断
→ 后续 Capability
→ Validation
→ Implementation
```

需求模式用于：

1. 消除措辞差异造成的伪需求；
2. 保留真正改变判断的差异；
3. 用有限模式覆盖大量现实任务；
4. 压力测试 P-L1 / P-L2 是否完整；
5. 为后续能力与 Benchmark 提供可追踪入口。

---

## 二、需求输入、问题与派生决策必须分开

### 2.1 原始输入事实

一条需求可以描述：

- 主体：个人、人机协作、团队、组织；
- 意图：解决问题、学习、研究、判断、执行、监测、探索；
- 目标对象；
- 当前项目阶段；
- 时间范围；
- 范围大小；
- 期望掌握深度；
- 查询延迟容忍；
- 错误后果；
- 证据要求；
- 发生频率；
- 不确定程度；
- 法律、隐私、安全、权限、预算和时间约束；
- 用户先验优先级。

### 2.2 问题现象

系统再判断：

> 为了完成这个任务，会遇到哪些 P-L1 / P-L2？

### 2.3 派生决策

以下不是 Requirement Pattern 本身：

- 最终系统处理优先级；
- 人是否必须深学；
- 是否继续研究；
- 使用 Search / RAG / Skill / Workflow / Agent / Software；
- 是否自动化；
- 是否软件化；
- 模型、数据库或 UI 选型。

这些必须后置推导。

## 四、需求模式不是互斥标签

一个现实任务可以同时命中多个 Requirement Pattern，也可以触发多个 P-L1 / P-L2。

例如：

```text
“我下周要做一次高风险方案决策，
需要快速进入一个陌生领域，
但大量事实不值得长期记忆。”
```

可能同时命中：

- RP-04 高风险决策前检查；
- RP-09 陌生领域进入；
- RP-17 随用随查；
- RP-20 人工判断与验收保留。

---

## 五、Requirement Pattern 不能直接跳到功能

正确顺序：

```text
RP
→ P-L1 / P-L2
→ 必须判断什么
→ Capability
→ Validation
→ Implementation
```

例如 RP-06“方案比较与选择”先要求判断：

- 候选方案是否完整；
- 各方案适用条件；
- 证据强弱；
- 成本与风险；
- 对当前主体的价值；
- 哪些未知可能翻转选择。

至于最终是否使用 RAG、Workflow 或软件，在这一层没有答案。

## 六、P-L1 覆盖视角

### 6.1 用户任务前端

- P-L1-01 用户需求与真实问题；
- P-L1-02 知识需求识别；
- P-L1-14 知识到判断、决策与行动。

### 6.2 知识获取、判断与综合

- P-L1-03 ～ P-L1-11。

### 6.3 主体价值、学习与委托

- P-L1-12 ～ P-L1-15。

### 6.4 规模与长期变化

- P-L1-16 规模、注意力与研究停止；
- P-L1-17 反馈、修正与长期再判断。

如果某个 P-L1 长期没有任何真实任务模式能够触发，应重新检查它是否应该存在。

## 七、压力测试用极端需求

1. 知识质量极高但当前完全无关；
2. 知识证据很弱但错误后果极大；
3. 内容简单但高频高损失；
4. 一次性低频但必须立即行动；
5. 已有成熟工具可以可靠替代；
6. 当前低价值但触发条件明确；
7. 高度新颖但没有独立证据；
8. 十本资料重复描述同一知识；
9. 同名概念指向不同机制；
10. 异名概念其实同一机制；
11. 知识稳定但实现工具快速变化；
12. AI 能给答案但用户无法可靠验收；
13. 系统内部处理准确，但最终没有解决用户原始问题；
14. 用户原始问题定义错，系统却高质量回答了错误问题；
15. 继续搜索能找到更多资料，但已经不会改变决策；
16. 资料很多但真正需要的是实践反馈，而不是继续阅读。

## 八、完整性回归规则

```text
先判断是否只是新的用户措辞
→ 是否可映射已有 Requirement Pattern
→ 是否只是已有 P-L2 的新实例
→ 是否是多个已有问题的组合
→ 是否其实属于 Capability / Implementation / Benchmark Error
→ 最后才考虑新增 P-L2
→ 只有真正新的独立问题空间才新增 P-L1
```

## 九、当前验收

任意现实需求都应该能够回答：

1. 属于哪些稳定需求模式？
2. 会触发哪些 P-L1 / P-L2？
3. 哪些问题必须解决，哪些可以跳过？
4. 本人需要学到什么深度，哪些可查询或委托？
5. 什么时候应该停止继续研究？
6. 什么变化会触发重新判断？
7. 是否仍然在用户/任务层，而没有提前跳到技术方案？

> **需求模式描述用户任务；P-L1/P-L2 描述问题；实现方式留到后面。**
