# 需求模式与场景矩阵

> 本文件把大量自然语言需求压缩成稳定的 Requirement Pattern（需求模式），并把需求模式继续映射到 `01_需求宇宙.md` 的 `P-L1 / P-L2` 问题现象宇宙。
>
> 核心目的不是建立“用户原话大全”，也不是直接生成产品功能，而是形成：
>
> **真实需求 → 需求模式 → 问题空间 → 必须判断什么 → 系统能力 → 路由 / Benchmark**。

---

# 一、为什么需要需求模式

现实需求表达方式近乎无限，但真正改变系统处理策略的变量有限。

因此采用：

```text
用户原始表达
→ 需求归一化
→ Requirement Pattern
→ 命中的 P-L1 / P-L2
→ 必须完成的判断
→ 系统能力
→ 后续路由
```

而不是：

> 一条用户原话 → 一个新分类 → 一个新功能。

需求模式的作用：

1. 消除措辞差异造成的伪需求；
2. 保留真正改变判断的差异；
3. 用有限模式覆盖大量现实任务；
4. 压力测试 `P-L1 / P-L2` 是否完整；
5. 为能力地图、Benchmark 和未来产品提供上游追踪入口。

---

# 二、需求输入、问题现象与派生决策必须分开

## 2.1 原始输入事实

一个标准化需求至少可以包含：

- `actor`：个人、AI、人机协作、团队、组织；
- `intent`：解决问题、学习、研究、判断、执行、监测、探索等；
- `target`：目标、项目、能力或决策对象；
- `project_stage`：当前项目阶段；
- `time_horizon`：立即、近期、中期、长期、条件触发；
- `scope`：单点、主题、领域、项目、跨领域；
- `mastery_depth`：知道、理解、判断、执行、迁移、熟练；
- `latency_tolerance`：是否允许任务发生时再查；
- `failure_cost`：错误或延迟的后果；
- `evidence_need`：证据要求；
- `recurrence`：一次、偶发、高频、持续；
- `uncertainty`：问题和答案空间的不确定程度；
- `constraints`：法律、隐私、安全、权限、预算、时间等约束；
- `prior_priority`：需求侧先验优先级。

## 2.2 问题现象

系统根据需求需要识别：

> **为了完成这个需求，会遇到哪些 `P-L1 / P-L2` 问题？**

例如“快速进入陌生领域”不仅是一个需求标签，还会触发：

- `P-L1-01` 用户需求与真实问题；
- `P-L1-02` 知识需求识别；
- `P-L1-03` 来源发现；
- `P-L1-04` 资料筛选；
- `P-L1-11` 多来源综合；
- `P-L1-13` 学习与内化；
- `P-L1-17` 停止条件。

## 2.3 派生决策

以下不是纯输入属性：

- 系统最终处理优先级；
- 人是否必须学习；
- 是否继续研究；
- Search / RAG / Skill / Workflow / Agent / Software 路由；
- 是否自动化；
- 是否延期或忽略；
- 资源投入强度。

它们必须由问题、证据、价值、风险、成本和能力共同推导。

# 四、需求模式不是单一标签

一个现实需求可以同时命中多个 Pattern，然后再映射到多个 `P-L1 / P-L2`。

因此：

> **Requirement Pattern 是任务入口，P-L1/P-L2 是问题覆盖，不是二选一。**

---

# 五、从需求模式继续推导“必须判断什么”

Requirement Pattern 不能直接跳到功能。

正确链路：

```text
RP
→ P-L1 / P-L2
→ Decision Questions
→ Capability
→ Validation
→ Implementation
```

例如 RP-06 方案比较与选择，会命中知识需求、条件边界、证据质量、主体价值、知识到决策等问题。

必须判断：候选方案是否完整、各方案适用条件、证据支持、成本风险、关键差异、验证方法。

可能需要的能力：方案发现、条件比较、证据比较、主体适配判断、决策支持、结果验证。

这里仍没有要求一定使用 RAG、Agent 或软件。

# 六、P-L1 覆盖视角

## 6.1 用户任务前端
- P-L1-01 用户需求与真实问题；
- P-L1-02 知识需求识别；
- P-L1-14 知识到决策与行动。

## 6.2 知识获取与综合中段
- P-L1-03～11。

## 6.3 主体学习与分工后段
- P-L1-12～16。

## 6.4 规模与持续演化
- P-L1-17～18。

如果某个 P-L1 长期没有任何 Requirement Pattern 能触发，应检查它是否真的值得成为一级问题空间。

# 七、压力测试用极端需求

1. 知识质量极高但当前完全无关；
2. 知识证据很弱但错误后果极大；
3. 内容简单但高频高损失；
4. 一次性低频但必须立即行动；
5. 已有成熟工具可稳定替代；
6. 当前低价值但触发条件明确；
7. 高度新颖但没有独立证据；
8. 十本资料重复描述同一知识；
9. 同名概念指向不同机制；
10. 异名概念其实同一机制；
11. 知识稳定但实现工具快速变化；
12. 系统能自动执行但失败不可逆；
13. 系统内部处理准确，但最终没有解决用户原始问题；
14. 用户原始问题定义错，系统却高质量回答了错误问题；
15. 继续搜索能找到更多资料，但已经不会改变决策；
16. 资料很多但真正需要的是实践反馈，而不是继续阅读。

# 八、完整性回归规则

```text
先判断是否只是新的用户措辞
→ 是否可映射已有 Requirement Pattern
→ 是否只是已有 P-L2 的新实例
→ 是否是多个已有问题的组合
→ 是否其实属于能力或实现问题
→ 最后才考虑新增 P-L2
→ 只有真正新的独立问题空间才新增 P-L1
```

禁止每发现一个新场景就新增一级空间。

# 九、最小机器对象

```yaml
requirement_pattern_instance:
  requirement_id: D-...
  patterns:
    - RP-02
    - RP-04
  problem_refs:
    - P-L2-02-02
    - P-L2-09-08
  actor: human_ai
  intent: project_decision
  target: "..."
  project_stage: "..."
  time_horizon: near_term
  scope: project
  mastery_depth: judgment
  failure_cost: high
  evidence_need: strong
  constraints: []
  prior_priority: high
  derived_routing_decision: null
```

`problem_refs` 表示当前需求实际命中的问题现象；`derived_routing_decision` 在输入阶段必须为空。

# 十、当前验收

任意现实需求都应该能够回答：

1. 属于哪些稳定需求模式？
2. 会触发哪些 P-L1 / P-L2 问题？
3. 哪些问题必须解决，哪些可以跳过？
4. 每个问题需要做什么判断？
5. 哪些系统能力可以复用解决多个问题？
6. 哪些结果需要 Benchmark？
7. 为什么最终选择某种实现？

> **需求模式负责压缩无限用户表达；问题宇宙负责保证系统没有漏掉真正需要解决的问题。**
