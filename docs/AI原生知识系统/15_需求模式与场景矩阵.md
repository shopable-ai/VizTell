# 需求模式与场景矩阵

> 本文件把大量自然语言需求压缩成稳定的 Requirement Pattern，用于验证 L1/L2/L3 框架覆盖度、生成机器输入、驱动后续知识与能力路由。它不是“用户原话大全”，也不是产品功能清单。

---

## 1. 为什么需要 Requirement Pattern

现实需求具有极高表述多样性，但真正改变知识处理策略的变量有限。

因此不采用：

> 一条用户原话 → 一个新分类

而采用：

> 原始需求 → 需求归一化 → Requirement Pattern → L1/L2/L3 维度组合 → 路由约束

Requirement Pattern 的目标是：

1. 保留真正改变判断的差异；
2. 消除语言风格、场景措辞造成的伪差异；
3. 用有限模式覆盖大量现实需求；
4. 反向压力测试现有 L1/L2 是否完整；
5. 为后续 Schema、Benchmark 和软件能力提供稳定接口。

---

## 2. 需求输入与派生结果必须分开

### 2.1 输入事实

一个标准化需求至少应能表达：

- `actor`：个人、AI、人机协作、团队、组织；
- `intent`：解决问题、学习、研究、判断、执行、监测、探索等；
- `target`：目标、项目、能力或决策对象；
- `project_stage`：当前项目阶段；
- `time_horizon`：立即、近期、中期、长期、条件触发；
- `scope`：单点、主题、领域、项目、跨领域；
- `mastery_depth`：知道、理解、判断、执行、迁移、熟练；
- `latency_tolerance`：是否允许任务发生时再查；
- `failure_cost`：错误或延迟的后果；
- `evidence_need`：允许经验性信息还是需要强证据；
- `recurrence`：一次、偶发、高频、持续；
- `uncertainty`：问题和答案空间的不确定程度；
- `constraints`：法律、隐私、安全、权限、预算、时间等约束。

### 2.2 派生结果

以下内容不应被误当成纯输入维度：

- 计算后的处理优先级；
- 人是否必须学习；
- 应进入 Search / RAG / Skill / Workflow / Agent / Software 中哪一种；
- 是否值得自动化；
- 是否应该忽略或延期；
- 最终资源投入强度。

它们是由多个 L1/L2/L3 联合推导出的 **Routing Decision**。

> `01_需求宇宙.md` 中的“优先程度”继续保留，但应解释为“需求侧先验优先级”；系统计算出的处理优先级属于派生决策，不与其混为一谈。

# 3. 稳定 Requirement Pattern 宇宙

## A. 当前任务与项目推进

| ID | Requirement Pattern | 典型目标 | 主要改变的判断 |
|---|---|---|---|
| RP-01 | 当前问题知识调用 | 现在就要解决一个问题 | 低延迟、强相关、可直接调用优先 |
| RP-02 | 当前项目知识差额 | 找出项目继续推进还缺什么 | 目标/阶段相关性、知识缺口 |
| RP-03 | 下一项目阶段准备 | 为即将进入的阶段预学习/准备 | 时间窗口、前置知识、阶段门槛 |
| RP-04 | 高风险决策前检查 | 决策前降低重大错误概率 | 证据、可信度、风险、人工关口 |
| RP-05 | 故障/异常诊断 | 查明为什么失败 | 反例、冲突、条件、可验证性 |
| RP-06 | 方案比较与选择 | 多个方法中选一个 | 边界、条件、效果、成本、风险 |
| RP-07 | 合规/安全约束检查 | 判断是否允许执行 | 法律、安全、隐私、权限 |
| RP-08 | 事实与主张核验 | 判断一句话是否可靠 | 来源、独立证据、科学状态 |

## B. 陌生领域与人类学习

| ID | Requirement Pattern | 典型目标 | 主要改变的判断 |
|---|---|---|---|
| RP-09 | 系统进入陌生领域 | 快速建立领域可用结构 | 概念骨架、前置知识、证据基线 |
| RP-10 | 基础知识地图建立 | 建立长期导航结构 | 核心概念、依赖关系、稳定性 |
| RP-11 | 阶段性能力提升 | 补当前任务需要的能力 | 学习差额、练习、反馈 |
| RP-12 | 刻意练习与熟练化 | 从“懂”变成“会” | 程序性知识、练习成本、反馈速度 |
| RP-13 | 相邻技能迁移 | 用已有能力降低新技能成本 | 知识重合、迁移距离、负迁移 |
| RP-14 | 高复利基础能力发现 | 找值得长期投资的底层能力 | 复用范围、持续时间、放大效应 |
| RP-15 | 高市场价值技能发现 | 找具有需求和支付意愿的能力 | 稀缺性、市场需求、变现路径 |
| RP-16 | 人必须内化的知识 | 判断什么不能只靠随查 | 低延迟容忍、高后果、即时判断 |

## C. AI、工具与能力化

| ID | Requirement Pattern | 典型目标 | 主要改变的判断 |
|---|---|---|---|
| RP-17 | AI 检索优先 | 人无需先学习即可调用 | 可检索性、可验证性、上下文稳定性 |
| RP-18 | 成熟工具替代优先 | 避免重复学习/重复造轮子 | 工具成熟度、可靠性、集成成本 |

| RP-20 | Workflow 候选发现 | 把稳定多步骤过程固化 | 顺序、关口、状态、失败恢复 |
| RP-21 | Agent 候选发现 | 让系统动态观察和决策推进 | 环境变化、分支、不确定性、状态 |

## D. 时间、变化与知识发现

| ID | Requirement Pattern | 典型目标 | 主要改变的判断 |
|---|---|---|---|
| RP-25 | 未来可能需要 | 建未来知识池 | 使用概率、保存成本、过期风险 |
| RP-26 | 条件触发知识 | 条件出现时才激活 | trigger、有效期、重验证需求 |
| RP-27 | 新知识变化监测 | 持续发现变化 | 更新频率、影响传播、增量 |
| RP-28 | 旧知识失效检查 | 判断哪些旧结论需重验证 | 替代、冲突、版本、依赖影响 |
| RP-29 | 未知未知探索 | 主动发现遗漏的问题空间 | 覆盖盲点、异常、外部弱信号 |
| RP-30 | 前沿/弱信号研究 | 提前识别潜在高价值变化 | 不确定性、证据稀缺、期权价值 |
| RP-31 | 延迟处理 | 当前不值得投入但不能删除 | 触发条件、机会成本、未来价值 |
| RP-32 | 忽略/归档 | 当前与可预见目标均低价值 | 低相关、低增量、低未来价值 |

# 4. 需求模式不是单一标签

一个现实需求可以同时命中多个 Pattern。

例如：

> “我们两周后要发布医疗相关 AI 功能，需要确认最新证据、找出团队不知道的高风险知识，并把发布前检查固化。”

可能组合为：

- RP-03 下一阶段准备；
- RP-04 高风险决策前检查；
- RP-08 事实与主张核验；
- RP-20 Workflow 候选发现；
- RP-27 新知识变化监测。

因此 Requirement Pattern 是组合式入口，不是互斥目录。

# 5. Pattern → L1/L2 的覆盖矩阵

| Pattern 类群 | 必须覆盖的主要空间 |
|---|---|
| 当前任务/项目 | 需求、主体价值、时间、证据、风险、人机分工 |
| 人类学习 | 知识本体、学习适配、主体价值、复利价值、时间 |
| AI/工具能力化 | 人机分工、风险、治理、技术基础设施、生命周期 |
| 变化监测 | 来源证据、关系增量、时间生命周期、系统治理 |
| 未知未知 | 需求、来源、关系增量、价值、风险、主动研究 |

矩阵的用途不是证明“所有格子都要有值”，而是检查：

> 某种现实需求是否存在一个无法由现有维度组合表达的、真正独立的判断变量？

# 6. 压力测试用极端需求

以下案例应进入后续 Benchmark：

1. **知识质量极高但当前完全无关**：不能因为专业度高就进入高优先级学习。
2. **知识证据很弱但错误后果极大**：不能直接采用，应升级验证与人工关口。
3. **内容很简单但高频高损失**：可能比复杂理论更值得内化或软件化。
4. **一次性低频但必须立即行动**：可能适合 Reference/RAG，不值得长期学习。
5. **已有成熟工具可稳定替代**：即使知识重要，人类学习投入也应下降。
6. **当前低价值但触发条件明确**：应进入 Monitor/Deferred，而不是删除。
7. **高度新颖但没有独立证据**：可进入研究队列，不得升级为已验证知识。
8. **同一知识被十本书重复描述**：来源数量不等于证据数量。
9. **同名概念指向不同机制**：不得因为字符串相同而合并。
10. **异名概念其实同一机制**：应建立 alias/canonical 映射，而非保留伪增量。
11. **知识本身稳定，但实现工具快速变化**：知识生命周期与工具生命周期分离。
12. **系统能自动执行但失败不可逆**：自动化潜力高不代表允许无人监督。

# 7. L1/L2 完整性回归规则

每次出现一个“现有框架表达不了”的新需求时，按以下顺序处理：

```text
先检查是否只是新的用户措辞
→ 是否可映射到已有 Requirement Pattern
→ 是否只是已有 L2 的新 L3 状态/指标
→ 是否只是多个已有维度的组合
→ 是否属于控制平面或实现平面
→ 最后才考虑新增 L2
→ 只有真正无法被现有空间表达的独立问题，才考虑新增 L1
```

禁止：

> 每发现一个新场景就新增一个一级空间。

# 8. 最小机器对象

```yaml
requirement_pattern_instance:
  requirement_id: D-...
  patterns:
    - RP-02
    - RP-04
  actor: human_ai
  intent: project_decision
  target: "..."
  project_stage: "..."
  time_horizon: near_term
  scope: project
  mastery_depth: judgment
  latency_tolerance: low
  failure_cost: high
  evidence_need: strong
  recurrence: repeated
  uncertainty: medium
  constraints: []
  prior_priority: high
  derived_routing_decision: null
```

`derived_routing_decision` 在输入阶段必须为空或独立记录，避免把结论偷偷写回问题定义。

# 9. 本文件的边界

本文件负责：

- 需求模式；
- 场景组合；
- 框架覆盖压力测试；
- 需求输入与派生结果分离。

- 知识原子的定义，见 `16_知识原子、标准知识与关系模型.md`；
- 去重与知识增量判定，见 `17_海量知识去重、增量与饱和协议.md`；
- 人是否值得学习，见 `18_知识价值、学习投入与消费路由.md`；
- Search/RAG/Skill/Workflow/Agent/Software 的实现边界，见 `19_知识到Search-RAG-Skill-Workflow-Agent-软件的能力路由.md`。
