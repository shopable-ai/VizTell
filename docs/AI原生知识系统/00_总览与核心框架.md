# AI 原生知识系统：总览与核心框架

> 目标：面对海量书籍、论文、文章、视频、课程、网页、代码、数据与经验，不以“读完资料”为目标，而以**围绕真实问题发现高价值知识差额、形成真实能力、让 AI 可可靠调用、持续更新知识资产**为目标。

---

# 一、核心原则

1. **先真实问题，后知识处理，再技术实现**：系统不是为了管理知识而管理知识，而是为了帮助人理解、学习、判断、决策、解决问题和完成任务。
2. **先问题空间，后解决方案空间**：不因为已有 RAG、Skill、Wiki、Agent，就把问题强行解释成某种技术问题。
3. **书籍只是来源容器之一**：知识组织单位逐步从文件转向概念、命题、机制、方法、证据、边界、案例与关系。
4. **知识质量 ≠ 主体价值 ≠ 市场价值**：高质量知识若与当前目标无关，当前学习价值仍可很低。
5. **人学 ≠ AI 学**：资料已入库、AI 可检索、人真正掌握、AI 可执行是不同状态。
6. **学习不是默认动作**：先判断是否需要人内化，还是理解即可、随用随查、AI 调用、Skill/Workflow 化、工具或服务替代。
7. **语义相似不等于知识等价**：相似只用于候选召回，最终需判断重复、改写、补充、扩展、支持、冲突、反例、替代等关系。
8. **增量优先**：优先识别新增机制、新条件、新证据、新边界、新反例、新版本与真正改变决策的信息。
9. **长期运行优先于一次性整理**：体系支持新增、变化、过时、替代、重新验证、重新激活与淘汰。
10. **输入事实、问题现象、评价状态、路由决策、实现载体分开**。
11. **问题空间追求覆盖率，解决空间追求优先级**：发现很多问题，不代表要做很多功能。
12. **真实资料验证受治理**：框架阶段不默认读取现有书库；真实样本必须先经过 Validation Sample Manifest。

# 二、整体五层架构

整个体系正式采用以下上位结构：

```text
Layer 1 真实用户问题 / 任务
        ↓
Layer 2 问题现象宇宙 P-L1 / P-L2
        ↓
Layer 3 知识与评价空间
        ↓
Layer 4 系统能力与消费 / 实现路由
        ↓
Layer 5 技术实现、产品与 Benchmark
```

## Layer 1：真实用户问题 / 任务

回答：

> 用户为什么需要知识，最终要完成什么？

典型目标包括：

- 理解；
- 学习；
- 问题解决；
- 决策；
- 研究；
- 方案设计；
- 项目推进；
- 行动；
- 验证；
- 长期能力形成。

## Layer 2：问题现象宇宙

由 `01_需求宇宙.md` 的 `P-L1 / P-L2` 承载。

回答：

> 在帮助用户完成任务的过程中，系统会遇到哪些稳定问题？

例如：

- 问题定义错误；
- 不知道需要什么知识；
- 资料过多；
- 相同原则反复出现；
- 只是换了案例；
- 新材料增加边界或证据；
- 多来源实际同源；
- 结论冲突；
- 知识过时；
- 人是否真的需要学习；
- Search / RAG / Workflow / Agent 哪种最小充分；
- 什么时候应该停止继续研究。

## Layer 3：知识与评价空间

使用既有 L1-01 ~ L1-12 评价、控制和基础设施空间，对问题中的知识对象、证据、主体价值、时间、学习和风险进行描述与判断。

## Layer 4：系统能力与路由

回答：

- 系统必须具备什么通用能力；
- 哪些问题可以被同一能力解决；
- 人、AI、工具、服务怎样分工；
- 最小充分实现方式是什么。

主要由 `18`、`19`、`20` 承载。

## Layer 5：实现、产品与验证

回答：

- 最终是否需要 Search、RAG、KG、Skill、Workflow、Agent、Automation、Software；
- 怎样用 Schema 表达；
- 怎样 Benchmark；
- 是否真正改善用户结果。

# 三、三条运行链必须分开

## 3.1 用户问题主链

```text
现实问题 / 目标
→ 问题澄清与框定
→ 知识需求
→ 已知 / 未知 / 缺口
→ 研究 / 查询 / 学习
→ 综合与判断
→ 答案 / 模型 / 方案
→ 人机分工
→ 决策与行动
→ 结果验证
→ 新问题 / 新知识缺口
```

## 3.2 知识支持链

```text
当前知识需求
→ 找候选资料
→ 筛选
→ 提取核心知识
→ 识别重复与增量
→ 处理关系、冲突、条件、边界
→ 检查来源和证据
→ 检查时间与版本
→ 多来源综合压缩
→ 找剩余缺口
→ 判断继续还是停止
```

## 3.3 后台知识工程链

```text
资料登记
→ 文件 / 版本识别
→ 原始片段
→ 知识原子
→ 标准知识身份
→ 知识关系
→ 增量判断
→ 证据 / 时间状态
→ 主体价值 / 学习差额
→ 消费路由
→ 实现路由
→ 使用 / 验证 / 更新
```

> `Source Registry → Raw Fragment → Knowledge Atom → Canonical Knowledge` 只属于第三层后台链，不再作为整个系统的用户主链。

# 四、层级定义

- **P-L1 一级问题空间**：用户任务过程中会遇到哪一大类问题；
- **P-L2 二级问题现象**：具体反复出现的稳定问题；
- **L1 一级评价空间**：从哪一大类专业角度描述、评价或治理知识与系统；
- **L2 二级维度**：评价空间中的主要维度；
- **L3 三级指标**：具体评价什么；
- **L4 状态 / 规则 / 量化方法**：怎样表示、测量、打分、验证或触发动作。

P-L1/P-L2 与 L1/L2 不应混用：

> **P 系列描述“会遇到什么问题”；既有 L 系列描述“用什么专业维度判断它”。**

# 五、既有评价与治理三平面

## Plane A：Problem / Evaluation Space

回答：

> 知识、需求、价值、证据、学习与分工本身应该怎样描述和判断？

主要包含既有 `L1-01 ~ L1-10`。

## Plane B：Control / Governance Space

回答：

> 对象现在处于什么系统状态，谁能处理，怎样审计、更新、回滚与退出？

主要为 `L1-11 系统状态与治理`。

## Plane C：Solution / Implementation Space

回答：

> 已经知道要解决什么后，用什么检索、RAG、Skill、Workflow、Agent、软件或外部能力承载？

历史编号 `L1-12 技术基础设施` 为兼容既有文档继续保留，但它不是与知识质量、主体价值同类的评价轴。

# 七、关键边界

## 7.1 问题宇宙与需求属性分开

`01` 现在同时承载：

- `P-L1/P-L2`：问题现象总地图；
- 需求属性：谁需要、什么时候、目标、范围、深度等输入维度。

前者回答“会遇到什么问题”，后者回答“这次需求具有什么属性”。

## 7.2 `L1-04` 不承担个人掌握状态

“已知、误解、遗忘、已掌握”归入 `L1-06 学习适配`。

## 7.3 `L1-09` 与实现路由分离

`L1-09` 回答谁应拥有/承担能力；`19` 回答最小充分实现载体。

## 7.4 风险与治理分开

- `L1-10`：能不能做、风险多大；
- `L1-11`：系统怎样控制、记录、发布、回滚和退出。

## 7.5 需求侧先验优先级与系统派生优先级分开

用户可以输入 `prior_priority`，但系统最终处理优先级必须由问题、相关性、影响、时机、证据、风险、增量和成本联合推导。

# 八、正式知识对象主链

以下链只属于**后台知识工程对象模型**：

```text
Requirement / Trigger
→ Source
→ Raw Fragment
→ Normalized Knowledge Atom
→ Canonical Knowledge
→ Relation Assertion
→ Increment Decision
→ Evidence / Epistemic State
→ Subject Utility
→ Learning Gap
→ Human / AI / Tool Consumption Route
→ Implementation Route
→ Use / Validation
→ Feedback / Version / Governance
```

其中：

- Raw Fragment 保证可回源；
- Knowledge Atom 是可独立判断的候选语义单元；
- Canonical Knowledge 是稳定知识身份，不等于“已经为真”；
- Relation Assertion 本身也需要证据、状态和版本；
- Routing Decision 是主体/需求相关的动态对象。

---

# 九、从问题到产品的正式追踪链

以后新增任何能力或功能，都应尽量能追踪：

```text
真实需求
→ Requirement Pattern
→ P-L1 / P-L2
→ 必须判断什么
→ Capability
→ Validation / Benchmark
→ Implementation
→ Product Feature（若必要）
→ User Outcome
```

因此：

- 有问题但没有能力 → 能力缺口；
- 有能力但没有 Benchmark → 无法证明可靠；
- 有功能但找不到 P-L2 → 可能过度工程化；
- 组件通过但用户结果失败 → 系统仍不合格。

---

# 十、价值判断基本结构

任何知识都不直接等于“值得学习”。至少联合考虑：

> **知识质量 × 主体相关性 × 目标影响 × 信息增量 × 使用概率 × 时间价值 × 复利／杠杆 × 市场价值 × 学习适配 ÷ 最优替代后的实际成本**

但当前不固定统一权重公式。

必须保留四个独立判断：

1. Epistemic Gate：可靠吗？
2. Subject Utility：对当前主体值吗？
3. Human Learning Investment：值得人内化吗？
4. Implementation/Substitution：AI、工具、Workflow、Agent、软件或服务是否更合理？

# 十二、当前阶段：V0 Framework / Synthetic Validation

当前默认仍处于：

> **V0：问题框架、协议、Schema、合成 Benchmark 阶段。**

当前允许：

- 读取正式框架文档；
- 建立和审计问题宇宙；
- 主流专业框架校准；
- Problem → Capability 映射；
- Schema 与 Synthetic Benchmark；
- 框架一致性验证。

当前不默认：

- 扫描 `temp/`；
- 读取真实书籍正文；
- 以真实资料反向塑造框架；
- 为了验证想法随意选择数据。

真实资料必须通过 `21_验证计划、样本清单与数据边界.md` 定义的 Manifest Gate。

# 十三、当前阶段成功标准

当前阶段不以“文档数量增加”作为完成。

至少要能回答：

1. 用户真正可能遇到哪些问题？
2. 哪些问题是 P0，哪些可以后置？
3. 每个关键问题需要什么通用能力？
4. 哪些能力可以复用解决多个问题？
5. 后台知识工程对象为什么存在？
6. 哪些实现是最低复杂度充分解？
7. Benchmark 是否覆盖用户问题而不只是组件？
8. 什么时候应该停止继续研究和工程化？

> **最终目标不是建设最复杂的知识系统，而是建设一个能用最合理成本持续帮助用户解决真实问题的 AI 原生知识系统。**
