# AI 原生知识系统：总览与核心框架

> 目标：面对海量书籍、论文、文章、视频、课程、网页、代码、数据与经验，不以“读完资料”为目标，而以**发现高价值知识差额、形成真实能力、让 AI 可可靠调用、持续更新知识资产**为目标。

---

# 一、核心原则

1. **先需求与问题空间，后解决方案空间**：不因为已有 RAG、Skill、Wiki、搜索引擎，就把问题强行解释成某种技术问题。
2. **书籍只是来源容器之一**：知识组织单位应逐步从文件转向概念、命题、机制、方法、证据、边界、案例与关系。
3. **知识质量 ≠ 主体价值 ≠ 市场价值**：科学、专业、高密度的知识，若与当前目标无关，当前学习价值仍可很低。
4. **人学 ≠ AI 学**：资料已入库、AI 可检索、人真正掌握、AI 可执行是不同状态。
5. **学习不是默认动作**：面对任何知识，应先判断是否需要人内化，还是理解即可、随用随查、AI 调用、Skill 化、Workflow 化、工具替代或服务替代。
6. **语义相似不等于知识等价**：相似只用于召回候选，最终需判断重复、改写、补充、扩展、支持、冲突、反例、替代等关系。
7. **增量优先**：海量知识处理中优先识别新增机制、新条件、新证据、新边界、新反例、新版本与真正影响行动的变化。
8. **长期运行优先于一次性整理**：体系必须支持新增、变化、过时、替代、重新验证、重新激活与淘汰。
9. **输入事实、评价状态、路由决策、实现载体分开**：不能把“项目紧急”直接当成“应该做 Agent”，也不能把“AI 能生成”直接当成“允许自动执行”。
10. **真实资料验证受治理**：框架阶段不默认读取现有书库；真实样本必须先经过 Validation Sample Manifest。

---

# 二、层级定义

- **L1 一级空间**：研究什么大问题。
- **L2 二级维度**：从哪些角度评价或判断。
- **L3 三级指标**：具体评价什么。
- **L4 状态／规则／量化方法**：如何表示、测量、打分、验证或触发动作。

示例：

> `L1 知识本体 → L2 知识密度 → L3 机制密度／方法密度／证据密度 → L4 计算与分级规则`

但需要进一步区分三种**平面（Plane）**，避免把不同性质的内容强行做成“正交评分轴”。

---

# 三、三平面架构

## Plane A：Problem / Evaluation Space

回答：

> **知识、需求、价值、证据、学习与分工本身应该怎样描述和判断？**

主要包含 `L1-01 ~ L1-10`。

## Plane B：Control / Governance Space

回答：

> **对象现在处于什么系统状态，谁能处理，怎样审计、更新、回滚与退出？**

主要为 `L1-11 系统状态与治理`。

## Plane C：Solution / Implementation Space

回答：

> **已经知道要解决什么后，用什么检索、RAG、Skill、Workflow、Agent、软件或外部能力承载？**

历史编号 `L1-12 技术基础设施` 为兼容既有文档继续保留，但它**不是与知识质量、主体价值等同类的评价轴**，而是 Solution Space。

这一区分是当前 L1 审计后的正式修正。

# 五、L1/L2 审计后的关键边界

## 5.1 `L1-04` 不再承担个人掌握状态

“已知、误解、遗忘、已掌握”是**主体与知识的学习状态**，正式归入 `L1-06 学习适配`。

`L1-04` 只描述：

> **知识对象彼此之间，以及新输入相对 Canonical Knowledge 的关系与增量。**

## 5.2 `L1-09` 与 `L1-12` 分离

`L1-09` 回答：

> 谁需要拥有/承担这项能力？人需要掌握多少？AI、工具、服务能替代多少？

`L1-12/19` 回答：

> 如果决定交给 AI/系统，最小充分实现载体是什么？

因此 Prompt / RAG / Skill / Tool / Workflow / Agent 不是 L1-09 的“知识属性”，而是下游 Implementation Route。

## 5.3 风险与治理分开

- `L1-10`：**能不能做、风险多大、有哪些约束**；
- `L1-11`：**系统怎样控制、记录、发布、回滚和退出**。

当前文件 `10_风险约束与系统治理.md` 为保持目录编号稳定，继续同时承载两个 L1，但必须在文档内保持逻辑分区。

## 5.4 需求侧先验优先级与系统派生优先级分开

用户/项目可以输入 `prior_priority`，但最终知识处理优先级必须由：

> 相关性 × 影响 × 时机 × 证据 × 风险 × 增量 × 学习/替代成本

联合形成 Routing Decision。

# 六、正式知识对象主链

```text
Requirement / Trigger
→ Source
→ Raw Fragment
→ Normalized Knowledge Atom
→ Canonical Knowledge
→ Relation Assertion
→ Increment Decision
→ Evidence / Epistemic State
→ Subject Utility
→ Learning Gap
→ Human / AI / Tool Consumption Route
→ Implementation Route
→ Use / Validation
→ Feedback / Version / Governance
```

其中：

- `Raw Fragment` 保证可回源；
- `Knowledge Atom` 是可独立判断的候选语义单元；
- `Canonical Knowledge` 是稳定知识身份，不等于“已经为真”；
- `Relation Assertion` 本身也需要证据、状态和版本；
- `Routing Decision` 是主体/需求相关的动态对象，不写死在知识本体中。

---

# 七、价值判断的基本结构

任何知识都不直接等于“值得学习”。至少联合考虑：

> **知识质量 × 主体相关性 × 目标影响 × 信息增量 × 使用概率 × 时间价值 × 复利／杠杆 × 市场价值 × 学习适配 ÷ 最优替代后的实际成本**

但当前不固定一个统一权重公式。

更重要的是保留四个独立判断：

1. **Epistemic Gate**：可靠吗？
2. **Subject Utility**：对当前主体值吗？
3. **Human Learning Investment**：值得人内化吗？
4. **Implementation/Substitution**：AI、工具、Workflow、Agent、软件或服务是否更合理？

高市场价值不能抵消证据不足，高主体价值也不能把未经验证的 Claim 变成 Fact。

# 十一、完成标准

系统尚未因为“文档多了”而完成。

任取一条知识或需求，至少要能稳定回答：

- 它是什么类型？
- 来源和原始定位是什么？
- Canonical 身份是什么？
- 可靠吗？
- 是否过时？
- 相对已有知识新增了什么？
- 与哪些知识重复、支持、冲突、依赖或替代？
- 对当前主体和项目有什么价值？
- 人还差多少才能达到目标掌握状态？
- 人真的需要学吗？
- AI、工具、服务能否稳定替代？
- 最合理的消费路由是什么？
- 最小充分实现载体是什么？
- 什么变化会触发重验证或重新路由？
- 所有关键判断能否回到来源、维度和 Benchmark？

如果这些问题仍不能稳定回答，不得宣布系统完成。
