# AI 原生知识系统：总览与核心框架

> 目标：面对海量书籍、论文、文章、视频、课程、网页、代码、数据与经验，不以“读完资料”为目标，而以**围绕真实问题发现高价值知识差额、形成真实能力、让 AI 可可靠调用、持续更新知识资产**为目标。

---

## 一、核心原则

1. **先真实问题，后知识处理，再技术实现。**
2. **先理解用户世界，再建立专业分类。** 普通人的目标、旅程和原话问题不能被 P-L1、Schema、Skill、Agent 等专业表达替代。
3. **用户原话、标准用户问题、专业问题必须分层。** 三者分别负责真实性、稳定去重和专业归类。
4. **问题空间与解决方案空间彻底分开。** Search、RAG、Skill、Workflow、Agent、Software 不属于 P-L1 / P-L2。
5. **用户问题与系统错误分开。** false merge、错误路由、模型成本、自动化过度等属于 Benchmark / System Error，不是用户专业问题分类。
6. **书籍只是来源容器之一。** 知识组织不能永远停留在文件级。
7. **知识质量 ≠ 主体价值 ≠ 市场价值。**
8. **人学 ≠ AI 学。** 资料已入库、AI 可检索、人真正掌握、AI 可执行是不同状态。
9. **学习不是默认动作。** 可以正确地选择理解即可、随用随查、委托 AI / 工具 / 服务，前提是保留必要判断、监督与责任边界。
10. **语义相似不等于知识等价。**
11. **增量优先。** 优先识别新增机制、条件、边界、反例、证据、版本和真正改变决策的信息。
12. **长期运行优先于一次性整理。**
13. **规模会改变用户问题本身。**一本到多书、领域、海量、多年使用会出现不同问题。
14. **AI 会降低机械成本，也会制造新的用户风险。** 包括来源失真、压缩遗漏、引用错配、过度信任、替代思考等。
15. **真实资料验证受治理。** 框架阶段不默认扫描真实书库。

## 二、整体六层架构

```text
Layer 1 用户世界事实层
        用户目标 / 用户需求 / 用户旅程 / 真实场景 / 用户原话问题
        事实源：01A
        ↓
Layer 2 标准用户问题桥梁层
        用户原话 → Standard User Problem（SUP）→ 覆盖审计
        事实源：01B
        ↓
Layer 3 专业问题宇宙
        P-L1 / P-L2 Problem Taxonomy
        事实源：01
        ↓
Layer 4 知识与评价空间
        知识、证据、关系、价值、学习、时间、风险、治理
        ↓
Layer 5 系统能力与消费 / 能力归属
        Capability、人 / AI / 工具 / 服务分工、验证要求
        ↓
Layer 6 解决方案、实现、产品与 Benchmark
        Search / RAG / Skill / Workflow / Agent / Software / Validation
```

### Layer 1：用户世界事实层

由 `01A_用户旅程、需求与高频问题现象宇宙.md` 承载。

回答：

- 用户为什么现在需要知识；
- 用户正在做什么；
- 用户真正想得到什么；
- 在什么阶段会遇到问题；
- 用户自己会怎样描述；
- 问题怎样随规模和时间变化。

### Layer 2：标准用户问题桥梁层

由 `01B_标准用户问题与专业问题映射.md` 承载。

```text
用户原话
→ SUP
→ COVERED / PARTIAL / MISSING / MISPLACED
→ P-L1 / P-L2
```

这一层防止：

- 一句话就创建一个分类；
- 同一个问题重复计数；
- 不同根因被笼统合并；
- 工程实现问题被伪装成用户问题。

### Layer 3：专业问题宇宙

由 `01_需求宇宙.md` 承载。

当前正式采用：

> **P-L1-01 ～ P-L1-17，共 17 个一级专业问题空间。**

专业问题宇宙只回答：

> “用户与知识使用过程中，稳定地会遇到什么问题？”

明确不回答：

- 应该做 RAG 还是 Search；
- 应该做 Skill、Workflow 还是 Agent；
- 是否要软件化；
- 模型成本多少；
- false merge 为什么发生。

这些分别进入 `19` 和 `13 / 22`。

### Layer 4：知识与评价空间

使用既有 `L1-01 ~ L1-12` 评价、控制和基础设施空间，对知识对象、证据、主体价值、学习、时间、风险和治理进行描述与判断。

### Layer 5：系统能力与消费 / 能力归属

回答：

- 为解决上游问题，系统必须具备什么能力；
- 哪些问题可以被同一能力共同解决；
- 哪些知识必须本人掌握；
- 哪些可以随用随查或委托；
- 委托后人仍应保留什么判断、监督和责任。

主要由 `09`、`18`、`20` 承载。

### Layer 6：解决方案、实现、产品与验证

回答：

- 最小充分实现载体是什么；
- 是否需要 Search / RAG / KG / Skill / Workflow / Agent / Automation / Software；
- 怎样验证；
- 是否真正改善用户结果。

主要由 `13`、`19`、`20`、`21`、`22` 承载。

## 三、用户生命周期与三条运行链必须分开

### 3.1 用户生命周期不是工程工作流

`01A` 正式采用 18 个用户阶段：

```text
J01 触发与真实目标
→ J02 是否需要本人学习
→ J03 陌生领域与知识缺口
→ J04 发现与收集资料
→ J05 候选筛选与优先级
→ J06 读前价值与处理深度
→ J07 阅读地图与重新进入
→ J08 阅读过程与认知负荷
→ J09 概念、论证与关系理解
→ J10 提取重点与压缩
→ J11 笔记、记录与回源
→ J12 正确性、来源与证据
→ J13 条件、边界、冲突与反例
→ J14 多来源综合、去重与增量
→ J15 联系个人 / 项目与当前判断
→ J16 记忆、主动回忆、练习与迁移
→ J17 决策、行动、反馈与调整
→ J18 长期调用、更新与生命周期
```

这是一张用户旅程地图，不要求所有场景顺序执行 18 步。

### 3.2 用户问题主链

```text
现实问题 / 目标
→ 问题澄清与框定
→ 判断本人是否需要学习
→ 知识需求
→ 已知 / 未知 / 缺口
→ 研究 / 查询 / 学习
→ 综合与判断
→ 答案 / 模型 / 方案
→ 本人掌握 / 委托 / 监督边界
→ 决策与行动
→ 结果验证
→ 新问题 / 新知识缺口
```

### 3.3 知识支持链

```text
当前知识需求
→ 找候选资料
→ 筛选与确定处理深度
→ 提取核心知识
→ 识别重复与增量
→ 处理关系、冲突、条件、边界
→ 检查来源和证据
→ 检查时间与版本
→ 多来源综合压缩
→ 找剩余缺口
→ 判断继续还是停止
```

### 3.4 后台知识工程链

```text
资料登记
→ 文件 / 版本识别
→ 原始片段
→ 知识原子
→ 标准知识身份
→ 知识关系
→ 增量判断
→ 证据 / 时间状态
→ 主体价值 / 学习差额
→ 消费与能力归属
→ 实现路由
→ 使用 / 验证 / 更新
```

> `Source → Raw Fragment → Knowledge Atom → Canonical Knowledge` 只属于后台链，不是用户主链。

## 四、层级定义

- **用户原话问题**：普通用户在真实情境中的自然表达；
- **SUP 标准用户问题**：对近似用户原话去重后的稳定问题；
- **P-L1 一级专业问题空间**：稳定的大类问题域；
- **P-L2 二级专业问题**：可跨场景复用的具体问题；
- **L1 / L2**：评价与治理维度；
- **Capability**：系统需要会什么；
- **Implementation**：最终用什么承载；
- **Benchmark / Error Taxonomy**：能力和组件哪里会失败、怎样验证。

关系：

```text
用户原话：这是真的吗？
SUP：是不是同一个稳定问题？
P-L1/P-L2：专业上属于什么问题？
L1/L2：从什么维度评价？
Capability：系统需要会什么？
Implementation：用什么实现？
Benchmark：是否可靠、哪里会失败？
```

## 五、既有评价与治理三平面

### Plane A：Problem / Evaluation Space

主要包含 `L1-01 ~ L1-10`，回答知识、需求、价值、证据、学习与风险应该怎样判断。

### Plane B：Control / Governance Space

主要为 `L1-11 系统状态与治理`，回答权限、状态、更新、审计、归档、回滚与退出。

### Plane C：Solution / Implementation Space

`L1-12 技术基础设施` 继续作为评价框架中的技术平面名称，但**不进入 P-L1 / P-L2 问题编号**。

## 七、关键边界

### 7.1 `01A / 01B / 01` 不能复制职责

- `01A`：用户什么时候遇到什么问题、怎样说；
- `01B`：用户原话怎样去重成 SUP，并映射专业问题；
- `01`：17 个 P-L1 / P-L2 专业 Taxonomy。

### 7.2 实现载体不属于 P Taxonomy

正确链路：

```text
用户原话 / SUP
→ P-L1 / P-L2
→ Capability
→ 19 判断最小充分实现载体
```

因此不再存在“为兼容而保留的实现桥接 P-L1”。

### 7.3 系统错误不属于 P Taxonomy

```text
用户感知后果 → 01A / 01B / 01
组件为什么判错 → 13 / 22
```

例如“AI 把条件删掉，导致我理解错”是用户问题；`false merge rate`、`routing error`、`LLM cost explosion` 是系统质量问题。

### 7.4 风险与治理分开

- `L1-10`：能不能做、风险多大；
- `L1-11`：系统怎样控制、记录、发布、回滚和退出。

## 八、正式知识对象主链

以下链只属于后台知识工程对象模型：

```text
Requirement / Trigger
→ Source
→ Raw Fragment
→ Normalized Knowledge Atom
→ Canonical Knowledge
→ Relation Assertion
→ Increment Decision
→ Evidence / Epistemic State
→ Subject Utility
→ Learning Gap
→ Human / AI / Tool Consumption & Ownership
→ Implementation Route
→ Use / Validation
→ Feedback / Version / Governance
```

## 九、从用户问题到产品的正式追踪链

```text
真实目标 / 用户原话（01A）
→ Standard User Problem（01B）
→ P-L1 / P-L2（01）
→ Requirement Pattern（如适用）
→ Capability
→ Validation / Benchmark
→ Implementation（19）
→ Product Feature（若必要）
→ User Outcome
```

因此：

- 有用户原话但无法形成 SUP → 继续用户研究；
- 有 SUP 但没有 P-L2 → 专业问题缺口；
- 有问题但没有能力 → 能力缺口；
- 有能力但没有 Benchmark → 无法证明可靠；
- 有功能但找不到 SUP / P-L2 → 可能过度工程化；
- 组件通过但用户结果失败 → 系统仍不合格。

## 十、价值判断基本结构

任何知识都不直接等于“值得学习”。必须分开判断：

1. **可靠吗？**
2. **对当前主体值吗？**
3. **值得本人内化吗？**
4. **可以查询、委托或由工具承担吗？**
5. **委托后本人还必须保留什么判断、验收和责任？**
6. **最终用什么实现？**——这一问后置到 `19`。

## 十三、当前成功标准

至少要能回答：

1. 普通用户能否看懂并判断问题是否真实？
2. 用户原话能否稳定归一为 SUP？
3. SUP 能否映射到纯粹的问题 Taxonomy，而不是技术名词？
4. 单书、多书、领域、海量、长期问题是否覆盖？
5. 理解、记忆、判断、行动、迁移是否分开？
6. 本人学习、查询、委托与监督是否允许不同结果？
7. 系统错误是否留在 Benchmark，而不是污染用户问题宇宙？
8. 实现选择是否后置到解决方案空间？

> **最终目标不是维护历史编号，而是让体系的每一层都只回答自己应该回答的问题。**
