# AI 原生知识系统：总览与核心框架

> 目标：面对海量书籍、论文、文章、视频、课程、网页、代码、数据与经验，不以“读完资料”为目标，而以**围绕真实问题发现高价值知识差额、形成真实能力、让 AI 可可靠调用、持续更新知识资产**为目标。

---

# 一、核心原则

1. **先真实问题，后知识处理，再技术实现**：系统不是为了管理知识而管理知识，而是为了帮助人理解、学习、判断、决策、解决问题和完成任务。
2. **先理解用户世界，再建立专业分类**：普通人的目标、旅程、原话问题不能被 P-L1、Schema、Skill、Agent 等专业表达替代。
3. **先问题空间，后解决方案空间**：不因为已有 RAG、Skill、Wiki、Agent，就把问题强行解释成某种技术问题。
4. **用户原话、标准用户问题、专业问题必须分层**：三者分别负责真实性、稳定去重和专业归类。
5. **书籍只是来源容器之一**：知识组织单位逐步从文件转向概念、命题、机制、方法、证据、边界、案例与关系。
6. **知识质量 ≠ 主体价值 ≠ 市场价值**：高质量知识若与当前目标无关，当前学习价值仍可很低。
7. **人学 ≠ AI 学**：资料已入库、AI 可检索、人真正掌握、AI 可执行是不同状态。
8. **学习不是默认动作**：先判断是否需要人内化，还是理解即可、随用随查、AI 调用、工具或服务替代。
9. **语义相似不等于知识等价**：相似只用于候选召回，最终需判断重复、改写、补充、扩展、支持、冲突、反例、替代等关系。
10. **增量优先**：优先识别新增机制、新条件、新证据、新边界、新反例、新版本与真正改变决策的信息。
11. **长期运行优先于一次性整理**：体系支持新增、变化、过时、替代、重新验证、重新激活与淘汰。
12. **输入事实、用户问题、专业问题、评价状态、路由决策、实现载体分开**。
13. **问题空间追求覆盖率，解决空间追求优先级**：发现很多问题，不代表要做很多功能。
14. **规模会改变问题本身**：一本到多书、百本、海量与多年使用会出现不同问题，不应只用“单本书工作流”解释整个系统。
15. **AI 会消除一些成本，也会产生新的用户风险**：例如偏离原意、压缩遗漏、引用错配、过度信任、替代思考和规模化错误放大。
16. **真实资料验证受治理**：框架阶段不默认读取现有书库；真实样本必须先经过 Validation Sample Manifest。

# 二、整体六层架构

整个体系正式采用以下上位结构：

```text
Layer 1 用户世界事实层
        用户目标 / 用户需求 / 用户旅程 / 真实场景 / 用户原话问题
        事实源：01A
        ↓
Layer 2 标准用户问题桥梁层
        用户原话 → Standard User Problem → 覆盖审计
        事实源：01B
        ↓
Layer 3 专业问题宇宙
        P-L1 / P-L2 Problem Taxonomy
        事实源：01
        ↓
Layer 4 知识与评价空间
        知识、证据、关系、价值、学习、时间、风险等
        ↓
Layer 5 系统能力与消费 / 实现路由
        Capability、人机分工、最小充分实现
        ↓
Layer 6 技术实现、产品与 Benchmark
        Search / RAG / Skill / Workflow / Agent / Software / Validation
```

## Layer 1：用户世界事实层

由 `01A_用户旅程、需求与高频问题现象宇宙.md` 承载。

回答：

- 用户为什么需要知识；
- 用户此时正在做什么；
- 用户真正想得到什么；
- 在什么生命周期阶段遇到问题；
- 用户自己怎样描述；
- 问题怎样随一本到多书、海量和长期使用发生变化。

典型用户目标包括：

- 理解；
- 学习；
- 问题解决；
- 决策；
- 研究；
- 方案设计；
- 项目推进；
- 行动；
- 验证；
- 长期能力形成；
- 随用随查；
- 委托 AI / 工具而本人只保留必要判断能力。

## Layer 2：标准用户问题桥梁层

由 `01B_标准用户问题与专业问题映射.md` 承载。

回答：

> 大量不同用户说法，怎样去重为稳定问题，同时不丢失真实场景？

正式链路：

```text
用户原话
→ Standard User Problem（SUP）
→ COVERED / PARTIAL / MISSING / MISPLACED
→ P-L1 / P-L2
```

这一层负责防止：

- 一句话就创建一个新分类；
- 多个不同根因被笼统合并；
- 专业术语掩盖真实用户问题；
- 工程实现问题被误当成用户问题。

## Layer 3：专业问题宇宙

由 `01_需求宇宙.md` 的 `P-L1 / P-L2` 承载。

回答：

> 大量具体用户问题，从专业 Problem Taxonomy 看属于哪些稳定类别？

例如：

- 问题定义错误；
- 不知道需要什么知识；
- 资料过多；
- 相同原则反复出现；
- 只是换了案例；
- 新材料增加边界或证据；
- 多来源实际同源；
- 结论冲突；
- 知识过时；
- 笔记长期不可再利用；
- 熟悉感误认为掌握；
- 需要时无法主动提取；
- AI 解释偏离来源；
- 执行失败后无法诊断原因；
- 什么时候应该停止继续研究。

`P-L1-16` 作为兼容编号保留，但正式视为**问题空间到解决方案空间的桥接分类**，不再把 Search / RAG / Agent 等实现选择当作普通用户问题。

## Layer 4：知识与评价空间

使用既有 L1-01 ~ L1-12 评价、控制和基础设施空间，对问题中的知识对象、证据、主体价值、时间、学习和风险进行描述与判断。

## Layer 5：系统能力与路由

回答：

- 系统必须具备什么通用能力；
- 哪些问题可以被同一能力解决；
- 人、AI、工具、服务怎样分工；
- 最小充分实现方式是什么。

主要由 `18`、`19`、`20` 承载。

## Layer 6：实现、产品与验证

回答：

- 最终是否需要 Search、RAG、KG、Skill、Workflow、Agent、Automation、Software；
- 怎样用 Schema 表达；
- 怎样 Benchmark；
- 是否真正改善用户结果。

# 三、用户生命周期与三条运行链必须分开

## 3.1 用户生命周期不是工程工作流

`01A` 正式采用 18 个用户阶段：

```text
J01 触发与真实目标
→ J02 是否需要本人学习
→ J03 陌生领域与知识缺口
→ J04 发现与收集资料
→ J05 候选筛选与优先级
→ J06 读前价值与处理深度
→ J07 阅读地图与重新进入
→ J08 阅读过程与认知负荷
→ J09 概念、论证与关系理解
→ J10 提取重点与压缩
→ J11 笔记、记录与回源
→ J12 正确性、来源与证据
→ J13 条件、边界、冲突与反例
→ J14 多来源综合、去重与增量
→ J15 联系个人 / 项目与当前判断
→ J16 记忆、主动回忆、练习与迁移
→ J17 决策、行动、反馈与调整
→ J18 长期调用、更新与生命周期
```

这是一张**用户旅程地图**，不是要求系统每次都按 18 步执行。

## 3.2 用户问题主链

```text
现实问题 / 目标
→ 问题澄清与框定
→ 判断本人是否需要学习
→ 知识需求
→ 已知 / 未知 / 缺口
→ 研究 / 查询 / 学习
→ 综合与判断
→ 答案 / 模型 / 方案
→ 人机分工
→ 决策与行动
→ 结果验证
→ 新问题 / 新知识缺口
```

## 3.3 知识支持链

```text
当前知识需求
→ 找候选资料
→ 筛选与确定处理深度
→ 提取核心知识
→ 识别重复与增量
→ 处理关系、冲突、条件、边界
→ 检查来源和证据
→ 检查时间与版本
→ 多来源综合压缩
→ 找剩余缺口
→ 判断继续还是停止
```

## 3.4 后台知识工程链

```text
资料登记
→ 文件 / 版本识别
→ 原始片段
→ 知识原子
→ 标准知识身份
→ 知识关系
→ 增量判断
→ 证据 / 时间状态
→ 主体价值 / 学习差额
→ 消费路由
→ 实现路由
→ 使用 / 验证 / 更新
```

> `Source Registry → Raw Fragment → Knowledge Atom → Canonical Knowledge` 只属于第三条后台链，不再作为整个系统的用户主链。

# 四、层级定义

- **用户原话问题**：普通用户在真实情境中的自然表达；
- **SUP 标准用户问题**：对近似用户原话去重后的稳定问题表达；
- **P-L1 一级专业问题空间**：用户任务过程中会遇到哪一大类稳定专业问题；
- **P-L2 二级专业问题维度**：可反复出现、可跨场景复用的具体问题；
- **L1 一级评价空间**：从哪一大类专业角度描述、评价或治理知识与系统；
- **L2 二级维度**：评价空间中的主要维度；
- **L3 三级指标**：具体评价什么；
- **L4 状态 / 规则 / 量化方法**：怎样表示、测量、打分、验证或触发动作。

关系：

```text
用户原话解决“真实不真实、像不像用户会说的话”
SUP 解决“是不是同一个稳定问题”
P-L1/P-L2 解决“专业上属于什么问题”
L1/L2 解决“从什么专业维度判断和治理”
Capability 解决“系统需要会什么”
Implementation 解决“最终用什么承载”
```

# 七、关键边界

## 7.1 `01A / 01B / 01` 三层不能复制

- `01A`：用户什么时候遇到什么问题、怎样说；
- `01B`：用户原话怎样去重成 SUP，并映射专业问题；
- `01`：P-L1 / P-L2 专业 Taxonomy。

`01` 不应继续堆大量用户原话，`01A` 也不应变成专业分类表。

## 7.2 问题宇宙与需求属性分开

`01` 中：

- `P-L1/P-L2` 回答“会遇到什么专业问题”；
- Requirement 属性回答“这次需求具有什么属性”。

## 7.3 `L1-04` 不承担个人掌握状态

“已知、误解、遗忘、已掌握”归入 `L1-06 学习适配`。

## 7.4 `L1-09` 与实现路由分离

`L1-09` 回答谁应拥有/承担能力；`19` 回答最小充分实现载体。

## 7.5 `P-L1-16` 不作为用户世界入口

Search、RAG、Skill、Workflow、Agent、Software 是解决方案空间概念。

正确顺序：

```text
用户原话 / SUP
→ P-L1/P-L2 问题
→ Capability
→ P-L1-16 / 19 才判断实现载体
```

## 7.6 风险与治理分开

- `L1-10`：能不能做、风险多大；
- `L1-11`：系统怎样控制、记录、发布、回滚和退出。

## 7.7 需求侧先验优先级与系统派生优先级分开

用户可以输入 `prior_priority`，但系统最终处理优先级必须由问题、相关性、影响、时机、证据、风险、增量和成本联合推导。

# 八、正式知识对象主链

以下链只属于**后台知识工程对象模型**：

```text
Requirement / Trigger
→ Source
→ Raw Fragment
→ Normalized Knowledge Atom
→ Canonical Knowledge
→ Relation Assertion
→ Increment Decision
→ Evidence / Epistemic State
→ Subject Utility
→ Learning Gap
→ Human / AI / Tool Consumption Route
→ Implementation Route
→ Use / Validation
→ Feedback / Version / Governance
```

其中：

- Raw Fragment 保证可回源；
- Knowledge Atom 是可独立判断的候选语义单元；
- Canonical Knowledge 是稳定知识身份，不等于“已经为真”；
- Relation Assertion 本身也需要证据、状态和版本；
- Routing Decision 是主体/需求相关的动态对象。

---

# 九、从问题到产品的正式追踪链

以后新增任何能力或功能，都应尽量能追踪：

```text
真实目标 / 用户原话（01A）
→ Standard User Problem（01B）
→ P-L1 / P-L2（01）
→ Requirement Pattern（如适用）
→ 必须判断什么
→ Capability
→ Validation / Benchmark
→ Implementation
→ Product Feature（若必要）
→ User Outcome
```

因此：

- 有用户原话但无法形成 SUP → 继续用户研究；
- 有 SUP 但没有 P-L2 → 专业问题缺口；
- 有问题但没有能力 → 能力缺口；
- 有能力但没有 Benchmark → 无法证明可靠；
- 有功能但找不到 SUP / P-L2 → 可能过度工程化；
- 组件通过但用户结果失败 → 系统仍不合格。

# 十、价值判断基本结构

任何知识都不直接等于“值得学习”。至少联合考虑：

> **知识质量 × 主体相关性 × 目标影响 × 信息增量 × 使用概率 × 时间价值 × 复利／杠杆 × 市场价值 × 学习适配 ÷ 最优替代后的实际成本**

但当前不固定统一权重公式。

必须保留四个独立判断：

1. Epistemic Gate：可靠吗？
2. Subject Utility：对当前主体值吗？
3. Human Learning Investment：值得人内化吗？
4. Implementation/Substitution：AI、工具、Workflow、Agent、软件或服务是否更合理？

# 十三、当前阶段成功标准

当前阶段不以“文档数量增加”作为完成。

至少要能回答：

1. 用户在完整生命周期中什么时候会遇到什么问题？
2. 普通用户是否能通过大量原话判断问题是否真实、有无遗漏？
3. 一句话用户表达能否稳定去重成 Standard User Problem？
4. 每个重要 SUP 能否追踪到 P-L1 / P-L2？
5. 一一本到多书、百本、海量、长期使用时问题怎样变化？
6. AI 参与后哪些旧问题减少、哪些新风险出现？
7. 哪些问题是 P0，哪些可以后置？
8. 每个关键问题需要什么通用能力？
9. 哪些能力可以复用解决多个问题？
10. 后台知识工程对象为什么存在？
11. 哪些实现是最低复杂度充分解？
12. Benchmark 是否覆盖用户问题而不只是组件？
13. 什么时候应该停止继续研究和工程化？

> **最终目标不是建设最复杂的知识系统，而是建设一个普通用户能理解上游问题、产品人员能验证需求、专业体系能稳定归类、工程系统能向上追踪的 AI 原生知识系统。**
