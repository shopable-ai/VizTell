# 软件产品需求与系统能力地图

> 本文件不预设必须做一个“大而全知识软件”。它把稳定问题映射为软件能力候选，并规定何时才值得从文档、脚本、Skill、Workflow 升级为长期软件产品。

核心顺序：

> **Problem → Capability → Validation → Productization**

---

# 1. 软件化不是最高级路线

一个需求更值得软件化，通常因为它同时出现若干特征：

- 高频重复；
- 数据规模使人工处理不可持续；
- 需要长期持久状态；
- 多用户/多角色协作；
- 权限、审计、版本、回滚复杂；
- 固定 UI 能显著降低认知成本；
- 需要稳定 API 给 AI/Agent 消费；
- 需要长期自动运行；
- 需要可观测、SLA、回归测试；
- 形成明确业务或组织闭环。

若需求低频、一次性、尚未稳定，优先：

> 文档 / Search / RAG / Script / Skill / Workflow / Existing Tool

而不是提前软件化。

# 3. A：资料盘点与进入

## CAP-A01 Source Inventory

问题：不知道资料库里有什么、多少版本、多少格式和重复资产。

输出：Source Registry。

最低字段：

- source_id；
- path/location；
- carrier_type；
- hash；
- size；
- created/modified/published time；
- source owner；
- processing state。

## CAP-A02 Parsing & Structural Normalization

把 PDF、EPUB、HTML、Markdown、字幕、代码、表格等解析成可处理结构，同时保留：

- 页面/章节/时间戳；
- 图表位置；
- 代码块；
- 原始来源定位。

不能简单等同于“全部转纯文本”。

## CAP-A03 Corpus Quality Diagnostics

识别：

- OCR 错误；
- 乱码；
- 重复页；
- 截断；
- 广告污染；
- 标题层级异常；
- 表格/代码破坏；
- 图片缺失。

# 4. B：来源、版本与治理

## CAP-B01 Provenance Graph

追踪：

> Source → Raw Fragment → Atom → Canonical Knowledge → Relation / Routing / Output

## CAP-B02 Version & Representation Resolver

区分：

- 真修订；
- 不同文件格式；
- OCR/转录版本；
- 精简/扩展版本；
- 并行版本；
- 名称像版本但没有修订关系。

## CAP-B03 Access / License / Retention Policy

保存：

- copyright/license；
- privacy class；
- access scope；
- allowed use；
- retention/deletion policy；
- audit requirement。

---

# 5. C：知识原子与标准知识

## CAP-C01 Knowledge Atom Extractor

提取 Concept、Claim、Mechanism、Method、Condition、Evidence、Case 等候选对象，并保留 provenance。

## CAP-C02 Canonical Resolver

将候选 Atom 路由为：

- 新 Canonical；
- alias；
- paraphrase；
- refine/extend；
- condition/boundary difference；
- unresolved review。

## CAP-C03 Terminology / Alias Manager

管理：

- preferred label；
- alternative label；
- acronym；
- multilingual label；
- broader/narrower；
- 同名异义。

---

# 6. D：跨资料去重、增量与冲突

## CAP-D01 Multi-stage Duplicate Candidate Discovery

支持文件、文本、近似文本、语义候选多层召回。

## CAP-D02 Proposition Relation Adjudication

输出明确关系，而不是只有 similarity score。

## CAP-D03 Knowledge Increment Report

对新输入报告：

- 新 Canonical；
- 新机制；
- 新条件；
- 新边界；
- 新证据；
- 新独立证据；
- 新反例；
- 新案例；
- 决策改变信息；
- 重复部分。

## CAP-D04 Saturation Analyzer

按主题观察边际知识增量，建议：

- continue；
- lower-frequency；
- monitor；
- stop deep processing。

## CAP-D05 Conflict Workbench

把冲突拆成定义、条件、人群、时间、指标、证据和真正逻辑冲突。

---

# 7. E：证据与可信度

## CAP-E01 Primary Source Tracing

从二手/三手信息尽可能回溯原始来源。

## CAP-E02 Evidence Independence Resolver

区分：

- raw source count；
- primary source count；
- independent evidence group count。

## CAP-E03 Claim–Evidence Matrix

每个 Claim 展示：

- supporting evidence；
- counterevidence；
- evidence quality；
- independence；
- unresolved gaps；
- scope/time validity。

## CAP-E04 Epistemic Status Review

知识状态升级/降级必须版本化并可审计。

---

# 8. F：主体与项目知识差额

## CAP-F01 Subject Knowledge Profile

记录的不是“读过哪些书”，而是：

- 识别；
- 理解；
- 判断；
- 执行；
- 迁移；
- 熟练；
- 最近验证时间。

## CAP-F02 Project Knowledge Requirement Graph

给任务/项目阶段定义：

- 必需知识；
- 前置知识；
- 高风险检查知识；
- 决策知识；
- 可随查知识；
- 可 AI/工具代理知识。

## CAP-F03 Knowledge Gap Report

> 项目/目标所需知识与能力 − 人/团队/AI 当前已拥有 = 真正差额。

# 9. G：价值、学习与消费路由

分别显示：

- epistemic quality；
- subject utility；
- project relevance；
- compound leverage；
- market value；
- learning cost；
- substitution maturity；

## CAP-G02 Learning vs Delegation Router

输出：

- Human Learn；
- Understand/Judge；
- Reference；
- Search；
- RAG；
- Tool；
- Skill；
- Workflow；
- Agent；
- External Service；
- Monitor/Deferred/Ignore。

## CAP-G03 Dynamic Route Recalculation

# 10. H：人工学习 Tutor

## CAP-H01 Adaptive Learning Queue

按知识差额、前置依赖、目标掌握层级和使用时机生成学习队列，而不是按书本顺序推进。

## CAP-H02 Evidence-aware Tutor

教学时同时显示：

- 可信度；
- 边界；
- 反例；
- 争议；
- 不确定性。

不能把 `unverified claim` 教成人工确定知识。

## CAP-H03 Practice / Transfer Engine

支持主动回忆、案例辨别、真实应用、异常案例和跨场景迁移。

---

# 11. I：AI 知识消费接口

## CAP-I01 Retrieval API

提供 Full-text / Semantic / Hybrid / Relation / Metadata 检索接口。

## CAP-I02 Minimal Context Pack Builder

按任务组装最小充分上下文，控制：

- relevance；
- source diversity；
- evidence；
- conflicts；
- token budget。

## CAP-I03 Citation & Epistemic Contract

AI 输出至少区分：

- source-backed；
- derived inference；
- unresolved；
- unsupported。

## CAP-I04 Capability Registry

让 Workflow/Agent 知道当前有哪些：

- Skill；
- Tool；
- Workflow；
- version；
- permission；
- Benchmark 状态；
- failure mode。

---

# 12. J：能力化候选自动发现

## CAP-J01 Skill Candidate Miner

发现重复出现、输入输出稳定、成功可验证的方法或判断规则。

## CAP-J02 Workflow Candidate Miner

发现稳定多步骤、重复关口、重试和异常恢复结构。

## CAP-J03 Agent Necessity Analyzer

识别哪些步骤真的需要动态环境观察、规划和重规划，避免“所有 Workflow Agent 化”。

## CAP-J04 Software Candidate Analyzer

持续观察：

- 使用频率；
- 用户数；
- 状态复杂度；
- UI 价值；
- 集成数量；
- 维护成本；
- 业务闭环；

给出产品化证据，而非凭感觉软件化。

# 13. K：变化监测与主动研究

## CAP-K01 Freshness / Change Monitor

监测知识、标准、法规、产品、工具和来源版本变化。

## CAP-K02 Impact Propagation

新证据/版本进入后找到受影响的：

- Canonical Knowledge；
- Wiki；
- RAG context；
- Skill；
- Workflow；
- Agent policy；
- 学习内容；
- 路由决策。

## CAP-K03 Unknown-Unknown Research Queue

从异常、冲突、高价值空白和失败记录中生成新的研究问题。

---

# 14. L：Benchmark、可观测与回归

## CAP-L01 Golden Set Manager

维护：

- gold relation；
- gold evidence judgment；
- gold route；
- edge case；
- regression case。

## CAP-L02 Pipeline Observability

监测每一步：

- 输入数量；
- candidate 数；
- LLM adjudication 数；
- 人工复核数；
- 错误率；
- latency；
- cost；
- fallback/retry。

## CAP-L03 Regression Runner

Schema、模型、Prompt、Embedding、阈值变化后自动重新跑合成与受控真实 Benchmark。

---

# 15. M：协作、权限与产品界面

## CAP-M01 Human Review Queue

把真正需要人判断的内容集中出来：

- 高风险；
- 低置信关系；
- 真冲突；
- merge/delete/replaces；
- 高影响路由。

## CAP-M02 Explainable Decision Surface

每个决策可展开：

> 输入维度 → 候选 → 证据 → 最终决策 → 未决问题。

## CAP-M03 Role / Permission / Audit

支持个人、团队、组织不同角色和数据范围。

# 16. 产品化阶段建议

## P0：文档与协议

当前阶段。

目标：语义、边界、Benchmark 稳定。

## P1：Research Prototype

优先实现最小纵向切片，例如：

```text
Source
→ Raw Fragment
→ Claim/Atom
→ Candidate Canonical
→ Relation Assertion
→ Increment Report
→ Routing Decision
```

不追求 UI 完整。

## P2：Workbench

加入：

- Review Queue；
- 搜索；
- Canonical 浏览；
- 证据/冲突；
- 项目知识差额；
- Benchmark。

## P3：Automation / Agentic Research

在基础数据模型和评测可信后，再增加主动监测、研究和低风险自动更新。

## P4：Product

只有真实用户、高频需求、权限/状态/UI/业务闭环被验证后，才进入完整产品工程。

---

# 17. 最优第一批软件能力不是“大一统 AI 知识库”

更合理的第一批工程候选通常是：

1. Source Registry + provenance；
2. Knowledge Atom / Canonical Store；
3. Relation Assertion + Increment Report；
4. Hybrid Retrieval；
5. Human Review Queue；
6. Benchmark Runner；
7. Routing Decision Store。

这七项构成底座后，Wiki、Tutor、Skill Mining、Agent Research 和产品 UI 才有稳定对象可依赖。

---

# 18. 验收

任何候选软件能力必须回答：

1. 它解决哪个稳定问题？
2. 为什么 Search/Prompt/Skill/Workflow/现成工具不够？
3. 输入输出对象是什么？
4. 需要哪些长期状态？
5. 失败如何发现？
6. 谁负责人工审核？
7. 如何回归测试？
8. 什么真实指标证明值得继续工程化？

不能回答这些问题时，不应因为“AI 原生”而提前产品化。
