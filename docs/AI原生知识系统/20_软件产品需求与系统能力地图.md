# 软件产品需求与系统能力地图

> 本文件不预设必须做一个“大而全知识软件”。它从 `01_需求宇宙.md` 的 `P-L1 / P-L2` 问题空间反推系统需要具备的通用能力，再判断哪些能力值得做成功能、Workflow、Agent 或长期软件产品。

核心顺序：

> **Problem → Capability → Validation → Implementation → Productization**

而不是：

> 技术名词 → 找场景证明它有用。

---

# 一、先补齐真正的上游能力

过去的能力地图主要从 Source Inventory、Atom、Canonical 开始，这对于知识工程底座合理，但仍然偏后台。

新的能力地图必须先覆盖用户问题链：

```text
现实问题
→ 问题澄清
→ 知识需求识别
→ 研究与资料策略
→ 多来源综合
→ 方案 / 决策支持
→ 学习 / 人机分工
→ 行动与验证
```

然后才调用资料、知识对象、证据和检索等后台能力。

# 三、P：用户问题与知识任务能力

## CAP-P01 用户需求澄清
解决原始需求模糊、多个问题混杂、用户表达与专业问题不一致。主要对应 `P-L1-01`。

## CAP-P02 问题框定与范围控制
解决范围过大/过小、表面问题与根因不同、成功标准不清。输出 problem statement、scope、assumptions、success criteria、out-of-scope。

## CAP-P03 问题分解与任务结构化
将复杂问题拆成子问题、决策点、依赖、风险问题、可并行研究项和人工关口。

## CAP-P04 知识需求推导
回答“为了完成当前任务究竟需要知道什么”，输出核心知识需求、前置知识、数据/方法/案例/证据需求和所需深度。主要对应 `P-L1-02`。

## CAP-P05 已知 / 未知 / 误解诊断
区分已掌握、知道但不会用、完全未知、错误理解、缺少前置和可由 AI/工具替代。

## CAP-P06 研究问题与搜索策略生成
决定查什么、去哪里查、需要什么来源、何时停止扩展查询。对应 `P-L1-03`、`P-L1-17`。

## CAP-P07 资料选择与阅读优先级
根据当前问题相关性、来源质量、预期增量、时间成本和证据缺口决定处理顺序。对应 `P-L1-04`。

## CAP-P08 多来源综合与知识压缩
合并重复、保留条件边界、发现增量、保留冲突、追踪证据、发现缺口、形成高密度结构。对应 `P-L1-05 ~ P-L1-11`。

## CAP-P09 方案形成与比较
形成候选方案、适用条件、预期收益、成本、风险、证据、不确定性和验证方法。

## CAP-P10 决策支持
回答当前选什么、为什么、什么变化会改变选择、哪些未知仍可能翻转决策。对应 `P-L1-12`、`P-L1-14`。

## CAP-P11 知识到行动转化
把原理、方法、方案转成任务、步骤、判断条件、检查点、人工关口和验收标准。对应 `P-L1-14`。

## CAP-P12 结果验证与新缺口发现
判断是否解决原问题、哪些假设被验证/推翻、还缺什么、是否继续研究。对应 `P-L1-17`、`P-L1-18`。

# 四、A-M 后台与支撑能力

## A 资料盘点与进入
- CAP-A01 Source Inventory：资料身份、版本、格式和处理状态。
- CAP-A02 Parsing & Structural Normalization：解析并保留原始定位。
- CAP-A03 Corpus Quality Diagnostics：识别 OCR、乱码、重复页、广告污染、结构异常等。

# 五、问题 → 能力映射原则

不能采用：

> 一个 P-L2 → 一个功能。

应该寻找可以同时解决多个问题的通用能力。

例如：

```text
P-L2-05-01 相同原则反复出现
P-L2-05-02 同义改写
P-L2-05-04 相同原理换案例
P-L2-06-09 有效细化
        ↓
共享能力：
Canonical Resolution
+ Relation Adjudication
+ Increment Decision
```

因此问题宇宙可以很大，而能力层必须持续压缩复用。

---

# 六、问题到产品的正式追踪结构

```text
Requirement Pattern
→ P-L1 / P-L2
→ Capability
→ Benchmark
→ Implementation
→ Product Feature（若必要）
→ User Outcome
```

任何功能进入产品路线前，应能回答：

- 对应哪个 P-L2；
- 为什么这个问题重要；
- 是否有更简单的解决方式；
- 能力是否可复用；
- Benchmark 是否证明有效；
- 是否真正改善用户结果。

---

# 七、软件化不是最高级路线

一个能力更值得软件化，通常同时出现：高频重复、规模不可人工处理、长期状态、多用户、多角色、复杂权限审计、UI 价值、稳定 API、长期自动运行、SLA/回归和明确业务闭环。

若需求低频、一次性、尚未稳定，优先：

> 文档 / Search / Prompt / Script / Skill / Workflow / Existing Tool。

---

# 八、产品化阶段

## P0 文档与协议
当前阶段：问题语义、能力边界、Benchmark 稳定。

## P1 Research Prototype
优先实现用户问题到知识结果的最小纵向切片：

```text
Problem
→ Knowledge Need
→ Retrieval / Sources
→ Synthesis
→ Evidence / Increment
→ Answer / Decision Support
→ Validation
```

后台按需加入 Atom / Canonical / Relation。

## P2 Workbench
加入问题工作台、Review Queue、搜索、Canonical 浏览、证据/冲突、知识差额和 Benchmark。

## P3 Automation / Agentic Research
基础模型和评测可信后，再增加主动监测、研究和低风险自动更新。

## P4 Product
只有真实用户、高频需求、权限/状态/UI/业务闭环被验证后，才进入完整产品工程。

---

# 九、第一批工程候选重新排序

不再默认先建设“大一统知识底座”。第一批候选应围绕一个真实纵向闭环组合：

1. Problem / Requirement Workspace；
2. Knowledge Need & Gap；
3. Retrieval + Source Trace；
4. Multi-source Synthesis；
5. Evidence / Conflict / Increment；
6. Decision / Learning Route；
7. Result Validation；
8. 必要的 Source / Canonical / Relation Store；
9. Human Review；
10. Benchmark Runner。

具体最小组合必须由首批目标场景和 Synthetic Benchmark 决定。

---

# 十、验收

任何候选系统能力都必须回答：

1. 它解决哪个 `P-L1 / P-L2` 问题？
2. 该问题来自什么真实 Requirement Pattern？
3. 它是在帮助用户解决问题，还是只优化后台工程？
4. 能否复用解决多个问题？
5. 为什么更简单的方案不够？
6. 输入输出是什么？
7. 失败如何发现？
8. Benchmark 怎样证明有效？
9. 最终是否改善用户理解、决策、学习或行动结果？
10. 什么证据证明值得软件化？

> **如果一个功能找不到上游问题 ID，也说不清对用户结果的影响，就不应进入核心产品路线。**
