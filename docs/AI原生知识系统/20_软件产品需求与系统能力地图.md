# 软件产品需求与系统能力地图

> 本文件不预设必须做一个“大而全知识软件”。它从 `01A → 01B → 01` 的用户问题链反推系统需要具备的通用能力，再判断哪些能力值得进入实现或产品化。

核心顺序：

> **Problem → Capability → Validation → Implementation → Productization**

而不是：

> 技术名词 → 找场景证明它有用。

特别注意：

> Search、RAG、Skill、Workflow、Agent、Software 的选择已经完全退出 P-L1 / P-L2；本文件与 `19` 才进入 Capability / Implementation 世界。

---

## 一、先覆盖真正的上游问题

```text
真实目标 / 用户原话
→ SUP
→ P-L1 / P-L2
→ 问题澄清
→ 知识需求
→ 研究与资料策略
→ 综合与判断
→ 学习 / 委托 / 监督边界
→ 决策与行动
→ 结果与变化反馈
```

然后才调用资料、知识对象、检索、工作流等后台能力。

### 1.1 Capability 的准入条件

一个候选能力要进入正式能力地图，至少应满足：

1. 能向上追溯到一个或多个 SUP / P-L2；
2. 描述“系统需要具备什么通用能力”，而不是预先规定某一种技术实现；
3. 能说明用户结果怎样改善；
4. 能定义验证方式或失败结果；
5. 尽量复用多个问题，而不是一个 P-L2 机械生成一个功能；
6. 不把模型、数据库、RAG、Agent 等实现名词伪装成能力；
7. 如果已有成熟工具或人工流程可满足，不默认必须软件化。

## 三、P：用户问题与知识任务能力

### CAP-P01 用户需求澄清

解决原始需求模糊、多个问题混杂、目标不明确。主要对应 `P-L1-01`。

### CAP-P02 问题框定与范围控制

解决范围过大/过小、表面问题与根因不同、成功标准不清。主要对应 `P-L1-01`。

### CAP-P03 问题分解与任务结构化

把复杂问题拆成子问题、决策点、依赖、风险问题和可并行研究项。

### CAP-P04 知识需求推导

回答“为了完成当前任务究竟需要知道什么”，主要对应 `P-L1-02`。

### CAP-P05 已知 / 未知 / 误解诊断

区分已掌握、部分理解、误解、未知、缺少前置，以及哪些无需本人深学。主要对应 `P-L1-02`、`P-L1-13`、`P-L1-15`。

### CAP-P06 研究问题与搜索策略生成

决定查什么、去哪里查、需要什么来源；允许信息需求随着新发现演化，而不是把最初查询永久冻结。对应 `P-L1-02`、`P-L1-03`。

### CAP-P07 资料选择与阅读优先级

根据当前问题相关性、来源质量、预期增量、时间成本决定处理顺序和深度。对应 `P-L1-04`、`P-L1-12`。

### CAP-P08 多来源综合与知识压缩

合并重复、保留条件边界、发现增量、保留冲突、追踪证据、形成高密度结构。主要对应 `P-L1-05 ~ P-L1-11`。

### CAP-P09 方案形成与比较

形成候选方案、适用条件、收益、成本、风险、证据、不确定性和验证方法。主要对应 `P-L1-08`、`P-L1-09`、`P-L1-12`、`P-L1-14`。

### CAP-P10 决策支持

回答当前选什么、为什么、什么变化会改变选择、哪些未知仍可能翻转决策。对应 `P-L1-12`、`P-L1-14`。

### CAP-P11 知识到行动转化

把原理、方法、方案转成任务、步骤、判断条件、检查点和验收标准。对应 `P-L1-14`。

### CAP-P12 结果验证、反馈与新缺口发现

判断是否解决原问题、实践反馈意味着什么、哪些旧判断需要重看、变化后产生了哪些新缺口。对应 `P-L1-17`，并与 `P-L1-01 / 02 / 14` 形成回路。

### CAP-P13 注意力预算、研究停止与重启

回答：

- 当前资料规模下还能投入多少人工注意力；
- 哪些材料只需粗筛，哪些值得深入；
- 什么时候继续搜索/阅读已经不再改变判断；
- 哪些关键未知仍阻止停止；
- 什么变化出现后应该重新启动研究。

主要对应 `P-L1-16`，并调用 `P-L1-04 / 06 / 12` 的判断结果。

### CAP-P14 委托、人工验收与责任边界支持

帮助用户判断：

- 哪些必须本人理解或掌握；
- 哪些可以随用随查；
- 哪些可以交给 AI、工具或专业服务；
- 委托以后本人至少需要保留什么验收能力；
- 哪些高风险、权限、隐私、版权或责任场景必须人工介入。

主要对应 `P-L1-15`，并与 `P-L1-13` 的人工能力状态和 `M` 的权限/审计能力关联。

## 四、A-M 后台与支撑能力

### A 资料盘点与进入

- CAP-A01 Source Inventory：资料身份、版本、格式和处理状态。
- CAP-A02 Parsing & Structural Normalization：解析并保留原始定位。
- CAP-A03 Corpus Quality Diagnostics：识别 OCR、乱码、重复页、广告污染、结构异常等。

### B 来源、版本与治理

- CAP-B01 Provenance Graph：追踪 Source → Fragment → Atom → Canonical → Output。
- CAP-B02 Version & Representation Resolver：区分修订、格式、OCR、并行版本和替代关系。
- CAP-B03 Access / License / Retention Policy：版权、隐私、权限、保留与审计。

### C 知识原子与标准知识

- CAP-C01 Knowledge Atom Extractor。
- CAP-C02 Canonical Resolver。
- CAP-C03 Terminology / Alias Manager。

### D 去重、增量与冲突

- CAP-D01 多阶段重复候选召回。
- CAP-D02 Proposition Relation Adjudication。
- CAP-D03 Knowledge Increment Report。
- CAP-D04 Saturation Analyzer。
- CAP-D05 Conflict Workbench。

### E 证据与可信度

- CAP-E01 Primary Source Tracing。
- CAP-E02 Evidence Independence Resolver。
- CAP-E03 Claim–Evidence Matrix。
- CAP-E04 Epistemic Status Review。

### F 主体与项目知识差额

- CAP-F01 Subject Knowledge Profile。
- CAP-F02 Project Knowledge Requirement Graph。
- CAP-F03 Knowledge Gap Report。

### G 价值、学习与委托路由

- CAP-G01 Multi-axis Value Workbench。
- CAP-G02 Learning vs Delegation Router。
- CAP-G03 Dynamic Route Recalculation。

### H 人工学习

- CAP-H01 Adaptive Learning Queue。
- CAP-H02 Evidence-aware Tutor。
- CAP-H03 Retrieval / Practice / Transfer Engine。

### I AI 知识消费接口

- CAP-I01 Retrieval API。
- CAP-I02 Minimal Sufficient Context Pack Builder：围绕当前任务组织足够但不过量的知识上下文。
- CAP-I03 Citation & Epistemic Contract。
- CAP-I04 Capability Registry。

> “AI 一次拿哪些、拿多少知识”在这里成为能力问题；上下文漏取、噪声过量、成本失控的错率和代价进入 `13 / 22`，不反向新增 P-L2。

### J 实现候选分析

- CAP-J01 Skill Candidate Analyzer。
- CAP-J02 Workflow Candidate Analyzer。
- CAP-J03 Agent Necessity Analyzer。
- CAP-J04 Software Candidate Analyzer。

> J 属于 Capability → Implementation 后段，不反向生成 P-L1。

### K 变化监测与主动研究

- CAP-K01 Freshness / Change Monitor。
- CAP-K02 Impact Propagation。
- CAP-K03 Unknown-Unknown Research Queue。

### L Benchmark、可观测与回归

- CAP-L01 Golden Set Manager。
- CAP-L02 Pipeline Observability。
- CAP-L03 Regression Runner。

### M 协作、权限与产品界面

- CAP-M01 Human Review Queue。
- CAP-M02 Explainable Decision Surface。
- CAP-M03 Role / Permission / Audit。

## 五、17 类 P-L1 → 能力族正式追踪表

| P-L1 | 主要能力 | 关键支撑能力 | 解决后的主要用户结果 |
| --- | --- | --- | --- |
| 01 用户需求与真实问题 | P01、P02、P03 | P12 | 不再高质量解决错误问题 |
| 02 知识需求识别 | P04、P05、P06 | F02、F03 | 知道当前真正缺什么、需要多深 |
| 03 来源发现与资料获取 | P06 | A01、E01 | 找到足以支持当前任务的候选来源 |
| 04 资料筛选与处理深度 | P07 | G01、D03 | 时间优先投入到最值得处理的资料 |

| 07 知识关系与结构 | P08 | C03、D02 | 从碎片形成可解释结构 |
| 08 冲突、条件与边界 | P08、P09 | D05、E03、E04 | 不强行消解真实冲突，知道何时成立 |
| 09 来源、证据与可信度 | P08、P09 | B01、E01～E04 | 重要判断可追溯、可校验、保留不确定性 |
| 10 时间、版本与失效 | P12 | B02、K01、K02 | 知道当前有效版本以及什么发生了变化 |
| 11 整理、综合与压缩 | P08 | B01、C、D、E、I03 | 高密度表达仍保留来源、边界和差异 |
| 12 主体价值与优先级 | P07、P09、P10 | G01 | 区分“正确”与“现在对我重要” |
| 13 理解、记忆、掌握与迁移 | P05 | H01～H03 | 从熟悉感走到可提取、判断、应用和迁移 |
| 14 知识到判断、决策与行动 | P09、P10、P11 | P12 | 知识能在真实任务中被调用、执行和调整 |
| 15 本人掌握、委托与监督边界 | P05、P14 | G02、G03、M01～M03 | AI 能帮忙但责任、验收和人工能力不丢失 |
| 16 规模、注意力与研究停止 | P13 | D03、D04、I02 | 海量资料下仍能控制注意力并知道何时够了 |
| 17 反馈、修正与长期再判断 | P12 | K01、K02、G03、L03 | 新结果和变化能触发正确的旧判断重查 |

### 5.1 这张表不意味着“一类问题对应一个模块”

同一能力可以服务多个 P-L1；同一 P-L1 也可能需要多个能力协同。

例如 `P-L1-06 知识增量` 同时需要：

```text
Canonical Resolution
+ Relation Adjudication
+ Evidence Independence
+ Increment Decision
```

因此能力层应该持续**压缩复用**，而不是跟着 183 个 P-L2 增长成 183 个产品功能。

## 六、旧候选问题如何进入能力层

对早期 `P-L2问题候选池` 中容易重新混入 Problem Space 的工程性候选，正式处理如下：

| 候选现象 | 正确承接 |
| --- | --- |
| 人看不懂大量知识原子 | P-L2 `11 / 13` + P08/H + 人工消费界面候选 |
| 人和 AI 不应使用完全相同的知识表达 | P-L2 保留用户后果；能力进入 P08/H/I，不新增“人机表示”P-L1 |
| AI 不知道一次应该拿哪些知识 | I01/I02 + Benchmark，不新增 P-L2 |
| AI 拿到知识太少/太多 | I02 + L，错误率/噪声/成本进入 13/22 |
| 海量资料不值得全部深加工 | P07/P13 + G01/D04；模型和存储成本进入工程评价 |
| 同一问题被反复发现 | P12 + 历史/状态能力候选；不恢复旧 P-L1-18 |
| Problem Graph / 问题状态机 | 只有在重复研究、依赖追踪等需求被验证后才作为能力/实现候选 |

## 七、问题 → 能力映射原则

不能采用：

> 一个 P-L2 → 一个功能。

应该寻找可以同时解决多个问题的通用能力。

例如：

```text
P-L2-05-01 相同原则反复出现
P-L2-05-02 同义改写
P-L2-05-04 相同原理换案例
P-L2-06-09 有效细化是否真增量
        ↓
Canonical Resolution
+ Relation Adjudication
+ Increment Decision
```

问题宇宙可以较大，能力层必须持续压缩复用。

## 八、问题到产品的正式追踪结构

```text
01A 用户原话
→ 01B SUP
→ 01 P-L1 / P-L2
→ Requirement Pattern（如适用）
→ Capability
→ Benchmark
→ Implementation（19）
→ Product Feature（若必要）
→ User Outcome
```

任何功能进入产品路线前，都应能回答：

- 对应哪个 SUP / P-L2；
- 为什么这个问题重要；
- 是否有更简单的解决方式；
- 能力能否复用；
- Benchmark 是否证明有效；
- 是否真正改善用户结果。

> **能力地图的目标不是“功能齐全”，而是让每个重要用户问题都有可验证、可复用、不过度工程化的承接方式。**
