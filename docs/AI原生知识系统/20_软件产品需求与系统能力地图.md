# 软件产品需求与系统能力地图

> 本文件不预设必须做一个“大而全知识软件”。它从 `01A → 01B → 01` 的用户问题链反推系统需要具备的通用能力，再判断哪些能力值得进入实现或产品化。

核心顺序：

> **Problem → Capability → Validation → Implementation → Productization**

而不是：

> 技术名词 → 找场景证明它有用。

特别注意：

> Search、RAG、Skill、Workflow、Agent、Software 的选择已经完全退出 P-L1 / P-L2；本文件与 `19` 才进入 Capability / Implementation 世界。

---

# 一、先覆盖真正的上游问题

```text
真实目标 / 用户原话
→ SUP
→ P-L1 / P-L2
→ 问题澄清
→ 知识需求
→ 研究与资料策略
→ 综合与判断
→ 学习 / 委托 / 监督边界
→ 决策与行动
→ 结果与变化反馈
```

然后才调用资料、知识对象、检索、工作流等后台能力。

# 三、P：用户问题与知识任务能力

## CAP-P01 用户需求澄清

解决原始需求模糊、多个问题混杂、目标不明确。主要对应 `P-L1-01`。

## CAP-P02 问题框定与范围控制

解决范围过大/过小、表面问题与根因不同、成功标准不清。主要对应 `P-L1-01`。

## CAP-P03 问题分解与任务结构化

把复杂问题拆成子问题、决策点、依赖、风险问题和可并行研究项。

## CAP-P04 知识需求推导

回答“为了完成当前任务究竟需要知道什么”，主要对应 `P-L1-02`。

## CAP-P05 已知 / 未知 / 误解诊断

区分已掌握、部分理解、误解、未知、缺少前置，以及哪些无需本人深学。主要对应 `P-L1-02`、`P-L1-13`、`P-L1-15`。

## CAP-P06 研究问题与搜索策略生成

决定查什么、去哪里查、需要什么来源、什么时候可以停止扩展查询。对应 `P-L1-03`、`P-L1-16`。

## CAP-P07 资料选择与阅读优先级

根据当前问题相关性、来源质量、预期增量、时间成本决定处理顺序和深度。对应 `P-L1-04`。

## CAP-P08 多来源综合与知识压缩

合并重复、保留条件边界、发现增量、保留冲突、追踪证据、形成高密度结构。对应 `P-L1-05 ~ P-L1-11`。

## CAP-P09 方案形成与比较

形成候选方案、适用条件、收益、成本、风险、证据、不确定性和验证方法。主要对应 `P-L1-08`、`P-L1-09`、`P-L1-12`、`P-L1-14`。

## CAP-P10 决策支持

回答当前选什么、为什么、什么变化会改变选择、哪些未知仍可能翻转决策。对应 `P-L1-12`、`P-L1-14`。

## CAP-P11 知识到行动转化

把原理、方法、方案转成任务、步骤、判断条件、检查点和验收标准。对应 `P-L1-14`。

## CAP-P12 结果验证、反馈与新缺口发现

判断是否解决原问题、实践反馈意味着什么、什么变化需要重新研究、什么时候停止或重启。对应 `P-L1-16`、`P-L1-17`。

# 四、A-M 后台与支撑能力

- CAP-A03 Corpus Quality Diagnostics：识别 OCR、乱码、重复页、广告污染、结构异常等。

# 五、问题 → 能力映射原则

不能采用：

> 一个 P-L2 → 一个功能。

应该寻找可以同时解决多个问题的通用能力。

例如：

```text
P-L2-05-01 相同原则反复出现
P-L2-05-02 同义改写
P-L2-05-04 相同原理换案例
P-L2-06-09 有效细化
        ↓
Canonical Resolution
+ Relation Adjudication
+ Increment Decision
```

问题宇宙可以较大，能力层必须持续压缩复用。

# 六、问题到产品的正式追踪结构

```text
01A 用户原话
→ 01B SUP
→ 01 P-L1 / P-L2
→ Requirement Pattern（如适用）
→ Capability
→ Benchmark
→ Implementation（19）
→ Product Feature（若必要）
→ User Outcome
```

任何功能进入产品路线前，都应能回答：

- 对应哪个 SUP / P-L2；
- 为什么这个问题重要；
- 是否有更简单的解决方式；
- 能力能否复用；
- Benchmark 是否证明有效；
- 是否真正改善用户结果。

---

# 七、软件化不是最高级路线

只有在高频重复、规模不可人工处理、长期状态、多用户、多角色、权限审计、UI 价值、稳定接口和明确业务闭环等条件被证明后，Software 才是合理候选。

低频、一次性、尚未稳定的任务，不应为了“产品化”提前制造复杂系统。

---

# 八、产品化阶段

## P0 文档与协议

稳定问题语义、能力边界和 Benchmark。

## P1 Research Prototype

验证最小纵向闭环：

```text
Problem
→ Knowledge Need
→ Sources
→ Synthesis
→ Evidence / Increment
→ Answer / Decision Support
→ Validation
```

## P2 Workbench

在真实高频需求出现后增加工作台、审阅、搜索、证据、知识差额和 Benchmark。

## P3 Automation / Agentic Research

只有基础能力和评测可信后，再增加主动监测与低风险自动更新。

## P4 Product

只有真实用户、高频需求、长期状态和业务闭环得到验证后，才进入完整产品工程。

---

# 九、验收

任何候选系统能力都必须回答：

1. 它解决哪个 SUP / P-L1 / P-L2？
2. 它是在帮助用户解决问题，还是只优化后台工程？
3. 能否复用解决多个问题？
4. 为什么更简单的方案不够？
5. 失败如何发现？
6. Benchmark 怎样证明有效？
7. 什么证据证明值得进入实现或软件化？

> **实现方式没有 P-L1 编号。P-L1/P-L2 只描述问题。**
