# 需求宇宙：人话问题地图、稳定问题身份与 P-L1 / P-L2 事实源

> 状态：正式事实源 / Taxonomy Stabilization V2
>
> 本文件回答两个问题：
>
> 1. 普通用户到底会遇到什么真实困难、为什么痛、解决后应该变成什么状态；
> 2. 这些真实困难怎样收敛成稳定 P-L1 / P-L2，并用多阶段、多场景、多关联标签描述，而不是按阶段重复造问题。
>
> `01A` 承载用户旅程、真实场景和用户原话；`01B` 承载标准用户问题（SUP）及其主映射/关联映射；本文件是专业问题身份、主归属、边界与审计状态的正式事实源。
>
> Search、RAG、Skill、Workflow、Agent、Software 是后续实现载体；系统 false merge、路由错误、模型成本等是 Benchmark / System Error，不属于 P-L1 / P-L2。

---

## 一、先看结论：本轮从“编号分类”改成“稳定问题身份 + 多维归属”

正式采用：

```text
一个稳定问题身份
+ 一个主归属 P-L1
+ 多个关联 P-L1
+ 多个用户旅程阶段
+ 多个场景 / 规模标签
+ 可选的问题关系
```

这里必须区分：

- **问题是什么**：稳定 P-L2 身份；
- **什么时候出现**：`journey_stages[]`；
- **在什么环境出现**：`scenario_tags[] / scale_tags[]`；
- **主要是哪种机制失败**：`primary_p_l1`；
- **还和哪些问题空间有关**：`related_p_l1[]`；
- **与其他问题是什么关系**：导致、被导致、阻塞、特殊情况、重叠、变化后重新触发。

禁止因为同一个问题出现在多个阶段，就复制多个 P-L2。

---

## 二、P-L2 准入与净化 Gate

一个正式 P-L2 至少满足：

1. 是稳定、可复现的困难、失败、冲突、缺口或判断不确定性；
2. 不依赖某个具体技术实现才成立；
3. 能说清不解决会阻碍什么用户结果；
4. 与同级邻居能给出边界；
5. 与相邻 P-L1 的主归属能解释；
6. 至少有用户表达、SUP 或合成反例支持；
7. 解决后存在可观察改善。

以下对象不能单独占 P-L2：

- 掌握深度状态：知道、理解、主动提取、判断、应用、熟练；
- 增量类型：新概念、新机制、新步骤、新案例、新证据；
- 关系类型：因果、前置、部分—整体、替代、补充；
- 场景/规模/主体：单书、多书、海量、AI 参与、团队；
- 实现：RAG、Skill、Workflow、Agent、Graph DB；
- 系统错误：false merge、citation mismatch、模型成本。

它们应该成为字段、标签、原因或测试条件，而不是问题身份。

### 3.1 P-L1 当前结论

本轮仍然**不新增、不合并 17 个 P-L1**。主要原因：

- 01 / 02 / 03 分别是“真正要解决什么 / 需要知道什么 / 去哪里找”；
- 05 / 06 分别是“是不是同一个 / 真正新增什么”；
- 07 / 11 / 13 分别是“知识关系 / 外部整理 / 人的内部理解”；
- 09 / 10 / 17 分别是“证据 / 时间版本 / 变化后的再判断”；
- 13 / 14 分别是“能力形成 / 当前现实行动”；
- 04 / 16 分别是“局部资料投入 / 组合规模与停止”；
- 15 是 AI 原生环境下稳定的人机分工、监督与责任问题。

团队/组织共同学习、无障碍与特殊认知需求仍然是 Missing Candidate，不为了形式完整强行新增 P-L1。

## 四、P-L2 人话问题地图：先人话，后编号与机器字段

阅读规则：

- 每一行先看前五列，先判断“这是不是一个真实问题”；
- 后面的归属、阶段、标签和编号只用于专业维护；
- `KEEP`：保留稳定问题；
- `REWRITE`：保留身份但改成人话/机制表达；
- `MERGE`：多个旧 ID 实际是同一问题的不同说法；
- `REMOVE FROM P-L2`：旧条目其实是状态、类型、关系或场景，降为字段/标签；
- 本轮未发现必须立即新增 P-L1 才能解决的 `MOVE`；若后续真实数据证明根因属于别处，再调整主归属；
- `SPLIT` 只在一个条目确有多个不同根因时使用，本轮优先通过改写和已有邻居吸收，避免无必要增号。

## 六、多阶段、多场景、多关联正式模型

### 6.1 主归属

`primary_p_l1` 回答：

> 这个问题最主要是哪一种失败机制？

例如“每一条都看懂，但脑子里没有整体模型”：

- 主归属：13（人的内部理解失败）；
- 关联：07（知识关系）、11（外部整理）；
- 如果外部关系和整理都正确，用户仍不能形成内部模型，13 仍然成立。

### 6.2 用户旅程阶段

`journey_stages[]` 回答“什么时候出现”，不是“问题是什么”。

典型例子：

`P-L2-13-13 长任务/长期学习中断后上下文恢复困难`

可同时出现：

- J07 阅读地图与重新进入；
- J08 阅读过程；
- J17 行动与项目推进；
- J18 长期调用。

仍然只有一个稳定问题身份。

### 6.3 场景与规模标签

建议值包括：

- 单书、多书、领域、海量知识；
- 陌生领域、项目驱动学习、随用随查；
- AI 参与、长期积累、高风险判断；
- 团队协作（候选维度，不自动生成 P-L1）。

场景只描述环境，不自动生成新问题身份。

### 6.4 问题关系

允许的问题间关系：

- `causes`：导致；
- `caused_by`：由……导致；
- `blocks`：阻塞；
- `special_case_of`：特殊情况；
- `overlaps_with`：部分重叠；
- `retriggered_by`：变化后重新触发。

关系本身不能成为 P-L2。

## 十一、需求属性维度

P-L1 / P-L2 回答“会遇到什么问题”。具体 Requirement 继续通过属性描述：

- 优先程度：必须、重要、一般、低优先、暂缓、忽略；
- 周期：一次性、短期、阶段持续、长期、周期复查；

## 十二、当前阶段正式结论

1. 正式 P-L1 仍为 17 类；
2. 旧 P-L2 从 183 个身份收敛为 **151 个 canonical P-L2 + 32 个迁移别名/降级项**；
3. 最大净化发生在重复变体、增量类型、关系类型、掌握深度状态和阶段特定重复；
4. 一个问题可以属于多个阶段、场景和关联空间，但只能有一个稳定身份和一个主 P-L1；
5. 机器注册表只能建立在人话问题、后果、需求和理想结果之后；
6. 学习动机/自我调节、行为维持、团队协作、无障碍仍继续审计，不强行扩类；
7. 后续能力继续从多个 canonical P-L2 聚合推导，禁止“一 P-L2 一功能”。

正式链路：

```text
01A 用户世界
→ 01B 标准用户问题 SUP
→ 01 canonical P-L1 / P-L2（本文件）
→ 20 Capability
→ 13 / 21 / 22 Validation
→ 19 Implementation
→ User Outcome
```
