# AI 人机协作高频问题现象宇宙

> 状态：v0.1｜问题空间基线  
> 定位：AI 人机协作问题诊断知识库的“现象层”  
> 目标读者：AI 重度用户、产品/需求人员、研究人员、Prompt/Context/Agent/Workflow 设计者  
> 注意：本文件优先记录“用户能感知到什么不对劲”，暂不把 Prompt、Skill、Schema、Agent 等实现方案混入现象层。

---

## 0. 核心结论

“AI 回答不好用”通常不是一个问题，而是一组不同层级问题在用户侧形成的表面现象。

本文件首先回答：

> **人在与 AI 协作时，通常会看到哪些高频异常、低质量表现、失败体验和不符合预期的行为？**

它不是 Prompt 技巧清单，也不是最终根因分类。

后续正确链路应是：

```text
用户感知现象
→ 专业问题类型
→ 可能根因
→ 所属任务阶段
→ 对应专业领域
→ 解决机制
→ 实现方式
→ 验证
```

不能直接变成：

```text
发现一个现象
→ 往 Prompt 再增加一条规则
```

# 1. 本文件在完整体系中的位置

建议完整体系至少区分两部分。

## 1.1 专业知识骨架

```text
以人为中心的问题发现
→ 问题定义与需求工程
→ 人机交互与认知设计
→ 研究、推理与决策
→ AI 解决方案与执行工程
→ 质量评价与风险控制
→ 长期运行与持续改进
```

## 1.2 横向问题诊断知识库

```text
现象
→ 问题类型
→ 根因
→ 机制
→ 规则
→ 案例与评测
```

“高频问题现象宇宙”属于第二部分的第一个入口。

它的价值不是创造一套脱离主流专业体系的新理论，而是把用户实际会遇到的“不对劲”系统化记录下来，后续再映射到需求工程、人机交互、设计科学、决策科学、信息架构、软件工程、AI/LLM/Agent 工程、质量工程等成熟知识体系。

---

# 2. 现象层的边界

现象层只记录：

> **用户看见了什么？**

例如：

- 回答太长；
- 一开始就进入实现细节；
- 没有给结论；
- 一直追问；
- 没有判断；
- 已经调用工具，却没有真正完成任务；
- 用户纠正后下一轮又犯同样问题。

现象层暂时不直接回答：

- 为什么发生；
- 应该采用哪个 Prompt；
- 是否应该建立 Workflow；
- 是否需要 Agent；
- Schema 如何设计；
- 代码如何实现。

同一现象可能来自多个根因；同一根因也可能制造多个现象。

---

# 3. 高频现象总览

为了便于人工阅读，当前先按 11 个“用户可感知失效域”组织。它们是导航分类，不代表已经存在一套同名的主流学术标准。

| 编号 | 高频现象域 | 用户最典型的感觉 |
|---|---|---|
| Q01 | 目标、意图与问题理解 | “你回答的不是我真正想解决的问题。” |
| Q02 | 澄清、共同理解与交互协商 | “该问的不问，不该问的一直问。” |
| Q03 | 阶段、状态与流程错位 | “现在明明还在想方向，你怎么已经开始实施了？” |
| Q04 | 研究、证据与事实可靠性 | “这些信息是真的吗？是不是旧的？依据在哪里？” |
| Q05 | 推理、方案与决策 | “说了很多方案，但还是不知道该选哪个。” |
| Q06 | 回答内容、优先级、粒度与结构 | “太长、太细、没重点，真正有用的信息很少。” |
| Q07 | 计划、执行、工具与 Agent | “分析很多却没推进，或者做了一堆动作但没达成目标。” |
| Q08 | 验证、验收、停止与完成判断 | “看起来做完了，但我不知道到底有没有真的解决。” |
| Q09 | 上下文、记忆、多轮与长期状态 | “前面说过的又忘了，旧结论还在干扰新方向。” |
| Q10 | 人机角色、控制、信任与个性化 | “你到底应该自己推进，还是应该先让我决定？” |
| Q11 | 指令、机制选择与复杂度失控 | “系统越来越专业、越来越复杂，但反而越来越难用。” |

# 4. Q01 目标、意图与问题理解现象

用户通常会感知到：

- 回答了字面问题，却没有解决真实问题；
- 用户提出一个办法，AI 把办法误认为最终需求；
- 用户只是提出一个猜想，AI 把它当成已经确认的事实；
- 把症状当成真正的问题；
- 问题范围被放得过大；
- 问题范围被缩得过小；
- 用户要“判断”，AI 给成“知识科普”；
- 用户要“方案”，AI 只给背景解释；
- 用户要“实际执行”，AI 一直停留在分析；
- 用户只是想探索可能性，AI 却把方向直接锁死；
- AI 没有识别用户真正想获得的是答案、判断、选择、方案还是行动；
- 用户的成功标准没有被识别；
- 明显错误的前提没有被指出；
- 用户随口举的例子反过来限制了整个答案；
- AI 为了迎合用户，忽略了反证或替代解释；
- 用户觉得“每句话都对，但合起来不是我要解决的事情”。

---

# 5. Q02 澄清、共同理解与交互协商现象

- 关键信息缺失时 AI 不追问，直接猜；
- 信息已经足够时仍机械追问；
- 一次性要求用户回答十几个问题；
- 用户已经提供过的信息再次询问；
- 次要信息缺失也阻塞整个任务；
- 可以合理假设的低风险信息也要求用户确认；
- 高风险信息却未经确认直接假设；
- AI 提的问题太专业，用户不知道怎么回答；
- AI 把信息收集负担重新全部交给用户；
- 用户说“不是这个意思”后，AI 只是换一种表述继续原方向；
- 用户纠正一个概念后，后续回答仍使用旧理解；
- AI 没有复述关键理解，双方一直在不同问题上讨论；
- 同一术语双方含义不同，却长时间没有发现；
- AI 不知道什么时候应该主动推进；
- AI 不知道什么时候必须把决定交还给用户；
- 用户不知道 AI 当前究竟理解成了什么。

---

# 6. Q03 阶段、状态与流程错位现象

这是大量下游问题的共同来源。

- 还在理解问题，AI 已经开始给最终方案；
- 还在探索方向，AI 已经开始写实施步骤；
- 需求尚未确认，AI 已经开始设计架构；
- 需求尚未稳定，Workflow、Skill、Schema、Agent、数据库、目录结构等工程描述已经占据大部分回答；
- 方案还没有比较，AI 已默认其中一个方案成立；
- 用户只想先看地图，AI 直接进入教程；
- 决策阶段仍不断添加更多可能性，迟迟不收敛；
- 执行阶段重新回到大篇幅理论研究；
- 调试阶段重新设计整个系统；
- 验收阶段继续添加新功能；
- 复盘阶段把项目重新做一遍；
- 用户已经确认过方向，AI 仍反复重新论证；
- 用户已经改变方向，AI 继续沿旧路线执行；
- AI 不知道当前已经完成哪些工作；
- AI 不知道当前仍有哪些未解决问题；
- AI 不知道什么时候应该进入下一阶段；
- 用户无法看出当前对话到底处于“探索、决定、计划、执行、验证”中的哪一阶段。

## 6.1 特别高价值现象：需求描述被工程描述淹没

典型用户描述：

> “需求还没有想清楚，回答里 70%—80% 已经是 Workflow、Skill、Schema、Agent、代码、文件结构，我反而无法判断真正的需求和方案是不是正确。”

暂定用户现象名称：

> **工程描述淹没需求。**

后续问题分类阶段需要进一步判断它是否涉及：

- 需求与实现层混淆；
- 过早方案化；
- 阶段错位；
- 方案锚定；
- 设计固着；
- 输出优先级失配。

注意：这些属于后续专业诊断，不在现象层直接下最终结论。

---

# 7. Q04 研究、证据与事实可靠性现象

- 需要最新信息时 AI 仍凭旧知识回答；
- 不需要研究的问题却进行了大量搜索；
- 搜索结果很多，却没有形成判断；
- 引用了来源，但来源并不支持对应结论；
- 只给链接，不解释证据和结论之间的关系；
- 使用低质量来源替代高质量一手资料；
- 没有判断资料是否过时；
- 多个来源互相冲突，却直接挑一个结论；
- 事实、推断、猜测和建议混在一起；
- 不确定的信息被写得像确定事实；
- AI 不知道时没有明确表现出“不知道”；
- 搜索变成资料堆积；
- 只寻找支持已有观点的证据；
- 忽略反例；
- 资料很多，但与用户当前决策几乎无关；
- 用户看完后仍然不知道“所以呢”。

---

# 8. Q05 推理、方案与决策现象

- 第一想到的方案直接成为最终方案；
- 没有真正探索方案空间；
- 看似给了十个方案，本质只是同一种方法换名称；
- 没有替代方案；
- 没有考虑“不做”；
- 没有考虑更低成本、更轻量的方案；
- 没有识别方案之间可以组合；
- 方案很多，但没有指出真正关键杠杆；
- 给出行业惯例，却没有针对当前场景；
- 没有明确选择标准；
- 给出大量选择但拒绝作出推荐；
- 永远回答“取决于”；
- 用户需要决策支持，却只得到信息罗列；
- 所有评价维度权重相同；
- 关键风险和次要风险混在一起；
- 没有考虑机会成本；
- 没有区分可逆和不可逆决策；
- 没有说明真正决定结果的关键变量；
- 用户已经提出某方案后，AI 过度迎合；
- 分析越来越多，但决策空间没有缩小。

---

# 9. Q06 回答内容、优先级、粒度与结构现象

这是“回答质量控制”的核心子宇宙。

## 9.1 内容选择

- 回答包含大量正确但当前无用的信息；
- 核心问题只占回答很小部分；
- 背景知识比真正解决方案更多；
- 用户已经知道的内容被重复解释；
- 为了显得完整加入大量低价值内容；
- 内容很多，但没有改变用户判断。

## 9.2 信息优先级

- 没有先给结论；
- 最重要的信息埋在最后；
- 关键风险和次要风险获得相同篇幅；
- 所有信息看起来同等重要；
- “必须知道”和“以后可以知道”没有区分；
- 用户看了很久才知道真正推荐什么；
- 有决策价值的信息被背景和术语淹没。

## 9.3 输出粒度

- 用户只需要结论，AI 给到操作参数；
- 用户只需要方向地图，AI 给成详细教程；
- 用户需要具体步骤，AI 只给抽象原则；
- 项目第一轮就进入三级、四级、五级细节；
- 复杂问题被过度简化；
- 简单问题被人为复杂化；
- 每一点都继续无限拆分；
- 用户难以判断当前应该在哪一层停止。

可用于描述粒度的工程化层次示例：

```text
结论
→ 框架
→ 模块
→ 方法
→ 步骤
→ 参数
→ 操作细节
```

## 9.4 展开深度

- 第一轮信息量过大；
- 用户还没有选择方向，所有方向已经被全部展开；
- 某个次要点被展开成回答主体；
- 当前只需建立地图，却把所有节点都展开；
- 用户已经需要执行，AI 仍保持过度抽象。

## 9.5 内容顺序

- 先讲背景，最后才给答案；
- 先讲实现，再说明需求；
- 先讲大量风险，最后才说明主方案；
- 原因、结论、案例、步骤交叉混杂；
- 读者必须自己重新排列信息才能理解。

## 9.6 信息密度

- 字很多，但有效新信息很少；
- 大量重复表达；
- 大量正确废话；
- 专业术语很多，但没有提高判断质量；
- 用户读完没有更接近决策或行动；
- 重要变量、因果关系、判断依据密度过低。

本项目暂定“高知识密度”为工程化工作概念：

> **单位用户认知成本中，能够改变判断、缩小决策空间、暴露关键变量或推动行动的信息含量。**

它不等于“字数少”，也不等于“专业术语多”。

## 9.7 结构与格式

- 标题过多；
- 每一句都被拆成独立段落；
- 列表滥用；
- 表格滥用；
- 表格看起来专业但比普通文字更难读；
- 同一层级内容抽象程度不同；
- Markdown 层级过深；
- 大量重复总结；
- 为了视觉整齐牺牲语义关系；
- 结构漂亮但用户无法形成心理模型。

## 9.8 认知负荷

- 一次给出十几个方案；
- 用户必须理解大量术语才能继续；
- 用户不知道下一步应该做什么；
- AI 把方案比较工作重新交还给用户；
- 用户需要在多个回答之间来回寻找关键条件；
- 信息组织顺序不符合人的决策顺序；
- 回答正确，但阅读成本明显高于所得价值。

## 9.9 停止与下一步接口

- 回答不断继续补充；
- 每个小点都附带更多扩展；
- 用户只问当前阶段，AI 把后续阶段也一次性全部展开；
- 没有明确当前回答到什么程度已经足够；
- 当前回答没有自然进入下一步的接口；
- 用户只能用“继续”来推动，而不知道下一步具体应该推进什么。

# 10. Q07 计划、执行、工具与 Agent 现象

## 10.1 计划

- 没有计划直接执行复杂任务；
- 简单任务却先生成一套庞大计划；
- 计划只有活动，没有交付物；
- 计划过于宏观，不能实际执行；
- 计划过细，维护计划本身成为主要工作；
- 没有任务依赖关系；
- 没有关键路径；
- 没有验收标准；
- 没有失败后的处理方式；
- 计划与最终目标脱节。

## 10.2 执行

- 分析很多但迟迟不执行；
- 未确认关键方案就直接执行；
- 执行过程中偏离原目标；
- 重复执行已完成工作；
- 中间失败后忽略错误继续；
- 长任务执行过程中目标发生漂移；
- AI 声称要做很多事，实际只完成其中一部分；
- 局部动作很多，但没有形成最终产出。

## 10.3 工具

- 本可直接回答却调用大量工具；
- 应查询工具却凭记忆回答；
- 选择了错误工具；
- 工具返回结果但 AI 没有分析；
- 工具调用成功即被当作任务成功；
- 工具权限被误认为实际已经完成业务动作；
- 获取了文件但没有真正阅读关键内容；
- 搜索了仓库但没有核实当前分支或版本；
- 工具异常后给出看似正常的最终回答。

## 10.4 Agent / 自动化

- 简单任务被 Agent 化；
- 多 Agent 数量增加但质量没有增加；
- Agent 反复循环；
- Agent 不知道什么时候结束；
- 自动化范围超过用户授权；
- 关键不可逆动作没有人工关口；
- Agent 执行路径很复杂，但用户无法知道当前状态；
- 工作流复杂程度超过任务本身。

---

# 11. Q08 验证、验收、停止与完成判断现象

- AI 生成结果后完全不检查；
- 只检查 Markdown、JSON 等格式，不检查内容；
- 只检查“有没有文件”，不检查文件是否解决问题；
- 只检查“工具有没有成功”，不检查业务目标；
- 子任务完成被误判为整体完成；
- 测试通过却没有满足用户真实需求；
- 没有预先定义什么叫完成；
- 验收标准和用户目标无关；
- 没有寻找反例；
- 没有遗漏检查；
- 没有事实核验；
- AI 用生成答案时的同一思路直接自评，明显存在盲区；
- 每次评价又产生新的改进点；
- “继续完善”变成无限循环；
- 95 分之后仍为了接近 100 分持续复杂化；
- 没有最低可接受质量；
- 没有边际收益判断；
- 不知道什么时候应该进入下一阶段；
- 用户最终仍无法判断“到底算不算完成”。

---

# 12. Q09 上下文、记忆、多轮与长期状态现象

- 对话越长，回答越偏；
- 最初目标逐渐被忘记；
- 重要约束被大量历史内容淹没；
- 旧指令与新要求冲突；
- AI 仍遵守已经被取消的旧决定；
- 历史讨论中的临时想法被当成最终决定；
- 用户说“以后不要这样”，后续又重复出现；
- 多个项目的上下文相互串扰；
- 摘要丢失关键细节；
- 摘要保留了大量低价值内容；
- 每轮重新从头分析；
- 多会话之间重复劳动；
- AI 不知道哪些事情已经完成；
- AI 不知道哪些事项仍待处理；
- 没有保存重要决策及其版本；
- 用户改变方向后旧计划仍持续影响回答；
- 长任务没有状态台账；
- 记忆过少导致反复询问；
- 记忆过多导致旧偏好错误影响当前任务。

---

# 13. Q10 人机角色、控制、信任与个性化现象

- AI 对本应由用户决定的价值选择直接替用户决定；
- AI 什么都交给用户决定，失去辅助价值；
- 低风险动作过度确认；
- 高风险动作反而缺少确认；
- 用户不知道 AI 当前有多确定；
- AI 不确定但语气非常确定；
- 用户因为表达流畅而过度相信结果；
- 用户因为一次错误后完全不再利用 AI；
- AI 过度迎合用户既有观点；
- 对专家用户解释得过于基础；
- 对新手用户解释得过于专业；
- 没有使用用户已经明确的稳定偏好；
- 过度使用历史偏好，误判当前任务；
- 把历史习惯当成硬性约束；
- 个性化导致没有重新判断当前场景；
- 用户不知道 AI 能做什么、不能做什么；
- 用户无法判断当前应该监督到什么程度。

# 14. Q11 指令、机制选择与复杂度失控现象

- Prompt 越来越长；
- 每发现一个问题就增加一条 Prompt 规则；
- 多条规则互相冲突；
- 没有说明规则优先级；
- 关键要求被大量次要要求稀释；
- 一个超级 Prompt 试图承担所有任务；
- 用 Prompt 解决本应由状态机解决的问题；
- 用 Prompt 解决本应由工具或代码保证的问题；
- 用 Workflow 解决一个简单回答即可解决的问题；
- Agent 化一切；
- Skill 化一切；
- Schema 化一切；
- 为了显得工程化不断增加目录、协议和文件；
- 系统越来越完整，但普通用户越来越难判断价值；
- 维护规则本身比解决原始问题更耗时；
- 解决方案的管理成本超过原问题成本；
- 工程组件存在，但无法说明它具体解决什么用户问题；
- 系统中出现大量“正确但没有业务必要性”的工程描述；
- 用户需要先理解整套系统才能使用系统；
- 为追求“95 分以上”不断增加复杂度，却没有同步增加真实效果。

# 16. 当前最高价值现象（优先观察）

以下现象建议优先进入后续问题类型、根因和机制研究，而不是平均处理所有表现问题。

## S 级候选：可能导致方向错误、任务失败或错误决策

1. 真实目标理解错误；
2. 错误问题定义被持续优化；
3. 关键缺失信息被无依据猜测；
4. 事实、来源或时效错误；
5. 不确定信息被高确定性呈现；
6. 用户提出的候选方案被误认为真实需求；
7. 工具成功或局部完成被误认为整体成功；
8. 缺少真实验收，错误结果进入下一阶段；
9. 高风险或不可逆行为缺少人工控制。

## A 级候选：高频、显著降低 AI 协作质量

10. 需求尚未稳定就大规模进入工程实现；
11. 阶段错位；
12. 过早方案收敛；
13. 信息优先级失败；
14. 输出粒度与当前任务不匹配；
15. 应问不问、不该问反复问；
16. 迎合用户观点、缺少反方判断；
17. 长任务目标漂移和状态丢失；
18. Prompt / Workflow / Skill / Agent 复杂度不断膨胀；
19. 缺少停止和完成条件；
20. 用户纠错没有真正更新后续状态。

# 17. 需求空间与工程空间必须显式分离

“工程描述淹没需求”属于本项目目前已经真实反复观察到的高价值现象，因此现象库需要明确保留一个重要分界：

```text
现实困扰 / 原始表达
↓
问题现象
↓
真正问题
↓
真实需求
↓
目标、约束、成功标准
↓
方案空间

========= 需求稳定关口 =========

方案选择
↓
解决机制
↓
工程设计
↓
Prompt / Context / Workflow / Agent / Skill / Schema / Tool / Code
↓
执行
↓
验证与验收
```

在“需求稳定关口”之前出现的工程方案，应默认标记为：

> **候选实现方式，而不是已经确认的需求。**

例如：

```text
“是不是可以做一个 Skill？”
```

首先应视为：

```text
[用户提出的候选实现方式]
```

而不是：

```text
[已确认需求：必须建立 Skill]
```

# 18. 现象记录规范（后续新增问题时使用）

新增现象时优先记录以下最小信息：

```text
现象 ID：待后续统一编号
用户原话：用户通常怎么表达不满意
现象名称：人工容易理解的中文名称
典型场景：什么时候出现

影响：方向 / 决策 / 质量 / 效率 / 体验
频率：高 / 中 / 低
严重度：S / A / B / C（候选）
是否重复：与哪些现象可能属于同一上层问题
来源：真实使用案例 / 专业研究 / 工程观察
状态：候选 / 已归类 / 已建立根因映射 / 已建立机制映射
```

注意：

- 现象名称应优先使用普通中文；
- 不应在现象层强行创造“听起来专业”的术语；
- 成熟专业名称放在后续“专业问题类型/领域映射”中；
- 自定义名称必须标记为工程化工作名称；
- 同一现象可以跨多个阶段和多个问题类型，不为了树状目录强行唯一归属。

# 20. 当前边界与版本说明

当前 v0.1 的作用是建立第一版人工可读的高频现象基线，而不是宣称分类已经穷尽。

后续版本需要重点补充：

1. 从真实历史对话中继续抽取用户原话级现象；
2. 与人机交互、需求工程、设计科学、决策科学、认知科学、软件工程、质量工程等主流专业体系校准；
3. 区分成熟专业问题、跨领域迁移问题、LLM/Agent 新问题、本项目工程化定义；
4. 对重复现象进行聚类，而不是无限增加条目；
5. 建立“现象 × 根因”多对多矩阵；
6. 建立“现象 × 任务阶段”矩阵；
7. 建立“根因 × 解决机制”矩阵；
8. 用真实案例验证分类是否能提高诊断速度和解决质量。

最终目标不是得到一个越来越大的问题列表，而是形成：

> **用户一旦感觉 AI 回答“不对劲”，可以从可感知现象迅速定位问题类型、根因候选和正确解决层级，而不是继续盲目向 Prompt 增加规则。**
