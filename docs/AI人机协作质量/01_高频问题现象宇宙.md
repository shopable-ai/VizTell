# AI 人机协作高频问题现象宇宙

> 状态：v0.2｜经主流专业体系校准后的现象层基线  
> 定位：AI 人机协作问题诊断知识库的“用户可感知现象层”  
> 目标读者：AI 重度用户、产品/需求人员、研究人员、Prompt/Context/Agent/Workflow 设计者  
> 关联文件：`03_主流专业领域与成熟框架映射.md`、`02_问题类型与根因宇宙.md`

---

## 0. 核心结论

“AI 怎么这么不好用”通常不是一个单一问题。

用户首先感知到的是：

> **回答、协作过程或最终结果哪里“不对劲”。**

这些表面现象后面可能对应完全不同的专业问题和根因。

本文件因此只回答：

> **人在与 AI 协作时，通常会看到哪些高频异常、低质量表现、失败体验和不符合预期的行为？**

正确诊断链是：

```text
用户可感知现象
→ 专业问题类型
→ 根因候选
→ 后续解决机制
```

本轮已经通过 HCI、Human-AI Interaction、需求工程、问题框定、决策科学、认知科学、软件/系统工程、质量工程、人因与 LLM / Agent 研究进行了反向校准。

但本文件仍刻意**不把专业术语和解决机制塞回现象层**。

# 1. “宇宙”的含义与边界

“高频问题现象宇宙”是本项目的知识工程组织名称。

> “宇宙”表示尽可能覆盖完整的问题空间，**不代表学界存在同名统一标准。**

现象层判断规则只有一个：

> **用户能否直接说：“我看见 AI 出现了这个表现。”**

适合放在这里：

- 回答太长；
- 没有结论；
- 需求还没想清楚就开始讲架构；
- 一直追问；
- 工具调用了但事情没办完；
- 用户纠正以后仍沿旧方向回答；
- 同样的要求隔一段时间行为变了却没有说明。

不适合直接放在这里：

- Design Fixation；
- Cognitive Load；
- Instruction Hierarchy；
- Context Pollution；
- 阶段识别失败；
- 缺少状态机；
- 应该增加 Evaluator；
- 应该做一个 Skill。

它们分别属于专业概念、问题类型、根因或解决机制。

# 2. 高频现象总览

当前按 11 个**用户可感知失效域**导航。

它们是项目内部导航分类，不宣称对应某个学术领域的标准分类法。

| 编号 | 高频现象域 | 用户最典型的感觉 |
|---|---|---|
| Q01 | 目标、意图与问题理解 | “你回答的不是我真正要解决的问题。” |
| Q02 | 澄清、共同理解与纠错 | “该问的不问，不该问的一直问；我纠正了你也没真改。” |
| Q03 | 推进时机、阶段与过程错位 | “我还在想方向，你怎么已经开始实施了？” |
| Q04 | 事实、证据、来源与不确定性 | “这些是真的吗？依据是什么？你到底确定不确定？” |
| Q05 | 方案探索、判断与决策支持 | “说了很多方案，但我还是不知道该选哪个。” |
| Q06 | 内容选择、优先级、粒度与呈现 | “太长、太细、没重点，真正有用的信息很少。” |
| Q07 | 计划、执行、工具与自动化 | “分析很多没推进，或者做了一堆动作却没达成目标。” |
| Q08 | 验证、验收、停止与完成感知 | “看起来做完了，但到底有没有真正解决？” |
| Q09 | 上下文、记忆、多轮与长期连续性 | “前面说过的忘了，已经废弃的东西却一直记着。” |
| Q10 | 能力透明、信任、控制与个性化 | “你能做到什么？我该信多少？什么时候该我决定？” |
| Q11 | 规则、机制与系统复杂度负担 | “系统越来越专业、越来越复杂，反而更难用了。” |

同一现象可以跨多个域，不为了目录整齐强行唯一归属。

# 3. Q01 目标、意图与问题理解

用户通常会直接感知到：

- 回答了字面问题，却没有解决真实问题；
- 用户提出一个办法，AI 把这个办法当成最终需求；
- 用户只是提出猜想，AI 把猜想当成已经确认的事实；
- 用户只是在举例，例子却反过来限制整个答案；
- 用户想判断“值不值得做”，AI 却直接教“怎么做”；
- 用户要结论，AI 只给背景知识；
- 用户要研究，AI 直接给最终决定；
- 用户要实际执行，AI 一直停留在分析；
- 用户只是探索可能性，AI 却把方向直接锁死；
- 问题范围被放得过大；
- 问题范围被缩得过小；
- 用户真正关心的成功标准没有进入回答；
- 明显错误或可疑的前提没有被指出；
- AI 过度顺着用户的已有观点；
- 每句话单独看都合理，合起来却没有解决用户真正的问题。

### 高价值新增检查

- AI 优化了用户给出的**代理目标**，但真实目标反而变差；
- 用户问的是“我应该解决什么”，AI 回答成“怎样把当前办法做得更完整”；
- 用户的价值判断、技术约束和随口想法被混成同等确定的信息。

---

# 4. Q02 澄清、共同理解与纠错

- 关键信息缺失时不追问，直接猜；
- 信息已经足够时仍机械追问；
- 一次性让用户回答十几个问题；
- 用户已经提供过的信息再次询问；
- 次要信息缺失也阻塞整个任务；
- 可以合理假设的低风险信息也要求用户确认；
- 高风险、高影响的信息却未经确认直接假设；
- 提问过于专业，用户不知道怎样回答；
- AI 把信息收集工作重新全部交给用户；
- AI 没有告诉用户自己目前究竟理解成了什么；
- 同一术语双方含义不同，却长时间没有暴露；
- 用户说“不是这个意思”以后，AI 只换一种说法继续原方向；
- 用户纠正一个概念后，后续分析仍继续使用旧概念；
- 用户修改目标后，旧目标仍出现在后续计划里；
- 用户否决一个方案后，它隔几轮又被当成默认方案；
- AI 不知道什么时候应继续推进，什么时候必须向用户确认；
- 用户不知道自己的纠正究竟有没有真正生效。

### 高价值新增检查

- 纠正只改变了当前一句话，没有传播到目标、计划、状态、文件或后续行动；
- AI 确认“明白了”，但下一步行为证明双方仍没有形成共同理解；
- 多人或多 Agent 交接后，同一个目标被重新解释成另一件事。

---

# 5. Q03 推进时机、阶段与过程错位

这里记录的是用户能看见的“时机不对”，而不是直接把“阶段识别失败”当作根因。

- 还在理解问题，AI 已经开始给最终方案；
- 还在探索方向，AI 已经开始写详细实施步骤；
- 需求尚未确认，AI 已经开始设计架构；
- 方案还没有比较，AI 已默认其中一个方案成立；
- 用户只想先看地图，AI 直接进入完整教程；
- 用户只想先看关键结论，AI 一开始就展开三级、四级细节；
- 决策阶段仍不断添加更多可能性，迟迟不收敛；
- 已经进入执行阶段，AI 又回到长篇理论研究；
- 调试局部问题时重新设计整个系统；
- 验收阶段不断追加新功能；
- 用户已经确认方向，AI 仍反复从头论证；
- 用户已经改变方向，AI 继续沿旧路线推进；
- AI 做了很多中间工作，但用户不知道当前到底推进到了哪一步；
- 用户无法看出现在到底是在探索、决定、计划、执行还是验证。

## 5.1 特别高价值现象：工程描述淹没需求

典型用户描述：

> “需求还没有想清楚，回答里 70%—80% 已经是 Workflow、Skill、Schema、Agent、代码、文件结构，我反而无法判断真正的需求和方案是不是正确。”

本项目继续保留普通中文现象名称：

> **工程描述淹没需求。**

典型可见表现：

- 用户提出“是不是可以做一个 Skill”，AI 后续直接按“必须做 Skill”展开；
- 真实业务问题只占很少篇幅，工程结构成为回答主体；
- 大量目录、协议、Schema 很完整，但用户仍不知道为什么需要它们；
- 工程细节越完整，用户越难重新质疑最初方向；
- 用户不得不反复说“先不要实现”“先给核心结论”。

专业诊断放在 02、03，不在这里直接把它等同于某一个成熟术语。

# 6. Q04 事实、证据、来源与不确定性

- 需要最新信息时仍凭旧知识回答；
- 不需要外部研究的问题却进行了大量搜索；
- 搜索了很多资料，却没有形成判断；
- 引用了来源，但来源并不真正支持对应结论；
- 只给链接，不说明证据与结论的关系；
- 使用低质量二手材料替代更可靠的一手资料；
- 没有判断资料是否过时；
- 多个来源互相冲突，却直接挑一个结论；
- 事实、推断、猜测和建议混在一起；
- 不确定的信息被写得像确定事实；
- AI 不知道时没有明确表现出“不知道”；
- 只寻找支持已有观点的材料；
- 忽略反例或反证；
- 资料很多，但与当前决策几乎无关；
- 用户看完仍然不知道“所以结论是什么”；
- 同一结论换了一个来源，可信度看似提高，实质证据没有增加。

### 高价值新增检查

- AI 无法说明当前结论主要基于哪些事实、哪些假设；
- 检索到了关键资料，但后续回答实际没有使用；
- 长上下文中关键证据存在，却被其他材料淹没；
- AI 的确定语气与证据强度明显不匹配。

---

# 7. Q05 方案探索、判断与决策支持

- 第一想到的方案直接成为最终方案；
- 没有真正探索方案空间；
- 看似给了十个方案，本质只是同一种办法换名称；
- 没有替代方案；
- 没有考虑“不做”；
- 没有考虑更低成本、更轻量的方式；
- 没有识别方案之间可以组合；
- 方案很多，但没有指出真正关键杠杆；
- 给出行业惯例，却没有针对当前场景；
- 没有明确选择标准；
- 给出大量选择，却拒绝作出推荐；
- 永远回答“取决于”；
- 用户需要决策支持，却只得到资料罗列；
- 所有评价维度获得相同权重；
- 关键风险和次要风险混在一起；
- 没有考虑机会成本；
- 没有区分可逆和不可逆决策；
- 没有说明真正决定结果的关键变量；
- 用户先提出一个方案后，AI 后续几乎只围绕它优化；
- 分析越来越多，但用户的决策空间没有缩小。

### 高价值新增检查

- AI 对“怎样做得更好”分析很多，但没有先确认“值不值得做”；
- 推荐理由无法追溯到用户目标或评价标准；
- AI 给出精确分数，却无法解释分数变化会不会改变最终选择。

---

# 8. Q06 内容选择、优先级、粒度与呈现

这是“回答内容为什么难用”的核心现象域。

## 8.1 内容选择

- 包含大量正确但当前无用的信息；
- 核心问题只占回答很小部分；
- 背景知识明显多于真正有决策价值的信息；
- 用户已经知道的内容被重复解释；
- 为了显得完整加入大量低价值内容；
- 内容很多，但没有改变用户判断或行动。

## 8.2 信息优先级

- 没有先给结论；
- 最重要的信息埋在最后；
- 关键风险和次要风险获得相同篇幅；
- 所有信息看起来同等重要；
- “必须现在知道”和“以后可以展开”没有区分；
- 用户看了很久才知道真正推荐什么；
- 有决策价值的信息被背景、术语和工程描述淹没。

## 8.3 输出粒度

- 用户只需要结论，AI 给到操作参数；
- 用户只需要方向地图，AI 给成详细教程；
- 用户需要具体步骤，AI 只给抽象原则；
- 项目第一轮就进入三级、四级、五级细节；
- 复杂问题被过度简化；
- 简单问题被人为复杂化；
- 每一点都继续无限拆分；
- 用户无法判断当前应该在哪一层停止。

用于人工理解的工程化粒度示例：

```text
结论
→ 框架
→ 模块
→ 方法
→ 步骤
→ 参数
→ 操作细节
```

这不是学术标准，只是项目内部描述工具。

## 8.4 展开深度

- 第一轮信息量过大；
- 用户还没选择方向，所有方向已被全部展开；
- 某个次要点被展开成回答主体；
- 当前只需建立地图，却把所有节点都讲完；
- 用户已经需要执行，AI 仍保持过度抽象。

## 8.5 内容顺序

- 先讲背景，最后才给答案；
- 先讲实现，再说明需求；
- 先讲大量风险，最后才说明主方案；
- 原因、结论、案例、步骤交叉混杂；
- 用户必须自己重新排列信息才能理解。

## 8.6 信息密度

- 字很多，但有效新信息很少；
- 大量重复表达；
- 大量正确但不推动判断的内容；
- 专业术语很多，但没有提高决策质量；
- 用户读完没有更接近选择或行动；
- 关键变量、因果关系、判断依据密度过低。

本项目继续把“高知识密度”作为 `[工程化工作名称]`：

> 单位用户认知成本中，能够改变判断、缩小决策空间、暴露关键变量或推动行动的信息含量。

它不等于“越短越好”，也不等于“术语越多越专业”。

## 8.7 结构与格式

- 标题过多；
- 每一句都拆成独立段落；
- 列表滥用；
- 表格滥用；
- 表格看起来专业但比普通文字更难读；
- 同一层级内容抽象程度不同；
- Markdown 层级过深；
- 大量重复总结；
- 为了视觉整齐牺牲语义关系；
- 结构漂亮，但用户无法形成清晰心理模型。

## 8.8 用户认知负担的可见表现

- 一次给出十几个方案；
- 用户必须先学习大量术语才能继续；
- 用户不知道下一步应该做什么；
- AI 把方案比较工作重新交还给用户；
- 用户需要在多个回答间来回寻找关键条件；
- 信息组织顺序与用户的判断顺序相反；
- 回答正确，但阅读成本明显高于所得价值。

# 9. Q07 计划、执行、工具与自动化

## 9.1 计划

- 复杂任务没有任何计划就直接执行；
- 简单任务却先生成一套庞大计划；
- 计划只有活动，没有明确交付物；
- 计划太宏观，无法实际执行；
- 计划太细，维护计划本身成为主要工作；
- 没有关键依赖；
- 没有失败后的处理方式；
- 计划和最终目标明显脱节。

## 9.2 执行

- 分析很多但迟迟不执行；
- 未确认关键方向就大规模执行；
- 执行过程中偏离原目标；
- 重复执行已经完成的工作；
- 中间失败后忽略错误继续；
- 长任务执行过程中目标逐渐变化；
- AI 声称要做很多事，实际只完成其中一部分；
- 局部动作很多，但没有形成最终产出；
- 为了完成一个容易测的局部指标，牺牲真实业务目标。

## 9.3 工具

- 本可直接回答却调用大量工具；
- 明显应该查询工具却凭记忆回答；
- 选择了不合适的工具；
- 工具返回结果但 AI 没有真正分析；
- 工具调用成功就被当成任务成功；
- 有权限被误写成已经完成真实业务动作；
- 获取了文件却没有真正阅读关键内容；
- 搜索了仓库却没有核实分支或当前版本；
- 工具异常后仍给出看似正常的最终结论；
- 用户看不到工具动作会产生什么真实副作用。

## 9.4 Agent / 自动化

- 简单任务被 Agent 化；
- 多 Agent 数量增加但质量没有提高；
- Agent 反复循环；
- Agent 不知道什么时候结束；
- 自动化范围超过用户理解或授权；
- 关键不可逆动作没有明显人工关口；
- Agent 执行路径很复杂，但用户无法知道当前状态；
- 工作流复杂程度超过任务本身；
- 人工接管时缺少足够上下文，只能重新从头判断。

# 10. Q08 验证、验收、停止与完成感知

- AI 生成结果后完全不检查；
- 只检查 Markdown、JSON 等格式，不检查内容；
- 只检查“有没有文件”，不检查文件是否真正解决问题；
- 只检查“工具有没有成功”，不检查业务结果；
- 子任务完成被误判为整体完成；
- 测试通过，却没有满足用户真实需求；
- 没有预先说明什么叫完成；
- 验收标准与用户真实目标无关；
- 没有寻找明显反例；
- 没有遗漏检查；
- 没有事实核验；
- 评价过程只优化容易测量的指标；
- “继续完善”变成无限循环；
- 已经达到足够可用质量仍不断复杂化；
- 没有最低可接受质量；
- 没有考虑继续优化的边际收益；
- 用户最终仍无法判断“到底算不算完成”。

### 高价值新增检查

- 技术 Verification 通过，但实际使用 Validation 失败；
- AI 自己宣称“完成”，用户却没有看到业务结果；
- 通过多个局部测试，却缺少端到端验收；
- 最终结果只满足了后来出现的工程目标，没有回到最初用户目标。

---

# 11. Q09 上下文、记忆、多轮与长期连续性

- 对话越长，回答越偏；
- 最初目标逐渐被忘记；
- 重要约束被大量历史内容淹没；
- 旧要求与新要求同时影响回答；
- 已经取消的决定仍继续生效；
- 历史讨论中的临时想法被当成最终决定；
- 用户说“以后不要这样”，后续又重复出现；
- 多个项目的上下文相互串扰；
- 摘要丢失关键细节；
- 摘要保留大量低价值内容；
- 每轮重新从头分析；
- 多会话之间重复劳动；
- AI 不知道哪些事情已经完成；
- AI 不知道哪些仍待处理；
- 没有保存重要决定及其版本；
- 用户改变方向后旧计划仍持续影响；
- 记忆太少导致反复询问；
- 记忆太多导致旧偏好错误影响当前任务；
- 明明上下文中存在关键约束，AI 却像没有看到；
- 用户无法知道 AI 当前实际采用了哪些历史信息。

### 高价值新增检查

- “已讨论 / 已否决 / 已确认 / 已完成”四种历史状态被混在一起；
- 长任务跨会话后，语义记住了，但决策状态丢失；
- 多 Agent handoff 后，目标还在，关键限制条件丢了。

---

# 12. Q10 能力透明、信任、控制与个性化

- 用户不知道 AI 当前能做什么、不能做什么；
- 用户不知道 AI 是在查事实、推断，还是猜测；
- 用户不知道 AI 当前有多确定；
- AI 不确定但语气非常确定；
- 用户因为表达流畅而过度相信结果；
- 用户因为一次错误后完全不再利用 AI；
- AI 对本应由用户决定的价值选择直接替用户决定；
- AI 什么都交给用户决定，失去辅助价值；
- 低风险动作过度确认；
- 高风险动作反而缺少确认；
- 用户不知道什么时候应该监督、什么时候可以放手；
- 对专家用户解释得过于基础；
- 对新手用户解释得过于专业；
- 没有使用用户已经明确且仍适用的稳定偏好；
- 过度使用历史偏好，误判当前任务；
- 把过去习惯当成硬性约束；
- 个性化导致没有重新判断当前场景；
- 系统能力或行为发生变化，用户没有被明确告知；
- 同样请求隔一段时间得到完全不同处理，用户不知道为什么；
- AI 采取真实世界行动前，用户看不到后果、可逆性或权限边界。

---

# 13. Q11 规则、机制与系统复杂度负担

这里保留的是用户**能直接感知到的复杂度后果**。

- Prompt 越来越长，用户已经很难判断关键要求在哪里；
- 每发现一个问题就增加一条规则；
- 多条规则看起来互相冲突；
- 用户不知道哪条规则优先；
- 关键要求被大量次要要求稀释；
- 一个提示词试图承担所有任务；
- 一个简单任务需要经过大量 Workflow / Skill / Agent / Schema 才能开始；
- 每个问题都被要求建立新文件、新协议、新目录；
- 系统越来越“完整”，普通用户却越来越难理解；
- 维护规则本身比解决原始问题更耗时；
- 解决方案的管理成本超过原问题成本；
- 工程组件很多，但说不清各自究竟解决什么用户问题；
- 系统中出现大量正确但没有业务必要性的工程描述；
- 用户需要先学习整套系统才能开始使用；
- 为追求极高评分不断增加复杂度，但真实效果没有同步提高；
- 同一个问题在 Prompt、Workflow、Skill、代码中被重复规定多次；
- 改一个规则会导致其他地方出现新的意外行为。

“应该用 Prompt、状态机、代码还是 Agent”属于后续解决机制选择，不在现象层直接下结论。

# 15. 当前最高价值现象

优先级用于研究顺序，不代表统计学频率已经经过大样本验证。

## S 级：可能造成方向错误、错误决策或虚假完成

1. 真实目标理解错误；
2. 错误问题被持续精细优化；
3. 用户候选方案被误认为真实需求；
4. 关键缺失信息被无依据猜测；
5. 事实、来源或时效错误；
6. 不确定信息被高确定性呈现；
7. 工具成功或局部完成被误认为整体成功；
8. 技术测试通过但真实用途未满足；
9. 高风险或不可逆行为缺少用户理解与控制；
10. 用户纠错没有真正更新后续状态。

## A 级：高频、显著降低协作效率和判断质量

11. 需求尚未稳定就大规模进入工程实现；
12. 推进时机和当前阶段明显不匹配；
13. 过早围绕第一个方案展开；
14. 信息优先级失败；
15. 输出粒度与当前任务不匹配；
16. 应问不问、不该问反复问；
17. 过度迎合用户观点、缺少反证；
18. 长任务目标漂移和状态丢失；
19. Prompt / Workflow / Skill / Agent 复杂度不断膨胀；
20. 缺少停止与完成感知；
21. 能力或行为变化对用户不可见；
22. 局部指标优化替代真实目标。

# 16. 现象记录规范

新增现象时使用以下最小信息：

```text
现象 ID：待统一编号
用户原话：用户通常怎样表达不满意
现象名称：人工容易理解的中文名称
典型场景：什么时候出现
所属现象域：Q01—Q11，可多选
影响：方向 / 决策 / 质量 / 效率 / 体验 / 风险
频率：高 / 中 / 低 / 未验证
严重度：S / A / B / C（项目内部优先级）
是否重复：与哪些现象可能属于同一上层问题
来源：真实使用案例 / 专业研究反向检查 / 工程观察
状态：候选 / 已归类 / 已建立问题类型映射 / 已建立根因映射
```

规则：

- 现象名称优先使用普通中文；
- 不在现象层强行创造“听起来专业”的术语；
- 成熟专业名称放到 03；
- 专业问题类型和根因放到 02；
- 自定义名称明确标记为工程化工作名称；
- 重复现象优先聚类，不无限扩展条目；
- 一条现象可以对应多个专业领域和多个根因。

# 18. v0.2 相对 v0.1 的主要调整

1. **保留 11 个用户可感知失效域，但重新校准命名。** 例如 Q03 从带根因色彩的“阶段、状态与流程错位”调整为更可观察的“推进时机、阶段与过程错位”。
2. **Q11 做减法。** “应该用 Prompt 还是状态机”等机制判断移出，现象层只保留用户能感知的复杂度负担。
3. **“工程描述淹没需求”继续保留为用户现象，不直接包装成 Design Fixation。**
4. **增加主流 Human-AI 研究反向发现的现象**：能力透明失败、系统变化不可见、纠错不传播、自治副作用不可见、不适当依赖。
5. **增加质量工程反向发现的现象**：局部指标替代真实目标、Verification 通过但 Validation 失败。
6. **保留“高知识密度”为项目工程工作名**，不提升为成熟学术指标。
7. **删除现象层中过多的解决方案预设**，把专业诊断和根因转交 02、03。

当前版本的目标不再是“问题越多越完整”，而是：

> **当用户感觉 AI 不好用时，能够先找到自己看到的现象，再进入专业问题类型与根因，而不是立即给 Prompt 增加规则。**
