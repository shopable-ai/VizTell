# AI 人机协作：问题类型与根因宇宙

> 状态：v0.1｜问题类型与稳定根因基线  
> 定位：连接“用户可感知现象”与“后续解决机制”的诊断层  
> 上游：`01_高频问题现象宇宙.md`  
> 专业校准：`03_主流专业领域与成熟框架映射.md`  
> 原则：不把 01 换一种说法；不提前进入 Prompt / Workflow / Agent / Skill / Schema 解决方案。

---

## 0. 核心结论

`01` 回答：

> **用户看到了什么不对劲？**

`02` 回答：

> **这些现象在专业上大概属于什么问题，为什么会发生？**

因此，本文件采用：

```text
用户现象
↓
专业问题类型
↓
直接原因
↓
稳定根因
↓
放大条件
```

而不是：

```text
回答太长
↓
“太长问题”
↓
“回答过长根因”
```

真正有价值的根因必须具备较高复用性：

> **一个稳定根因应能解释多个表面现象；同一表面现象也允许由多个根因共同制造。**

本轮将大量候选根因压缩为 **17 个高解释力根因族**，避免发展成几百个互相重叠的小原因。

# 1. 概念来源标签

沿用 `03_主流专业领域与成熟框架映射.md` 的四类标签：

| 标签 | 含义 |
|---|---|
| `[成熟专业概念]` | 已有相对稳定的专业、学术或标准定义 |
| `[跨领域迁移]` | 原本来自需求、设计、HCI、系统工程、人因等，迁移到 AI 协作 |
| `[AI 新型问题]` | 已有 LLM / Agent 特有研究或工程证据 |
| `[工程化工作名称]` | 本项目为了诊断与检索建立的工作名称 |

重要规则：

> **问题类型允许是跨多个成熟领域的诊断组合，不必强行找到一个“唯一学术术语”。**

例如“需求—解决方案混淆”非常有诊断价值，但它并不是 ISO 29148 中某个完全同名的标准术语。它应被标记为跨需求工程与设计科学的 `[跨领域迁移 / 工程诊断类别]`。

# 2. 三个容易混淆的层级

## 2.1 用户现象

用户可直接观察：

> “需求还没想清楚，你已经讲了一大堆 Workflow、Agent、Schema。”

## 2.2 问题类型

对一组相似现象进行专业诊断：

> 需求—解决方案混淆；过早方案承诺；阶段 / 推进失配。

## 2.3 根因

解释为什么这些问题会反复出现：

> 未正确维护需求状态与方案边界；当前阶段状态表示错误；信息优先级 / 粒度选择错误。

三层必须保持可区分。

# 4. T01 目标 / 意图对齐失效

### 它是什么

AI 对用户当前真正要优化的目标、产出类型或成功条件形成了错误表示。

### 常见现象

- 字面答对但真实问题没解决；
- 用户要判断，AI 给科普；
- 用户要实际执行，AI 一直分析；
- 局部指标变好，用户真实目标反而变差。

### 与成熟体系的关系

这不是单一 HCI 标准术语，而是 HCI 的“用户目标 / 使用情境”、需求工程的 stakeholder needs，以及 Human-AI Interaction 中 intent / expectation alignment 的交叉诊断。

### 主要根因

RC01、RC04、RC05、RC09。

# 5. T02 问题框定失效

`[成熟专业概念]`

### 它是什么

尚未正确确定“究竟在解决什么问题”，或者把症状、已有方案、局部约束误当成问题本身。

### 常见表现

- 对错误问题进行越来越精细的优化；
- 用户的问题定义本身明显可疑，AI 却没有重新框定；
- 现实目标被一个局部技术问题替代；
- Problem Space 还没有充分探索就进入 Solution Space。

### 相关成熟知识

- Problem Framing；
- Double Diamond 的 Discover / Define；
- 设计中的发散—收敛。

### 主要根因

RC01、RC02、RC03、RC09。

# 6. T03 需求—解决方案混淆

`[跨领域迁移 / 工程诊断类别]`

### 它是什么

尚未确认的候选实现方式被当作稳定需求，或低层设计反过来限制用户需要与上层目标的定义。

### 典型错误链

```text
用户：“是不是可以做一个 Skill？”
↓
系统错误升级为：
“需求 = 建立 Skill”
↓
开始设计 Skill 文件、Schema、Runtime
↓
真实业务需要仍未确认
```

### 成熟专业对应

- 需求工程：需求应能够追溯到 stakeholder needs；功能需求在适用时尽量保持 implementation-neutral；
- 设计科学：premature commitment；
- 若已有方案或示例限制后续方案探索，才进一步可能涉及 Design Fixation。

### 重要边界

它**不等于**“需求阶段禁止讨论技术”。

技术限制、法规、成本、兼容性、既有平台等可能是真实约束；设计证据也可能导致需求迭代。

真正的问题是：

> **把未经确认的实现假设错误提升为需求，并失去重新打开问题空间的能力。**

### 主要根因

RC02、RC03、RC06、RC07、RC09。

# 7. T04 共同理解与对话修复失效

`[成熟专业概念 + 跨领域迁移]`

### 它是什么

人与 AI 没有建立足够 shared understanding / common ground，或出现误解后没有真正修复。

### 不只是“有没有复述用户的话”

有效修复应能影响：

```text
当前理解
→ 目标
→ 约束
→ 方案
→ 状态
→ 后续行动
```

### 常见现象

- 用户说“不是这个意思”，AI 只是改写措辞；
- 同一术语双方含义不同；
- 已否决方案后来再次出现；
- AI 说“明白了”，行为却证明没有真正更新。

### 主要根因

RC04、RC05、RC13。

---

# 8. T05 阶段 / 推进状态失配

`[跨领域迁移]`

### 它是什么

当前任务实际处于探索、定义、决策、计划、执行、验证中的某一阶段，但系统使用了另一阶段的行为模式。

### 常见现象

- 需求探索阶段输出完整架构；
- 决策阶段不断发散；
- 执行阶段重新做大篇幅基础研究；
- 验收阶段继续扩需求；
- 用户已经改变方向，仍沿旧路线推进。

### 主要根因

RC05、RC06、RC13。

---

# 9. T06 信息相关性、优先级与粒度失配

`[跨领域迁移]`

### 它是什么

输出内容本身可能正确，但内容选择、顺序、深度或格式与用户当前认知任务不匹配。

### 可由成熟知识解释

- HCI / usability；
- Cognitive Load；
- Progressive Disclosure；
- 信息层级与任务适配。

### 常见现象

- 太长、太细、没重点；
- 背景淹没结论；
- 用户要地图却得到教程；
- 用户需要执行却只有抽象原则；
- 表格 / 标题很多但理解成本更高。

### 主要根因

RC01、RC06、RC07。

# 10. T07 证据、来源与时效管理失效

`[跨领域迁移]`

### 它是什么

系统没有正确选择、验证、组织或使用支持结论所需要的证据。

### 常见现象

- 需要最新信息却用旧知识；
- 来源并不支持结论；
- 低质量二手来源替代一手资料；
- 搜索很多却不形成判断；
- 关键检索结果存在但后续回答没有使用。

### 主要根因

RC04、RC08、RC17。

# 11. T08 不确定性与置信表达失配

`[成熟问题 + AI 扩展]`

### 它是什么

模型实际证据强度、知识边界或预测不确定性，与向用户表达出的确定程度不一致。

### 常见现象

- 猜测被写成事实；
- AI 不知道时仍使用高确定性语气；
- 多个来源冲突却不给出不确定性；
- 用户因语言流畅而过度相信。

### 主要根因

RC08、RC15、RC17。

---

# 12. T09 方案探索不足 / 过早收敛

`[成熟专业问题]`

### 它是什么

在替代方案空间尚未合理探索时，过早承诺某一方向。

### 相关成熟概念

- Divergence / Convergence；
- Premature Commitment；
- Design Fixation（仅当既有方案限制后续想法时）；
- 决策科学中的 alternatives generation。

### 常见现象

- 第一个方案直接成为最终方案；
- 十个方案其实是同一种办法换名字；
- 没考虑“不做”；
- 用户先提一个方案，AI 后续只围绕它优化。

### 主要根因

RC02、RC03、RC09、RC17。

---

# 13. T10 决策目标、标准与权衡模型缺失

`[成熟专业问题]`

### 它是什么

有信息、有方案，但没有明确：

```text
优化什么
→ 用什么标准判断
→ 哪些约束不可违反
→ 各结果有什么后果
→ 怎样权衡
```

### 常见现象

- 方案很多但不知道选哪个；
- 永远回答“取决于”；
- 所有评价维度同权；
- 推荐无法追溯到用户目标；
- 分数很精确，但无法说明分数变化是否会改变选择。

### 主要根因

RC01、RC09。

# 14. T11 计划—执行—目标脱节

`[跨领域迁移]`

### 它是什么

计划、任务、执行动作与最终目标或交付物之间缺少清晰依赖和追踪。

### 常见现象

- 计划很完整却没有实际交付；
- 活动很多但看不到目标推进；
- 已完成工作重复执行；
- 执行中目标逐渐漂移；
- 声称完成很多任务，最终产物只覆盖其中一部分。

### 主要根因

RC01、RC06、RC10、RC12、RC13。

---

# 15. T12 工具动作与业务结果脱节

`[AI / Agent 工程诊断]`

### 它是什么

系统把“技术动作成功”错误当成“真实世界结果已经达成”。

### 典型错误

```text
API 返回 200
≠ 用户业务目标已实现

文件创建成功
≠ 文件内容正确且可用

搜索成功
≠ 已理解资料

有权限调用工具
≠ 已经执行用户要求的真实动作
```

### 常见现象

- 工具调用成功就宣布完成；
- 获取文件却没读关键内容；
- 仓库写入成功却没检查最终 main 状态；
- Agent 做了很多动作却没有端到端业务产出。

### 主要根因

RC10、RC11、RC12、RC17。

---

# 16. T13 Verification / Validation / Acceptance 混淆

`[成熟专业概念]`

### 核心区分

- Verification：是否满足已经规定的要求；
- Validation：结果是否适合预期使用、满足真正用途与 stakeholder expectation；
- Acceptance：是否达到预先约定的可接受条件并可由相关责任方接受。

### 常见现象

- 格式正确就当内容正确；
- 技术测试通过就当需求满足；
- 文件存在就当任务完成；
- 自动测试全部绿色，用户仍认为“不好用”。

### 主要根因

RC01、RC11、RC12。

---

# 17. T14 完成与停止判定失效

`[跨领域迁移 + Agent 新问题]`

### 它是什么

系统不知道：

- 什么结果算足够完成；
- 什么条件需要继续；
- 什么条件需要失败退出；
- 什么时候应该交还给用户；
- 继续优化是否还有价值。

### 常见现象

- 一直继续完善；
- Agent 循环；
- 达到足够质量仍不断加复杂度；
- 子任务完成就宣称整体完成；
- 没有明确最终状态。

### 主要根因

RC11、RC12、RC15、RC16。

---

# 18. T15 上下文、记忆、状态与版本不一致

`[跨领域迁移 + AI 新问题]`

### 它是什么

当前有效目标、约束、决策、历史状态与模型实际使用的上下文不一致。

### 常见现象

- 已废弃规则继续生效；
- 临时想法被当成正式决定；
- 关键约束在长上下文中被忽略；
- 多会话之间重复劳动；
- 记得用户偏好，却忘了项目当前状态；
- 多 Agent handoff 丢失限制条件。

### 主要根因

RC05、RC06、RC13、RC14、RC17。

---

# 19. T16 指令冲突与权限 / 优先级解析失效

`[AI 新型问题]`

### 它是什么

模型面对来自不同来源、不同时间、不同权限层级的指令时，没有正确处理优先级、冲突、覆盖与撤销。

### 常见现象

- 新要求与旧要求同时生效；
- 关键规则被次要规则淹没；
- Prompt 越来越长后行为不可预测；
- 外部工具或检索内容中的指令污染任务；
- 用户已撤销某要求，模型仍继续遵守。

### 主要根因

RC13、RC14、RC17。

---

# 20. T17 人机控制权、信任与依赖配置失衡

`[成熟专业概念 + AI 扩展]`

### 它是什么

AI 与用户在决策权、自动化程度、监督强度和可信程度之间没有形成合理配置。

### 成熟相关概念

- Automation Bias；
- Appropriate Reliance；
- Human Oversight；
- Human-AI Interaction 中的控制、纠错和反馈。

### 常见现象

- AI 替用户作价值决策；
- AI 什么都要求用户确认；
- 低风险动作反复确认，高风险动作反而直接执行；
- 用户因为语言流畅而过度相信；
- 用户不知道何时应监督或接管。

### 主要根因

RC08、RC15、RC17。

---

# 21. T18 机制复杂度与任务复杂度失配

`[跨领域诊断类别]`

### 它是什么

为解决问题引入的规则、组件、工作流和自治程度，超过了任务本身实际需要的复杂度。

### 常见现象

- 简单问答被 Agent 化；
- 每个小问题都新增 Skill / Schema / 文件；
- 维护规则比完成任务更费力；
- 多 Agent 增加但质量没有提高；
- 工程系统很完整，却说不清解决了什么用户问题。

### 主要根因

RC01、RC07、RC16。

---

# 22. T19 反馈 / 纠错未传播到后续状态

`[跨领域诊断类别]`

### 它是什么

用户反馈在当前回复中被“口头接受”，但没有传播到依赖它的目标、计划、状态、记忆、文件或后续行为。

### 为什么单独保留

这是现代长任务与 Agent 协作中非常高价值的失效模式：

```text
收到纠正
≠
状态已经更新
≠
所有依赖项已经重算
```

### 常见现象

- 用户说“不要再创建新文件”，下一轮仍继续创建；
- 用户改了方向，旧计划还在执行；
- 用户修正术语，后续输出仍按旧含义推理。

### 主要根因

RC05、RC13、RC14。

# 23. 稳定根因宇宙：17 个高解释力根因族

## RC01 目标表示错误

**定义：** 系统没有正确表示用户真正要优化的结果、优先级或成功条件。

可制造：答非所问、代理指标替代真实目标、计划脱节、决策标准失效。

主要来源：需求工程、HCI、决策科学。

---

## RC02 问题框定错误

**定义：** 症状、局部问题、既有方案或错误前提被当成真正问题。

可制造：错误问题精细优化、过早进入方案、忽略替代问题定义。

主要来源：Problem Framing、设计科学。

---

## RC03 需求状态与方案边界错误

**定义：** “原始表达、候选需求、已确认需求、约束、候选方案、已选方案”之间的状态或边界没有被正确维护。

可制造：用户随口提 Skill 就被当成正式需求、工程描述淹没需求、设计固着。

主要来源：需求工程、系统工程、设计科学。

---

## RC04 信息缺口与假设控制错误

**定义：** 系统没有正确判断当前缺少什么、哪些可合理假设、哪些必须查询或向用户确认。

可制造：该问不问、不该问反复问、无依据猜测、过度澄清。

主要来源：需求获取、HAI、决策与风险。

---

## RC05 共同理解与修复状态错误

**定义：** 人和 AI 对目标、术语、约束或当前状态没有形成足够共同理解，或修复未生效。

可制造：用户反复说“不是这个意思”、纠正后继续犯错、handoff 语义漂移。

主要来源：Common Ground、Conversational Repair、HAI。

---

## RC06 阶段与推进状态表示错误

**定义：** 系统对当前处于探索、定义、决策、计划、执行、验证等哪种状态表示错误或缺失。

可制造：需求未定就实现、决策阶段继续发散、执行阶段重新研究。

主要来源：软件 / 系统生命周期、Workflow；迁移到 AI 长任务。

---

## RC07 相关性、优先级与粒度选择错误

**定义：** 系统没有根据用户当前任务决定哪些信息现在最重要、应该展开到哪一层。

可制造：太长、太细、没重点、低价值工程描述占主体、认知负担过高。

主要来源：HCI、认知科学、信息架构。

---

## RC08 证据、来源与不确定性管理错误

**定义：** 对证据质量、来源、时效、冲突、事实/推断边界和不确定性处理失当。

可制造：过时事实、伪引用、高确定性幻觉、过度依赖。

主要来源：研究方法、质量工程、决策科学、AI 可靠性。

---

## RC09 决策模型缺失或错误

**定义：** 目标、价值、评价标准、替代方案、后果、权重、风险和权衡关系没有形成足够决策结构。

可制造：十个方案但无法选、永远“取决于”、过早收敛、只优化用户第一个方案。

主要来源：决策科学、Value-Focused Thinking。

---

## RC10 执行与工具结果语义脱节

**定义：** 系统把工具层动作、局部执行状态或技术返回值错误解释为更高层业务结果。

可制造：API 成功即宣布业务成功、文件创建即宣布交付完成、Agent 动作很多但目标未达成。

主要来源：软件工程、系统集成、Agent Tool Use；AI 场景显著放大。

---

## RC11 Verification / Validation / Acceptance 基准缺失或混淆

**定义：** 没有正确区分“是否按要求做对”“是否做了真正需要的东西”“是否达到可接受交付条件”。

可制造：格式通过但内容失败、测试通过但用户不满意、只测局部技术指标。

主要来源：系统工程、质量工程、测试。

---

## RC12 完成与停止条件错误

**定义：** 完成、失败、继续、升级、交回用户和停止优化的条件缺失或错误。

可制造：无限完善、Agent 循环、子任务完成误报整体完成、过度复杂化。

主要来源：项目 / 系统工程；Agent 中成为关键新型工程问题。

---

## RC13 上下文、记忆、版本与依赖更新错误

**定义：** 有效历史、当前状态、已撤销决策、依赖关系和记忆没有被正确选择、更新或传播。

可制造：旧规则复活、目标漂移、重复劳动、纠错不传播、跨会话状态断裂。

主要来源：状态管理、配置 / 变更管理；迁移到 Context / Memory。

---

## RC14 指令权限与冲突解析错误

**定义：** 来自不同来源、时间和权限层级的指令没有被正确排序、覆盖、撤销或隔离。

可制造：Prompt 规则冲突、旧要求和新要求同时生效、外部上下文影响核心指令。

主要来源：LLM Instruction Hierarchy / Prompt Security；`[AI 新型问题]`。

---

## RC15 人机控制权与依赖配置错误

**定义：** AI 与用户之间的自主权、确认门槛、监督强度、风险暴露和可信程度配置不合理。

可制造：过度确认、缺少确认、自动化偏差、过度信任、用户无法接管。

主要来源：Human Factors、Human-AI Interaction、Appropriate Reliance。

---

## RC16 机制复杂度与任务适配错误

**定义：** Prompt、Workflow、Agent、Tool、Skill、Schema、代码、人工等机制组合没有与任务的稳定性、复杂度、风险和可验证性匹配。

可制造：Agent 化一切、维护成本大于收益、复杂工作流反而降低可靠性。

主要来源：软件设计、自动化、人机协作与 Agent 工程；`[跨领域迁移]`。

注意：本文件只诊断，不在本轮给出机制选择算法。

---

## RC17 模型能力与行为边界

`[AI 新型根因族]`

**定义：** 由于生成式模型本身的概率性、训练目标、长上下文利用能力、指令遵循和校准边界，即使外部流程设计合理，仍可能出现错误。

当前已有研究支持的代表性问题包括：

- 长上下文中相关信息位置影响模型使用效果（如 Lost in the Middle）；
- sycophancy：模型可能迎合用户观点；
- 指令层级 / 冲突解析并非天然可靠；
- 模型会产生 hallucination 或不可校准的高确定性输出。

RC17 不能成为“所有问题的万能解释”。

只有在目标、需求、状态、证据、工具、验证等外部系统问题已经得到合理控制后，才能更有把握把剩余错误归因到模型能力边界。

# 24. 根因之间不是互斥关系

同一个失败通常是链式组合。

例如：

```text
RC03 需求状态与方案边界错误
↓
RC06 阶段状态表示错误
↓
RC07 信息粒度选择错误
↓
大量工程细节提前展开
↓
用户被锚定在一个实现上
↓
RC09 决策模型进一步失真
```

因此不要试图为每个现象找到唯一根因。

# 28. 重点案例完整诊断：工程描述淹没需求

## 28.1 用户现象

来自 01：

> **工程描述淹没需求。**

用户仍处于需求探索 / 问题定义 / 方案空间探索阶段，但回答中 Workflow、Agent、Skill、Schema、API、目录、代码等实现描述已经成为主体。

## 28.2 不是一个单一专业术语

它通常同时映射：

| 层 | 诊断 |
|---|---|
| 需求工程 | T03 需求—解决方案混淆 |
| 设计科学 | T09 过早收敛；满足条件时才是 Design Fixation |
| 任务过程 | T05 阶段 / 推进状态失配 |
| HCI / 认知 | T06 信息优先级与粒度失配 |
| 机制治理 | T18 机制复杂度与任务复杂度失配 |

## 28.3 直接原因示例

```text
用户提到候选实现
↓
AI 未区分“候选方案”和“已确认需求”
↓
把实现名称写入内部目标
↓
按实施阶段展开
↓
工程细节获得最高内容优先级
```

## 28.4 深层根因

主要：

- RC03 需求状态与方案边界错误；
- RC06 阶段与推进状态错误；
- RC07 相关性、优先级与粒度选择错误；
- RC09 决策模型缺失或错误；
- RC16 机制复杂度与任务适配错误。

可能放大：

- RC17 模型迎合 / 上下文行为边界；
- AF03 用户先提出具体候选方案；
- AF07 长 Prompt / 大量工程规则；
- AF08 历史中已经存在大量旧工程设计。

## 28.5 为什么 Design Fixation 不能当总名

只有当已有方案或示例**实际限制了后续新方案的产生与探索**时，Design Fixation 才是较准确的成熟专业解释之一。

如果只是“回答太早进入代码细节”，但并没有证据表明方案空间被既有设计固定，则更准确的诊断可能只是 T03 + T05 + T06。

# 29. 其他高价值失败链

## 29.1 工具成功但任务没完成

```text
工具返回成功
↓
RC10 把技术状态解释成业务状态
↓
RC11 没有业务 Validation / Acceptance
↓
RC12 触发错误完成条件
↓
用户看到：工具调用了，但事情没办完
```

## 29.2 用户纠正但 AI 继续犯错

```text
用户修正理解
↓
当前文本表面接受
↓
RC05 common ground 修复不充分
+
RC13 旧状态 / 依赖未更新
↓
旧计划、旧术语或旧目标继续生效
```

## 29.3 方案越来越多但无法决策

```text
缺少清晰价值 / 目标
↓
RC09 决策模型不完整
↓
继续增加 alternatives
↓
RC07 信息量继续增加
↓
用户认知成本上升
↓
决策空间却没有缩小
```

## 29.4 长对话越聊越偏

```text
长期历史不断增加
↓
RC13 有效状态和废弃历史没有充分区分
+
RC17 长上下文利用存在模型边界
↓
旧目标、旧约束、临时想法混入当前推理
↓
用户看到：前面说过的忘了，不该记的反而一直记着
```

## 29.5 指标全部优秀但实际不好用

```text
选择容易测量的局部指标
↓
RC01 真实目标没有进入评价模型
+
RC11 Validation / Acceptance 不充分
↓
局部 Verification 很好
↓
真实使用价值下降或未提升
```

- Common Ground；

- Human Oversight；

## 30.2 主要属于跨领域迁移

- sycophancy；
- long-context position sensitivity；
- instruction hierarchy / prompt conflict；

- “问题现象宇宙 / 根因宇宙”；
- “工程描述淹没需求”；
- “高知识密度”；
- T01—T19、RC01—RC17、AF01—AF12 的编号与组合方式。

这些名称用于知识工程和诊断，不包装成学术标准。

# 31. 根因诊断规则

为了避免“看见现象就随便归因”，后续案例诊断至少遵守：

### 规则 1：先描述现象，再命名问题

不要直接从“回答太长”跳到“认知负荷失败”。

### 规则 2：至少保留两个根因候选，直到证据足够

同一现象可能来自不同机制。

例如“一直追问”可能来自：

- RC04 信息缺口判断错误；
- RC15 过度保守的控制权配置；
- RC01 目标未明确；
- 甚至只是产品层确认策略。

### 规则 3：区分直接原因和深层根因

“Prompt 写得太长”可能是直接原因，但更深层可能是 RC16：每个问题都用 Prompt 补丁解决。

### 规则 4：模型能力不足不能成为默认解释

先排查目标、需求、状态、证据、工具、验证和控制结构。

### 规则 5：专业术语必须满足适用条件

例如不能把所有“提前讲实现”都叫 Design Fixation。

### 规则 6：根因应能预测其他现象

一个好的诊断应该可以反推：

> 如果 RC13 真的是根因，还应该在哪些地方看到旧决策复活、重复劳动、纠错不传播等现象？

这使根因体系具有可证伪性，而不只是事后解释。
