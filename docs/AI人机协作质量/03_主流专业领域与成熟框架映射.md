> 状态：v0.1｜主流专业体系校准基线  
> 研究基线日期：2026-08-25  
> 定位：为 `01_高频问题现象宇宙.md` 与 `02_问题类型与根因宇宙.md` 提供专业知识骨架  
> 原则：成熟专业体系优先；跨领域迁移明确标注；AI 新问题单独标注；项目工作名不包装成学术标准。

## 0. 核心结论

目前仓库所研究的“AI 人机协作质量”**不是一个已经存在完全同名、边界统一的单一学科**，更准确的理解是：

```text
HCI / Human-Centred Design
+ Human-AI Interaction / Human-Centered AI
+ 需求工程
+ 问题框定与设计方法
+ 决策科学
+ 认知科学与信息呈现
+ 软件工程 / 系统工程
+ 质量工程 / Verification / Validation / Testing
+ 人因与自动化信任研究
+ LLM / Context / Prompt 研究
+ Agent / Workflow 工程
= 本项目的 AI 人机协作质量知识骨架
```

因此，本项目后续不应采用“看到一个现象就创建一个新 AI 术语”的方式扩展，而应采用：

```text
用户现象
→ 先寻找成熟专业对应
→ 判断是否属于跨领域迁移
→ 再判断 LLM / Agent 是否引入新的失效机制
→ 必要时才建立工程化工作名称
```

另一个重要校准是：

> **“需求与设计分离”不能理解成严格瀑布式的、永不回退的绝对隔离。**

成熟系统工程和设计实践都允许需求、问题理解与设计通过证据迭代；真正需要避免的是：**把尚未确认的候选实现方式误当成稳定需求，并在证据不足时过早承诺到具体方案。**

# 3. HCI / Human-Centred Design

## 3.1 它主要解决什么

HCI 不是“界面好不好看”，核心问题之一是：

> 指定用户能否在指定使用情境中，以可接受的有效性、效率和满意度完成指定目标。

ISO 9241-11 将 usability 放在“用户—目标—情境”的组合中理解；ISO 9241-210 提供以人为中心设计过程；ISO 9241-110 给出与任务适配、自描述性、符合用户预期、可学习性、可控性、使用错误鲁棒性、用户参与等交互原则。

## 3.2 与 AI 人机协作的关系

可直接解释：

- AI 回答技术上正确但用户无法使用；
- 系统没有围绕用户当前任务组织信息；
- 用户不知道 AI 当前能力、状态或下一步；
- 控制权过多或过少；
- 错误后无法恢复；
- 输出结构提高了阅读负担而不是提高理解。

## 3.3 可以直接迁移的知识

`[成熟专业概念]`

- Context of Use；
- Usability；
- Human-centred Design；
- Suitability for the user’s tasks；
- Self-descriptiveness；
- Conformity with user expectations；
- Controllability；
- Use error robustness。

## 3.4 不能机械迁移的部分

传统交互标准通常假设系统行为比生成式模型更稳定。LLM 的随机性、能力边界变化、长上下文、工具调用和多步自治，使“可预测性、错误恢复、能力透明”更难。

## 3.5 LLM / Agent 新增问题

- 同一自然语言请求存在多种合理解释；
- 模型能力并非对所有任务均匀；
- 输出可能流畅但错误；
- Agent 可能产生真实世界副作用；
- 长任务中用户难以观察内部状态。

### 成熟度

**高**。这是本项目最稳定的上位骨架之一。

# 4. Human-AI Interaction / Human-Centered AI

## 4.1 它主要解决什么

Human-AI Interaction 重点研究：AI 的不确定性和错误存在时，人怎样与 AI 建立正确预期、协作、纠错、反馈和控制。

Microsoft Research 的 *Guidelines for Human-AI Interaction*（CHI 2019）综合并验证了 18 条交互指导，覆盖首次使用、日常交互、AI 出错和长期使用。Google PAIR Guidebook 同样围绕用户需求、心智模型、信任、解释、反馈与控制组织实践。

## 4.2 对当前问题宇宙最关键的成熟知识

`[成熟专业概念 / Human-AI Interaction]`

- 让用户知道系统能做什么、能做到什么程度；
- 根据情境决定 AI 何时介入；
- AI 不确定或出错时支持高效纠正；
- 允许用户提供细粒度反馈；
- 让用户知道其操作会怎样改变系统后续行为；
- 长期适应要谨慎，能力变化要可感知；
- 用户需要全局控制，而非只能逐轮被动纠错。

## 4.3 与本项目的直接关系

这套研究直接覆盖：

- “该问不问 / 不该问一直问”；
- “用户纠正后 AI 没真正更新”；
- “AI 自己推进还是先交给用户决定”；
- “用户不知道 AI 能做什么”；
- “AI 行为变化但用户不知道为什么”；
- “错误后没有恢复接口”。

## 4.4 不能机械迁移的部分

2019 年的指南并不是为今天的长上下文、多工具、长运行 Agent 完整设计的。Agent 的状态可见性、跨工具权限、长时间自治、多人/多 Agent handoff 等仍需要新增研究。

### 成熟度

**高-中**：核心交互原则成熟，生成式 Agent 扩展仍快速演进。

# 5. Common Ground 与 Conversational Repair

## 5.1 主流来源

Clark 与 Brennan 的 *Grounding in Communication* 将共同活动建立在不断更新的 common ground 上。这个理论原本不是 LLM 理论。

因此在本项目中：

- Common Ground：`[成熟专业概念]`；
- 将其系统化迁移到 LLM 多轮协作：`[跨领域迁移]`。

## 5.2 它解释哪些 AI 现象

- 双方对同一个词含义不同；
- AI 没有暴露自己当前理解；
- 用户说“不是这个意思”，AI 只换表述不换模型；
- 纠正没有传播到后续计划、状态和执行；
- 长任务中双方对“已经完成什么”理解不同。

## 5.3 重要校准

“共同理解失败”不是一句 Prompt 能完全解决的问题。它可能同时涉及：

```text
信息缺失
+ 澄清策略
+ 状态表示
+ 纠错传播
+ 历史版本
+ 用户可见反馈
```

微软关于 Human-Centered AI Agents 的近期研究也把 agent 与用户建立 common ground 视为生成式 Agent 的重要新挑战，尤其涉及能力说明、目标/偏好/约束传达、状态监控和降低用户负担。

### 成熟度

**原理论高；迁移到现代 Agent 中等。**

# 6. 需求工程

## 6.1 它主要解决什么

ISO/IEC/IEEE 29148 是需求工程的重要国际标准。成熟需求工程关注：

```text
利益相关者需要 / 期望
→ 获取与分析
→ 需求定义
→ 约束
→ 验证
→ 追踪
→ 变更管理
```

截至 2026-08，现行已发布版本仍为 ISO/IEC/IEEE 29148:2018；第三版 DIS 正在开发中。

## 6.2 “需求与实现”应怎样准确理解

NASA Systems Engineering Handbook 的实践性表述非常清楚：好的功能需求应尽量保持 implementation-neutral，说明“需要什么”，而不是过早规定“怎样实现”。

这支持本项目的重要判断：

> 用户提出“是不是可以做一个 Skill / Workflow / Agent”时，除非它已经被明确确认为约束或设计决定，否则首先应视为**候选实现方式**，而不是自动升级成需求。

## 6.3 但不能走向另一个极端

不能机械理解成：

> “需求阶段永远不能谈技术。”

成熟系统工程本身是递归和迭代的。设计发现的新证据可能迫使需求修订；有些技术、合规、兼容性、本钱或既有系统限制本来就是合法约束。

真正要避免的是：

- 未验证的方案假设冒充需求；
- 低层实现细节过早冻结上层问题空间；
- 技术选择无法追溯到用户需要或上层目标；
- “做了很多设计”掩盖“还不知道为什么要做”。

## 6.4 对应现象

- 用户方案被 AI 当成需求；
- 需求尚未稳定就设计架构；
- 规格、Schema、目录、API 大量展开；
- 最后技术交付完整，但用户真正目标没有满足。

### 成熟度

**高。**

# 7. 问题定义、Problem Framing 与设计科学

## 7.1 Double Diamond

Design Council 的 Double Diamond 用 Discover → Define → Develop → Deliver 表达设计过程，并明确体现发散与收敛：先理解而不是假设问题，再定义挑战，然后探索多个潜在解，最后交付与迭代。

它不是软件生命周期标准，但非常适合校准本项目的“问题空间—方案空间”边界。

## 7.2 Design Fixation

Jansson & Smith（1991）把 design fixation 描述为对有限既有想法的盲目坚持，从而限制概念设计输出。后续研究也将 premature commitment 与 fixation 联系起来。

因此：

- `Design Fixation`：`[成熟专业概念]`；
- “过早方案承诺”可作为成熟设计研究中的现象描述；
- “需求—解决方案混淆”是本项目跨需求工程与设计科学的诊断类别，不应伪装成某一个单一标准术语。

## 7.3 不要误用 Design Fixation

不是所有“提前讲工程”都叫 Design Fixation。

只有当已有示例、先入方案或既有实现明显**压缩后续方案空间、阻碍替代方案探索**时，Design Fixation 才是更准确的解释。

### 成熟度

**高。**

# 8. 决策科学

## 8.1 它补足了什么

AI 常见问题不是“没有方案”，而是：

> 方案很多，但没有把决策空间缩小。

Ralph Keeney 的 Value-Focused Thinking 强调：不要一开始只围绕既有替代方案打转，应先澄清价值和目标，再据此创造与评估替代方案。

## 8.2 可迁移的成熟结构

`[成熟专业概念]`

```text
决策目标 / 价值
→ 决策标准
→ 约束
→ 替代方案
→ 后果与风险
→ 权衡
→ 不确定性
→ 信息价值
→ 选择
```

## 8.3 对应现象

- 十个方案但没有推荐；
- 永远回答“取决于”；
- 所有评价维度同权；
- 没有说明关键变量；
- 没有考虑“不做”、可逆性、机会成本；
- 信息越来越多，决策却没有前进。

### 成熟度

**高。**

# 9. 认知科学、信息架构与渐进式展开

## 9.1 Cognitive Load

Sweller 的 Cognitive Load 研究说明人的认知处理容量有限。对本项目最重要的迁移不是“回答越短越好”，而是：

> 不应让与当前判断无关的信息占用大量认知资源。

## 9.2 Progressive Disclosure

Progressive Disclosure 是成熟交互设计模式：先呈现当前最需要的信息，需要时再展开更多细节。

在本项目中它适合解释：

```text
第一轮：结论 / 高价值变量 / 主要选项
↓ 用户选中方向
第二轮：方法 / 比较 / 风险
↓ 确认执行
第三轮：步骤 / 参数 / 工程细节
```

这只是交互组织原则，不代表所有任务都必须三轮完成。

## 9.3 重要校准

- “标题多、表格多”不等于信息架构好；
- “字少”不等于认知负荷低；
- “专业术语多”不等于信息密度高；
- 输出结构应该服务用户的任务与决策顺序。

本项目的“高知识密度”继续保留为 `[工程化工作名称]`，而不是成熟学术指标。

### 成熟度

Cognitive Load：**高**；Progressive Disclosure：**成熟设计实践**；“高知识密度”：**项目定义**。

# 10. 软件工程与系统工程

## 10.1 生命周期与状态

ISO/IEC/IEEE 15288:2023 提供系统生命周期过程的公共框架，覆盖概念、开发、生产、使用、支持和退出，并允许过程迭代、并行和递归使用。

对 AI 长任务最有价值的迁移是：

- 生命周期阶段不是装饰；
- 状态需要被显式管理；
- 需求、设计、实现、验证、变更之间需要追踪；
- “当前版本是什么”与“哪个决定已经作废”属于配置/变更管理问题；
- 长任务不能只依赖自然语言历史自动维持状态。

## 10.2 对应现象

- 已经改变方向但旧计划继续影响；
- 已完成任务被重复做；
- 不知道当前处于研究、决定、执行还是验收；
- 长任务目标漂移；
- 局部产出无法合成最终交付。

### 成熟度

**高；迁移到 LLM 长任务属于跨领域迁移。**

# 11. 质量工程、Verification、Validation 与 Testing

## 11.1 最重要的成熟区分

NASA Systems Engineering Handbook 对 Verification 与 Validation 的区分可直接用于本项目：

- Verification：是否符合已经规定的要求；
- Validation：结果是否在目标使用情境中满足真正用途和利益相关者期望。

因此：

```text
格式正确
≠ 内容正确

测试通过
≠ 用户目标满足

工具调用成功
≠ 业务结果完成

子任务完成
≠ 整体任务完成
```

## 11.2 其他成熟框架

- ISO/IEC 25010:2023：产品质量模型，可用于定义、测量和评价 ICT / 软件产品质量，也可支持验收标准；
- ISO/IEC/IEEE 29119 系列：软件测试概念与测试过程。

## 11.3 AI 时代新增难点

`[AI 新型问题]`

- 生成结果具有概率性；
- 同一个模型既生成又自评时可能共享盲区；
- “语言看起来正确”比传统格式错误更容易误导；
- Agent 的工具执行日志只是验证输入之一，不是最终业务验收。

### 成熟度

V&V / Testing：**高**；LLM 评测方法：**中、快速演进**。

# 12. 人因、Automation Bias 与 Appropriate Reliance

## 12.1 Automation Bias

自动化偏差是成熟人因研究问题：人在自动化辅助下可能发生 omission errors 或 commission errors，例如没有在自动化未提示时主动发现问题，或即使存在反证仍跟随自动化建议。

## 12.2 Appropriate Reliance

生成式 AI 场景不应该追求“用户越信任越好”，而应追求**适当依赖**：正确结果该接受，错误结果能够识别和拒绝。

微软近期关于 GenAI appropriate reliance 的研究继续强调 overreliance 是人机协作障碍。

## 12.3 对应现象

- AI 语气流畅导致用户直接相信；
- 一次错误后用户彻底不再使用 AI；
- 用户无法判断 AI 当前有多确定；
- 高风险动作缺少人工复核；
- AI 自信程度与真实证据不匹配。

### 成熟度

Automation Bias：**高**；Appropriate Reliance 在 Human-AI 中：**中-高**。

# 13. LLM / Prompt / Context Engineering

这一领域必须克制：不能把所有失败都归结成“Prompt 不够好”。

## 13.1 已有较强研究证据的 AI 特有问题

### A. Long-context position sensitivity

`[AI 新型问题]`

*Lost in the Middle*（TACL 2024）显示，长上下文模型并不总能稳健使用上下文；相关信息的位置可以显著影响表现，中间位置在多个设置下更容易丢失。

这为以下现象提供模型层解释之一：

- 关键约束在长对话中被忽略；
- 历史越长不一定越可靠；
- 检索更多材料不一定持续提升答案。

### B. Sycophancy

`[AI 新型问题]`

Anthropic 等研究表明，RLHF 训练的模型可能偏向匹配用户表达的观点，而不是坚持更真实的回答。

它可以放大：

- 用户提出候选方案后 AI 过度赞同；
- 反证不足；
- 错误前提没有被挑战。

### C. Instruction Hierarchy / Instruction Conflict

`[AI 新型问题]`

OpenAI 的 Instruction Hierarchy 研究明确讨论了来自不同权限来源的指令冲突以及模型错误等价处理不同优先级指令的风险。

这说明“Prompt 规则越来越多并互相冲突”不能只当成写作问题，还涉及指令治理、权限来源和冲突解析。

## 13.2 不应被泛化为 Prompt 问题的现象

以下问题即使重写 Prompt，也可能没有解决根因：

- 需求本身没定义清楚；
- 决策标准不存在；
- 任务需要外部事实但没有检索；
- 工具权限和人工审批边界错误；
- 没有验收标准；
- Agent 本来就没有必要；
- 状态应该持久化但只塞在长对话里。

### 成熟度

**中，且快速变化。**

# 14. Agent / Workflow 工程

## 14.1 当前较稳定的工程共识

OpenAI 与 Anthropic 的 Agent 工程资料都强调：

- Agent 适合复杂、含判断、含非结构化信息、传统确定性流程难以覆盖的任务；
- 不应默认把所有任务 Agent 化；
- 先寻找最简单可行方案；
- 单 Agent 能解决时不要过早多 Agent；
- 工具需要明确语义、权限和错误处理；
- 循环必须有退出条件；
- 关键高风险动作需要 guardrails / human intervention；
- 复杂度增加必须换来可测的任务收益。

Anthropic 明确区分：

- Workflow：LLM 与工具沿预定义代码路径编排；
- Agent：LLM 动态决定过程与工具使用。

这两个词不应混用。

## 14.2 哪些问题根本不值得 Agent 化

通常优先考虑非 Agent 解法的情形：

- 单轮解释、总结、写作；
- 路径完全确定且规则稳定；
- 工具调用很少、没有复杂分支；
- 自动化收益小于维护、延迟和风险成本；
- 任务很难验证却要求长时间自治。

### 成熟度

**工程实践中等，快速演进；不是成熟统一学术标准。**

# 15. 重点案例：工程描述淹没需求

## 15.1 用户现象

`[工程化工作名称｜现象层]`

> **工程描述淹没需求**：用户仍在理解问题、探索需要或比较方向时，Workflow、Agent、Skill、Schema、目录、API、数据结构、代码和实施步骤已经占据主要信息空间，使用户难以继续判断“真正要解决什么”。

## 15.2 不能用一个专业术语强行等价

它通常是多个成熟问题叠加：

```text
需求工程
→ 未确认候选实现被升级为需求
→ Implementation-neutral 原则被破坏（在适用时）

设计科学
→ Premature commitment
→ 若既有方案压缩了后续方案空间，则可能出现 Design Fixation

问题框定
→ Problem definition 尚未收敛，Solution exploration 已主导对话

认知 / 信息呈现
→ 低时机价值的工程细节产生额外认知负荷

阶段 / 状态
→ 当前任务仍是探索，却按实施阶段输出
```

## 15.3 LLM 时代可能的放大因素

`[AI 新型问题 / 工程观察]`

- 用户在提示中提到一个具体实现，模型可能继续沿该实现生成大量一致细节；
- Sycophancy 可能放大“用户既然提出这个方案，就顺着它做”的倾向；
- 长对话里大量既有工程上下文会增加旧实现继续进入当前回答的机会；
- 指令和历史决策没有明确版本时，模型可能无法可靠区分“曾讨论”“已否决”“已确认”。

其中后两项不能简单归结为某一个单一论文结论；应在具体系统中通过案例与评测验证。

## 15.4 本项目推荐的专业表达

现象层继续保留普通中文：

> **工程描述淹没需求**。

问题类型层推荐拆成：

- 需求—解决方案混淆；
- 过早方案承诺；
- 阶段 / 状态失配；
- 信息优先级与粒度失配；
- 必要时再标记 Design Fixation。

不要把“Design Fixation”当成上述全部现象的总名。

# 16. 主流框架反向带来的高价值新增检查项

从成熟框架反向审计后，除现有问题外，至少还应长期检查以下高价值现象：

1. **能力透明失败**：用户不知道 AI 当前能做什么、不能做什么、是否发生能力变化；
2. **共同理解修复失败**：纠正发生了，但没有传播到后续目标、状态和执行；
3. **不适当依赖**：用户对 AI 过度依赖或过度不信任；
4. **局部指标替代真实目标**：格式、工具成功、测试分数或子任务指标被误当成最终价值；
5. **适应变化不可见**：系统因历史、记忆、模型更新或个性化改变行为，但用户无法理解原因；
6. **自治副作用不可见**：Agent 在采取真实行动前没有充分呈现影响、可逆性与控制边界；
7. **设计固着被 AI 放大**：用户随口提出的例子成为后续所有方案的锚点。

这些检查项应进入现象层或根因层，但不应因此立即创建新的 Agent / Skill / Schema。

# 18. 当前专业地图的边界

本文件目前已经足以为 01、02 提供稳定骨架，但仍有三类内容不应被假装成“已经定论”：

1. **LLM 长任务状态管理**仍处于快速工程演进期，尚没有一套像 ISO 15288 那样统一的 Agent 生命周期标准；
2. **Prompt / Context Engineering**的大量术语仍是工程实践语言，不能全部提升为成熟学术概念；
3. **AI 人机协作质量**是本项目的总工程名称，不能声称是学界统一领域边界。

后续应通过真实案例验证这些专业框架能否提高诊断速度和正确率，而不是继续扩大术语表。
