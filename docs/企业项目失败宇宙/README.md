# 企业项目失败宇宙（V0.1）

> **独立跨行业研究域**。对象是公司中的项目/复杂计划及其价值、立项、资源、治理、交付、验收和退出；可包含 IT、研发、运营、营销、供应链与组织变革项目，但不是 [软件IT失败宇宙](../软件IT失败宇宙/README.md) 的上级目录或副本。

## 1. 首先定义什么算失败

一个项目可能：技术失败、交付失败、用户/业务采用失败、经济价值失败、战略适配失败、合规失败、部分达成、险情后恢复、验证后及时终止。不能把“按时上线”自动视为成功，也不能把“终止错误路线”自动视为失败。

记录**原始目标、目标提出者、实际价值、阶段、约束和证据**，避免用后来的目标倒填原始成功标准。

## 2. 项目生命周期失效地图

| 阶段 | 典型风险 | 必需的证据或关口 |
| --- | --- | --- |
| 战略/立项 | 选错问题、目标含糊、机会成本失衡 | 需求/价值/目标/退出标准 |
| 可行性验证 | 关键假设没验证、过早扩大投入 | 小试验、可行性与未知清单 |
| 需求与范围 | 需求漂移、缺少基线、利益冲突 | 来源、批准、变更证据 |
| 方案选择 | 未调查替代、单方案偏见 | 不同机制的候选方案及反例 |
| 资源与计划 | 工期/成本估计失真、依赖遗漏 | 参考类、现金/人员/依赖 |
| 执行协作 | 责任缺口、隐性阻塞、质量债 | 交付物、责任与过程监测 |
| 验证与验收 | 测试不覆盖需求、证据不可追溯 | 需求—实现—测试—价值链 |
| 上线与采用 | 已交付但不被接受/使用 | 采用、运营、业务价值 |
| 运营与退出 | 维护失衡、沉没成本、退出过晚 | 复盘、维护、迁移与止损 |

一个项目可同时在多个阶段出现失效，**按发生时间与作用机制**表达，不用单一“根因”掩盖复杂互动。

## 3. 分析单位：公司、项目、工作包不能混写

- **企业层**：战略、资本、组织能力、组合资源和持续经营。
- **项目层**：明确目标、范围、价值结果、阶段约束与决策。
- **成果/交付层**：交付物、工作包、任务、实现及验收。
- **事件层**：偏差、决策、故障、预警、干预和结果。

这些是分析层级，不意味着简单的单一父子树。同一企业倒闭不能直接推断其每个项目均失败；项目失败也不等于企业必然失败。

## 4. 最小项目失败案例卡

- **project_case_id / 行业 / 企业情境 / 时间**：匿名化亦可，来源明确。
- **目标与价值假设**：原始成功标准、预期收益与参与方。
- **投入/约束**：预算、现金跑道、团队、审批与外部依赖。
- **时间线**：立项、阶段门、需求变更、实验、交付、验收/退出。
- **实际结果**：按技术、交付、采用、经营价值等维度分别判断。
- **观察事实与主张**：哪些直接可核，哪些仅为推断？
- **失败路径/备选解释**：内部决策、环境、外部冲击及反馈。
- **应有预警与实际信号**：当时可获得的信息，不使用事后诸葛。
- **修复/挽救/止损动作**：是否发生、影响怎样被验证？
- **对照组与反例**：相似条件下为何有人成功？
- **可迁移规则**：成立条件、适用边界、验证方式。
- **来源/证据/版本/待核问题**：确保可复核。

## 5. 失败预演不是“提前判定失败”

项目决策链：定义目标 → 列关键未知 → 找相似历史项目（含成功/失败/险情）→ 事前假设项目失败并倒推原因 → 形成不同方案 → 为关键风险设计便宜的验证 → 通过阶段门 → 监测纠偏 → 验收价值 → 复盘回写。

决策结论分为：推进、验证后推进、调整、暂停/终止、证据不足。阻断必须写明明确约束及证据，风险模式默认只是验证建议。

同类项目的成本/进度基准应优先考虑有可比性的数据，不用单个戏剧化失败故事替代参考类预测。高风险或不可逆操作保留人工审批。

## 7. 最小验证与下一步

在 IT 项目和非 IT 项目中各选一例，同时各选一个“早停挽救/成功对照”。检查是否能区分公司层与项目层结局、目标变化、交付与真实价值、事后归因偏误、竞争解释，并产出可验证的阶段门。**V0.1 仅为研究设计，不是已核实的失败案例库。**
