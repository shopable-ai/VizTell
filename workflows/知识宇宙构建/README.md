当前目录已经形成一套较完整的研究骨架，但还没有经过足够多的真实案例验证，因此暂时不把它升级为正式 Skill，也不开发复杂 Agent Runtime。

尚未确认的研究问题见 `TODO.md`；待验证提示词与候选方案放在 `drafts/`。

## 目的

本工作流用于把少量、零碎、来源不统一的知识种子，逐步转化为一个具有明确边界、稳定分类、较高覆盖度和正式输出结构的知识宇宙。

典型输入包括：

- 一本书中的部分模型或方法；
- 几个零散概念；
- 一批课程、文章、图片或笔记；
- 用户只有模糊方向，但尚不知道最准确的知识类型名称；
- 一个已有清单，希望扩展为跨来源、跨领域的完整体系；
- 一个已经存在、但怀疑分类或覆盖不完整的知识库。

典型输出包括：

- 总体定义；
- 一级分类；
- 二级知识群；
- 具体知识清单；
- 覆盖与遗漏审计；
- 可直接写入 `docs/` 的总览与完整分类文件。

## 用户层主链路（候选）

当前为了降低使用门槛，将详细 S1—S8 压缩为 6 个用户能够直接理解的主环节：

```text
零碎输入
→ ① 目标识别
→ ② 范围确认
→ ③ 内容扩展
→ ④ 整理与分类
→ ⑤ 完整性审计
→ ⑥ 正式成果
```

用户不需要知道 S1、S2 等内部编号；这些编号只用于详细研究与维护。

## 详细执行结构

```text
零碎输入
  ↓

  ↓
G1 目标确认门（必要时）
  ↓

  ↓

  ↓

  ↓

  ↓
S5 分类体系发现
  ↓

  ↓

  ↓

  ↓

```

## 核心原则

本工作流不是全自动流水线，而是：

> AI 自动研究 + 关键决策点人工确认 + 必要时回退重做。

默认只在“不同选择会显著改变后续研究结果”时请求用户确认，避免每一步都打断用户。

同时遵守：

1. 书籍和零碎样本只是“种子”，不是知识边界。
2. 分类不能替代具体知识内容。
3. 先有真实知识数据，再收敛 Taxonomy。
4. 如果分类明显限制新知识进入，应允许回退重建。
5. 用户只修改局部决策时，应回到最近受影响阶段，不无理由全部重跑。
6. 当前阶段不优先设计复杂数据库、Schema、交叉索引或 Ontology。

## 与 Taxonomy / Ontology / Knowledge Mapping 的关系

- **Taxonomy（分类体系）**：主要在 S5—S7 形成，回答“这些知识应该怎样分类”。
- **Knowledge Mapping（知识地图）**：贯穿 S3—S8，回答“整个知识空间有什么、哪里已经覆盖、哪里仍有空白”。
- **Ontology（本体 / 语义关系模型）**：属于分类稳定后的增强能力，不是当前 V1 的必需产物。

V1 优先完成：

> 稳定的分类体系 + 足够完整的具体知识内容 + 可读的知识地图。

## 当前不做什么

在真实案例验证前：

- 不创建 `SKILL.md`；
- 不把工作流包装成复杂 Agent；
- 不开发 Runtime；
- 不把 Ontology 设为默认必经流程；
- 不因为未来可能有用而增加大量空目录或工程文件。

当前判断标准只有一个：

> **这套流程是否真的能把用户的模糊知识输入稳定推进成高质量、可分类、较完整的知识结果。**
