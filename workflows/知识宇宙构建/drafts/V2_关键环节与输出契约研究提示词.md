# 知识宇宙构建工作流 V2｜关键环节与输出契约研究提示词

> 状态：Draft / 待在新对话中验证。
>
> 本提示词的目的不是直接升级 Skill，而是验证“最小正确工作流 + 每个关键环节的数据格式 + 必要人工交互”。

请基于 GitHub 仓库：

`https://github.com/shopable-ai/VizTell`

重点读取：

`workflows/知识宇宙构建/`

本轮暂时不要把它升级成 Skill，不要开发 Agent Runtime，也不要急于增加更多工程结构。

当前真正需要解决的问题是：

> **知识宇宙构建从“几个零碎知识 / 一本书 / 一份清单 / 一个模糊想法”到“完整分类知识地图”，究竟只有哪些不可缺少的关键环节？每个环节必须产生什么内容，用户在哪些节点需要参与？**

请先把当前 V1 看作“候选工作流”，而不是已经正确的最终答案。

## 一、重新压缩核心链路

完整审计现有 S1—S8。

不要为了保留现有结构而保留它们。

从用户真实任务出发，判断最小但完整的主链路究竟应该有几步。

要求：

- 普通用户能够理解；
- 每一步解决一个清晰的问题；
- 阶段之间边界明确；
- 不产生大量无必要中间流程；
- 可以映射回详细工程步骤。

先给出 2—3 套候选链路，比较后推荐一套。

重点判断当前候选：

```text
目标识别
→ 范围确认
→ 内容扩展
→ 整理与分类
→ 完整性审计
→ 正式成果
```

是否已经最小且完整。

## 二、为每个关键环节定义固定输出格式

每一环必须明确：

- 输入是什么；
- 这一环回答什么问题；
- AI 要完成什么；
- 输出必须包含什么；
- 是否需要用户反馈；
- 什么情况下才能进入下一环；
- 出错后回到哪一步。

不要只写抽象说明。

必须给出真实 Markdown 输出模板。

重点判断：

> 上一环的输出能否直接成为下一环的输入，而不需要 AI 重新猜测前文结论？

## 三、专门设计人工交互节点

重点研究：

> 用户什么时候真的必须参与？

避免两个极端：

- 每一步都询问用户；
- AI 完全自动跑到底。

对于需要用户决策的节点，给出：

- AI 应怎样提供 2—4 个候选；
- 每个候选应该解释哪些差异；
- AI 怎样给推荐；
- 用户只回复“A”“第二个”“范围再宽一点”“按你推荐的”“这两个都要”等简短答案时，下一步怎样继续；
- 哪些结论应保留；
- 哪些阶段需要回退。

## 四、定义统一的阶段结果块

研究是否应该要求每个关键阶段末尾统一输出：

```text
【阶段结果】
当前阶段：
核心结论：
用户已确认：
AI 默认假设：
尚未确定：
下一步：
是否需要用户输入：是 / 否
```

判断：

1. 字段是否过多或过少；
2. 是否能够支持下一轮继续；
3. 是否适合人工快速判断；
4. 哪些字段必须保留；
5. 是否需要为某些阶段增加“关键数据”字段。

给出最终推荐模板。

不要在本轮直接升级成复杂 JSON Schema。

## 五、专门验证“内容空转”失败模式

之前实际执行曾出现：

> AI 完成了大量研究和方法说明，却没有真正产生“分类 + 具体知识数据”。

因此必须逐环定义失败判定。

重点检查：

### 内容扩展阶段

必须真正输出具体知识内容，不能只说“应该搜索哪些领域”。

### 整理与分类阶段

必须出现：

```text
一级分类
→ 二级知识群
→ 具体知识
```

不能只输出一级分类名称。

### 完整性审计阶段

必须真正找到并补入缺失知识群，不能只写“可能存在遗漏”。

### 正式成果阶段

必须形成可直接阅读的总览和完整分类内容，不能重新变成研究计划。

为这些失败模式设计简短、可执行的纠正规则。

## 六、用三个真实场景验证

至少使用三种不同输入验证主链路和输出契约。

### 场景 A｜极少种子

只有 3—5 个零碎知识种子。

验证：

- 从哪个环节进入；
- 如何反推目标；
- 是否触发人工确认；
- 是否会过早锁定分类。

### 场景 B｜一本书 / 大型清单

一本包含大量模型、方法或概念的书或清单。

验证：

- 是否把来源当种子而不是知识边界；
- 哪一步进行外部扩展；
- 去重和分类怎样衔接；
- 用户需要在哪一步确认。

### 场景 C｜已有知识体系升级

已经存在定义、分类和大量条目的知识库，但怀疑存在遗漏或结构问题。

验证：

- 是否能够跳过不必要环节；
- 是否可以直接进入整理 / 完整性审计；
- 是否会错误地强制从第一步重新开始。

本轮不要真正展开数百条知识。

只验证：

> 工作流从哪里进入、经过哪些关键节点、哪里询问用户、每一步输出什么。

## 七、检查回退逻辑

至少模拟：

1. 用户在目标识别后说“第二个”；
2. 用户说“第二个，但范围再宽一点”；
3. 分类完成后用户说“我更希望按现实任务分类”；
4. 用户说“你自己判断，继续”；
5. 用户中断后在新对话说“继续上次那个知识宇宙”。

判断每种情况：

- 当前结论哪些仍有效；
- 应回退到哪个最近环节；
- 是否需要重新问用户；
- 下一步怎样继续。

## 八、最后判断当前成熟度

明确区分四类内容。

### A. 已经稳定

可以保留或进入正式 `workflow.md`。

### B. 候选规则

仍应留在 Draft。

### C. 待办问题

应该进入 `TODO.md`。

### D. 当前明确暂缓

例如：

- Skill 化；
- Agent Runtime；
- 复杂 Workflow State Schema；
- Ontology；
- 数据库与知识图谱工程。

如果真实验证表明其中某一项已经成为当前阻塞问题，再重新评估。

## 九、仓库修改原则

如果本轮研究得到稳定结论，可以：

- 修正 `workflows/知识宇宙构建/workflow.md`；
- 修正各阶段文件中过于宽松或不一致的输出格式；
- 更新 `TODO.md`；
- 在 `drafts/` 保存尚未稳定的方案。

不要创建 Skill。

不要因为“未来可能有用”创建大量目录或文件。

不要创建新分支或 PR。

## 十、最终输出顺序

### 第一部分｜结论

先回答：

1. 最小主链路应该有几环；
2. 当前 6 环是否合理；
3. 哪些环节必须有人参与；
4. 当前最重要的输出契约是什么；
5. 现阶段最容易失败在哪里。

### 第二部分｜推荐主链路

给出清楚、普通用户可理解的完整链路。

### 第三部分｜各环节输出模板

逐环给出真实 Markdown 模板。

### 第四部分｜三个案例验证

展示不同输入怎样进入和推进。

### 第五部分｜正式 / Draft / TODO / 暂缓

明确哪些内容分别属于哪一类。

### 第六部分｜必要的仓库修改

只有经过前面验证后再执行。

本轮最终目标只有一个：

> **先把最小正确工作流、每个关键环节的数据格式和必要的人机交互确定下来，再考虑 Skill 化。**
